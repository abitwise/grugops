# Workflow: context compaction

## When to use
Whenever an agent has accumulated a verbose local trajectory for a task and is about to promote results into the shared verified context. This workflow is the single source of the two-tier compaction protocol. The protocol covers how the verbose local trajectory is distilled and which structure is mechanically protected before promotion. It also covers how the dial tunes body verbosity and how a promoted finding is re-verified. Every role references this file rather than restating the protocol — there is one protocol, named here, not forked into each role.

It builds directly on `agent-factory/workflows/16-context-read-write.md` (the read/write/admission protocol) and reuses its admission rules for the re-verify; it does not restate them.

## Agents involved
- Every role that accumulated a verbose local trajectory. A third seam workflow with no owning specialist: whichever role is about to promote results runs it, then returns to the workflow it came from. The role owns the words — the semantic distillation is its intelligence and cannot be delegated to a tool.
- `scripts/compactor.ts` owns the structure. It is the mechanical floor, not a participant: it checks the proposed promoted set, refuses, and names the fault. It cannot summarize and never does.
- The §14 gate and a named human remain the only stamp issuers, exactly as in Workflow 16. A re-verified finding cross-checks against them and never against this workflow.

## Inputs required
- The task id and the agent's own local trajectory for it (the ephemeral, gitignored per-task-per-agent tier).
- The proposed promoted set — the notes the agent intends to carry into the committed shared context.
- `context.compaction` from `.grugops/factory.config.json`; when the key or the whole file is absent, `aggressive` is the lean default.
- The load-bearing field set and the raw `failed-attempt` ids the carve-out check compares against. Read them from the trajectory; never restate them here as protocol the agent self-polices.

## The body/structure seam
Two distinct jobs, never blurred:

- **The agent compresses note _bodies_** — the semantic judgment. The agent reads its verbose local trajectory and writes the terse gist, collapsing the narrative prose of note bodies. The distillation is the role's intelligence: keep the load-bearing constraint, drop the restatement.
- **`scripts/compactor.ts` protects note _structure_** — the deterministic carve-out invariant. It is a `node:fs`-only helper with zero host runtime deps; it cannot summarize and never does. It checks, refuses, and names the fault. It is the un-cheatable mechanical floor.

The agent owns the words; the tool owns the structure. Never ask the tool to summarize, and never let the agent quietly drop a load-bearing field — that is the tool's to refuse.

## The two tiers
The verbose trajectory lives in the ephemeral, gitignored local tier `.grugops/context/{task}/threads/{agent}.md`. That tier is per-task-per-agent scratch, created on the agent's first write for the task, appended to as the agent works, and never committed. Only the compact, re-verified distillation promotes to the committed shared verified context (`notes/` + the derived `index.*` that `scripts/context-io.ts` produces).

The local tier is local scratch, not part of the permanent audit trail. The permanent trail is the committed shared context. Unfold-on-demand operates within the live session against the local tier, not post-hoc from git history.

## Steps
Run these in order.

1. Distill the trajectory body. Read the local `threads/{agent}.md` trajectory. Write the compact gist of each note body the agent intends to promote. Keep every load-bearing constraint — especially a recorded dead-end. Collapse only restatement and narration. Body compression is not note dropping. The carve-out below fixes which durable notes promote, not how hard you compress.

2. Apply the dial to body verbosity, and to nothing else. Read `context.compaction` at point-of-use. When the key — or the whole config file — is absent, default to `aggressive`. The dial moves how much prose survives and how much raw reaches the read-by-default shared tier:
   - Set `aggressive` (the lean default) to send only the compact gist to the shared context. The raw trajectory stays in the local `threads/` tier, unfolded on demand. Maximum token win.
   - Set `balanced` to promote the gist plus a fuller mid-tier summary.
   - Set `retain-raw` to admit the full trajectory bodies into the committed shared context. The enterprise and audit choice pays the tokens to keep everything durable. Because `threads/` is ephemeral, this dial is the only way raw becomes durable.

   The dial governs body verbosity and how-much-raw-reaches-shared ONLY. It NEVER drops a durable note and NEVER drops a load-bearing field. The carve-out below is the un-dialable safety floor. It holds identically at `aggressive`, `balanced`, and `retain-raw` (the same way `quality.test_integrity` is `warn | block`-only and never `off`).

3. Hand the proposed promoted set to the carve-out check before promotion. `scripts/compactor.ts` checks the set mechanically. Every raw `failed-attempt` note id present in the trajectory survives into the promoted set. A reusable dead-end is never compacted away. `verified_by` / `supersedes` / `by` / `at` stay intact on every promoted note. On any dropped load-bearing element the checker refuses, exits non-zero, and names the dropped element. The checker is the mechanical floor the tool enforces. Do not re-implement or restate the field set as protocol the agent self-polices. Run the checker and honor its refusal.

4. Promote only via the sanctioned write path, and know which of its two routes you are on. Promotion happens ONLY via `scripts/context-io.ts` (`scripts/context-io.js`). Never a hand-written `.grugops/context/` path, and never a forked writer. This preserves the single sanctioned write path. Two routes sit behind it. The distinction is which question the destination has to answer.

   - Promote a note the compaction CHANGED with `appendNote`. That note is a NEW admission. Phase-21 admission fires on every note that route takes, of every kind. A promoted `artifact-ref` is re-bound by that authority at the destination. One whose `gate_run` names no live green verdict there is refused. A promoted `finding` whose `§14-gate` stamp names none is refused too. Nothing is written in either case. Degrade it honestly rather than re-pointing it. Honest degradation is the posture step 6 prescribes for a note the compaction changed.
   - Promote a note carried forward UNCHANGED from an already-admitted origin with `promoteAdmitted`. Name the origin note id and the origin context root. That note is a RE-BINDING, not a new admission. The route proves the origin note is live there and byte-identical on its load-bearing fields before it writes. It carries forward ONLY the human disposition this in-script tier cannot re-verify. It carries forward nothing else. A promotion it cannot prove is refused, naming the clause that failed, with nothing written.

     Name a real context store as the origin. The route accepts one origin shape and no other. The shape is a directory named `context` inside a directory named `.grugops`. The `.grugops` directory must sit directly under a directory the route independently resolves as a governance root. The shape admits another repository's own store, and it excludes a subdirectory of this one. The route refuses an ordinary directory whether or not that directory sits inside this repository. Proximity to the repository you run in is not evidence, because every directory you can create sits there. A caller that authors the bytes its own proof is judged against has a flag wearing a filesystem path, not a proof.

     Know that the destination's dial decides whether a human disposition means anything there. The route asks the same gated predicate the writer asks. Where the destination's dial does not gate the note, a `human:NAME` disposition binds nothing there. The promotion is refused on the writer's own ground. Accepting one would forge a `disposed_by` audit record. Promote that note as a new admission with an empty or `§14-gate` stamp instead.

   A `§14-gate`-stamped `finding` and an `artifact-ref` never take the re-binding route. Both are re-checked at the destination against a live green verdict there, exactly as before.

   Neither route ever replaces a note. The shared verified context is append-only. A write onto an id the destination already holds under different bytes is refused, and a supersession is a NEW note carrying a `supersedes` field. Re-promoting bytes the destination already holds is idempotent and changes nothing.

5. Run the explicit re-verify on a promoted `finding`. The writer already refuses a promoted `finding` whose stamp names no live green verdict there. That refusal is step 4's mechanism. It needs nothing from you. The re-verify adds the bounded repair loop around it. It reuses Workflow 16's admission rules and the `self_fix_attempts` loop in `agent-factory/workflows/05-pr-quality-gate.md` (default `2`, "two rounds then human"). Those rules live in those files; this workflow references them and does not restate or re-dial them. A faithful body compaction keeps the finding's `§14-gate#<id>` stamp valid against the live green verdict. The verdict verified the _work_, not the _words_. So the re-admission is cheap — a stamp cross-check, not a re-run of the gate. The `claim` / `observation` / `decision` / `failed-attempt` kinds carry no stamp and are admitted without a cross-check. An unreadable governance configuration still refuses every kind (D-14). An `artifact-ref` carries no stamp either, and it does not pass through. Its `gate_run` and `sha` are re-checked against a live green verdict there. A promotion that leaves that verdict behind is refused.

6. Degrade honestly when compaction CHANGED the note. A compaction sometimes materially changes a finding, so its stamp no longer cross-checks a live green verdict. The re-verify is then refused. Degrade to a `claim` carrying `confidence: UNKNOWN - verify` (the Phase-21 escape hatch). Never hand-carry a stamp, never re-stamp, never fake a pass. A `claim` never satisfies a finding's admission requirement. Recording it honestly is the floor.

   Scope that posture to a note that changed. It is NOT the posture for a faithful promotion of a note a named human already disposed. That case has its own route in step 4 and its own stop condition below. Stop for a human when a faithful re-binding is refused. A downgrade there discards the human's adjudicated disposition, and the substrate then records nothing about it.

## Stop conditions
- The carve-out checker refuses (a dropped `failed-attempt` id, or a missing `verified_by` / `supersedes` / `by` / `at`) → stop; do not promote. Fix the distilled set so the named element survives, then re-run the checker.
- A promoted `finding`'s re-verify is refused, and the bounded `self_fix_attempts` budget is exhausted without a real stamp → stop and hand to a human. A promoted `artifact-ref` whose gate run is absent from the destination context is refused on the same terms. Stop, degrade it honestly, and never re-point it at a different run. The budget is referenced from `05-pr-quality-gate.md`. Do not loop, do not fake a stamp. `checkpoint: exhaust_self_fix_budget`
- A faithful re-binding is refused → stop and hand to a human. The named origin note is absent, superseded, or the promoted note differs from it. Do NOT degrade it. A named human already disposed that note, and a downgrade discards their adjudication while the substrate records nothing about it. `checkpoint: escalate_unadjudicable_result`
- The destination already holds a different note under the promoted id → stop; do not promote. The context is append-only, so this is never a rewrite. Record the new result as a NEW note that supersedes the old one, or find the id the compaction actually meant.
- The named origin is not a context store the route recognises → stop; name the real origin context root. Never copy the origin notes into a directory to make the promotion pass. Copying them is hand-authoring a context path by another name, and the constraint refuses it. Know what the constraint does not refuse, and at what cost. Building a whole governance root around the copied notes still presents a store the route accepts. Such a root is a version-control marker, a governance configuration and the store directory. The cost is stated per position, because the enclosing repository's configuration is what varies. Inside a repository that carries a governance configuration it is three filesystem operations. Inside a repository that carries a version-control marker and no configuration it is two. Outside every repository it is two. The residual `T-31-18-01` names that construction, and this workflow does not sanction it. Fabricating a governance boundary to admit your own bytes is a stop condition of its own. Stop and hand to a human.
- The destination does not resolve to a governed store → stop; the repository whose audit trail would record the write cannot be named. Name a destination inside a governed repository. Never build one around the bytes: that is the forgery the condition above refuses. The re-binding route refuses this on every path, whatever the dial's retention value. The admit-then-persist route refuses it where a record would be written, and under a lean `audit_retention` value it writes instead (`R-31-41-02`).
- The destination's dial does not gate the note → the human disposition binds nothing there. Promote it as a new admission with an empty or `§14-gate` stamp, or set the destination's `human_admission` dial to the posture that governs it. Never carry the stamp across.
- The only way to promote would be to hand-write the `.grugops/context/` path → stop; the sanctioned writer is `context-io.ts` via `appendNote` or `promoteAdmitted`.

## Board moves
None of its own. Compaction changes how much prose survives into the committed shared context; it changes nothing about a ticket's position on `plans/board.md`. A ticket never sits in a "compacting" state and compaction is never a reason to hold one. The board move belongs to the invoking workflow.

## Trace updates
None of its own, and this is a safety property rather than an omission. `plans/traceability.md` is rendered from the admitted notes, so compaction must leave the trail unchanged. An `artifact-ref` keeps its trace ids, a `finding` keeps its `verified_by`, and a `failed-attempt` id can never be compacted away. If a promoted finding can no longer cross-check a live green verdict, it degrades to a `claim` carrying `confidence: UNKNOWN - verify`. The trail records that honestly. A note re-bound unchanged keeps its `verified_by` and its id, so the trail reads identically on both sides of the compaction. Never edit a traceability row to preserve a trace the compaction actually broke. A promotion never removes a row either: the write refuses rather than replacing a note, so a trail can only grow. Under `audit_retention: retained`, two routes write both a note and a GOV-02 ledger event. The routes are the re-binding route (`promoteAdmitted`) and the admit-then-persist route (`admitAndAppend`). On both routes the ledger event is appended before the note is written. Each branch below states its own answer. The re-binding route resolves the destination store's owning repository at its entry. Its gated arm writes the note into that store and the event into that repository's ledger. A destination it cannot resolve is refused by name before anything is written. Its fall-through carries the same answer into a new admission, so the note and the event land in one repository. The same refusal fires on that path. The refused input set grew when the clause moved above it, and `R-31-41-01` records what it now refuses. The admit-then-persist route resolves its own store's owning repository at its entry. Its gated branch writes the note into that store and the event into that repository's ledger. An owner it cannot name refuses the admission where a record would be written. Its non-gated branch hands the same answer to the admission authority, so the note and the event land there too. `R-31-33-01` records what remains: the owner is a parameter, and a caller may supply a different one. When that ledger already records the id, the re-binding appends nothing. When it does not, the re-binding appends one event marked `re_bound`. The mark keeps the event distinguishable from a fresh admission. The append precedes the write on both routes. So the destination never holds a human-disposed finding with no ledger line. The converse is reachable, and is the deliberately safe direction. A crash or a refused write between the two steps can leave a ledger line for an unwritten note. A stray ledger line is an over-record: legible, and reconcilable against the notes directory. A note with no ledger line would instead be a repudiation. The two steps cannot be made atomic, so the ordering chooses which asymmetry is possible. The caller's repository argument answers the governance dial. On the re-binding route it decides whether a promotion is permitted, and so decides where nothing lands. On the admit-then-persist route it decides that same question for both branches. Neither route lets it decide where a record lands. With no arguments supplied, the dial reads the host repository while the write follows the kit's own store, and `R-31-33-02` records that split. A destination ledger that is present and cannot be read refuses the promotion by name. The refusal is deliberate: the response to "not recorded" is to append, and a wrong answer would manufacture a duplicate event. Under any other `audit_retention` value no ledger is kept. No route then writes a record, so an owner that cannot be named refuses nothing there, and `R-31-41-02` records that scope.

## Done condition
The verbose local trajectory was distilled at the dialed body verbosity. The proposed promoted set passed the `compactor.ts` carve-out check, with every `failed-attempt` id and the load-bearing fields intact. Every promoted note was written only through `context-io.ts` — `appendNote` for a note the compaction changed, `promoteAdmitted` for one carried forward unchanged. Every promoted `finding` re-admitted against a live green verdict, or re-bound unchanged from an admitted origin. Otherwise it was honestly degraded to a `claim` with `confidence: UNKNOWN - verify`. Every promoted `artifact-ref` either re-bound to a live green verdict in the destination context or was degraded the same way. No refused re-binding was downgraded instead of escalated. Every promoted note landed on an id the destination did not already hold, and no note that was already in the shared context was replaced. Every re-binding named a real origin context store and ran under a destination dial that gates the note it carried. No load-bearing element was dropped at any dial value, and no refusal was faked into a pass.

## Commit
Commit the compact, re-verified context this workflow promoted per `agent-factory/_commit-convention.md` — branch guard first (never a protected branch), then `type(scope): summary`. The artifacts are the `notes/` files and the derived `index.md` / `index.jsonl` that `context-io.ts` produced. The ephemeral `threads/` tier is gitignored and is never committed. This workflow records verified context; it never merges and never deploys — humans hold both.
