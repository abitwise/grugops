WHAT IS UNDER TEST, AND WHY IT NEEDS A BASELINE AT ALL.

DASH-06 and DASH-08 ask the guard to decide two EMPTINESS claims: the dashboard's import
closure reaches no mutating `node:fs` symbol, and it imports none of the banned socket /
process modules. An emptiness claim is the exact shape that passes whether or not the
mechanism behind it works — an empty closure, an empty specifier set, or a derivation that
silently parsed nothing all produce the same green. So the case that pins the property has
to be a case a broken or absent guard FAILS, and this file is the measurement that it does.

The PREMISE assertions in the guard close the vacuity direction. This file closes the other
one: that the guard can fail at all, and that it fails for the reason claimed.

WHAT WAS PLANTED, AND INTO WHAT.

Both plants were appended to the COMMITTED `.js` — the artifact a host actually runs, which
is also the artifact the guard walks. Never the `.ts`, never a fixture, never the test's own
harness. Each was reverted with `git checkout -- <one file>` immediately after its run, and
`git status --short scripts/` was clean afterwards.

WHY THE CONTROL CASE IS IN THE FAILING LIST, AND WHY THAT IS THE POINT.

`CONTROL: an UNPLANTED mirror of the live closure is still green` builds its mirror FROM THE
LIVE SOURCES at test time. With the plant sitting in the live source, the mirror carries it
too — so the control failing here is direct evidence that the mirror is not a stale fixture.
In the GREEN run it passes, which is what makes it a control rather than a duplicate.

------------------------------------------------------------------------------------------
THE SAME TWO PLANTS, IN-SUITE
------------------------------------------------------------------------------------------
The same two mutations are reproduced inside the guard itself, as cases that BUILD a mirror
of the live closure under the repository scratch root, plant into the mirror, and assert the
predicate fails against it:

    a planted mutating fs symbol makes the intersection case FAIL
    a planted node:net import makes the module-ban case FAIL
    the UN-PREFIXED spelling of a banned module is caught too
    a module acquiring node:fs by a route the pass cannot name is REFUSED, not ignored

Those cases run on every suite execution, so the discrimination this file measured ONCE is
re-measured continuously. This file is the record that it was measured against the real
committed artifacts first, with no mirror in the way.
