## MECHANISM DECISION — confirm at plan review (PROMINENT, human-confirmable)

RESEARCH ranked two mechanisms. This plan implements **(a) a structured admission TOOL (MCP server)**
and recommends it over (b). The human should confirm (a) at plan review before execution.

- **(a) CHOSEN — a structured admission tool (zero-dep stdio MCP server) wrapping appendNote.**
  Why: it is the ONLY mechanism that simultaneously (1) gives the agent a STRUCTURED admission channel
  the hook reads with no shell expansion, AND (2) keeps context-io.appendNote the SINGLE sanctioned
  writer (the server calls it; it forks no writer). Posture-B + the GOV-02 ledger are reused (the new
  combiner reuses admit() for non-gated paths and the in-module validate/composeNote/appendNote/
  appendAuditLedger for the gated path — see APPROVED-PATH DESIGN below). The un-forgeable CC gate is the
  PER-CALL PreToolUse hook (25-10), not the server. Today there is NO ergonomic agent-facing write verb
  (the CLI exposes only
  validate/admit/render; admit() does not persist; appendNote is programmatic) — so (a) also completes
  a genuinely missing piece of the architecture, it does not merely relocate the gate.
- **(b) REJECTED — gate the Write/Edit tool on the notes path.** Honest reasoning: notes are NOT
  written via the Write tool today (the sole sanctioned writer is appendNote, invoked programmatically
  via `node`, not the Write tool — context-io.ts:693, CLI :1268). So a Write|Edit matcher fronts an
  UNUSED path: the real sanctioned write (appendNote via Bash `node`) would be left UNGATED once the
  Bash matcher is removed — a regression. Making (b) real requires rerouting note-writing onto the
  Write tool, which BREAKS the single-sanctioned-writer invariant (appendNote's validate/compose/
  atomicWrite/noteId/Phase-22 id-discipline would no longer run; the hook would have to re-implement

## APPROVED-PATH DESIGN — per-note disposition; the un-forgeable gate is the PER-CALL HOOK (D-03/D-07)

The gate is not only "deny an un-approved high-severity admission"; it MUST also ADMIT a human-APPROVED
one PER NOTE (D-07: the human disposes a SPECIFIC entry; the ledger's `disposed_by` must attribute that
entry to the human who reviewed it). Two design facts drive this:

1. `admit()`'s D-04 branch (context-io.ts:947) refuses EVERY high-severity finding under any active dial
   unconditionally — even one carrying a `human:NAME` stamp (the 25-04 forged-stamp backstop) — because
   the in-script tier cannot verify a human placed it. So routing the CC persist naively through `admit()`
   would have the gate ALLOW while the combiner REFUSES — the approved note never admits.
2. CONFIRMED Claude Code capability: a PreToolUse hook runs FRESH PER CALL and reads the CURRENT session
   env; an MCP server's `process.env` is FROZEN at launch and CANNOT see a mid-session export. So a
   server-env approval would be PER-SESSION, silently narrowing D-07's per-ENTRY disposition to a blanket
   and mis-attributing `disposed_by` to a human who never reviewed that specific entry (an audit-integrity
   failure — the core value of this governance feature). The gate therefore must be the per-call hook,
   not the server.

The design:

- **The un-forgeable CC gate = the PER-CALL PreToolUse hook on `mcp__grugops__.*` (25-10), mirroring
  guard.ts (D-01/D-02) — NOT the server env.** Per call the hook reads the FRESH session env
  `GRUGOPS_ADMISSION_APPROVED_BY`, calls the shared `isGatedNote(by, kind, configResult)` to decide
  whether THIS note is gated, and for a GATED note DENIES unless (env present) AND
  (`tool_input.verified_by` === `human:${env-name}`). This binds the persisted stamp to the env-verified
  approver PER CALL, un-forgeably, with only confirmed capabilities (the agent supplies the stamp; the
  hook validates it against the fresh env — no undocumented `updatedInput` needed).
- **The server is NOT the gate — it forwards the structured args to the combiner and persists what the
  hook allowed.** The server does NOT read its own env for approval (removed). It calls
  `admitAndAppend(task, note, body, contextRoot?, repoRoot?)` (admit() byte-frozen).
- **The combiner (`admitAndAppend`) is the persist arbiter, on ALL CLIs:** determine GATED via the SHARED
  `isGatedNote(by, kind, configResult)` (the SAME predicate the hook uses — W-A; it reads
  `readGovernanceConfigResult` and folds in kind + the high-sev classifier + the dial canonicalization,
  treating unreadable as gate-or-stricter → fail closed, SC3). NEITHER the combiner nor the hook
  reconstructs that composition locally.
  - GATED note: persist ONLY if a valid `human:NAME` stamp is present in `verified_by` (on CC the per-call
    hook validated it un-forgeably; on non-CC / direct-node this is the weaker self-settable D-05 tier =
    documented residual), then ledger `disposed_by: human:NAME`; else REFUSE naming the fault. This also
    BACKSTOPS a gated-routine-under-`all` note lacking a disposition (W5). The gated branch does NOT call
    `admit()` (its D-04 would refuse regardless); it reuses the IN-MODULE composeNote / validate /
    appendNote / appendAuditLedger.
  - NON-GATED note (routine under high-severity, or dial off): a `human:NAME` stamp is ILLEGITIMATE here
    (it would forge a `disposed_by` ledger entry) — the combiner REJECTS an agent-supplied `human:NAME`
    on a non-gated note (`verified_by` must be empty or a `§14-gate#<id>` stamp); W3. Then call `admit()`
    unchanged (validate + Posture-B §14-gate cross-check + D-04-won't-wrongly-fire + ledger) and appendNote.
- **The FULL gated predicate is PROVABLY SINGLE-SOURCE (W-A, round-8 anti-drift):** export `isGatedNote(by,
  kind, configResult)` (the complete decision) and its dependency `isHighSeverityRole(by)` (NFKC + strip
  whitespace/zero-width + lowercase + allowlist of the 3 role literals) from context-io. BOTH the hook
  and the combiner IMPORT `isGatedNote`; NEITHER reconstructs `((high-sev && active) || all)` or the
  classifier locally (the duplicated composition was the 10-round drift surface — the allow-forge risk is
  the hook reading not-gated/allow-unchecked while the combiner reads gated/trust-the-stamp). `admit()`'s
  frozen `.trim().toLowerCase()` D-04 classifier is a THIRD, weaker, intentionally-FROZEN DEGRADE
  classifier — its coverage ⊆ `isGatedNote`'s, so it never under-gates relative to the un-forgeable tier
  and is not exploitable; it MUST NOT be touched (mechanically frozen by a per-function span hash, W-B).
- **Defense-in-depth + non-CC honesty:** hook (un-forgeable, per-call, CC) + combiner stamp-check (weaker,
  all CLIs, D-04/D-05). Claim the un-forgeable tier CONSERVATIVELY for Claude Code; do not over-claim
  non-CC. UX (mirrors the deploy guard): the human exports `GRUGOPS_ADMISSION_APPROVED_BY=<name>` for the
  SPECIFIC disposition, the per-call hook validates it against the agent-supplied `human:<name>` stamp,
  optionally unset after — per-note, no server restart needed.
