<objective>
End the CMP-02 carve-out bypass cycle (round 3). The carve-out oracle in `scripts/compactor.ts`
has NO stable per-note identity, so it guesses the raw→promoted correspondence from forgeable,
collidable CONTENT TUPLES. All three surviving bypasses are this one defect:

- **CR-01** (compactor.ts:225-241): `verifiedKey = (kind, verified_by, by, at)` keyed into a Set,
  tested with `.has()` — set MEMBERSHIP not COUNT. One §14-gate run stamps N findings identically,
  they collapse to one key, one promoted survivor satisfies all N, the rest drop at exit 0.
- **CR-02** (compactor.ts:194-219, 251-263): `if (!counterpart) continue` (line 197) is FAIL-OPEN.
  A non-verified note matched on `(kind, at)` returns null when both `by` AND `at` are mutated, or
  when two notes share `(kind, at)` → the field check is skipped → a `by` swapped engineer→attacker
  survives.
- **IN-01** (compactor.ts:198, 225-241): `supersedes` is in the alter-list but has no affirmative
  existence check → a wholly-dropped note loses its load-bearing supersedes link undetected. (And the
  round-3 BLOCKER: any promoted-side `supersedes` claim must NOT be allowed to AUTHORIZE a drop — the
  required-survival set is the raw-side `currentState()` fold ONLY, never a promoted-side line.)

The fix is the **STABLE-ID REWRITE** (not the minimal multiplicity patch). The id already exists:
`context-io.ts noteId()` (line 369) computes `<at-compact>-<by>-<kind>-<nonce>` and stores it as the
filename `notes/<id>.md`. This plan threads that existing identity through as an explicit frozen
`id:` frontmatter field, makes the carve-out an exact 1:1 id match (affirmative existence, fail
closed, byte-equal fields), and DELETES the `findCounterpart` tuple fallback + the `verifiedKey`
Set — they are the defect.

The required-survival set is **asymmetric** (the convergent invariant — both round-3 raw-side and
promoted-side blockers are this same tension). Its base is **`currentState(rawThread)`** —
context-io.ts's deterministic raw-side supersedes collapse (lines 436-444, the ONE fold D-03
sanctions, per the compactor.ts header lines 24-27). BUT `currentState` is **kind-blind and
verified_by-blind** (context-io.ts:440-443 folds out ANY id that appears in another note's
`supersedes`). So the fold may remove a note from the required set **ONLY for soft, non-verified
kinds**. TWO classes survive **UNCONDITIONALLY** and are NEVER supersede-foldable:

1. **Failed-attempt ids** — protected by carve-out rule 1 (the FA-token check over the UNFOLDED
   rawThread, compactor.ts:154-184). Rule 1 stays EXACTLY as is; it MUST keep iterating the full
   unfolded raw set (refactoring it to iterate `currentState` would convert the safe FA case into a
   live FA-erasure hole).
2. **§14-gate-verified findings** (a durable note with NON-EMPTY `verified_by`) — must survive into
   promoted byte-equal REGARDLESS of any raw-side `supersedes: X`. A weaker (or any) raw-side note
   must NOT be able to fold a verified finding out of the required set. This restores the
   fold-independence the deleted `verifiedKey` existence check had (lines 221-241), minus its CR-01
   collision bug — the id-keyed match already fixed the collision.

For soft non-verified notes only: every note in the raw-side live set MUST have a byte-equal promoted
counterpart matched by `id`. The supersedes existence requirement for soft notes is derived SOLELY
from the raw thread's own supersedes graph — and a promoted-side `supersedes` line NEVER authorizes a
drop (closing the round-3 promoted-side BLOCKER: a forged promoted-side `supersedes: X` cannot fold
away a live raw note X). The round-3 raw-side BLOCKER (probe (b)) is closed by the verified-finding /
failed-attempt UNCONDITIONAL exemption above: replacing the deleted fold-independent verifiedKey check
with a fold-GATED set was a net regression on the raw side for verified findings — the exemption
restores it. A matched note's own `supersedes` is still byte-equal-checked as a load-bearing field, so
a real link cannot be altered.

**Consolidated required-survival rule** (state it this precisely so no v3 hole opens): a durable raw
note X may be ABSENT from the promoted set ONLY IF ALL hold: (i) X is a SOFT kind with EMPTY
`verified_by` (not a failed-attempt; not a verified finding), AND (ii) X is folded out by
`currentState(rawThread)` — a raw note S carries `supersedes: X` RAW-SIDE (raw-grounded), AND
(iii) that superseding note S itself survives into promoted byte-equal (passes its own existence +
byte-equal checks). Otherwise X MUST be present in promoted, matched by `id`, with byte-equal
load-bearing fields. Failed-attempt FA-tokens are required UNCONDITIONALLY via rule 1.

Read-path guard: the carve-out `check` verb parses raw+promoted notes through compactor.ts's OWN
`readNoteFields` (lines 96-113) — a SEPARATE parser from context-io's `parseNote`. `readNoteFields`
must therefore enforce its own duplicate-key fail-closed reject (mirroring parseNote's seen/dupes

## The thread-representation model (RESOLVED — implement exactly this, consistent with D-07/D-08)

D-08 keeps the thread tier a SINGLE file `.grugops/context/<task>/threads/<agent>.md`. The carve-out
`check` verb reads a DIRECTORY of per-note `.md` files. For id-based matching to be REAL (not test
fiction), the RAW side must carry per-note `id:` fields.

**Resolution (chosen): the `check` verb's "raw" input is an explicit per-note id-bearing
representation produced AT COMPACTION TIME.** The agent, following Workflow 18 step 3, hands the
carve-out check a per-note snapshot directory where each raw durable note is one `id:`-bearing `.md`
file. This is consistent with D-08: the ephemeral `threads/<agent>.md` blob stays a single file for
the agent's own scratch; the carve-out operates on the structured per-note set the agent proposes to
promote, and every such raw note carries the same frozen `id:` its promoted counterpart preserves.

`writeThread` is updated to APPEND an id-bearing structured note FENCE per recorded note (not
freeform body text), so the thread file itself is a sequence of id-bearing notes the compaction step
parses into the per-note raw set. The `id:` it stamps is the creation-time `noteId()` value — the
SAME id the promoted note must preserve byte-for-byte.
