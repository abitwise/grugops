## Warnings

### WR-10: The dogfood runbook still sends the human to the environment's settings alone (WR-09 fix incomplete)

**File:** `docs/dogfood-human-runbook.md:127-131`
**Issue:** Plan 43.1-15 fixed the hard-floor bullet at lines 49-59. Its must-have truth says: "The
dogfood runbook no longer sends the human to the environment's settings alone". But Check 2's
"Where the two remaining safety tiers are evidenced instead" list still has a **Hard floor (git
host)** bullet that ends:

```
check does not read the production environment (33.1 D-31), so confirm its settings yourself on
the git host.
```

That is the instruction WR-09 removed everywhere else. It sends the human to the environment's
settings for every production line. Two lines cannot be seen there. The deploy-path line
(`deploys_through_environment`) is confirmed in the workflow files and in any hosting platform or
GitOps controller. The credential line is confirmed in repository and organization secrets and
variables, on runners, and in cloud trust policies. A human who follows this bullet can tick both
lines without looking where they can be seen.

The plan's acceptance grep looked for `so confirm the environment's settings yourself on the git
host`, and its read scope was lines 44-60. This sentence says `so confirm its settings yourself on
the git host`, so neither the grep nor the scope caught it. The plan's truth is therefore false as
shipped.

**Fix:** Replace the end of the bullet with the pointer the same file uses at line 58:

```markdown
  You will also see one `environment <name>: UNKNOWN - verify — not checked by design …` line: the
  check does not read the production environment (33.1 D-31), so confirm each production line
  yourself where `install/README.md` §5 says it can be seen, not only in the environment's settings.
```

Then widen the guard to the pronoun form, for example
`git grep -n -E "confirm (its|the environment's) settings yourself" -- ':!.planning' ':!docs/audit' ':!CHANGELOG.md'`
must print nothing.

## Info

### IN-11: Workflow 05 step 3 counts the deploy-path condition as a requirement of the credential condition

**File:** `agent-factory/workflows/05-pr-quality-gate.md:31`
**Issue:** Step 3 reads: "For a deploy, that floor holds only when the deploy credentials live
solely in the production environment. This requires that a stored deploy secret … It also requires
that an OIDC trust policy … The third requirement is that every production deploy runs as a job
that references that environment." Grammatically, "this" and "the third requirement" refer to the
credentials condition. But "every deploy runs as a job that references the environment" is not
part of keeping credentials in the environment. It is a separate condition on the floor. Workflow
12 says this correctly: "The floor also holds only while every production deploy runs as a job
that references that environment."
**Fix:** Phrase it the way Workflow 12 does, within WP-02's 20 words: "The floor also holds only
while every production deploy runs as a job that references that environment." Re-measure
C-28-059's mechanism in the same commit.

### IN-12: "This repository" is ambiguous on pages that describe the grugops checkout

**File:** `docs/GUARANTEES.md:35-40`, `scripts/audit-model.ts:336,339` (and the generated table row
at `docs/GUARANTEES.md:56`)
**Issue:** The widened condition says the trust policy "accepts only tokens whose subject names
this repository and that environment". `docs/GUARANTEES.md` says it shows which safety claims hold
"in the grugops source checkout", so a reader can take "this repository" to mean grugops's own
repository rather than the reader's. In the §5 checklist ("this environment") and in a workflow
running in the user's repository, the phrase is unambiguous. On the guarantees page and in the
floor model it is not.
**Fix:** In the floor-model `why`/`hardFloor` strings and the `generate-guarantees.ts` tier
paragraph, write "names the deploying repository and that environment" or "names your repository
and that environment". Regenerate `docs/GUARANTEES.md` and refresh the hook manifest hash for
`scripts/audit-model.js`.

### IN-13: The environment line says "the setting lines" without saying which lines those are

**File:** `scripts/runnable-ref/host-protection.ts:1672`
**Issue:** The reason now says "the setting lines in the environment's settings, the deploy-path
line in …, and the credential line in …". Only `install/README.md` §5 defines "the setting lines"
(name, reviewer, self-review, administrator-bypass, deployment-branch). A human who reads only the
check's output cannot tell which of the seven checklist lines are "setting lines". The name line
("has the name your deploy jobs use") also cannot be confirmed fully in the environment's settings:
whether the deploy jobs use that name shows only in the workflow files. The deploy-path line covers
this in practice, but the README sentence at `install/README.md:1943-1945` still lists the name line
as confirmable in the environment's settings.
**Fix:** Optional. Say "the reviewer, self-review, administrator-bypass and deployment-branch lines
in the environment's settings". Move the name line next to the deploy-path line, under the workflow
files, both in the reason string and in `install/README.md`. Keep the test's `toContain` pins in
step.

### IN-14: The install guide's positive `--migrate` condition does not cover a target without an install marker

**File:** `install/README.md:239-244`, `CHANGELOG.md:183-186`
**Issue:** The new text says a `--migrate` "that has a layout to move (the old in-repo layout, or
planning state on the pre-v3 layout) continues into the install run". The stated stop case (already
two-root, state not pre-v3) matches `install.ts:8948` exactly. But the code also continues into the
install run on a target with no marker and nothing to move: `isClean` falls through, as the comment
at `install.ts:9007` notes. A reader can infer from the text that a `--migrate` with nothing to move
always stops, which is false. No stale runnable is removed in that case, because there is no usable
ledger, but the presence note still runs.
**Fix:** State the stop case alone and say every other `--migrate` continues: "A `--migrate`
continues into the install run and does the same, except on a target already on the two-root
layout whose planning state is not on the pre-v3 layout: there it stops before the install run …"
