<objective>
Repair the gate that is supposed to make a committed `.js` unable to drift from its `.ts`, and prove the
repair is not vacuous.

`tsconfig.json` sets `outDir` and `rootDir` to `./`, so `npm run build` rewrites the tracked, committed
`.js` files in place. `scripts/freshness.ts` reads the committed side from the WORKING TREE.
`.github/workflows/ci.yml` runs the build at `:59` and every freshness check at `:87` and after, with no
dirty-tree assertion anywhere in the file. So continuous integration compares a fresh build against a
fresh build, and cannot detect a committed `.js` that was hand-edited or simply never rebuilt — the exact
guarantee `CLAUDE.md`'s tech-stack section names as the reason the tooling layer ships as committed `.js`
at all.

This is pre-existing since Phase 20 and is named by no LANG requirement. It is repaired here because round
7's own verification sweep used this ordering as its build-parity evidence, and the identical command
appears in the automated verification of every plan in this phase. Every mechanical claim this phase makes
about its shipped artifact rests on a gate that cannot fail (D-57).

The fix is ordering-independent by construction: the gate reads the committed side from git, so a build
step earlier in the same job has nothing to repair. The workflow reorder and a working-tree assertion are
the belt-and-braces half, wired through one named script so there is one authority rather than a copy.

**A fix to a vacuous gate that is itself unproven repeats the defect.** The acceptance criteria therefore
require the same planted drift to be shown green on the pre-fix tree and red on the post-fix tree.

Purpose: after this, the `.js` a host machine runs with bare Node is provably the build of the `.ts` a
reviewer read.

Output: a gate whose subject is HEAD, a case table with a fail-closed verdict for every branch, a
discrimination pair, and one script that owns the working-tree question.
</objective>

    Move the comparison's committed side to git. Derive the committed output set from `git ls-tree -r HEAD --name-only`

    Invoke git through `spawnSync` with no encoding so both sides are Buffers — a byte comparison decoded as
    text is not a byte comparison — and set an explicit `maxBuffer` above the largest committed output rather
    than relying on the default. Normalise every path to POSIX separators before handing it to git, because
    `git show` does not accept a Windows separator and the existing walk builds paths with the platform one.

    Select the comparison arm from a derived set, not from a flag. Derive once, from git, the set of paths
    under the output directories that differ from HEAD in the working tree or are untracked. Then for each
    committed output: if its corresponding source is NOT in that set, compare the HEAD blob against the fresh
    rebuild — this is the load-bearing arm and the only one a clean checkout ever takes; if its source IS in
    that set, compare the WORKING file against the fresh rebuild instead, because a rebuild of a modified
    source is not a rebuild of HEAD's source and comparing it to HEAD's output would report a cause that is
    not there. Name the two verdicts differently and give each its own remedy sentence. This is two arms over
    one predicate, so write the arm selection in one place, derive it from one command, and assert in the
    published output that the two arm counts sum to the compared total.

    Give every remaining case a named, fail-closed verdict. A committed output with no rebuilt counterpart is
    an orphan, as today. A rebuilt output whose path is in neither the HEAD set nor the working tree is an
    uncommitted build output. A path in the HEAD set that is absent from the working tree is a deleted
    committed output. Any git invocation that exits non-zero — no repository, no `HEAD`, a path `git ls-tree`
    listed that `git show` cannot produce — is a refusal: report it, and never print the fresh line. Keep the
    existing broken-rebuild behaviour exactly: a `tsc` that does not compile cleanly never reports fresh.

    Publish the numbers a human can check by hand. The success line states how many committed outputs were
    compared against HEAD, how many were compared against the working tree because their source is
    uncommitted, and how many refusals were raised — and the arm counts are asserted to sum. State in the
    output which question this gate answers, so a reader is not left to infer it.

    Write the case table into the module header, in clear professional voice, as the record of what "closed"
    means for each branch. Name D-57 by id. Record why the subject is HEAD in one paragraph: the build writes
    over tracked outputs in place, so a gate reading the working tree compares a fresh build against itself,
    and no step ordering can be relied on to prevent that.

    Sequence the self-validation deliberately, and record both halves. Build the twin and run the gate BEFORE
    committing: its own source is uncommitted at that moment, so it takes the working-tree arm and reports one
    path in that arm. Quote that transcript. Then commit source and twin together and run it again: now it
    takes the HEAD arm for its own twin and reports zero in the working arm. Quote that transcript too. Those
    two runs are how a gate that changed its own rule is validated against it.
