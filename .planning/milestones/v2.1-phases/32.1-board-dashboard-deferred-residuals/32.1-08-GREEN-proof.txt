Section 2 -- the three classes a runtime probe over this corpus cannot observe
-------------------------------------------------------------------------------

Each class is stated with the REASON it is unobservable and the AUTHORITY that
does or does not cover it. A reason is structural, never a schedule: "nobody
has got to it" is not a reason a waive may rest on.

CLASS 1 -- A WRITER VALUE PASSED AT RUN TIME.  (ledger row 208)

  What it is: a function that writes is handed to a closure module as an
  argument, a property, or a captured binding, rather than imported by it.

  Why the probe cannot see it: the module identity never enters the resolver.
  A `resolve` hook observes module RESOLUTION -- a specifier being turned into
  a URL -- and a value passed between two already-resolved modules produces no
  resolution at all. There is no event to record, so no recording, however
  complete, contains one.

  The authority that DOES cover it: the static acquisitions census in
  `scripts/board-readonly.test.ts`. It refuses every route by which a module
  identity could be obtained other than a static import declaration with a
  string-literal specifier, and task 1 of this plan restored its second
  predicate -- a bare specifier the runtime does not resolve as a builtin is
  now an acquisition, so the write-detection mechanism reds for it rather than
  a census count moving. The residual the census does not cover is a writer
  value that arrives through a parameter of an exported function, which is a
  property of the CALLER rather than of this closure.

CLASS 2 -- A DEPENDENCY THAT DOES NOT EXIST YET.  (ledger row 208)

  What it is: a `node_modules` package a future commit adds and a closure
  module then imports.

  Why the probe cannot see it: a recording is a measurement of what THIS corpus
  loads on THIS tree at THIS commit. It is a statement in the past tense about
  five files. A specifier a future change introduces is not absent from the
  recording because the probe looked and found nothing; it is absent because
  there was nothing to look at. No probe can enumerate a set that does not
  exist.

  The authority that DOES cover it: the standing control in
  `scripts/board-readonly.test.ts` -- `package.json` still has no
  `dependencies` key, asserted as a failing case, so the day a runtime
  dependency appears the guard reds at that commit rather than silently
  reporting a closure short by everything under `node_modules`. Task 1's
  restored predicate is the second half: a bare specifier that is a PACKAGE
  identity rather than a builtin is refused by the acquisitions premise even if
  the manifest gained a key.

CLASS 3 -- A KEY SPELLING ASSEMBLED AT RUN TIME.  (ledger row 184)

  What it is: a ticket-frontmatter key built by `String.fromCharCode`, through
  a template with substitutions, or read from a variable, in a file that also
  scans text -- a second ticket-frontmatter reader the split-reader census
  cannot name.

  Why NEITHER authority covers it: the static census sees EXPRESSIONS and the
  question is about VALUES -- the spelling does not exist until the program
  runs, so a static pass has nothing to resolve. And the runtime probe observes
  MODULE RESOLUTION, not string construction: a key assembled inside a module
  that Node has already resolved produces no resolve event, so the recording is
  silent about it for the same reason it is silent about class 1. Two
  authorities, one gap, and it is the same gap seen from two sides.

  What IS measured: zero carriers on this tree. The census's own case,
  `it("does NOT see a reader whose key spellings are assembled at RUNTIME -- the
  stated blind spot")` at `scripts/validate.test.ts:3088`, plants a
  `String.fromCharCode` shape and asserts the census reports nothing -- so the
  boundary is pinned by a passing case rather than left to be discovered. Plan
  32-36's `[...].join(sep)` arm closed the STATIC half (a key assembled by
  joining literal characters now resolves and is counted). The rest is not
  closable by one more resolution arm.
