7. TWO SCAFFOLDING FAULTS, RECORDED BECAUSE THEY BEAR ON THE EVIDENCE
=====================================================================

Neither of these is a property of the lane. Both are faults in the harness this executor
wrapped around the lane, and both are written down because one of them cost a measurement
and the other could be misread as a first run.

FAULT ONE - AN ABORTED LAUNCH THAT NEVER REACHED THE LANE. The first launcher used `setsid`
to put the lane in its own process group. macOS has no `setsid`. The launcher died at that
line with `setsid: command not found` and exit 127, after 1 second, having produced a
163-byte log containing only that error. `npm test` WAS NEVER INVOKED by it. No vitest
process started, no CLI call was made, and nothing was spent. This is not a first run of the
lane and must not be counted as one; the single-run property in section 1 is intact. The
launcher was repaired to use `perl -e 'setpgrp(0,0); exec("npm","test")'`, and the repaired
exec path was PROVEN to reach npm with a harmless probe - `perl -e 'setpgrp(0,0);
exec("npm","--version")'` printed `11.7.0` and exited 0 - BEFORE the one authorized run was
spent on it.

FAULT TWO - A WATCHDOG WHOSE HANG HEURISTIC WAS WRONG FOR THIS RUNNER. The watchdog treated
"no new output for 900 s" as a hang. Vitest buffers its per-file output when stdout is not a
terminal: at 11 minutes into a healthy run the capture still held only its 172-byte header,
and the watchdog was roughly three minutes from killing a run that was working correctly -
which would have destroyed the one authorized run and recorded it as a hang that never
happened. The watchdog was suspended so it could not signal the lane. The harness then
treated that suspension as its child terminating and reaped the watchdog shell, which left
the lane orphaned to init - still running, still healthy, and never signalled - but removed
the `wait()` that would have returned its exit status. That is the whole of section 4's
limitation. The lane's own completion is unaffected: it printed its own summary block and
its pid disappeared on its own.

WHAT A LATER PLAN SHOULD TAKE FROM FAULT TWO, if it ever needs to bound this lane again: a
no-output interval is not a liveness signal for a buffered runner. Bound it on total
wall-clock only, or make the runner emit progress, and capture the exit status in a process
that is not the same one making the kill decision.
