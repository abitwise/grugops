## Summary

Reviewed the install-time render path (`renderAdaptersInMirror`, `transformAdapter`, `materializeAdapter`, the agents-loop cross-checks and refusal arms, the `--check` staleness verdict), the three prose sites (`factory.config.md`, `install/README.md`, `CHANGELOG.md`, the `model-tiers.ts` header), and the test re-aim in `model-dial-consistency.test.ts`. The committed `.js` twins were verified fresh (`npm run freshness`: 50/50 match; `check:build-parity` clean), so no separate finding is raised on them.

The render path is well-bounded where the phase's own red-team looked: the twins pre-check, the mkdtemp and mirror-construction guards, the config-copy guard, the two-direction set equality, the count and alias-set cross-checks, the banner count floor and the routing floor all hold as described, and every one I traced refuses closed. The `process.execPath` / no-`shell` spawn is correct, no twin reads `process.env`, the probe is a fixed literal, and the relayed refusal channel is bounded (`quoteValue` goes through `JSON.stringify`, so control characters cannot reach the terminal unescaped).

Three defects were reproduced live against the committed `install.js`, not inferred:

1. **Data loss (BLOCKER).** `materializeAdapter()` writes through a live symlinked destination. A target adapter the user replaced with a symlink to their own file had that file overwritten with adapter bytes on the next re-run, at exit 0. The repository already names this hazard as a HIGH-severity "LANDMINE (Pitfall 1)" and guards it, but only inside `migratePreSteps()` on the old-layout `--migrate` path. The ordinary re-run has no guard, and this phase made the ordinary re-run the documented delivery mechanism.
2. **Dry-run preview disagrees with the run it describes.** Over an unchanged target, `DRY_RUN` printed 18 `would-materialize` lines where the real run printed 24 `skipped`.
3. **Shipped prose false for its audience.** `factory.config.md` still tells an installed user that `agent-factory/config/factory.config.json` is a consulted location. A target carrying only that file rendered 17 `inherit` and reported that no configuration file was found (D-06 by construction).

The remaining findings are robustness and quality: an unguarded `rmSync` in a `finally` that can convert a completed render into a crash, a dead `linkOrCopy` fallthrough that is the R2 hazard left latent, and a success-path relay naming a removed temp directory.

## Critical Issues

### CR-01: `materializeAdapter()` writes through a live symlinked destination — user content overwritten on re-run

**File:** `install/install.ts:1821-1845` (also reached from the skills loop at `:2160` and the agents loop at `:2387`)
**Issue:** The function reads `dest` (following the link), compares, and on difference calls `writeFileSync(dest, final)` — which follows the symlink and overwrites whatever it points at. Nothing asks what bounds `dest`; it is assumed to be a regular file or absent. `linkOrCopy()` at `:1251` refuses a symlinked destination (`skipped (symlink present)`); `materializeAdapter()` does not.

Reproduced against the committed build: install a target, replace `.claude/agents/grugops-ba-pm.md` with a symlink to `<elsewhere>/notes.md` containing `MY PRECIOUS USER NOTES`, re-run install. Output: `materialized .claude/agents/grugops-ba-pm.md (KIT=…, model=sonnet)`, `== install complete ==`, exit 0. Afterwards `notes.md` holds the adapter's frontmatter and the path is still a symlink.

This violates the CLAUDE.md hard constraint ("never overwrite or delete user content") and the D-13 comment's own rationale ("CLAUDE.md's never-overwrite rule protects USER content"). The write-through existed before this phase, but two things this phase did make it a release blocker rather than a latent residual: (a) D-13 explicitly ratified unconditional rewrite-on-difference as ownership, and (b) D-07/D-15 made re-running the installer the routine, documented way to deliver a `models` edit (`install/README.md:294-300`, `factory.config.md:140`, the `TARGET_BANNER` in every installed adapter). The repository already classifies this as the "LANDMINE (Pitfall 1)" HIGH-severity shape at `:1156` / `:1192-1223`, and guards it there — but only when `isOldLayout` is true, so the guard never runs on the path users are now told to take. The `--check` doctor has the same blind spot at `:750`: it `readFileSync`s the target adapter through the link and will report a symlinked adapter as current or stale by the *linked file's* content.

**Fix:** Refuse a symlinked destination by name, before the read/compare, in the same shape `linkOrCopy` uses — and since the file is kit-owned, either refuse loudly or take the migrate path's unlink-then-rewrite. Refusing is the safer default under never-overwrite:

```ts
function materializeAdapter(src: string, dest: string, label: string, alias?: string): void {
  const suffix = alias === undefined ? `(KIT=${KIT_ROOT})` : `(KIT=${KIT_ROOT}, model=${alias})`;
  if (!existsSync(src)) {
    report("skipped", `${label} (source missing: ${src})`);
    return;
  }
  // NEVER WRITE THROUGH A LIVE SYMLINK (Pitfall 1). The migrate pre-step unlinks these on the
  // old-layout path only; the ordinary re-run — the documented delivery path — must refuse.
  if (isSymlink(dest)) {
    verify(
      `${label} — ${dest} is a symbolic link, and writing the rendered adapter would overwrite ` +
        `whatever it points at. It was left untouched. Replace the link with a regular file (or ` +
        `remove it) and re-run; the installer never writes through a live symlink.`,
    );
    return;
  }
  // ...unchanged from here
}
```

Add a case to `install/install.test.ts` that plants a symlink at a target adapter path pointing at a sentinel file outside the target, re-runs with a differing config, and asserts the sentinel is byte-unchanged, the run exits 3, and the finding names the path. Mirror the same `isSymlink` distinction in the doctor loop at `:747-755` (name it rather than reading through it).

## Warnings

### WR-01: `DRY_RUN` reports `would-materialize` for files the real run would skip

**File:** `install/install.ts:1826-1829`
**Issue:** The `DRY_RUN` early return sits *before* the build-then-compare, so every adapter and the resolver skill report `would-materialize` regardless of whether the final bytes already match. Reproduced: over an unchanged target the dry run printed 18 `would-materialize` / 6 `skipped`, and the real run immediately after printed 24 `skipped`. D-11's stated property — "a re-run is a visible no-op and a refresh a visible change" — is not visible in the preview, and the preview is inconsistent with `linkOrCopy()`, which checks identity before its `DRY_RUN` branch (`:1256-1263`). A user asked to preview a `models` edit cannot tell from `--dry-run` whether anything would change.
**Fix:** Move the `DRY_RUN` return below the comparison. Both sides are read-only (the mirror exists under `DRY_RUN`; `mkdirp` is already `DRY_RUN`-aware):

```ts
const final = transformAdapter(readFileSync(src, "utf8")).text;
let current: string | null = null;
try { current = readFileSync(dest, "utf8"); } catch { current = null; }
if (current === final) {
  report("skipped", `${label} (identical copy present)`);
  return;
}
if (DRY_RUN) {
  report("would-materialize", `${label} ${suffix}`);
  return;
}
mkdirp(dirname(dest));
writeFileSync(dest, final);
report("materialized", `${label} ${suffix}`);
```

Adjust the `DRY_RUN` case at `install.test.ts:1936` (it currently asserts 17 `would-materialize` over a *fresh* target, which stays true) and add a second-run dry-run assertion of 17 `skipped`.

### WR-02: `factory.config.md` still tells an installed user that the in-kit config location is consulted

**File:** `agent-factory/config/factory.config.md:138` (the paragraph beside the one D-15 rewrote at `:140`)
**Issue:** The "Where the block is read from" paragraph states the resolver "looks in exactly two places … `.grugops/factory.config.json` first, then `agent-factory/config/factory.config.json`" and that writing the block into the in-kit file is read when no `.grugops/` file exists. For an installed repository this is false by construction: D-06 never places an `agent-factory/config/` file in the mirror, so the second location cannot be consulted. Reproduced: a fresh target carrying only `agent-factory/config/factory.config.json` with `{"models":{"preset":"tiered"}}` installed 17 `model: inherit` adapters and reported `no configuration file was found at <target>/.grugops/factory.config.json`. The paragraph is explicitly addressed to installed users ("the standard installed shape"), and the new `:140` paragraph deliberately "names no configuration-file location", so nothing in the file corrects it. Under D-15's own rule ("kit prose states what is true now") and CLAUDE.md's no-fabrication constraint, this is a false claim shipped to every installed user.
**Fix:** Add one sentence to `:138` or `:140`, e.g. after "This whole-file precedence is deliberate…": *"In an installed repository only the first location exists to the render: the installer never hands an in-repo `agent-factory/config/factory.config.json` to the generator, so for an installed repository `.grugops/factory.config.json` is the only file consulted."* Extend the location-spelling count case in `model-dial-consistency.test.ts` if the sentence adds a spelling.

### WR-03: `rmSync` in the render helper's `finally` can throw after retries and crash a completed run

**File:** `install/install.ts:1691`
**Issue:** `rmSync(dir, { recursive: true, force: true, maxRetries: 3 })` throws after three retries on `EBUSY`, `EPERM`, `ENOTEMPTY` (documented Node behaviour; the exact shape a Windows antivirus or indexer produces on a just-written temp tree — the phase records Windows as `UNKNOWN - verify`). The throw escapes `renderAdaptersInMirror`. On the install path that happens *after* `use()` has written all seventeen adapters and *before* `seedState()` / `writeMarker()`, so the process dies at exit 1 with a raw stack, no closing banner, and a target holding adapters but no marker — the same crash-where-a-finding-belongs shape R1 and F-D were fixed for, now sitting one line after them. On the `--check` path the doctor dies mid-verdict. A cleanup failure is not a verdict failure and must not be reported as one.
**Fix:**

```ts
} finally {
  try {
    rmSync(dir, { recursive: true, force: true, maxRetries: 3 });
  } catch (e) {
    // A leftover temp tree is a housekeeping fact, never a reason to lose a completed verdict.
    report(
      "verify",
      `the render mirror at ${dir} could not be removed (${e instanceof Error ? e.message : String(e)}); ` +
        `it holds no target data and can be deleted by hand.`,
    );
  }
}
```

(`report` rather than `verify()` so the counter is not incremented for a non-install condition; or use `verify()` if the team prefers exit 3 — but decide explicitly.)

### WR-04: The `linkOrCopy` fallthrough in the agents loop is the R2 hazard left as live code

**File:** `install/install.ts:2388`
**Issue:** `if (srcCarriesSlot(src)) materializeAdapter(...); else linkOrCopy(src, dest, label);` — the `else` arm is dead by construction after the routing floor at `:2330-2345` refused every rendered file without the slot. But it is still reachable code whose `src` is a path inside the temp mirror: if reached under `INSTALL_MODE !== "copy"` it symlinks the target at a directory the `finally` deletes moments later and reports `linked` at exit 0 (the reviewer's R2 reproduction). The floor is the only thing standing between the loop and that outcome, and nothing structural stops a future edit to the floor from re-exposing it.
**Fix:** Replace the fallthrough with a hard refusal so the loop cannot ever copy or link raw mirror bytes:

```ts
if (!srcCarriesSlot(src)) {
  // Unreachable: the routing floor above refused every slot-less render before the first write.
  verify(`.claude/agents/ — ${label} reached the write loop without the kit slot line; refusing to copy or link raw mirror bytes.`);
  continue;
}
materializeAdapter(src, dest, label, aliasOf.get(f));
```

### WR-05: The success-path relay names a temp mirror that no longer exists

**File:** `install/install.ts:2369`
**Issue:** The generator's first stdout line — `generate-role-adapters: wrote 17 adapters to <tmp>/grugops-install-render-XXXX/.claude/agents (...)` — is relayed verbatim on every successful install. The phase's own rule, applied to the failure arm at `:2333-2340` and to the doctor's R4 fix, is that "nothing this repository hands a reader may name a path they cannot go and look at". The happy path is the one every user reads, and it hands them a path that was removed before the banner printed. No disclaimer accompanies it.
**Fix:** Keep the verbatim relay (it is the one-authority announcement) and add the same one-line disclaimer once after the relay loop, e.g. `report("resolution", "any path inside the relayed lines above is a temporary render mirror that no longer exists; the adapters were written to " + join(TARGET, ".claude", "agents"))`. Do not rewrite the generator's line (that would be a second grammar).

## Info

### IN-01: `transformAdapter` is not idempotent on its own output for the banner slot

**File:** `install/install.ts:1755-1795`
**Issue:** The kit slot keeps its anchor (`MAT_SLOT`) and re-injects above it, so `T(T(x)) = T(x)`. The banner slot *consumes* its anchor (`KIT_BANNER` is replaced, `:1781`), and the injected `BAN_OPEN…BAN_CLOSE` block is stripped on re-entry, so a materialized file fed back through the transform yields zero banners. Unreachable today (agent sources are always fresh renders; the skill source is kit text; `--migrate` runs pre-steps then the ordinary install), so no behavioural defect — but D-14's "a second slot handled like `KIT=`, strip-then-inject, content-idempotent" overstates the symmetry.
**Fix:** State the asymmetry and its reachability bound in the comment above the state machine, or make the banner slot anchor-preserving.

### IN-03: The doctor reports an unreadable or directory-shaped target adapter as "absent"

### IN-04: `--check --strict` behaviour change is not in the CHANGELOG entry
