<objective>
Make the shipped kit name a command that exists.

The capability announcement authored into the packaging template, and copied byte-for-byte into the
generated coordinator adapter, tells a reader that the reduced tier is what one particular command
gets. That command does not exist in either install form. The standalone skills are named such that
the real command is the full brand name, and the plugin form namespaces it with a colon. The same
phase's two user-facing documents — the install readme's entry-tier section and the packaging
adapters document — both name it correctly, and the summary that shipped them claimed one vocabulary
across two surfaces while pinning only the three tier labels. The labels matched. The command name
was never compared, so the contradiction shipped inside a capability and safety announcement, which
is the worst place for it: a reader told what a given tier gets cannot map that onto anything they
can type.

The voice guard cannot see the difference either, because its phrase neutralization rewrites the
command token to a marker-free filler before it looks at anything.

The fix is three source edits and a regeneration, plus one mechanical pin so the four surfaces can
never diverge again on the command name the way they just did on it while agreeing on the labels.

The byte budget is tight enough to state up front rather than discover: the coordinator role file
sits at 7087 bytes against a 7165-byte warn tier, and the coordinator adapter sits at 3055 bytes
against a 3072-byte warn tier. The correction adds three bytes per occurrence, one occurrence in the
role file and two reaching the adapter — its description and its body — so the expected results are
7090 and 3061. Both fit. Neither ceiling is touched.

Purpose: the kit's own capability announcement should be actionable.
Output: three corrected sources, seventeen regenerated adapters, and a beat that compares the command
name the way the tier labels are already compared.
</objective>
