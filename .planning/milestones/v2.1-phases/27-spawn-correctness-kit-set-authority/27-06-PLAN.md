<objective>
Prepare the two inputs the adapter generator consumes: a `capabilities:` key on every role, and the
packaging template that defines what a generated adapter body looks like.

Per D-11 each adapter's tool grant derives from a neutral `capabilities:` key added to role
frontmatter, which the generator maps to platform tool names. The alternative — a per-role map living
inside the generator — is precisely the drift class this phase exists to delete, and putting
platform-specific tool names into role text would be a portability smell, because role files serve all
five host CLIs. Per D-12 each adapter's description derives from the role's existing one-job and
activates-when sections, both of which already exist in all 17 roles and are already phrased as routing
triggers, so there is zero new authoring and zero drift: editing the role updates the adapter.

Two mechanical constraints shape the key's syntax. The zero-dependency frontmatter parser reads only
inline scalars, so a YAML list would parse as an empty value, the generator would emit an empty tool
list, and the platform refuses to launch a subagent whose tools resolve to nothing — a loud failure, but
loud at runtime on a user's machine, which is the worst possible place for it. The value is therefore a
space-separated inline scalar, and the generator validates it against a closed vocabulary at build time
in plan `27-07`. Separately, every tool the vocabulary maps to must survive the background-subagent tool
filter, or the mapping silently produces a role that loses the tool at runtime.

The template is the other half. It is already the copy-ready source carrying the correct memory wording
that the live adapter lost, so the generator must be built from it rather than from the drifted live
file. This plan brings it up to the shape the generator will emit: the specialist body per D-08, and a
coordinator body carrying the three-tier announcement.

That announcement is the phase's honesty deliverable. The original premise — that the brand's headline
skill entry structurally could not spawn — was disproven: the field it was blamed on is a per-turn
permission pre-approval, not a capability restriction, so that entry has always had the spawn tool and
could always spawn, unscoped. The real gap on that path is not capability, it is allowlist enforcement.
So the coordinator announces which of three tiers it is in, chosen by capability-sensing, and never
claims an enforced allowlist it does not have (D-03).

Purpose: the generator can only be as correct as the template and the frontmatter it reads.
Output: 17 role files carrying a validated capability declaration, and a template defining both body
shapes and the mapping table.
</objective>
