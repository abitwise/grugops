§ 3 — THE BOUNDARY, ADJACENCY, EMPTY-INPUT AND ORDERING PROBES, NOW CASES
════════════════════════════════════════════════════════════════════════════════════════════════

  BOUNDARY   `carrierVerdict(n)` is the instrument, and the live tree is judged through it rather
             than by a bare equality. `CARRIER_BOUNDARY_ROWS` drives three real inputs:
               0 carriers  (the eight exempt files alone)   -> "vanished-authority"    RED
               1 carrier   (board-model.ts alone)           -> "exactly-one-authority" the live tree
               2 carriers  (board-model.ts + the control)   -> "second-authority"      RED
             and the case asserts explicitly that neither neighbour reads as one authority — zero
             is a census whose subject vanished, not a satisfied upper bound.

  ADJACENCY  Two readers identical except `^column:` vs `^column[:]` (two spellings `skeleton`
             normalizes to one) -> 3 carriers, listed by name. A duplicate cannot hide behind a
             sibling.

  EMPTY      A zero-file scanned set -> 0 carriers, verdict "vanished-authority". A one-file
             scanned set is asked the same question and answers "exactly-one-authority". The
             pre-existing non-vacuity premise case (glob non-empty, floored against `git ls-files`)
             is unchanged.

  ORDERING   BEFORE: the carrier list came out in the order the scanned set arrived in —
               sorted input   [board-model.ts, dup-1.ts, dup-2.ts]
               shuffled input [dup-2.ts, board-model.ts, dup-1.ts]      identical: false
             AFTER: `censusOver` sorts its rows by name before anything else, so the two runs over
             the same planted tree return the same LIST. The case runs the census forwards and
             reversed and compares, asserts the list equals its own sort, asserts the list has more
             than one member (an ordering probe over one element proves nothing), and asserts
             `SCANNED` is sorted.

  PRECISION  Unchanged and re-stated: every number here is `Array.prototype.length` over an array,
             compared with `toBe` against a small integer. No arithmetic, no rounding, no tie-break
             and no floating-point step occurs in either derivation. (Backstop marker.)

§ 6 — EVERY TARGET GETS ITS OWN REACHABILITY ROW (WR-05 / F-07)
════════════════════════════════════════════════════════════════════════════════════════════════

`classifyCheckScript` (first match via `.exec`) is replaced by `classifyCheckScriptTargets`, which
returns EVERY gate-module target and EVERY suite target a command carries, each row naming the
script it came from. The `null` posture for a command with no target and no recorded toolchain
reason is kept verbatim — an unclassifiable script is a red that names it, never a skip.

  synthetic command                                       before (first match)        after
  ------------------------------------------------------  --------------------------  ------------
  node scripts/a.js && node scripts/b.js                  gate -> a.js  (b.js unnamed) two gate rows
  node scripts/a.js && vitest run scripts/x.test.ts       gate -> a.js  (suite lost)   one of each
  vitest run x.test.ts && vitest run y.test.ts            suite -> x    (y unnamed)    two suite rows
  (cd . && node scripts/a.js)                             gate -> a.js                 gate -> a.js
  bash tools/does-whatever.sh --quietly                   null                         null

  Case: "DISCRIMINATION: five synthetic commands, each with the row set it must produce".

PINNED NUMBERS ARE TARGET COUNTS.

  CHECK_SCRIPT_CLASSES  gate-module 9 targets | suite-test-file 1 target | toolchain 1 target
  sum of pinned target counts                     11
  targets the live manifest carries               11    (asserted equal)
  scripts every one of which contributes a row    11    (asserted, so the sum hides no drop-out)

  The three per-class reachability proofs now iterate over ROWS, not over scripts, so a command
  running two gate modules is asked the ci.yml question twice — once about each. Each case pins its
  own row count against the class's pinned target count, so a class emptying out is a red rather
  than a loop that runs zero times.

THE DASH-06 CONTROL KEEPS ITS OWN ROW. `check:dashboard-readonly` produces exactly one
suite-test-file row, the row names the script it came from, and the LIVE per-target derivation is
re-queried for it — a control that dissolved into a list somebody iterates would be the round-1 skip
in a new shape. `npm run check:dashboard-readonly` exit 0.

THE DISJOINTNESS CASE WAS REPAIRED, NOT DELETED. It used to assert the three class shapes were
disjoint over the live script set, and its premise was first-match: a script matching two shapes
would lose one half to arm order. A script may now legitimately contribute to two classes, so the
case asserts the stronger property the fix bought — every shape a command matches is REPRESENTED in
its classification — and a command matching no shape at all must be the recorded toolchain decision
and nothing else.
