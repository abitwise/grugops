§ 3 — WHICH HALF OF THE PAIR LET EACH PLANT THROUGH

The pair is "names BOTH keys" AND "reaches a text-scanning primitive". 32-21 widened the primitive
half to a named five-member table and left the key half a syntactic-position rule. The two gaps are
different findings, and each plant is recorded against the half it defeats.

  plant  key half                                     primitive half
  -----  -------------------------------------------  --------------------------------------------
  A      FAILS  named: []                             FAILS  reached: []          (.matchAll absent)
  B      FAILS  named: []                             PASSES reached: [exec]
  C      PASSES named: [column, status]               FAILS  reached: []          (.replace absent)
  D      FAILS  named: []                             PASSES reached: [split, indexOf]
  CTRL   PASSES named: [column, status]               PASSES reached: [match]

  KEY-HALF GAP (A, B, D). `keyInText` requires the key to be preceded by a start-of-string, a `^`
  or a newline. In `/^(column|status):\s*(.+)$/gm` the keys are preceded by `(` and by `|`, so the
  pattern names NEITHER key. Plant B is the sharp one: it uses `.exec`, a primitive the table
  already enumerates, so it defeats the half round 2 WIDENED rather than the half it did not.
  Plant D's keys are assembled by `["c","o","l","u","m","n"].join("")`, which `staticText` cannot
  resolve at all — the exact spelling `.planning/WINDOWS.md` ledger row 184 records as a stated
  blind spot.

  PRIMITIVE-HALF GAP (A, C). `TEXT_SCAN_PRIMITIVES` at HEAD enumerates exactly five spellings:
  .match, .exec, .split, .indexOf, new RegExp. `.matchAll` and `.replace` are not in it, and
  neither is any other member of String.prototype or RegExp.prototype. The complement of the
  enumeration was never bounded, so a text-scanning call nobody listed passes by not being listed.

  ADJACENCY.     Two planted readers whose static texts are identical except for the key spelling
                 (`/^column:/` vs `/^column[:]/`, which `skeleton` normalizes to the same text)
                 -> carriers 3 (delta 2). They are counted as two, not merged into one. This is
                 the current behaviour and it is correct; it has no case pinning it.

  ORDERING.      The carrier list's order follows the ORDER OF THE SCANNED SET, not a sort of the
                 carriers themselves:
                   run 1, sorted input:    [board-model.ts, dup-1.ts, dup-2.ts]
                   run 2, shuffled input:  [dup-2.ts, board-model.ts, dup-1.ts]
                   identical across runs:  false
                 On the live tree the order IS deterministic, because `SCANNED` ends in `.sort()`
                 (verified: SCANNED is sorted -> true). The determinism therefore rests entirely on
                 that one `.sort()` and nothing asserts it. A reader comparing two runs is
                 comparing traversal order unless the sort holds.

  PRECISION.     Every number in this census is `Array.prototype.length` over an array of findings
                 or of [name, findings] pairs, compared with `toBe` against a small integer
                 literal. No arithmetic, no rounding, no tie-break and no floating-point step
                 occurs anywhere in the derivation. (Backstop marker, per must_haves.)
