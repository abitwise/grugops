<objective>
Close the three findings that decide WHICH ticket documents the grammar refuses, and the one
document an agent copies from that the grammar refuses by construction.

Gap mapping for this plan (from `32-REVIEW.md`):

| Finding | What is wrong | Task |
|---------|---------------|------|
| WR-03 | `readVerifyReread` keeps a leading byte-order mark on purpose (`ignoreBOM: true`, load-bearing for the byte-agreement tear detector), so `parseTicketDocument` compares `lines[0] !== "---"` against a line that still carries it and refuses a Windows checkout with a message quoting a line that renders as `---`. Since plan 32-12 this is a hard error in the structure validator. | Task 1 |
| WR-04 | `TICKET_CONTROL` includes `\x09`, and the control check runs before `TICKET_KEY_LINE`, so a tab is refused as a control character with a reason that is false of a tab — while the comment beside the pattern says a tab is caught by the key pattern, describing a program the file does not contain. | Task 2 |
| WR-11 | The builder specification's ticket template is a fence of six bare key lines with no `---` region. An agent following it produces a document `parseTicketDocument` refuses, which is now a validator error. The contract records the `## Blocked (2)` disagreement for the heading grammar and records nothing for this one. | Task 3 |

Purpose: a refusal is the projector's most expensive output — it is a hard error in the validator, it
removes an identifier from the record set, and (after plan 32-15) it surfaces as a conflict on the
screen. A refusal that is right for the wrong reason, or right about a document a kit document told
an agent to write, spends that cost on nothing.

Output: one normalization authority instead of two spellings, a tab refused by the rule that claims
it, and the two documents that disagree named where a reader looks.

This plan runs after 32-15 because 32-15 changes what a refusal COSTS, and both plans edit
`scripts/board-model.ts` — a real `files_modified` overlap, not build serialization.

There is no `SPEC.md` for this phase, so there is no `## Edge Coverage` and no `## Prohibitions`
section to satisfy.
