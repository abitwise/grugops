## Decisions Made

- **`tieredCorpusRefusals` is a named export the live-corpus consumers ask, and `resolveModels` does
  not call it.** The corpus relationship is a question about a whole corpus; the resolver runs over
  subsets. This is the same split plan 29.1-01 established for `roleCorpusCardinalityRefusal`, and
  the header records the argument in both places so a later author finds it rather than rediscovers
  it.
- **`resolveModels` builds the tiered map and collects the stems it could not assign in ONE loop.**
  A pre-pass that computed the unassigned set and a second loop that built the map would be two
  authorities for one predicate, and the in-loop `undefined` branch would be unreachable dead code
  that a later reader would either delete or trust.
- **An override for a stem outside the current resolution is skipped, not refused.** A caller
  resolving a six-role mirror legitimately holds overrides for roles outside it. "Is this key a real
  role" is `readModelsConfig`'s question, asked against the derived corpus, which is where the
  user's typo actually is — one authority, asked at the point of the mistake.
- **The vacuity sentence is declared once (`TIERED_VACUITY_REFUSAL`) and returned by both table
  predicates.** An empty table and a short table must not share a sentence; an empty table and an
  empty table must not have two.

### Deliberate departures from the plan's literal wording

**3. `resolveModels` does NOT run the both-direction corpus comparison — honouring coverage item D5**

The plan's Task 2 action says to run, inside `resolveModels`, "a table whose length differs from the
derived stem count", "a table stem with no corresponding role stem" and "a role stem with no table
entry". Implemented literally on that path, all three refuse a legitimate hermetic-mirror run: the

coverage item **D5** (`human_judgment: true`) and which this plan was instructed to honour.

Resolution — nothing was dropped, the predicates were placed where each is decidable:

| Predicate | Where it lives | Correct on a mirror? |
|---|---|---|
| Vacuous table | `tieredTableRefusals` (and `tieredCorpusRefusals`) — run by `resolveModels` | yes |
| Duplicated stem | `tieredTableRefusals` — run by `resolveModels` | yes |
| Blank rationale | `tieredTableRefusals` — run by `resolveModels` | yes |
| **Every handed stem has an entry** | `resolveModels` itself | **yes — and it NAMES the stem** |
| Two-sided count against the corpus | `tieredCorpusRefusals` (named export) | n/a — corpus question |
| Both-direction set equality | `tieredCorpusRefusals` (named export) | n/a — corpus question |

The plan's own `key_links` anticipate this: *"`MODEL_TIERS_COUNT` sits beside `TIERED`, but its
exact cardinality is adjudicated in `guard_model_assignment` (plan 29.1-04) … the library throws
only on the vacuous set."* Every acceptance criterion (a)–(e) was still observed RED with the
required number of separate findings, because the oracle asks `tieredCorpusRefusals` over the live
derived corpus. **No live-tree `ROLE_COUNT` floor was reintroduced inside `resolveModels`.**

**4. `readModelsConfig` takes the derived stems as a second argument**

The plan's action writes it as `readModelsConfig(repoRoot)`. Validating a `roles` key against the
derived stem set — D-06 and the ASVS V12 control — requires that set, and this module deliberately
does not import `listRoles` (plan 29.1-01 deviation 2: it performs no corpus derivation of its own,
and `noUnusedLocals` would refuse an unused import). The stems are therefore passed in, exactly as
`resolveModels` takes them, so the caller's derivation stays the one place the role set is decided.
