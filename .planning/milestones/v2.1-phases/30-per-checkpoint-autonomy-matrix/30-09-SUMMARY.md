- **`dropped` is a real status with a stricter bar.** The registry parser admits it and still refuses an unknown status by name, quoting all four legal values. A dropped row is exempt from the `disposition` / `finding_id` obligations — because its text is mechanically replaced rather than left standing — and reaching it requires a lowered floor in the live configuration plus agreement in both directions.

## Decisions Made

See `key-decisions` in the frontmatter. Two are worth restating in prose because they were reached against a red gate rather than in the abstract:

**The [B1] heading-recogniser pin was not moved.** The first draft of `declaredDroppedRows` declared and applied `/^### (C-28-\d{3})$/`, and `check-foundation-guards.test.ts` reported it within the same run: the tree pins its declaration-lines that apply a heading recogniser at exactly one site, in `audit-model.ts`. Moving that pin was available and would have been defensible. Instead the pass was rewritten to the literal-prefix idiom its own sibling `declaredSafetyRows` already uses, so the tree still owns one heading recogniser rather than two. The resulting looseness is stated at the site: a prefix test admits `### C-28-banana` where the canonical form would refuse it, which over-attributes rather than under-attributes, so the two sets disagree by membership and the render refuses. The failure direction it cannot have is the one where a dropped row goes unseen.

**The gate does not re-split a document the authority already assembled.** The deletion predicate needs the first line the block expects and the first line the document carries. Computing them in `check-claim-anchors.ts` was a second line assembly beside `scanAnchoredDocument`'s — the coordinate-shear axis that shape exists to delete — and the tree's own guard caught it. Both values are now published by `anchoredBlockAt` from the same `want`/`slice` derivation that already produces the extent and the byte verdict.
