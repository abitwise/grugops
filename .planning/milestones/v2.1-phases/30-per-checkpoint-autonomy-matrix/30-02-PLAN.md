<objective>
Settle the floor set. Retire the `autonomy` floor id from `SAFETY_FLOORS`, name the checkpoints that
inherit the claims it backed, and remap every registry row that pointed at it — all in one commit,
because `audit-model.ts` enforces that every `depends_on` value is a `SAFETY_FLOORS` member and the
two surfaces cannot disagree for even one commit.

Purpose: the floor ids are consumed by config keys, env var names, registry `depends_on`, the render
and the banner. Everything downstream in this phase reads them, so they are settled here, second,
right after the architecture is proven.

Output: a four-member `SAFETY_FLOORS`, a registry whose `depends_on` values all resolve, and a
`readRegistry()` that refuses duplicate ids.
</objective>

  <decision>
Which four ids constitute `SAFETY_FLOORS` after `autonomy` is retired, and which checkpoints inherit
each of the five rows that named it.

Recommended (RESEARCH A3 + D-05 + D-06): `protected_branch_merge`,
`production_requires_human_confirmation`, `test_integrity`, `open_pr`. `commit_to_branch` exists as a
non-floor checkpoint. The five rows remap as: the four rows reading
`autonomy, production_requires_human_confirmation, protected_branch_merge` become
`open_pr, production_requires_human_confirmation, protected_branch_merge`; the single row reading
`autonomy` alone becomes `open_pr, protected_branch_merge`.

Why this is one-way: the Phase 28 floor to claims index and every remapped `depends_on` cell are
rewritten. Restoring the scalar later would mean re-deriving, row by row, which claims it backed —
the derivation that this plan consumes and then discards.

Alternatives: (a) drop `SAFETY_FLOORS` to three members and let the claims hang on
`protected_branch_merge` alone — cheaper, but it silently loses the "stop at a pull request"
guarantee that four of the six safety rows actually assert; (b) make `commit_to_branch` the fourth
floor instead of `open_pr` — but its documented default is `off`, so a floor that is off by default
would be a floor in name only.

Also confirm the `test_integrity` value mapping: its legacy config enum is `warn` or `block` with
`off` excluded per the TINT-03 carve-out. Recommended mapping into the ternary is `warn` becomes
`notify` and `block` stays `block`, with `off` refused for this one id by the validator as a
documented per-id restriction rather than a fourth disposition value.
  </decision>
