<objective>
Close WR-21 of `31-REVIEW.md` — the residue the round-3 review left when it closed WR-15, and which the
round-4 verification independently reproduced and singled out beside the two blockers.

`31-15` gave `trustedRepoRoot()` a documented four-step resolution order so the target repository's
governance dial is read on all five hosts rather than on one. That fix is real and re-verified. But the
upward search it added stops only at a configuration, at an ancestor carrying `.git`, at the filesystem
root, or after a bounded number of ancestors. **None of those is the user's home directory** — while the
function's own docstring says the walk "never continues past" a boundary so a resolution "can never
reach a user's home directory", and `agent-factory/workflows/16-context-read-write.md` repeats the claim
to every reader of the protocol. Both sentences are non-sequiturs: the marker stop fires only if some
ancestor happens to carry `.git`.

The verification reproduced the consequence directly. With both project-directory variables unset and a
working directory three levels below a planted ancestor carrying `.grugops/factory.config.json`, with no
`.git` anywhere on the path, `trustedRepoRoot()` returned the planted ancestor and read its dial. Under
the shipped shared-install model the kit lives at `~/.grugops` — so a home-directory-shaped ancestor
carrying exactly that path is the shape the installer creates, not a contrived one. And because
`trustedRepoRoot()` is the answer every consumer asks, the blast radius is not only a wrong dial: the
audit ledger writer lands in that directory too, so one project's admission records — note id, author,
stamp, severity, disposer — can be written into another's committed audit trail.

The review also names the same rule running the other way: a factory configuration sitting BELOW a
repository root wins over the repository's own for any process whose working directory is under it. The
residual register names the outer-repository case and not this inner one.

Purpose: `31-15`'s own plan carried the prohibition "the resolution order must never resolve to a root
ABOVE the repository boundary ... and never reaches a user's home directory" as a flagged, unverified
statement. Round 4 verified it and found it false. This plan makes it true.

Output: a walk that halts at the user's home directory and never inspects it or above; a boundary set
that does not depend on one VCS being present; a frozen exported stop set the workflow prose is quoted
from under an asserted equality; the inner-configuration case decided or named; a monotonicity proof and
a re-measurement of WR-15's own closure; and a dated decision recorded beside D-19 and D-22.

**Ordering note:** wave 4 and `depends_on: ["31-18"]`. This plan and `31-18` both modify
`scripts/context-io.ts`, `scripts/context-io.js`, `scripts/context-io.test.ts`, `hooks/hook-entry.ts`,
`hooks/hook-entry.js` and `.planning/phases/31-autonomous-manual-testing/31-CONTEXT.md`. Sequencing
removes the conflict and lets this plan's monotonicity control run against a tree where the promotion
route's own constraints already exist, so a change in resolution cannot be confused with a change in
what the route decides.
</objective>
