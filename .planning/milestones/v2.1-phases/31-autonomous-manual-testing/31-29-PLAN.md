<objective>
Close **CR-19** and **CR-20** of `31-REVIEW.md`, both independently reproduced by
`31-VERIFICATION.md` round 6 against the committed `scripts/context-io.js`, plus **WR-27**, **WR-28**,
**IN-14** and residuals **R-31-21-02**, **R-31-21-04** and **R-31-22-02**.

Two defects, one shape. Round 5's `31-21` gave this module one non-blocking regular-file reader with a
size ceiling and inverted the note-then-ledger write order in both derived routes. Both closures are
real and are re-measured here as controls. What each of them cost is a coordinate the fix did not
reach.

The ceiling was wired into the reader and into nothing else. Measured: `appendNote` with a 9 MiB body
returns WROTE with an id, cleanly, and the very next `readContext` for that task returns ZERO notes.
The note is not corrupt, not refused, not logged — it is invisible, to every reader, permanently, on
the only memory this project has between agents. And the idempotent re-write of the identical bytes is
then refused with a clause asserting the file is not a regular file, which is false of a 9,437,353-byte
regular file. A bound enforced only where things are READ lets the writer create objects the reader is
required to reject; a refusal that misnames its condition is a claim about the mechanism that the
mechanism does not support.

The write order was inverted correctly and the two writes were left aimed at two different
repositories. The note goes to the caller's `to`; the GOV-02 event goes to `repoRoot`, which defaults
to the process's own root. Measured with three real governance roots: the finding lands in one
repository's note store and its audit record lands in another's ledger. `18-context-compaction.md`
line 83 — rewritten in the same round to assert that a re-binding first looks in the destination
repository's ledger and that the destination never holds a human-disposed finding with no ledger line
— is false of the mechanism at exactly the sentence that exists to state it.

So this plan installs two properties rather than two patches. **A bound is owned by the side that
admits**, with one exported constant read by both sides and an over-ceiling regular file carrying its
own honest clause. **Two halves of one action are keyed on one variable**, with the destination
repository DERIVED from the store path through the anchoring resolver that already exists, so a
promotion whose destination is not a governed store is a named decline before anything is written
rather than a split record afterwards.

Around them go the three findings that are the same class one register down: the derived read-site axis
that only ever looked at top-level functions (WR-27) — the axis that exists to prevent set-literal
drift, itself drifting; the forged-origin price stated as three where it measures two (WR-28); and one
`catch` covering three different facts with one silence (IN-14). And the four `R-31-21-*` residuals get
an exported register with the same two-sided binding the other three registers have, because round 5's
own closing measurement recorded that they are bound by nothing a test can read.

Purpose: make it impossible for this module to write something no reader can return, and impossible for
one action's two halves to name two repositories.

Output: an exported note ceiling enforced at the write side with its own clause; the same reconciliation
at the ledger; one derived destination-root binding with a `destination-outside-governed-store` decline;
a three-armed, counted and reported skip in `readRawNotes`; an exported `WRITE_PATH_RESIDUALS` with a
two-sided binding; a recursive, scope-attributing read-site derivation with three seeded mirrors; two
corrected workflow sentences; and decision **D-31** appended to `31-CONTEXT.md`.

**Ordering note:** wave 3, `depends_on: ["31-28"]`. Sequenced rather than parallel for two genuine
reasons: every fix plan of this round appends its own dated decision to `31-CONTEXT.md`, and this plan
and `31-27` both edit `scripts/context-io.ts` — a real `files_modified` overlap, not an incidental one.
This plan runs after `31-27` because `31-27` changes the module's root resolution, and the destination
binding this plan derives must be measured against the resolution order that will actually ship.

<assumption_delta_decision>
**Decision: `promote`.** The assumption-delta scan surfaces the identity question this plan exists to
settle: `promoteAdmitted` names two repositories — the caller's `to` and the process's `repoRoot` —
where one action has one owner. This plan PROMOTES the destination root, derived from `to`, to the
single primary noun: the note write and the GOV-02 ledger event both key on it, and `repoRoot` stops
being the ledger's key. `repoRoot` is not kept alongside as an alternative owner, because keeping two
nouns for one owner is precisely what CR-20 exploited. Where `repoRoot` remains a parameter for other
purposes, a case asserts it can no longer decide where an audit record lands.
</assumption_delta_decision>
