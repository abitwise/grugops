### Findings and fixes

- **B1 (DC-1): a garbled value that is still a string counted as "provably another" entry.** An extra `protection_rules` entry typed `""`, `"Required_Reviewers"` or `"REQUIRED_REVIEWERS_"` read as another rule, so the reviewer rows stayed held. An extra environment named `"Production"`, `""` or `"production​"` beside `production` read as another environment, so the target stayed protected with exit 0.
  - Each list now has one partition authority.
  - `reviewerRules()` classifies every entry through the new `ACCEPT.reviewerRuleType`:
    - held: the entry is a `required_reviewers` rule.
    - failed: the entry is provably another rule. Only a documented other type shows this: `wait_timer` or `branch_policy`, the environment protection rule types of GitHub's REST description, recorded in 33.1-RESEARCH.md.
    - unknown: anything else. The entry may be a second required_reviewers rule.
  - `environmentPartition()` puts every environments entry in one of three groups: an exact match; provably another environment; or possibly another environment of the configured name.
  - The new `provablyAnotherName()` decides "provably another". It accepts a name only when all of these hold:
    - The name is a non-empty string.
    - After NFKC normalisation, it has no whitespace at either end and no whitespace other than a plain space.
    - It has no control, format, private-use, unassigned or default-ignorable (invisible) character.
    - It does not equal the configured name apart from case. GitHub documents environment names as not case sensitive.
- **B2 (DC-1): first-page-only evidence.**
  - One authority, `linkNamesNextPage()`, is asked of every `Link` header line. It reads the token `next` outside the `<URI>` parts, quoted or unquoted, in any case, alone or among several relation types. It serves all three list endpoints. The old parser missed the unquoted `rel=next` of case q01.
  - Rule list: when the list names a further page, no ruleset's source agreement is shown (`RulesetArm.morePages`), so no ruleset binds. A classic record can still show the rows, so the union rule is kept.
  - Environments list: every environment row reads UNKNOWN - verify when either of these holds:
    - The list names a further page.
    - `total_count` is present, and it is not a whole number (read through the new `ACCEPT.environmentTotalCount`) or it does not equal the length of the list read.
  - An absent `total_count` stays neutral, and the code states why: the count restates the length of the list, so its absence removes a cross-check and asserts nothing.
  - The protected-branch list (`per_page=1`) behaves as before: a held element with a further page is still read.
- **B3 (DC-1): the main/master probe took any string name as a rename.**
  - A name counts as a rename only when it passes `usableBranch()` and `provablyAnotherName()` reads it as another name.
  - Anything else (for example `""`, `..`, `-x`, `a b`, a NUL, `Master`, or the name with an invisible character) goes into `unshownBranches`. The branch is then reported UNKNOWN - verify, quoting the answered name.

### Sibling search

The search read every `hostField(` use in host-protection.ts, and every comparison of a host-supplied name or type string.

Fixed:
- `usableBranch()` refused control characters and spaces but let invisible and format characters through. It is the one check every host branch name passes: the default branch's name, the protected-branch list's element (through ACCEPT.protectedBranchList), and the probe's rename. It now also refuses `\p{C}` and default-ignorable characters (`dff40fc0`). This only lowers a reading: a `--branch` holding such a character also reads UNKNOWN - verify.
- On the non-admin path, a branch answer with any other string name still taints the whole branch, as before. Only a usable, provably other name is now described as another branch. This is a text-only change (`b4d6cf88`).

Reviewed and left as they are, with the reason:
- Ruleset rule `type` (`rulesOfType`) is compared exactly to the documented floor types. A garbled type only stops that rule from showing its item, which gives failed or unknown and never held. The ruleset list makes no "exactly one" claim, and source agreement already asks every entry by id, whatever its type.
- Reviewer element `type` is compared exactly to the documented `User` or `Team`.
- Ruleset `enforcement`, `target` and `current_user_can_bypass` accept only documented values.
- `source` and `source_type` use exact equality: a garbled side disagrees and reads unknown.
- The protection endpoint's `message` is compared exactly.
- The protection url's decoded branch is compared exactly: any difference reads UNKNOWN - verify.

### Not fixed, with the reason

- `printable()` replaces C0 and C1 control characters but not format characters such as U+202E (right-to-left override). A host value holding one could visually reorder the audit line it is printed in. This is the IN-04 audit-line class, not DC-1: it never changes a verdict. It is recorded here for the reviewer and plan 33.1-25 rather than changed in this round.
- A consequence to state in README §5 (plan 33.1-25 owns it): an environment protection rule of a type GitHub does not document (for example a custom deployment protection rule, if the API lists one), next to the required_reviewers rule, now makes both reviewer rows UNKNOWN - verify.
