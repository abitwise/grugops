<objective>
Finish DC-3 for the installer as a class: route the uninstall and marker reads, then make the class rule
permanent. A static read axis is derived from node:fs itself, and a behavioural test covers every path any install
variant can write. This is gap-closure round 2 of the 4-round cap (D-06).

Sibling search (brief §2.3) for this plan's modules, over every content-reading fs API:
- install/uninstall.ts:
  - :339 removeSentinelBlock;
  - :415 the empty-file remover;
  - :448 unmergeGemini;
  - :569 removeAskRules;
  - :696 sameFileBytes, both arguments.
- install/install-marker.ts:
  - :83 readInstallMarker (IN-04).
- uninstall.ts has no copy-family call.
Plan 33.1-26 did install.ts. The census axis here makes a missed site, or a new one, fail.

Why derive the API set from node:fs. The first draft of this axis listed readFileSync, openSync, readSync and
createReadStream, and so could not see the two copyFileSync sites whose source is a user path; plan 33.1-26
fixed those. A hand list of APIs is the set-literal drift this repository has paid for before. So the test
takes node:fs's own export list, and every export that could read content must be classified.

Why derive the path set from several installs. One default install into an empty target does not write every
path install can write. `--symlink` writes links, `--migrate` writes the seeded config from a legacy file and
timestamped backups, and the checkpoint configuration decides whether `.claude/settings.json` is written. The
union over those variants is the path set, and one shared test-support module owns the derivation, so the DC-2
and DC-3 tests (plans 33.1-33, 33.1-34, this one) cannot drift apart.

Purpose: no install, uninstall, `--migrate` or `--check` run can hang on a special file at any path the
installer uses, and a new unguarded read cannot land.
Output: the routed uninstall and marker reads, the derived read axis, the shared path derivation, and the
derived behavioural test.
</objective>
