<objective>
Make the kit write all-or-nothing on every path. D-32's reason, in the human's words, is that it "would be
risky if some kit files are updated and the ones that were edited are not". Plan 33.1-32 adds the edited-file
pre-flight and the prompt. This plan first removes a path that already produces a mixed-version kit without any
edited file. The skills loop writes, and then the adapters block can `return` early on a render or alias
refusal, leaving new skills beside old adapters. This is gap-closure round 2 of the 4-round cap (D-06).

The fix is a two-phase kit write. Phase one builds the complete plan, with every destination, the exact bytes
or link target, and every refusal check including the adapter render. Phase two writes, only if phase one
refused nothing. Plan 33.1-32's pre-flight then runs over the finished plan, so D-32's decision sees every
destination before any write.

Residual, stated rather than hidden: a filesystem error in phase two (for example a permission error on the
twelfth adapter) can still leave a partly written kit. A true transaction needs a staging directory and a
rename over existing files, which is the Windows EPERM class D-15 keeps out of 33.1. The write phase reports
such an error by name as a `verify`, and the next run's pre-flight sees the recorded state.

Purpose: no refusal leaves a mixed-version kit.
Output: buildKitPlan, executeKitPlan, and the refusal cases.
</objective>
