## Critical Issues

### CR-01: The host check reads an absent `bypass_pull_request_allowances` as "no one can bypass" and answers `protected`

**File:** `scripts/runnable-ref/host-protection.ts:532-534` (pinned by `scripts/runnable-ref/host-protection.test.ts:874-883`)
**Issue:** D-30 (33.1-CONTEXT.md) fixes the rule: "anything unreadable, absent or oddly shaped is
`UNKNOWN - verify`". The module's own header says the same at lines 50-52: "a field that is missing
or of an unexpected type is never read as its safe default". `classicBinding()` breaks that rule
for the one field that decides the `no_bypass` qualifier on the classic arm:

```ts
const allowances = isObject(rpr) ? rpr.bypass_pull_request_allowances : undefined;
if (allowances === undefined) return { state: "binds", evidence: `${applies} and grants no pull request bypass allowance` };
```

A missing key becomes positive evidence that "classic protection ... grants no pull request bypass
allowance". The pull-request row, the approval row and then the `does not let administrators or the
account the agent works under bypass it` row all become `held`, so the branch reads `protected`
(exit 0). The test at line 874 asserts exactly this outcome. The header comment at lines 70-72 and
33.1-19-PLAN.md both describe "absent" as binding. The plan chose this knowingly, but it
contradicts the human decision it implements. The CHANGELOG entry this round adds says "A missing
or unreadable setting is reported as `UNKNOWN - verify`, never as protected", and for this field
that sentence is false.

For the pull-request and approval rows, the classic arm treats an absent
`required_pull_request_reviews` as `failed` (lines 386 and 406), which is fail-safe. The same
module then reads an absent sibling field inside that object as a pass.

**Fix:** Pick one of two options:
- Map an absent key to `unknown`, matching D-30:
  ```ts
  if (allowances === undefined) {
    return { state: "unknown", evidence: "classic protection carries no readable bypass_pull_request_allowances" };
  }
  ```
- If measurement shows that GitHub omits the key whenever no allowance is set, the human must
  record that as a D-30 amendment, cite the measurement in the header, and correct the CHANGELOG
  sentence. It must not stay an undocumented exception inside the canonical table.

Either way, flip the test at line 874 to assert the chosen outcome.

### CR-02: The environment row "allows deployments only from protected branches" is `held` even when the same run shows no protected branch

**File:** `scripts/runnable-ref/host-protection.ts:845-863`
**Issue:** The row is `held` whenever `deployment_branch_policy.protected_branches === true`. The
README text this round adds (`install/README.md` §5, production list) states the dependency:
"GitHub documents that 'Protected branches only' lets every branch deploy when no branch in the
repository has branch protection, so the last line depends on the branch list above". The check
never consults that dependency. The environment verdict is computed in isolation
(`environmentVerdict`, lines 871-908) and is `protected` even when every branch the same run
inspected is `unprotected`.

Reproduced with the committed `.js` and a stub fixture:
- `rules/branches/main` returns `[]`.
- `branches/main/protection` returns 404 `Branch not protected`.
- The environment has `protected_branches: true`.

The output was:

```
branch main: unprotected — ... the host reports no classic branch protection ...
environment production: protected — ... allows deployments only from protected branches (deployment_branch_policy.protected_branches is true) ...
```

Workflow 12 step 6 records "the production environment's verdict" alone, as the release's
evidence. That record states a floor line the host did not show, which is the "never answers
`protected` without positive evidence" rule this phase exists to enforce.

**Fix:** Make `branch_policy` `held` only when the host also shows that at least one branch has
classic protection. For example, read `GET repos/{owner}/{repo}/branches?protected=true&per_page=1`
once. A non-empty array means `held`, an empty array means `failed` (every branch can deploy), and
anything else means `unknown`. Add a fixture: `protected_branches: true` with no protected branch
must not yield `protected`.

### CR-03: Uninstall edits or deletes a user's `.gemini/settings.json` by substring presence, with no install record, and reports "removed" when it changed nothing

**File:** `install/uninstall.ts:439-507` (`unmergeGemini`, called at 865)
**Issue:** This predates the phase. It sits on the reversal path this round rebuilt around
ownership (CR-02, "never delete user content"), and it breaks that contract in three reproduced
ways. All three used the committed `uninstall.js` on a fresh `git init` target with **no install
and no marker**:

1. **A user config value is deleted.** The target held
   `{"context":{"fileName":"GEMINI.md"},"notes":"we also keep AGENTS.md"}`. The gate at line 453
   (`raw.includes("AGENTS.md")`) passes on the substring in `notes`. Line 493 turns the non-array
   `fileName` into `[]`, and line 496 deletes it. The file afterwards is `{"notes": ...}`: the
   user's `fileName: "GEMINI.md"` is gone, reported as `removed`, and the run exits 0.
2. **A whole user file is deleted.** A user-authored `{"context":{"fileName":["AGENTS.md","GEMINI.md"]}}`
   is exactly the shape CLAUDE.md recommends for Gemini. It matches `isGrugopsDefault` and is
   unlinked at line 489, although grugops never wrote it. The directory-ownership fix then reports
   the now-empty `.gemini/` as `left ... no record that install created it`. So the run keeps the
   user's empty directory but has already deleted the user's file inside it.
3. **A false report.** On unparseable JSON, lines 465-466 and 471-472 write
   `verify: ... left untouched` to stderr only, then report `removed ... AGENTS.md entry`. The
   `VERIFY_FINDINGS` counter is not incremented, so the banner says `== uninstall complete ==` with
   exit 0.

**Fix:** Apply the ask-rule ledger pattern. Install records in the marker what it did to
`.gemini/settings.json`: `createdFile`, and whether it appended `AGENTS.md` to `fileName`.
Uninstall then reverses only what the ledger records. The unparseable case should go through
`verify()`, not a `report("removed", …)`. Until a ledger exists, apply two minimum rules:
- Never delete the file. Remove only an exact `"AGENTS.md"` array element, and only when
  `fileName` is an array.
- Leave a string `fileName` untouched.

## Warnings

### WR-01: The reviewer row counts any non-empty `reviewers` array, whatever its elements are

**File:** `scripts/runnable-ref/host-protection.ts:810-813` (and `reviewerRule`, line 790)
**Issue:** `Array.isArray(r.reviewers) && r.reviewers.length > 0` is `held` for `[null]`, `[{}]` or
`["x"]`. That is a wrong-typed field read as positive evidence, which the D-30 mapping forbids.
Reproduced: `reviewers: [null]` produced `requires at least one reviewer (a required_reviewers rule
names 1 reviewer)` and an environment verdict of `protected`.
**Fix:** Count only elements of the documented shape, for example
`isObject(e) && (e.type === "User" || e.type === "Team") && isObject(e.reviewer)`. If any element
is not of that shape and none is, the row is `unknown`.

### WR-02: The `no_bypass` row claims "administrators" cannot bypass, but on the ruleset arm it only asks about the checked account

**File:** `scripts/runnable-ref/host-protection.ts:436-439, 452-480`; `install/README.md` §5 (the ruleset paragraph)
**Issue:** The requirement text is "does not let administrators or the account the agent works under
bypass it". The ruleset arm decides the row solely from `current_user_can_bypass` for the account
the check runs under, and never reads `bypass_actors` (by design, T-33.1-193). Suppose a ruleset
lists the Repository admin role as a bypass actor, and the check runs under a non-admin (write or
maintain) account. It reports `"never"`, the row is `held`, and the published record says
administrators cannot bypass it, which is false. The README's ruleset guidance tells the user to
keep "the account your agent works under (and any role or team it belongs to)" off the list. It
does not mention the admin role, although the checklist line itself names administrators. D-30
chose `current_user_can_bypass` as the mechanism, so this is an overclaim in the verdict text
rather than a deviation from the decision.
**Fix:** Either narrow the checklist line and evidence to what is measured ("does not let the
account the check runs under bypass it"), which needs a D-30 amendment since the line is bound
byte-for-byte to README §5, or read `bypass_actors` when the response includes them. When they
are present, treat any `RepositoryRole`/`OrganizationAdmin` actor as `failed`. When they are
withheld, the answer is `unknown` for the administrator half.

### WR-03: The floor accepts a stale approval, so `protected` holds while an agent can merge commits no human reviewed

**File:** `scripts/runnable-ref/host-protection.ts:376-440` (the `BRANCH_FLOOR` table); `install/README.md` §5 branch checklist
**Issue:** Neither arm reads the stale-approval settings:
- classic `required_pull_request_reviews.dismiss_stale_reviews` / `require_last_push_approval`;
- ruleset `pull_request.parameters.dismiss_stale_reviews_on_push` / `require_last_push_approval`.

On a multi-person repository the agent's account (A) opens a PR and a human (B) approves it. A then
pushes further commits and merges on the old approval. Every floor line is met, and the check says
`protected`. The phase's premise is "agents never merge a protected branch without named human
confirmation" backed by the host, and that premise does not hold for the pushed-after-approval
content. This is a floor-definition gap (D-30 is one-way and human-owned), not a code defect in
the table as specified.
**Fix:** Raise this with the human as a D-30 amendment: add "dismisses stale approvals when new
commits are pushed" and/or "requires approval of the most recent push" to README §5 and to
`BRANCH_FLOOR`. Read them with the same absent-is-`unknown` mapping.

### WR-04: The report never names the repository it inspected, and `{owner}/{repo}` may resolve to a different one

**File:** `scripts/runnable-ref/host-protection.ts:937-941, 960-1003`
**Issue:** Every path uses gh's `{owner}/{repo}` placeholder, which gh fills from `GH_REPO` or from
its own remote choice. According to gh's remote ordering, `upstream` ranks above `origin` unless
`gh repo set-default` was run. This was not reproduced live. The check fetches
`repos/{owner}/{repo}` but prints neither `full_name` nor any repository identity. The `--json`
`calls` array holds the literal placeholder. In a fork clone, or with a stray `GH_REPO`, the
recorded `protected` note can describe a different repository from the one the agent pushes to,
and nothing in the evidence shows it.
**Fix:** Read `full_name` from the repository response that is already fetched. Print it in the
summary line and in the JSON as `repository`. If it is not a string, make the whole run
`UNKNOWN - verify`. Optionally compare it with `git remote get-url origin` and report a mismatch.

### WR-05: Uninstall deletes a whitespace-only `.github/copilot-instructions.md` it never wrote, and labels it "grugops-created"

**File:** `install/uninstall.ts:410-429, 875-876`
**Issue:** `removeIfEmpty()` runs unconditionally after `removeSentinelBlock()`, even when that call
found no grugops block. Reproduced on a target with no install and no marker: a user's one-line
blank `copilot-instructions.md` was removed with `removed ... (file empty after block removal —
grugops-created)`. The label asserts provenance the run never checked. This is the same
ownership-by-presence class as CR-03.
**Fix:** Call `removeIfEmpty` only when this run actually removed a sentinel block from that file,
or better, when the marker records that install created it (as `createdFile` does for the ask
rules).

## Info

### IN-01: The "left" reason for a directory states "install did not create it" when the ledger cannot know that

**File:** `install/uninstall.ts:313-316`
**Issue:** A pre-ledger install that is re-installed gets `createdDirs: []` from `writeMarker()`,
because the directories already exist and the previous marker had no ledger to carry forward. Its
uninstall then says `.claude` "install did not create it", which is false. It is also inconsistent
that `tools` is written into `createdDirs` (confirmed in a scratch install), yet uninstall always
leaves it with "grugops owns tools/grugops/ only".
**Fix:** Say "there is no record that install created it". Also, either stop recording `tools` or
explain in the `tools/` line why the ledger entry is ignored.

### IN-02: The DRY_RUN uninstall preview names none of the directories the real run removes

**File:** `install/uninstall.ts:262-294`; `install/README.md` §"uninstall"
**Issue:** The preview names only directories that are already empty, and this is documented. In
the scratch run it named 0 directories, and the real run then removed 12
(`.claude/skills/grugops*`, `.claude/skills`, `.claude/agents`, `.gemini`, `tools/grugops`).
Nothing is lost, but the preview is not a plan of the destructive run.
**Fix:** Simulate emptiness. A directory would be empty if every entry it holds is in this run's
would-remove set. Name those directories in the preview.

### IN-03: The `createdDirs` carry-forward keys ownership by path, not by identity

**File:** `install/install.ts:2367-2376`
**Issue:** A previous entry is kept whenever that path is still a directory. If a user deletes a
grugops-created `.github/` and later creates their own, a re-install inherits the old "install
created it" record. The next uninstall then removes the user's directory if it is empty.
**Fix:** Acceptable as low impact (empty directories only). If tightened, record inode and device
alongside the path and drop entries that no longer match.

### IN-04: The marker reader blocks forever on a FIFO at `.grugops/install.json`

**File:** `install/install-marker.ts:75-90`
**Issue:** `lstatSync` succeeds on a FIFO, and `readFileSync` then blocks waiting for a writer.
Install, uninstall and `--check` would all hang. This shape was already found elsewhere in this
repository (P31 round 5). It predates the phase, because `readMarker` had the same shape, but the
new one-reader module is the place to fix it.
**Fix:** After `lstatSync`, return `unreadable` unless `isFile()` is true (or `isSymbolicLink()`
resolving to a regular file).

### IN-05: Header sentence fragment in the host check

**File:** `scripts/runnable-ref/host-protection.ts:17-19`
**Issue:** An inserted sentence ("The two tables are ... both ways).") splits the "One line per
inspected target ... and one summary line" sentence. Line 19 now starts mid-sentence with "and one
summary line".
**Fix:** Move the inserted sentence after line 19.
