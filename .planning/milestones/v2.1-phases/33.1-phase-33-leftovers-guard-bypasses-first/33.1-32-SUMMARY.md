# Phase 33.1 Plan 32: D-32 edited-kit consent Summary

**Re-install no longer overwrites a grugops kit file the user edited. A pre-flight over the kit plan finds every edited file by its `kitFiles` record. Install then backs up every edited file and writes the whole kit, or writes no kit file. Consent comes from a terminal `[y/N]` answer or from `--backup-edited-kit`, never from `--yes`.**

## Accomplishments

- `kitPreflight(plan)` runs once over buildKitPlan's finished entries and asks no second per-path question. The plan's own answer (`planned`, now stored on each entry) says which destinations the write would replace: a `write` over an existing regular file, or an `unlink` of install's own link. Only those are examined.
  - With a record, `checkRecord` decides (the one content-ownership read, which refuses hard links).
  - With no usable record (no marker, an unreadable marker, a malformed `kitFiles`, a legacy marker, or no entry), a file is unedited only when it is byte-identical to the kit source file (read through readUserFile), and a link only when it is install's own link.
- `kitWriteDecision` is the one KIT_WRITE gate. A hazard gives a verify and no prompt. Nothing edited: write. `--backup-edited-kit`: back up, then write. A terminal on stdin and stdout without `--yes`: the `[y/N]` prompt, default no. Otherwise: no kit write and a counted verify naming the files and the flag. Under DRY_RUN it prints `would-back-up <file> → <backup>` lines and asks nothing.
- `backupEditedKitFiles` writes `<file>.grugops-edited-<UTC stamp>` with `writeFileSync(..., { flag: "wx" })`, from the bytes the pre-flight read (a link is backed up as `symlinkSync(target, backup)`), all before the first kit write. On any failure: a verify, every completed backup kept and reported, and no kit file written.
- A `--migrate` over an old layout takes the decision in its pre-check. A refused consent is a migrate refusal, so nothing is migrated (plan 31's whole-or-nothing rule), and the prompt is asked once.
- writeMarker keeps the previous `kitVersion` when this run wrote no kit file (`--check` then shows `kit-version skew: marker=<old> kit VERSION=<new>`). An edited file keeps its `kitFiles` record (see Deviations).
- `readlineSync` waits out EAGAIN. Once `process.stdin` is touched, libuv makes a terminal's fd 0 non-blocking. Before this fix a read with no key pressed yet threw EAGAIN and was taken as an empty answer. The target prompt was also affected: it always took the default without waiting. The TTY check uses `isatty(0) && isatty(1)` (node:tty), so the D-32 prompt does not touch `process.stdin`.
- uninstall `reportKitBackups()` lists names only, in `.claude/agents/` and each `.claude/skills/grugops*/` (real directories inside the target). It reports each `*.grugops-edited-*` as `left (a backup install made of your edited kit file)` and never removes one. The directory holding a backup is kept.

## Decisions Made

See `key-decisions` in the frontmatter. The two with the most effect on users:
- **`--migrate` needs consent too.** The old layout's kit files have no record and differ from the kit source, so D-32's literal rule marks them possibly edited. The migration asks, or needs the flag. A refusal refuses the whole migration.
- **A backup-path problem is found before the prompt.** A taken path or one over PATH_MAX is a pre-flight hazard. A backup directory that cannot be written is not predicted, so it fails at the backup, before any kit write.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] readlineSync read EAGAIN as the end of input**
- **Found during:** Task 1, while probing script(1) before writing the pty tests.
- **Issue:** Once `process.stdin` is touched, a terminal's fd 0 is non-blocking, and `readSync(0)` throws EAGAIN before a key is pressed. readlineSync treated the throw as EOF and returned "". The existing target prompt was affected too: it always took the default.
- **Fix:** Wait 25 ms with Atomics.wait and retry on EAGAIN. The D-32 prompt uses `isatty` and does not touch `process.stdin`.
- **Verification:** the "interactive without --target" case, and mutation (g) is red.
- **Commit:** dac2e8f3 (the fix), 4b77bf32 (its test)

**2. [Rule 1 - Bug] The verify's remedy "restore them first" was false after a refusal**
- **Found during:** the scratch replay.
- **Issue:** A refused run dropped the edited file's `kitFiles` entry (plan 31's stale-entry rule). A file restored to what install wrote then had no record, still differed from the kit source, and was asked about again.
- **Fix:** KIT_EDITED_RECORDED. When no kit file is written, the record of a file the pre-flight found edited against a record is carried forward unchanged. Every other entry keeps plan 31's rule. `kitFiles` is now literally unchanged after a refusal (the plan's truth), and uninstall's reason for such a file reads "it has changed since install wrote it".
- **Verification:** the restore case and mutation (n).
- **Commit:** 4b77bf32

**3. [Rule 3 - Blocking] Existing tests that assumed a silent overwrite**
- **Found during:** Task 1 GREEN (19 failures in install/).
- **Issue:** D-32 changes behaviour that these tests relied on: the D-13 hand-edited adapter case, 30 `--migrate` invocations over the old-layout fixture, the KIT-02 stale single-adapter update, the B1 own-link re-installs, and the migrate variant of the derived write set.
- **Fix:** Each gives consent with `--backup-edited-kit`, with a comment citing D-32, and asserts the backup where it matters (D-13, KIT-02). The write-set counts were updated (see above). No assertion about migration behaviour was loosened.
- **Commit:** dac2e8f3

**4. [Scope] The prompt and the DRY_RUN listing landed in Task 1**
- kitWriteDecision is the one decision, so the prompt and the preview are part of it. Task 2's RED therefore failed only on the uninstall report. The prompt, DRY_RUN, legacy and hazard cases passed on the Task 1 build, and mutations (a), (b), (g) and (n) show that they detect regressions.

**5. [Precision] kitFiles after a no-consent run**
- The plan says "kitFiles unchanged", and plan 31 says "drops only entries proved stale". With deviation 2 both hold: edited entries are kept, and entries that are stale for any other reason (a hard link, a missing file) still follow plan 31's rule.

If that removal fails too, the verify names the file INCOMPLETE and says it is not a full copy. Uninstall reports a `.incomplete` name as "an incomplete copy … NOT a full copy of the edit", never as a backup. The pre-flight checks both names for being free and within the path limit. |
