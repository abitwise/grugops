# Phase 33.1 Plan 38: Uninstall walks the install ledger through owns Summary

**Uninstall now reverses what the install ledger records instead of what the uninstalling checkout ships. walkLedger visits every entry and each reversal asks install-marker.ts owns before any delete or edit. The kit-source passes only report unrecorded grugops-shaped paths. A census derives every delete/edit site on the uninstall path from the syntax tree and requires an owns reference before each one.**

## Performance

- **Duration:** about 62 min (2026-10-05T07:37:21Z to 08:39:42Z), plus two full regressions of about 18 min each
- **Tasks:** 3 of 3
- **Files modified:** 14 (one created)

## Accomplishments

- **The walk (`install/uninstall.ts`).** `walkLedger` runs only on an `ok` ledger. The kinds go in this order: ask-rules, gemini, block, file, backup, dir. A block takes its pointer file with it. Directories go deepest first, after every file. The reversals:
  - `reverseFile` asks `owns(LEDGER, TARGET, path, "file")` and hands the answer to the `removeFile` helper. `ownLink` comes from the entry's own `link:` record.
  - `removeSentinelBlock` and `removeOwnedEmptyFile` are reached through `reverseBlock`.
  - `unmergeGemini` and `removeAskRules` are reached through `reverseGemini` and `reverseAskRules`. Each gets its entry from `owns`.
  - `rmdirIfEmpty` is reached through `reverseDir`. Both ask `owns(..., "dir")`.
  - `reportBackup` only reports.

  `OUTCOMES` records `removed`, `gone`, `reversed`, `left` or `verify` for every entry.
- **Report-only passes.** These six call no removal helper:
  - `reportUnrecordedKitPaths`
  - `reportUnrecordedAgentsMd`
  - `reportUnrecordedRunnables`
  - `reportUnrecordedBlock`
  - `reportUnrecordedSettings`
  - `reportUnrecordedDir`

  An unreadable kit source now prints a `note`, not a `verify`. `ownsKitFile`, `ownsFile`, `ownsFileNow`, `ownsDir`, `ownsBlock`, `ownsMarker`, `GEMINI_LEDGER` and `ASK_LEDGER` are deleted. The header and the kit-set comment now describe the walk. The `isProtected` guard and the self-checkout guard are unchanged.
- **`install/install-marker.ts`.** `owns` takes the pseudo-kind `marker` (`MARKER_KIND`). It is valid only for `MARKER_REL` and owned exactly when the ledger read is `ok`. `Ownership<K>` now accepts `OwnsKind`. `removeMarker` and `updateKeptMarker` ask it.
- **The census (`install/installer-fs-census.test.ts`).**
  - `LEDGER_GATES` holds `owns` alone.
  - `CallerOwnership` has two classes, `ledger` and `helper-gated`. The `kit-record` and `source-identical` classes are deleted.
  - The caller rows were re-pinned from `helperCalls()`: 11 calls in 10 rows. No report-only pass has a row.
  - `removeFile` must take a required `owns: () => Ownership<"file">` and call it before `unlinkPath`.
  - A new case derives every delete/edit site on the uninstall path and requires an `owns` reference in its calling scope before each one. Its probe proves the check can tell a gated scope from an ungated one. Pinned: `DELETE_EDIT_SITE_COUNT = 11`.
  - `KNOWN_EXCEPTIONS` 12 and 13 stay.
- **IN-06.** `UNINSTALL_SOURCE_VARIANTS` has three variants: empty-source, unreadable-source, other-checkout-symlink. With `runUninstallWithSource` it drives the new `install/installer-cross-version.test.ts`, which has 7 tests. The recorded set comes from the installed marker's ledger and is checked by the test's own record check. `RECORDED_FILE_COUNT = 31`: 17 adapters, 7 skills, AGENTS.md, 4 runnables, and the 2 pointer files install created (CLAUDE.md, .github/copilot-instructions.md).
- **IN-05.** The `install/install.ts` row of `CONFIG_PATH_SITES` now says the installer reads `checkpoints.protected_branch_merge` and `checkpoints.production_requires_human_confirmation` through its restated canonicalizer to decide the ask rules (D-18). install.test.ts proves that canonicalizer equal to `canonicalizeDisposition`.
- **Docs.** README "Undo" now says the record decides, not the kit source, and that a `--symlink` install is reversed by its link record. The symbolic-link paragraph and the "In short" list are updated. The CHANGELOG [Unreleased] "Fixed" section has a WR-01 entry.
- **Replay.** New case `wr-01-cross-source`: the uninstalling kit source lacks `grugops-agents-md-scribe.md`. The adapter is removed on its record and named, every recorded file is gone or named, and uninstall exits 0.

## Decisions Made

- **The verify/left rule for a link at a recorded path.** The plan says to take ownLink from the entry's `link:` record and never from the kit source. Under that rule, a link at a path recorded as a regular file, or a `link:` path that was re-pointed, is a link install did not make. It is left, never followed, and counted as a verify, by the existing B1/B2 rule.

  Before, whether it was `left` or `verify` depended on whether the link pointed into the uninstalling checkout. Two tests pinned that source-dependent answer and were updated:
  - uninstall-removal "the own-shape link ... is left and counted"
  - install.test.ts "a link re-pointed to another checkout's copy ... is left and counted"

  Nothing is removed in either case.
- **The report-only kit pass also lists the target's names.** It covers `.claude/agents/grugops*.md` and `.claude/skills/grugops*/SKILL.md`, read with readdir only, without following links. That way a grugops-shaped file is named even with an empty or unreadable kit source. The plan's own behaviour item asks for `grugops-mine.md` to be named. Names are never a reason to remove anything.
- **Seeded per-repo state.** Directories install recorded under `.grugops/`, `plans/` and `memory-bank/` are visited and never removed. They get no line, and the "preserved" footer covers them.
- **A recorded directory that is not empty** stays silently, as before. Its outcome is `left` in OUTCOMES.
