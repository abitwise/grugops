- **Finding 3 (DC-1): a garbled probe value switched the contradiction check off.**

### Sibling search

The search read every `hostField(` use in host-protection.ts and every comparison over its result.

Fixed:
- The 404 `Not Found` path compared `branches/<b>.protected` raw (`=== true` / `=== false`). It now reads the value through ACCEPT.branchProtectedFlag. A garbled value about this branch is now `unreadable`, where it used to be reported as "answered about another branch" (`e0b23515`).
- A probe of `protected: true` with both arms showing nothing used to read `unprotected`. It now reads UNKNOWN - verify (`217d64c5`).

Reviewed and left as they are, with the reason:
- `message === "Branch not protected"` / `"Not Found"` on the protection 404: this is an exact match on GitHub's measured messages (33.1-RESEARCH.md Q4). Any other value falls to `unreadable`, and it never produces `held`.
- The identity checks `hostField(res.body, "id") === id` (rulesets), `brName === name` and `answeredName === b` (branches): a mismatch or an absent value falls to unknown or rename. They select nothing.
- Selections by the check's own constants: `rulesOfType`, `type === "required_reviewers"`, and environment `name === <configured name>`, which already has the duplicate rule. Also `typeof default_branch === "string"`, whose name then passes `usableBranch`.
- The deployment policy's `custom` flag compares raw values only to choose the evidence text. The state comes from ACCEPT.deploymentBranchPolicy.
- Reuse after a contradiction:
  - `classicArmCache` is read only through branchVerdict and classicShownOn, and both sit behind contradictedName.
  - `rulesetBindingCache` is keyed by ruleset id and describes the ruleset, not a branch name.
  - A `noteProtectionShown` made before a branch is found `elsewhere` is kept. It can only turn an empty list's `failed` into `unknown`.

### Not fixed, and why

- **The probe's `protected: false` against a non-empty rule list.**
  - GitHub documents that the `protected=true` list filter includes rulesets. For the branch object's `protected`, it says only "required, boolean", without saying whether rulesets count (docs page read 2026-09-29).
  - If rulesets do not count, treating a ruleset-protected branch whose probe says false as contradicted would turn every such branch UNKNOWN - verify on a real host.
  - Whether rulesets count is `UNKNOWN - verify`, so the behaviour is unchanged: a false probe contradicts only a classic protection body. A live reading of a ruleset-only branch would settle it.
- `environmentName`'s file reads are untouched, because plan 33.1-25 owns them. `full_name` is not read, also plan 33.1-25's. Plan 33.1-25 may want to compare its `full_name` with the repository url used here.
