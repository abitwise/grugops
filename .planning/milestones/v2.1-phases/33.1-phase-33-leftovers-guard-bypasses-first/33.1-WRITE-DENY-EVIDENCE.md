# D-33-R4-05: does `claude -p --permission-mode default` deny an out-of-target `Write`?

This record is the committed, re-runnable measurement that D-11 part (a) requires before the live
capture's go. The capture runner may pin `--permission-mode default` only on this measurement. Every
value in the result tables was printed by the harness named in `precheck:`. Nothing in them was typed
by hand.

## What is being checked

In the round-4 live capture, both sessions ran in `permissionMode: auto`, which they inherited from
the operator's own settings. Role agents then used the `Write` tool on seven paths outside the target,
even though the runner's grant names no `Write` (33-R4-DIAGNOSIS § 3.1). The runner pinned no
permission mode. The human decided (D-33-R4-05) that the capture pins `--permission-mode default`,
but only after a zero-token check shows that this mode actually denies such a write in `-p` mode.

The claim measured: with the exact tool grant the live capture passes (`liveAllowedTools(target)`,
imported from the built `scripts/capture-live.js`), a `Write` to a file outside the target is denied
in a `-p` run under `--permission-mode default`. This must hold both when the main thread issues the
`Write` and when a subagent issues it.

## How it was measured

- **No model was called.** `ask-p-mode/mock-api.mjs` (plan 33.1-03, extended by this plan with an
  optional two-step script) stands in for the Messages API on `127.0.0.1` only. `claude` runs with:
  - `ANTHROPIC_BASE_URL` pointed at the mock;
  - a placeholder API key;
  - `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`;
  - a temporary `CLAUDE_CONFIG_DIR`;
  - every inherited `CLAUDE*` / `ANTHROPIC*` variable removed.
  A case whose mock log shows no `POST /v1/messages` is refused with exit 2 rather than reported. No
  case was refused.
- **Only project settings apply.** The invocation is
  `claude -p write --setting-sources project --output-format stream-json --verbose --permission-mode <m> --allowedTools <liveAllowedTools(target)>`,
  run in a scratch git target (one commit on `main`) with stdin empty and a 60 s bound. The grant
  printed by the harness was:
  `Agent, Read, Grep, Glob, Edit(//<target>/**), Bash(node *), mcp__plugin_grugops_grugops__propose_note`.
- **The probe file is outside the target.** It is `<outside>/probe.txt`, where `<outside>` is a
  separate `mkdtemp` directory that is not under the target.
- **main case.** The mock answers the main thread's first tool-bearing request with one `Write` of the
  probe file.
- **subagent case.** The mock first answers the main thread with an `Agent` tool use
  (`subagent_type: general-purpose`, a short prompt). It then issues the `Write` inside the subagent's
  own conversation. That conversation is recognised by a request that offers `Write`, carries no
  `tool_result`, and does not carry the `Agent` tool use's id. The main thread's own continuation
  always carries that id.
- **What decides a verdict.** Three observables:
  - whether the probe file exists after the run;
  - the transcript's `Write` tool call and its `tool_result`, including the `parent_tool_use_id` that
    places them in the main thread or the subagent;
  - the `result` frame's `permission_denials`.
  `denied` needs all of these: the file is absent, the call appears in the expected session, and the
  call is either named in `permission_denials` or has an error `tool_result`. `UNKNOWN - verify` is
  printed when the call never appears in the transcript.
- **The control proves the harness sees a write.** The same two cases are run with
  `--permission-mode bypassPermissions` and must read `ran`.
- **Supplementary in-target case.** A `Write` to `<target>/probe.txt` under `default` shows whether
  the pin still lets the grant's own scoped `Edit(//<target>/**)` rule through.

**Reading.** On Claude Code 2.1.283, `-p --permission-mode default` with the live capture's grant
denied an out-of-target `Write`:
- on the main thread, where the denial is also recorded in `permission_denials`;
- inside a subagent, where the denial appears only as the subagent's error `tool_result`.

In both cases the file was not created. The `bypassPermissions` control created the file in both
cases, so the harness does observe a write that happens. An in-target `Write` under `default` went
through, because the scoped `Edit(//<target>/**)` rule covers `Write`. So the pin leaves the grant's
own file writes working.

**Pin decision (mechanical, plan 33.1-13 Task 2 step 4):** `main` reads `denied` and `subagent`
reads `denied`. The pin lands: the runner's spawn argv gains `--permission-mode default` immediately
before `--allowedTools`.

the Claude Code version present at the go.

## What this does not show

- **The subagent's denial is not in `permission_denials`.** The `result` frame's
  `permission_denials` names only the main-thread denial. A subagent denial is visible only as the
  subagent's error `tool_result` (`parent_tool_use_id` = the spawn). The two denials also use
  different wording ("requested permissions … haven't granted it yet" on the main thread, "Permission
  to use Write has been denied" in the subagent). Anyone who later counts denials for the live capture
  must read both channels.
- **`default` is not in the `--help` choice list.** The 2.1.283 `--help` lists `acceptEdits`, `auto`,
  `bypassPermissions`, `manual`, `dontAsk` and `plan`, and does not list `default`. The CLI still
  accepted `--permission-mode default`, and the init frame reported `permissionMode=default`. Whether
  `default` is a documented, stable alias of `manual` is `UNKNOWN - verify`. If a later version drops
  it, the flag probe added to the runner's preconditions catches only a missing flag, not a rejected
  value.
- **Only one tool and one spelling.** This record covers `Write` to one absolute path. It does not
  cover:
  - `Edit` or `NotebookEdit` outside the target;
  - writes made through `Bash(node *)`, which the grant allows in every mode (node can write
    anywhere; 33-R4-DIAGNOSIS § 3.1 recorded `Write` routes, not node routes);
  - any MCP tool.
- **Only project settings.** The harness passes `--setting-sources project` and a temporary
  `CLAUDE_CONFIG_DIR`. The live capture runs under the operator's own settings. A command-line
  `--permission-mode` is expected to take precedence over a settings `defaultMode`, but an operator
  allow rule for `Write` or an `additionalDirectories` entry would still widen the session. The
  round-4 operator settings had neither (33-R4-DIAGNOSIS § 3.1). That is `UNKNOWN - verify` at the go
  for whatever settings are present then.
- **Only one nesting shape.** The subagent case uses the built-in `general-purpose` agent one level
  below the main thread. A plugin-defined role agent, or a deeper nesting level, was not driven here.
- **A deny is a refusal, not a sandbox.** The denial is the host CLI's permission check. The subagent
  deny message invites the model to reach the same goal with other tools. This record says nothing
  about such workarounds.
- **One Claude Code version, one host.** The result is for 2.1.283 on one macOS host. Re-run the
  harness after an upgrade.
