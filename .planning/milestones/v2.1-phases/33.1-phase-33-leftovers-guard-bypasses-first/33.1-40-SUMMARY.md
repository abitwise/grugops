# Phase 33.1 Plan 40: Install records its backups; --prune-old-kit removes only what install recorded, unchanged Summary

**Install now records every backup it makes in the target as a `backup` entry of the install ledger, with a file, link or tree record taken once the backup has its final name. `--prune-old-kit` removes only recorded in-repo-kit, legacy-config and kit-home backups, outside the protected paths, and only after `owns(..., "backup")` shows the backup still holds its record. A user's `thesis.bak.<ISO>/` or `budget.xlsx.bak.<ISO>` is left byte for byte and named (CR-02). A D-32 backup keeps the edited file's permission bits (IN-03).**

## Accomplishments

- **Recorded backups (Task 1, `install/install.ts`).**
  - `BACKUPS` maps each final backup path to its entry. `recordBackup(path, origin, of)` records nothing under DRY_RUN, for a path outside the target, or for a path `readLedger` would refuse (`isLedgerPath`), so a backup can never make the whole ledger malformed.
  - When a backup is made of a path, any entry this run recorded inside that path is dropped: it now lives inside the new backup and is covered by its tree record.
  - Call sites: `backupIfDiffers` (in-repo-kit), `backupDir` (handoffs), the `migratePreSteps` config rename (legacy-config), and `backupEditedKitFiles` (edited-kit-file), recorded after the staging name is gone, because a backup with two names reads as a hard link and records null.
  - `nextLedgerEntries` unites the previous ledger's backup entries whose path still holds something (`carriedBackups`) with this run's, outermost only. A carried entry keeps its own content record.
  - An already-migrated `--migrate` stops before `writeMarker`, so `recordBackupsInMarker` adds its handoffs backup to the marker through `rewriteLedger`.
- **The pure rules (`install/install-marker.ts`).** `backupContentRecord` returns the file record (bytes and mode, read through `readOwnedContent`, so no link is followed and a hard link records null), `treeRecord` for a directory or a link, and null otherwise. `outermostBackups` and `carriedBackups` are the two carry rules. All three are unit-tested in `ledger.test.ts`.
- **IN-03.** `EditedKitFile` carries the edited file's `mode`. The staging copy is created with `{ flag: "wx", mode: bits }` and then `chmodSync`'d to exactly those bits before `linkSync` gives it the backup name. A chmod failure discards the incomplete copy and is a verify.
- **Uninstall.** `reportBackup` names each recorded backup with its origin ("install's backup of your content: …; uninstall never removes a backup"). `reportKitBackups` skips a name with a ledger entry and keeps its name-pattern wording for an unrecorded one.
- **Prune by record (Task 2).**
  - `pruneRoots` reads the target's marker and ledger and the kit-home record once each (both through `readForWrite`: no link followed, no special file opened). A record that is not usable gets a `note` line.
  - For each `backup` entry: an origin outside {in-repo-kit, legacy-config} (target) or {kit-home} (kit home) is `left` ("prune never removes a backup of your content"). Otherwise `owns(ledger, root, path, "backup")`; not owned is `left` with owns' reason (or "it is no longer there"); owned goes to `removeBackup`, which re-checks the protected paths and returns `removed`, `would-remove` or `kept`.
  - `rewriteLedgerWithout` takes the removed entries out of each record through `rewriteLedger`: a DRY_RUN `would-edit`, a same-bytes re-read through `readForWrite`, `readLedger` again, `ledgerJson`, `writeTargetFile` for the marker and one `writeFileSync` for the kit-home record, and a verify naming what was not done.
  - The name-shape scan is report-only: a root name matching `GRUGOPS_BACKUP_SUFFIX` with no entry is `left` ("not recorded by install, so prune does not remove it …").
  - `readKitHomeRecord` now returns the record's `bytes` for the same-bytes check.
- **Tests.**
  - New `install/installer-prune.test.ts`, 21 tests: 6 for Task 1 (derived-set equality, carry, IN-03 at 0600 and 0664, uninstall real and DRY_RUN), the class test (count check plus 4 runs: installed and never-installed, real and DRY_RUN), and 11 recorded cases (the full migrate-then-prune flow with DRY_RUN and a second prune, 4 kinds of change to a recorded tree, an edited config backup, null records hand-made and natural, a protected path, a forged entry, a failed rewrite at both roots).
  - `installer-paths.test-support.ts`: `backupShapes(set)` derives 16 shapes from the migrate variant's write set plus `BACKUP_USER_BASES`; `plantBackupShapes` plants them.
  - `installer-special-files.test.ts`: `install --yes --prune-old-kit` is a sixth run kind (`RUN_KIND_COUNT = 6`, over a migrated tree) and a third kit-home run, plus three site cases (a FIFO inside a recorded tree, a FIFO added after recording, a FIFO named like a backup at both roots). 43 tests, up from 32.
  - `ledger.test.ts`: 3 unit cases. `installer-fs-census.test.ts`: the prune-scope ownership case and two DRY_RUN rows.
- **Docs (Task 3).** README "Pruning old backups" rewritten for the recorded rule; the D-32, `--migrate`, manual-restore, Undo-list and kit-home paragraphs say install records its backups and uninstall reports them by record. ## Decisions Made

- **The pure rules live in install-marker.ts.** install.ts runs on import, so the outermost rule, the carry rule and the content record are exported from install-marker.ts and unit-tested; install.ts calls them.
- **The outermost rule is applied twice.** recordBackup drops an entry under the path it just moved, and nextLedgerEntries keeps only the outermost of the carried and new entries. M1 showed why the first matters: without it, the inner config backup would be recorded at a path that no longer exists.
- **A null record is the bound.** A backup install could not read in full (an unreadable file inside, a hard link, a FIFO at the top) is recorded with `content: null` and is never pruned.

## Decisions needed from the human

Plan 33.1-43 collects these.

1. **A kit-home backup of something that was not install's kit is prunable** (reversible; installer behaviour). copyKit records every kit-root backup with origin `kit-home`, whether it is `--update` keeping a recorded kit that differs, or a directory of the user's at `agent-factory/` renamed aside (plan 37's rename-aside). Prune cannot tell them apart, so it removes either while it is unchanged. README keeps the warning to move anything you want out of such a backup before you prune.
   - **Alternative:** record which arm made the backup (for example a separate origin for "not install's kit") and never prune that one, the way handoffs and edited-kit-file backups are never pruned.
   - **Cost of the alternative:** a grammar change in the kit-home record and one more origin; the user removes those backups by hand.
2. **Backups made before this release are left by prune** (marked **Breaking** in the CHANGELOG, as the plan specifies). They have no record, so prune names them `not recorded by install`, and the user removes them by hand. Please confirm the Breaking marking and the wording.
3. **The already-migrated `--migrate` arm now writes the marker** to record its handoffs backup (deviation 2). The alternative is to leave that backup unrecorded: prune never removes a handoffs backup anyway, and uninstall would report it by its name pattern.
4. **For information:** plan 39's D-33 (b) narrowing still applies. Backups do not keep the marker, so after uninstall removes it, prune can no longer see the target's backups. README and CHANGELOG say "run `--prune-old-kit` before uninstall". That decision is already listed in plan 39's SUMMARY.
