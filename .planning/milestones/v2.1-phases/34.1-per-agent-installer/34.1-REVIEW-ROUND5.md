## Critical Issues

### CR-08: the "kit home moved" FAIL fires when nothing moved, and its remedy breaks another repository's install

**File:** `install/install.ts:2135-2148` (predicate and FAIL text); `install/kit-route.test.ts` R54 rows (no row covers the case)

**Issue:** The predicate is "an `ok` marker, GRUGOPS_HOME given and different from the recorded kit home, the recorded kit root holds no kit, and the given kit home's agent-factory holds one." That condition is also true when the recorded kit home was **deleted**, not moved, and the run's GRUGOPS_HOME points at a different, legitimate kit home that other repositories use. CHANGELOG.md says GRUGOPS_HOME is often exported in the shell, which makes this common: every `--check` of a repository whose recorded kit home is gone then trips the FAIL. The line states a fact it never established ("kit home moved") and tells the human to move a shared kit home.

Reproduced:
1. Install `t1` with `GRUGOPS_HOME=<S>/r3/A` and `t2` with `GRUGOPS_HOME=<S>/r3/K2` (both `--codex`, exit 0).
2. Run `rm -rf <S>/r3/A`.
3. Run `GRUGOPS_HOME=<S>/r3/K2 node install/install.js --check --target <S>/r3/t1`. It prints `FAIL kit home moved: install recorded the kit home <S>/r3/A ... given the kit home <S>/r3/K2 ... Move <S>/r3/K2 back to <S>/r3/A, then run ...`.
4. Follow the remedy (`mv K2 A`). `t1`'s check exits 0, but `t2`'s `--check` now reports 3 FAILs: its recorded kit home K2 is gone.

The moved kit's own kit-home record at A is also bound to K2 (`readKitHomeRecord(A)` reads `unbound`, boundTo K2). So a later install into A treats that kit as unrecorded. That is the second-kit path D-42 set out to avoid.

The evidence to tell the two cases apart already exists. A kit home that really moved carries a `.grugops-kit.json` whose `grugopsHome` names the OLD path (`readKitHomeRecord(B)` is `unbound` with `boundTo` equal to the recorded kit home). K2 in the repro reads `ok`, bound to K2 itself. The predicate never consults it.

A second, smaller gap: the predicate never checks that the recorded kit home is absent. If it still exists as a directory (for example, only `agent-factory/` was moved), "Move B back to A" done as `mv B A` puts B inside A.

D-42 fixed the predicate's wording. This finding is about what that predicate enumerates, and it goes to the human under D-40's flexibility clause.

**Fix:** Say "moved" only when the given kit home's own record proves it, and only when the recorded path is free:
```ts
const givenRecord = readKitHomeRecord(GIVEN_KIT_HOME);
const movedFromRecorded =
  givenRecord.state === "unbound" &&
  givenRecord.boundTo !== null &&
  sameRecordedPath(givenRecord.boundTo, DOCTOR_KIT_HOME) &&
  !existsSync(DOCTOR_KIT_HOME);
if (markerRead.state === "ok" && GIVEN_KIT_HOME !== null && GIVEN_KIT_HOME !== DOCTOR_KIT_HOME &&
    !kitReal(DOCTOR_KIT_ROOT) && kitReal(join(GIVEN_KIT_HOME, "agent-factory")) && movedFromRecorded) {
  docFail(`kit home moved: ...`); // as now
}
```
Otherwise, fall through to the existing cross-check or kit-stat FAIL, which states only what was observed. Add an R54 control row: recorded kit home deleted, given kit home bound to itself and used by a second repository. It should print no `kit home moved:` line and no line telling the user to move the given kit home.

### WR-39: the unreadable-first ordering does not hold; a presence check still runs first, and the same run says "never delete the marker" and then "marker not present"

**File:** `install/uninstall.ts:1621-1640` (removeMarker); `install/install.ts:1318-1328` (markerUnreadable subject); `CHANGELOG.md:511-515`

**Issue:** Plan 34.1-55's comment says "A read this run could not use is asked FIRST, before the path's shape." But `if (!pathExists(m))` (an `lstat` presence test) runs before the `MARKER_READ.state === "unreadable"` arm. When `.grugops` is a regular file, or a dangling symbolic link, the reader answers `unreadable`/`blocked` and `lstat` of `.grugops/install.json` throws.

Reproduced in a target where grugops was never installed and `.grugops` is a regular file (`<S>/r4`), and again with `.grugops` as a dangling link (`<S>/r2`). The uninstaller prints:
- the module-top verify: "Fix .grugops/install.json by hand (...); never delete the marker: it is the one record install keeps of the agents installed here ...; then run ... again";
- `skipped .grugops/install.json (marker not present)`;
- in the closing, `.grugops/ (seeded state) is kept` and `.grugops/install.json (the install marker): not present, so there was nothing to remove`.

One run contradicts itself on the same path (REC-1). The verify's remedy can't be followed because no marker exists (MSG-1). `--check` on the same target prints `the install marker <path> is present but could not be read`, which is false for the path it names.

The new CHANGELOG line ("or `.grugops` is a symbolic link, the uninstaller's line about it names the cause it saw ... and points at the verify line") is false for a dangling `.grugops` link (DOC-1). The reader-state matrix in agents-record.test.ts did not catch this because its blocked shapes have no regular-file `.grugops` and no dangling `.grugops` link. The ordering itself predates this round, but the claims that it is fixed are new.

**Fix:** Ask the read before presence, as the comment says:
```ts
function removeMarker(): MarkerOutcome {
  const m = `${TARGET}/${MARKER_REL}`;
  if (MARKER_READ.state === "unreadable") {
    report("left", `${MARKER_REL} (left in place — ${markerDefectText(MARKER_READ.defect)}; see the verify line above)`);
    return { kind: "left" };
  }
  if (!pathExists(m)) { report("skipped", `${MARKER_REL} (marker not present)`); return { kind: "absent" }; }
  ...
```
In markerUnreadable, use a subject that does not say "is present" when `read.defect === "blocked"` and the blocking component lies on the way (`read.why` names a path other than the marker). Add the two shapes (`.grugops` a regular file, `.grugops` a dangling link) to READER_STATES.blocked.

### WR-40: the D-43 census enumerates two literal spellings; the sibling "does not read as a grugops install marker" ships in every `field` remedy

**File:** `install/install-marker.ts:454`; census at `install/agents-record.test.ts:4332` (NOT_INSTALLS) and `:3713` (MATRIX_NOT_INSTALLS)

**Issue:** D-43's census claims "no printed reading says the marker is not install's". The regex is `/not install's|not the marker install writes/i`, so it only bounds those two spellings. installMarkerProblems' arm builds `why: "it does not read as a grugops install marker — ..."` for every `field` read, and a `field` read is install's own marker with a hand-edited field. That `why` reaches every verify and FAIL through markerUnusableText and the kitPreflight reason. On a scratch install with `installMode` set to `"banana"`, `--check` prints:

`FAIL the install marker <path> is present but is a JSON object but could not be used as install's marker (it does not read as a grugops install marker — installMode is neither copy nor symlink) — ... never delete the marker: it is the one record install keeps of the agents installed here ...`

This is the WR-38 class (telling the user the file is not install's marker in the same line that says it is the one record) in a spelling the census does not enumerate. R53 asserts against the same two-spelling regex, so it passes over the sibling.

**Fix:** Reword the arm so it names the field rather than the file's identity, e.g. `why: \`a field in it does not hold install's value — ${problems.join(", ")}\``. Then widen both censuses to the class rather than the spellings, e.g. `/\bnot install's\b|\bnot the marker install writes\b|\b(?:does not|doesn't) read as (?:a |an )?(?:grugops )?install(?:'s)? marker\b|\bnot (?:a |an )?(?:grugops )?install marker\b/i`. Keep the exempt-table count assertion.
