- `markerRemedy(read, run)` and `markerFixText(remedy)` in install/install-marker.ts under the section "THE MARKER REMEDY (phase 34.1 gap round 3, D-35, 34.1 review CR-04)". After the hand fix, the printed check command, run from outside the checkout with no GRUGOPS_HOME, gives exit 0 and no FAIL. A flag-less uninstall then removes the marker and both skills and leaves no recorded path.
- R36 control: a not-JSON marker still gets the fix-or-remove FAIL with the install and check commands.
- R37: `install --claude` (writeAskRules) and `install --codex` (askRulesStep) each exit 3 with the never-remove verify and leave the marker byte for byte. ## Decisions Made

- markerFixText has no conditional inside its string. Its callers always pass a non-empty `fix`, because an `unreadable` read with a parsed object always carries its problems. With no conditional, the census reads exactly one owner site.
- The never-remove problem strings in readInstallMarker contain no verb that would put them into the census. For example, the retired-record problem reads "... next to the install ledger (install never writes it; take it out)".
- The I1, I5 and I6 census texts did not change. Their may-remove readings are byte-identical to the old text, so only their reasons were re-pinned.

- **Found during:** Task 1 (R36)
- **Issue:** Uninstall's `left` lines name paths relative to the target, so lineNamesPath against absolute paths would never match, and the assertion could never fail. Also, a clean flag-less uninstall leaves `tools/`, which is a recorded `dir` entry, by design ("grugops owns tools/grugops/ only").

I checked by hand that it discriminates. The CR-04 harm path (delete the marker, re-install `--claude`, flag-less uninstall) gives 31 such lines; the fixed path gives 0.
