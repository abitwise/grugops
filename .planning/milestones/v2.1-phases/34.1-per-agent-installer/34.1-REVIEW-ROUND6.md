## Warnings

### WR-41: Over an unreadable marker, the refusal's "same agents again" command names agents picked by detection, not the record, and following it installs an agent that was never installed

**File:** `install/install.ts:6004-6040` (selection), `install/install.ts:6089-6117` (refuseOverMarker), `install/install.ts:7647-7666` (printInstallIncomplete)
**Issue:** `installedAgents` answers NONE for every read that is not `ok` (install-marker.ts:1702). So over an
unreadable marker, a flag-less unattended run falls through to `detectedHosts()`. The refusal then prints
`printInstallIncomplete(true)`: "Once each is fixed, `<agentCommand(..., SELECTION, ...)>` installs for the same
agents again". refuseOverMarker does not print the run banner's `agents:` line (install.ts:6101-6104), so the user
never sees that these agents came from detection. In the same output, the verify ends with markerFixText's "then
re-run the installer" (install.ts:6109). Re-running that, once the marker is fixed, chooses the RECORDED agents. The
two next steps disagree.

Reproduced (scratch HOME/GRUGOPS_HOME):
1. `install --codex` exits 0; the marker has `agents: ["codex"]`.
2. Add `.claude/`, put a trailing comma in the marker, run flag-less `--yes`. It exits 3, and the banner prints
   `... install.js --target <t> --claude`.
3. Remove the comma and run the printed command (with `--yes`) from outside the checkout. It exits 0, writes
   `.claude/agents`, `.claude/skills` and `.claude/settings.json` ask rules, and the marker's `agents` becomes
   `["claude","codex"]`.

So "the same agents again" installed an agent this repository never had, and it left out the recorded one. It is
reversible because the writes are recorded. It is still a printed remedy that does not do what it says (brief MSG-1:
"a remedy names concrete flags from THIS run"; a run that could not read the record has no "same agents").
**Fix:** When `INSTALL_REFUSAL !== null` and the selection did not come from flags or the picker, print no
agent-naming command. `then` is already "re-run the installer", which picks the record once the marker is fixed. Or
print the banner's `agents:` line with each agent's reason before the verify. For example:
```ts
const namedByUser = SELECTED_BY_FLAG.size > 0 || [...SELECTION_WHY.values()].some((w) => w === "chosen at the prompt");
printInstallIncomplete(remedy.defect !== "foreign" && namedByUser);
```
Then add a row: install `--codex`, a detected `.claude/`, a trailing comma, a flag-less `--yes`; follow everything
printed and assert that `agents` is still `["codex"]`.

### WR-42: A flag-less run over an unreadable or foreign marker with nothing detected exits 1, says "none is recorded in .grugops/install.json", and prints no verify about the marker. This contradicts D-45, the CHANGELOG and the README

**File:** `install/install.ts:6035-6038` (refuseSelection message), `install/install.ts:6116-6117` (the refusal sits after selection), `CHANGELOG.md:537-543`, `install/README.md:198`
**Issue:** The refusal is asked only after `SELECTION_WHY`. When no flag is given, the read is `unreadable`
(`installedAgents` returns NONE) and nothing is detected, `refuseSelection` exits 1 first, with: "no agent was named,
none is recorded in .grugops/install.json and none was detected ... so nothing was installed". That sentence makes a
claim about a record the run could not read (or, for `foreign`, treats a user's own file as install's record). Its
printed example command (`--claude`) then ends in the exit-3 refusal. It is a two-step remedy whose first step is
known to fail.

D-45 item 3 says install refuses "exit 3 ... the same verify wording". CHANGELOG.md:537-543 says "It exits `3` with
its `verify` line about the file". install/README.md:198 says `install.js` "also exits `3` ... when
`.grugops/install.json` is a file it cannot use". None of these holds for this run. At a terminal the same thing
happens through the picker's cancel or empty-confirm arms.

Reproduced: a fresh repo, `{"a":1,}` at `.grugops/install.json`, flag-less `--yes`. It exits 1 with the sentence
above, and no line names the marker's defect.
**Fix:** Ask `installRefusal(PREVIOUS_MARKER_READ)` before `refuseSelection` can fire. One way is to have
`refuseSelection` check `INSTALL_REFUSAL` first: when it is non-null, call `refuseOverMarker` with an empty command
(`printInstallIncomplete(false)`-style closing that names no agents). Another is to split the refusal into "decide"
(before selection) and "print" (after it). Add a flag-less no-detection row for `not-json` and `foreign` that
asserts exit 3 and the marker verify.

### WR-43: A `--migrate` run refused over an unusable marker prints the install banner and an install command without `--migrate` (the DI-09 class again)

**File:** `install/install.ts:6089-6117`, `install/install.ts:7647-7666`; `install/README.md:198`
**Issue:** The refusal runs before the `--migrate` branch (install.ts:6125). Its closing is
`printInstallIncomplete`, which prints `== install INCOMPLETE` and `agentCommand("install.js", TARGET, SELECTION,
COMMAND_CONTEXT)`, with no `--migrate`. The migrate branch's own banners use `migrateCommand()`
(install.ts:575-577), which was added to fix DI-09 ("a flag-less --migrate ... may not be the agents this run
named"). This sibling prints a plain install command for a run the user started as a migration. Over an old in-repo
layout, following it as printed runs an ordinary install: no config carry, and no `agent-factory/` backup or rename.
The "(add any other option this run was given)" hedge leaves it to the user to know that `--migrate` matters.
README:198 says `--migrate` prints its banner "with `migrate`".

Reproduced: an old layout (`agent-factory/roles/orchestrator.md`) plus `{"a":1,}` at the marker, then
`--migrate --codex --yes`. It exits 3, prints `== install INCOMPLETE`, and the command ends `--target <t> --codex`.
**Fix:** In refuseOverMarker, choose the closing by run kind. When `MIGRATE` is set, print the `migrate` banner and
`migrateCommand()` (MIGRATE_AGAIN_LINE). Add a row that follows it as printed over an old layout and asserts the
migration ran.

### IN-44: The refusal's decision and its malformed-ledger wording have more than one authority

**File:** `install/install-marker.ts:616-618`, `install/install.ts:6089-6100, 6105-6110, 5638-5643, 6976-6980`
**Issue:** `installRefusal` is a bare alias of `markerRemedy`, so any future change to which reads markerRemedy
answers silently changes which reads install refuses. refuseOverMarker then decides a second time: it calls
`readLedger` again and throws if the answer disagrees (install.ts:6091-6100). The "`<MARKER_REL>` — the install ledger
is malformed (<why>)" cause clause is hand-built in three places (refuseOverMarker, writeMarker, writeAskRules). That
goes against the brief §2.2 rule of one owner per rule.
**Fix:** Have installRefusal return the cause clause along with the remedy (or put a `markerCauseText(read)` in
install-marker.ts), and have all three sites print it. Give installRefusal its own explicit switch over states, so
that a markerRemedy change cannot widen or narrow the refusal unnoticed.

### IN-45: At a terminal, the agent list is asked before the refusal, and over a foreign read the answer is thrown away

**File:** `install/install.ts:6010-6020`, `6112`
**Issue:** The picker runs before `installRefusal`. Over a `foreign` read the closing names no command
(`printInstallIncomplete(false)`), so the user is asked to choose agents for a run already known to write nothing,
and the choice is not used. Over the other reads, the choice only feeds the printed command. The ordering is
documented ("so the closing can name the install command"). This is a UX note, not a correctness defect.
**Fix:** For a `foreign` read, refuse before the picker. The read is known at install.ts:5953, before `SELECTION_WHY`.

### IN-46: Class boundary for the human: an `unbound` marker of this directory (no `target`, or no ledger) is still replaced, and its earlier records are dropped

**File:** `install/install-marker.ts:603-618` (markerRemedy/installRefusal answer null for `unbound`), `install/install.ts:5617-5631`
**Issue:** installRefusal's rule is "install writes only what it can record ... every file install writes stays
recorded". That holds for this run's writes. For an `unbound` marker of kind `no-target` (written before markers were
bound) or `no-ledger`, the records almost certainly describe this same directory. writeMarker replaces the marker,
and its own note says "What an earlier install made here has no record, and uninstall leaves it". That is the DI-25
harm (install's files left with no record) one state over. D-45/D-46 named only foreign, unreadable and malformed
ledger, and the docblock deliberately answers null for `unbound`, so this is recorded as a decided boundary, not a
defect in this round.
**Fix:** None in this round. If the human wants the class closed, `no-target` could carry the old ledger forward, or
refuse the same way.
