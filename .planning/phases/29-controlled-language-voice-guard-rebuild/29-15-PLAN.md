<objective>
Close CR-02: `guard_diff_disposition`'s companion-edit rule is implemented as "changed anywhere since
the recorded base" while its own contract says "changed in the SAME commit". Once any commit in the
range touches the companion, every frozen clause from that source is permanently satisfied for the
rest of the phase — no per-clause correspondence, no check at all. This is live on HEAD:
`docs/audit/28-claim-registry.md` already appears in the range diff, so all 42 registry-anchored
frozen clauses are unprotected right now.

This is a range-versus-commit bug, and the reason no test caught it is structural: `makeMirror`
builds exactly two commits, so "same commit" and "since base" are indistinguishable in every existing
fixture. The harness must gain a third commit before the fix can be believed.

The `positiveGuardLiterals` arm has the identical shape and is safe today only because
`scripts/check-foundation-guards.ts` happens not to have changed in the range. It closes in the same
edit. Splitting a root cause by which side a finding happened to be reported against is precisely the
incrementalism this project has already paid for three times.

LANG-03's requirement is that load-bearing security, compliance and admission text is never reworded
by a style pass. The exclusion LIST is intact and correctly derived; the FREEZE that makes the promise
mechanical is the part that is vacuous. This plan makes it mechanical.

Purpose: turn a range-wide file-presence test into a per-carrier correspondence, fail-closed.
Output: a carrier-attributed companion rule on both arms, a harness that can express three commits,
and a measured statement of the fix's effect on the live range.
</objective>

  <decision>Which predicate replaces the range-wide companion test: per-carrier attribution, or per-clause pairing against the companion's own diff?</decision>
  <context>
The code review sketches both, and the verification report's `missing` list names both. They are not
equivalent and the choice sets the standard every future kit change is judged against, so it is
raised rather than taken silently.

Measured on the live range before this plan was written: **36** commits between the recorded base and
HEAD; exactly **one** of them touched `docs/audit/28-claim-registry.md`; and **zero** changed clauses
currently intersect either the registry-anchor set or the positive-guard-literal set. Both options are
therefore GREEN on the live tree today, so this is a choice about the rule, not about clearing a red.
  </context>
  <options>
    <option id="per-carrier">
      <name>Per-carrier attribution — resolve the commit that actually changed each clause and require the companion in that commit (recommended)</name>
      <pros>This is literally what the contract string already says, so no wording is weakened to match a weaker check. It closes the range-versus-commit class rather than an instance, applies identically to both arms, and is decidable with a bounded amount of git work. It also makes the uncommitted case a named carrier instead of an unattributed pass.</pros>
      <cons>More machinery: an ordered carrier list, a per-carrier diff, and an attribution map. Slower than one file-list read — the loop must be measured and its cost reported.</cons>
    </option>
    <option id="per-clause-pairing">
      <name>Per-clause pairing — require the changed clause's own text to appear on one side of the companion file's range diff</name>
      <pros>One extra git invocation and no attribution map. Strictly stronger than today's file-presence test, and satisfiable retroactively wherever the registry row genuinely moved with the text.</pros>
      <cons>It is still range-wide over the companion, so a clause changed in commit 5 whose registry row moved in commit 2 passes. The contract string would have to be WEAKENED to say what is actually checked, which is the opposite direction from the one LANG-04's naming discipline pushes. It also does not generalise to the positive-literal arm, whose companion is a source file rather than a register of the frozen text.</cons>
    </option>
  </options>
  <resume-signal>Select: per-carrier, per-clause-pairing, or describe a third rule. `per-carrier` is the plan's default and the rest of this plan is written against it; selecting `per-clause-pairing` requires the contract wording to be corrected in the same edit and the positive-literal arm re-planned.</resume-signal>
</task>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git history → gate verdict | The diff is this gate's entire left-hand side. A git invocation that dies, a base that cannot be resolved, or an attribution that silently returns empty empties the changed set and admits every rewrite under a clean green. |
| repo-relative path → git argument | Watched file paths and commit SHAs are interpolated into git arguments, including a `tree:path` refspec on the removed side. A path that reads as an option or as a different revision would make the gate read bytes it was not asked about. |
| carrier loop → gate runtime | The new attribution walks every commit in the range; an unbounded or superlinear walk hangs the gate, and a hung gate is not a red gate. |
