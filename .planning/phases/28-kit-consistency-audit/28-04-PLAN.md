<objective>
Give every public claim an id, map it to the floor whose lowering would falsify it, measure whether it
is currently true, and anchor it so a prose rewrite cannot silently invalidate the record.

Per D-13 this is a mapping and not a list. AUDIT-03's stated purpose is that Phase 30's
claim-dropping mechanism has a named target, so the row that matters answers "which public sentences
become false if floor F is lowered" — the join to Phase 30's AUTO-01 closed checkpoint set. Per D-15

while architecture and install claims get ids and stop being able to drift back unnoticed.

this registry and its only consumer and rewrites prose for a living. Without the bijection, Phase 29
silently invalidates the registry Phase 30 depends on. The residual is named rather than implied away:
no grep recognizes an assertive sentence, so a brand-new claim written without an anchor is not
mechanically detectable.

Per D-17 every row's status is measured against its named mechanism, and anything not true becomes an
AUDIT-01 finding. CLAUDE.md's hard constraint is never to fake a passing gate, a test result or a
citation; measuring a public claim false and shipping it anyway sits in that same family. Four

the drift-affected ones recorded false, and 28-05's rewrite must flip them in the same commit — with
the gate built here catching it if it does not, on a real commit rather than on a fixture. That
leaves an audit trail of each false claim being recorded, corrected, and flipped.

Purpose: turn a prose search into a named target set, and make it survive the phase that rewrites the
prose.

gate wired at both ends.

## Registry schema — the format `readRegistry()` parses

One section per claim. The verbatim text lives in a fenced block, not a table cell, because a claim
sentence contains pipes, em dashes and backticks that a table cell cannot hold without escaping — and
an escaped copy is not verbatim.

~~~~
### CLM-001

- file: README.md
- line: 3
- kind: architecture
- depends_on: —
- status: false
- mechanism: <what the status was measured against>
- disposition: <fixed | accepted | deferred, present when status is not true>
- finding_id: <F-28-NNN, present when status is not true>

```claim
One Orchestrator routes work through the full software-delivery lifecycle …
```
~~~~

The outer four-tilde fence above exists only so this plan can show a backtick fence inside another
fence. In the real artifact the claim block is an ordinary triple-backtick fence with the info string
`claim`, and there is no outer fence. **The executor must write plain ASCII.** Do not use a
zero-width space, a word joiner, or any other invisible character to escape a nested fence — this
repository spent five gap-closure rounds on invisible-character bypasses in exactly this file family,
and `readRegistry()` extracts the fence contents byte for byte with no normalization, so an invisible
character inserted here becomes part of a claim's verbatim text and silently breaks the comparison in
task 3.

**`line` is recorded, not asserted.** The gate asserts `file`, anchor presence, and the verbatim text
at the anchor. It does not assert the line number, because Phase 29 rewrites prose for a living and
an assertive line number would go red on every unrelated edit above the claim — training people to
ignore a red gate, which is the failure mode this milestone has spent itself fighting. The registry
states this inline as a named residual rather than leaving a reader to wonder why the number is
advisory.
