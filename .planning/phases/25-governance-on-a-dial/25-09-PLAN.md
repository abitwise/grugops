## MECHANISM DECISION — confirm at plan review (PROMINENT, human-confirmable)

RESEARCH ranked two mechanisms. This plan implements **(a) a structured admission TOOL (MCP server)**
and recommends it over (b). The human should confirm (a) at plan review before execution.

- **(a) CHOSEN — a structured admission tool (zero-dep stdio MCP server) wrapping appendNote.**
  Why: it is the ONLY mechanism that simultaneously (1) gives the agent a STRUCTURED admission channel
  the hook reads with no shell expansion, AND (2) keeps context-io.appendNote the SINGLE sanctioned
  writer (the server calls it; it forks no writer). Posture-B + the GOV-02 ledger + the D-04 degrade
  tier are reused (the new combiner reuses admit() for routine/unapproved paths and the in-module
  validate/composeNote/appendNote/appendAuditLedger for the approved high-severity path — see APPROVED-
  PATH DESIGN below). Today there is NO ergonomic agent-facing write verb (the CLI exposes only
  validate/admit/render; admit() does not persist; appendNote is programmatic) — so (a) also completes
  a genuinely missing piece of the architecture, it does not merely relocate the gate.
- **(b) REJECTED — gate the Write/Edit tool on the notes path.** Honest reasoning: notes are NOT
  written via the Write tool today (the sole sanctioned writer is appendNote, invoked programmatically
  via `node`, not the Write tool — context-io.ts:693, CLI :1268). So a Write|Edit matcher fronts an
  UNUSED path: the real sanctioned write (appendNote via Bash `node`) would be left UNGATED once the
  Bash matcher is removed — a regression. Making (b) real requires rerouting note-writing onto the
  Write tool, which BREAKS the single-sanctioned-writer invariant (appendNote's validate/compose/
  atomicWrite/noteId/Phase-22 id-discipline would no longer run; the hook would have to re-implement
  them). RESEARCH ranked (b) #1 before accounting for this; the in-repo facts demote it.
- **Footprint / brand trade-off (state honestly):** (a) ships a new persistent stdio subprocess, in
  mild tension with CLAUDE.md "grugops is NOT a platform, runtime, database, queue, or hosted service."
  It is a zero-dependency committed .js run by `node` with nothing installed (honors "host runs
  committed .js with ZERO runtime deps") and exists solely to BE the admission gate's structured
  channel — within "grugops supplies … gates." It also adds a one-time per-server CC approval. This is
  a real footprint addition and is the reason the mechanism is surfaced for explicit human confirmation.
- **What (a) does NOT close (carried into SC1 restatement, plan 25-11):** the same-uid direct-FS-write
  residual — an agent can still drop a `.md` into notes/ via the Write tool / Bash echo/cp/tee /
  a modified context-io copy / a programmatic `node -e` appendNote or emitVerdict, bypassing the channel.
  This is IRREDUCIBLE in-box, PRE-EXISTING (the Bash hook never closed it either), and backstopped by
  autonomy=pr (humans hold merge) + the no-fabrication floor (D-05 lineage). (a) converts an
  actively-exploited shell-obfuscation surface into this bounded, documented limit — a strict
  improvement with no regression.

## APPROVED-PATH DESIGN — the positive GOV-01 capability MUST succeed (D-03/D-07)

The gate is not only "deny an un-approved high-severity admission"; it MUST also ADMIT a human-APPROVED
one (D-07: after the human disposes, admission re-runs and ADMITS with the `human:<name>` stamp). Naively
routing the CC persist through `admit()` would REGRESS this: `admit()`'s D-04 branch (context-io.ts:947)
refuses EVERY high-severity finding under any active dial unconditionally — even one carrying a valid
`human:NAME` stamp (the 25-04 forged-stamp backstop), because the in-script tier cannot verify a human
placed it. That D-04 refusal was only ever the NON-CC DEGRADE tier (no hook ⇒ block high-sev at the
script level); making the CC persist inherit it would have the hook ALLOW while the combiner REFUSES —
the approved note never admits. The fix:

- **The un-forgeable approval source for the CHANNEL = the SERVER's OWN `process.env` (harness-set at
  server launch; the agent issues tool CALLS to the already-running server and cannot set env on it).**
  Reading `process.env.GRUGOPS_ADMISSION_APPROVED_BY` INSIDE the server is as un-forgeable as the deploy
  hook for the channel path. An agent doing `GRUGOPS_…=eve node -e "…admitAndAppend…"` sets its OWN
  process env = the DOCUMENTED same-uid direct-node residual, NOT the channel.
- **The new combiner takes an explicit `approvedBy: string | null`** (the only new context-io surface;
  `admit()` stays byte-frozen). The SERVER reads its own env and passes `approvedBy`; the combiner NEVER
  reads an approval from a tool argument.
- **Combiner high-severity-under-active-dial branch:** if `approvedBy` is a valid name → ADMIT, bind
  `verified_by: human:${approvedBy}` (the env-verified name — IGNORE any agent-supplied `human:NAME`
  stamp), persist via appendNote, and append the GOV-02 ledger; else → REFUSE naming the fault, persist
  nothing. The combiner does NOT call `admit()` for this branch (admit's D-04 would refuse regardless);
  it reuses the IN-MODULE composeNote / validate / appendNote / appendAuditLedger / HIGH_SEVERITY_ROLES
  (no new exports, no re-implementation, no drift). For routine / non-finding / dial-off it calls `admit()`
  unchanged (validate + Posture-B + D-04-won't-fire + ledger) then appendNote.
- **Defense-in-depth + non-CC honesty:** `admit()`'s D-04 unconditional refusal stays the WEAKER degrade
  tier for any path with no harness-set approval (the 4 non-CC CLIs and the CLI `admit` verb). On CC the
  per-call PreToolUse hook (fresh session env) is the belt and the server-env check is the suspenders.
  Claim the un-forgeable tier CONSERVATIVELY for Claude Code only; the server-env tier MAY extend to
  other MCP-launching CLIs if they launch the server with an agent-uninjectable env — note this as
  "verify per-CLI," do NOT over-claim.
- **Operational constraint to DOCUMENT (D-03 session-var model):** the server's env is fixed at server
  launch, so the approval is a SESSION-SCOPED grant — the human exports `GRUGOPS_ADMISSION_APPROVED_BY`
  BEFORE launching Claude Code (or restarts the server to pick it up). The per-call hook sees fresh env;
  the persisting server does not. The grant is session-scoped, consistent with the deploy-guard pattern;
  do not pretend per-note mid-session approval works without a server restart.
