# Phase 43.1: Code Review Report

**Reviewed:** 2026-11-19
**Depth:** standard (changed regions per `git diff 648d2276 HEAD`, plus the code they call)

## Summary

I reviewed the phase 43.1 changes: the STALE RUNNABLES removal in `install/install.ts`, the
`pathNodes`/`kitHomeOverlap` identity test in `install/user-file.ts`, the new regexes in
`scripts/check-story-docs.ts`, the `AGENT_BULLET` matcher in `scripts/generate-catalog.ts`, the
guarantees and host-protection wording, and the documentation claims.

The safety core holds up under tracing:
- **Removal is limited to ledger-owned files.** `staleRunnables` reads only kit-false `file` entries
  of an `ok` previous ledger. `STALE_RUNNABLE_PATH` limits them to direct children of
  `tools/grugops/`, and the ledger reader already refuses `\`, `:`, `/`-leading, `.` and `..`
  segments (`install-marker.ts:704-709`).
- **Ownership is checked twice.** `owns()` is asked again just before `unlinkSync`. `checkRecord`
  refuses a link on the way and a hard link.
- **DRY_RUN changes nothing.** It `continue`s before the unlink.
- **No other kit-false file under `tools/grugops/` can be removed by mistake.** `LICENSE` and
  `package.json` are RUNNABLES destinations, so they are excluded.
- **`pathNodes` fails closed** on any non-ENOENT stat error and on an unanchored root.
- **The anchor and degenerate-guard logic is sound** in the shapes I traced: a missing kit home under
  the target, an unrelated missing ancestor, a sibling kit home, a firmlinked spelling, and FAT-style
  `ino 0`.
- **No ReDoS in the new regexes.** Adversarial 50k-character inputs ran in ≤1 ms.

I found no BLOCKER. The findings are gaps around the new removal path (the doctor and uninstall do
not know about it, and the install guide does not document it), a safety-doc condition that is
incomplete for OIDC deploys, generated text that asserts something the generator does not check,
and a link checker that silently misses one shape its comment says it reads.

## Warnings

### WR-01: `install.js --check` (doctor) says nothing about a stale runnable, unlike stale adapters

**File:** `install/install.ts:1082-1121` (staleRunnables / retireStaleRunnables); doctor at `install/install.ts:3594`
**Issue:**
- **The doctor misses the D66 hazard.** It reports a stale adapter as a `FAIL` with a remedy
  (`staleKitAdapters(ledgerRead)` at :3594, documented in `install/README.md` §2 "An adapter this
  kit version no longer ships"). The new stale-runnable set has no doctor counterpart. A host whose
  plain `node --test` still runs `tools/grugops/test-skip-integrity.js`, which is the hazard D66
  exists to close, gets a clean `--check`.
- **Only a write-capable re-install learns about the file.** That conflicts with the doctor's role
  as the read-only health check.

**Fix:** Call the same derivation from the doctor, using its own `ledgerRead`, and report each
member through the one wording:
```ts
for (const s of staleRunnables(ledgerRead)) docFail(staleRunnableText(s)); // or docWarn, matching the adapter precedent
const u = unrecordedStaleRunnables(ledgerRead);
for (const rel of u.paths) docReport("note", unrecordedStaleRunnableText(rel, ledgerSays(ledgerRead)));
```
`staleRunnables` reads the module-level `TARGET`. Check that the doctor's target is the same, or
pass `root` in.

### WR-02: Uninstall no longer names an unrecorded `tools/grugops/test-skip-integrity.js`

**File:** `install/uninstall.ts:2795-2824` (RUNNABLES_MIRROR, reportUnrecordedRunnables)
**Issue:**
- **The old name drops out of the report.** `reportUnrecordedRunnables` names only the
  RUNNABLES_MIRROR destinations, and the rename removed the old name from that list.
- **This hits ledger-less installs.** A target installed before runnables were recorded (pre-33.1-28,
  no ledger entry) still holds `tools/grugops/test-skip-integrity.js`. A new-kit uninstall now leaves
  it without a word.
- **It contradicts the uninstaller's own promise:** "every grugops-shaped path the ledger does not
  record is named, never removed". The file is also exactly the one D66 says breaks a host's
  `node --test`.

**Fix:** Mirror install's presence path in uninstall. Name every `.js` directly under
`tools/grugops/` that is neither a RUNNABLES_MIRROR destination nor a ledger entry, report-only.
Alternatively, keep a report-only list of retired destinations. A derived scan is closer to the
"no retired name is written down" rule.

### WR-03: The install guide does not document that install now deletes a file

**File:** `install/README.md` (section "What the installer touches (per-repo), and only this", line ~460, and §2 at :198-230)
**Issue:**
- **Install deletes a file for the first time.** Plan 43.1-02 makes install delete a held stale
  runnable, and only `CHANGELOG.md` says so.
- **The guide has nothing on it.** It has a full subsection for the analogous adapter case (line
  198), with its exit code, `--dry-run` and `--check` behaviour. It has no subsection for stale
  runnables. Nothing explains the `would-remove`/`removed` lines, the exit-3 verify for an edited
  copy, or the repeating `note` for an unrecorded `.js`.
- **The registry row does not cover it.** The touch-list heading is now registered as claim
  `C-28-088` with status `true`, measured only on a fresh install. Its own row says a re-install was
  not measured, and a re-install is exactly where the removal happens.
- **The constraint text makes the gap matter.** CLAUDE.md says "never ... delete user content", so
  a reader of the guide cannot learn that install removes its own recorded file.

**Fix:** Add a subsection after "An adapter this kit version no longer ships", for example
"A runnable this kit version no longer ships". It should state:
- the held case: removed, with `would-remove` in `--dry-run`;
- the edited case: a verify, exit 3, and the record is dropped;
- the unrecorded case: a `note` on every run, never removed.

Then re-measure or qualify `C-28-088` for the re-install arm.

### WR-04: The new "credentials live solely in the environment's secrets" condition is wrong for OIDC deploys

**File:** `install/README.md:1854`, `install/README.md:1868-1871`; `scripts/runnable-ref/host-protection.ts:1650`; `scripts/audit-model.ts:336-339`; repeated in `agent-factory/workflows/12-release.md:9`, `docs/concepts.md`, `docs/how-it-works.md`, `docs/faq.md`, `agent-factory/packaging/adapters.md`, `AGENTS.md`, `agent-factory/config/factory.config.md`, `docs/GUARANTEES.md`
**Issue:**
- **The condition is presented as the one necessary condition.** Every page says the production
  environment "is the hard floor for a deploy only when the deploy credentials live solely in that
  environment's secrets".
- **OIDC, the setup GitHub recommends, has no stored deploy credential.** What gates the deploy is
  the cloud provider's trust policy and whether it pins the token's `sub` claim to
  `environment:<name>`.
- **Example:** a team whose trust policy accepts `repo:org/repo:ref:refs/heads/main` holds no secret
  anywhere, so it can honestly tick the new checklist item. Yet any job on `main` that does not
  reference the environment can deploy with no reviewer.
- **The checklist therefore misses the most common modern credential setup.** A safety page that
  readers are told is the hard floor gives false assurance to exactly those users.
- **The registry rows are marked `true` without the OIDC case.** They are `C-28-089`/`C-28-090`, and
  the GitHub paragraph at :1868 only covers secrets.

**Fix:** Widen the condition and the checklist item. For example:
```
- [ ] keeps the deploy credentials to itself: a stored deploy secret lives only in this environment's
      secrets (not in a repository or organization secret, a CI variable, a runner or a developer
      machine), and an OIDC trust policy for the deploy accepts only tokens whose subject names this
      environment (`repo:<owner>/<repo>:environment:<name>`), not a branch or the whole repository;
```
Mirror the wording in `ENVIRONMENT_FLOOR` and the `SAFETY_FLOORS` text, then regenerate
GUARANTEES.md. Re-measure the two registry rows.

### WR-05: The guarantees pointer and page heading assert "at its default settings" without checking it

**File:** `scripts/generate-guarantees.ts:205` and :873; `scripts/generate-guarantees.ts:512`
**Issue:**
- **The text is fixed.** `pointerLine` always says the page shows claims "in the grugops source
  checkout at its default settings", and so does the heading in `renderGuarantees`.
- **The page is computed from the checkout's live checkpoint matrix.** If the checkout's config ever
  lowers a floor, the same generated page will carry both "at its default settings" and
  `disclosureFor`'s "**This guarantee is lowered in this checkout's configuration.**"
- **The generator never checks the phrase.** Today it is true only because the checkout is at its
  defaults. That is the kind of unchecked claim the registry and generator exist to prevent.
- **The phrase is copied widely.** It appears in README.md, AGENTS.md, `agent-factory/README.md`,
  `docs/README.md`, concepts, faq and how-it-works, so a lowered floor would make each of them false
  with no gate turning red.

**Fix:** Derive the qualifier from the matrix. If no floor is `lowered`, emit "at its default
settings". Otherwise emit "at its current settings (N floor(s) lowered; see the page)". Make the
story or guarantees freshness check compare against that derived text. Alternatively, drop "default"
and say "at the settings committed in this checkout".

### WR-06: The derived "none" Workflows cell contradicts the role file and the seam workflows

**File:** `scripts/generate-catalog.ts:310`, :944-948; output in `docs/reference/agents/compliance-officer.md:11`, `docs/reference/agents/installer.md:11`
**Issue:**
- **The pages give a definite answer.** Plan 43.1-03 replaced `UNKNOWN - verify` with "none — no
  workflow's `## Agents involved` names this role".
- **The role files contradict it.** Both `agent-factory/roles/compliance-officer.md:21` and
  `agent-factory/roles/installer.md:19` say "read and write per
  `agent-factory/workflows/16-context-read-write.md`; compact per `.../18-context-compaction.md`".
- **So do the seam workflows.** The `## Agents involved` sections of WF16, WF17 and WF18 open with
  "Every role" or "Every role that takes a queued subtask".
- **The derivation cannot see them.** `AGENT_BULLET` only resolves display names, so an "Every role"
  bullet counts as unmatched and is dropped. The generator then states "none" as derived fact while
  the corpus says the role takes part in at least two workflows.
- **The literal wording is technically defensible but misleading.** "names this role" is true word
  for word, but a reader of a Workflows cell that says "none" will conclude the role is in no
  workflow.

**Fix:** Treat an `Every role` bullet as naming all roles, so WF16/WF17/WF18 are linked or counted
for every role. Alternatively, make the text say what was measured, for example "no SDLC workflow
names this role by name (every role runs the seam workflows 16 and 18)". At minimum, do not emit a
negative answer while `unmatchedBullets > 0` includes an "Every role" bullet.

### WR-07: `HTML_LINK_ATTR` silently skips an attribute at the start of a continuation line, contrary to its comment

**File:** `scripts/check-story-docs.ts:229-232`
**Issue:**
- **The comment promises multi-line tags are read.** It says "The attribute name follows whitespace,
  so a tag whose attributes run onto the next line is still read."
- **The regex cannot see an unindented continuation line.** `linkFindings` splits on `\n`, and
  `(?<=\s)` needs a whitespace character before the attribute *within the line*. A continuation line
  that starts at column 0 is not read. I measured this:
  ```
  lineLinkTargets('href="a.md">x</a>')   => []
  lineLinkTargets('  href="a.md">x</a>') => ["a.md"]
  ```
- **The result is a silent pass on a dead link.** That shape is common in markdown, for example the
  README art and `<p align>` blocks. The comment states the opposite.

**Fix:** Accept start-of-line as a boundary:
```ts
const HTML_LINK_ATTR = /(?<=^|\s)(?:href|src)\s*=\s*(?:"([^"]*)"|'([^']*)')/gi;
```
Add a case for it in `check-story-docs.test.ts`.

### IN-02: The overlap refusal message misdescribes identity hits and stat failures

**File:** `install/install.ts:3876` and :3855-3861
**Issue:**
- **An identity hit prints two unrelated-looking paths.** The message says "(real paths
  `/System/Volumes/Data/Users/u/repo/...` and `/Users/u/repo`)". Neither is a prefix of the other,
  so the user cannot see why they overlap.
- **A null `pathNodes` (a stat failure) says the wrong thing.** It is reported as "the real path of
  ... could not be read", even though the real path was read and a component's `stat` failed.

**Fix:** Have `kitHomeOverlap` return which test hit, and add "(the same directory by device and
inode)" for an identity hit. Say "its identity (device and inode) could not be read" when only the
`pathNodes` side is null.

### IN-03: A non-ENOENT lstat error on a stale runnable is worded as a user edit

**File:** `install/install.ts:1086-1092`, :1097-1110
**Issue:**
- **Other errors fall through.** An `lstatSync` failure such as `EACCES` or `ELOOP` still pushes the
  entry, and `owns()` then answers not-owned.
- **The user is blamed for it.** The verify reads "you have since edited or replaced it, or a link
  is on its way ... so it is yours". An unreadable path is not evidence of a user edit.

**Fix:** Carry `owns(...).reason` into the not-held wording, or give a separate "could not be
examined (CODE)" verify when lstat fails with another code.

### IN-04: The old-name runnable is removed even when the replacement was not written

**File:** `install/install.ts:10458-10461`
**Issue:**
- **The removal does not wait for the replacement.** `retireStaleRunnables()` runs after
  `materializeRunnable()` whatever the outcome. If `tools/grugops/skip-integrity.js` was blocked or
  its source was missing, the held `test-skip-integrity.js` is still removed.
- **The host is then left with no skip checker at either path.**
- **Workflow 05 can misread the result.** Node exits `1` for a missing script, and Workflow 05 reads
  exit `1` as a finding, not as could-not-run.
- **Also, the `removed` line never names the new path**, so a host CI step that calls the old path
  breaks with no pointer to the new one.

**Fix:** Consider keeping a held stale runnable while this run reported the same-source destination
as not written, or add "this kit installs the same program at <dest>" when a RUNNABLES row shares
the stale file's source basename.

### IN-05: `HTML_LINK_ATTR` also matches inside HTML comments and in bare prose

**File:** `scripts/check-story-docs.ts:232`, :248-253
**Issue:** `[x](a.md) <!-- href="gone.md" -->` yields `["a.md","gone.md"]`. Prose such as
`the href="x" form` outside a code span is also checked. This fails loudly rather than silently, so
it is low risk, but it can block on a commented-out link.
**Fix:** Strip `<!-- ... -->` spans the same way code spans are stripped before matching.

### IN-06: The `docs/skills.md` sentence registered as C-28-076 contradicts the same page

**File:** `docs/skills.md:9` vs. the "What install.js --check does" paragraph
**Issue:**
- **Line 9 is easy to misread.** It says `install.js --check` "only reports a declared skill it
  cannot find".
- **The same page says otherwise.** Further down it says "A skill it finds gives an `ok` line" and
  that an unseeable folder gives an advisory.
- **The registry row only keeps it true by reinterpretation.** It reads "only reports" as "does
  nothing but report", which a reader will not.

**Fix:** Reword to "`install.js --check` only reports on declared skills; it never installs one".

### IN-07: A user's own `.js` in `tools/grugops/` gets a note on every install

**File:** `install/install.ts:1154-1163`, :1168-1185
**Issue:** The presence path notes every unshipped and unrecorded `.js` in `tools/grugops/` on every
run, with no way to quiet it. That includes a directory whose name ends in `.js`. This is by design
(the adapter precedent), but it is noise for repositories that keep their own helpers next to the
kit's.
**Fix:** Filter to regular files, by lstat `isFile()`. Optionally limit the note to names matching
Node's default test globs, the actual D66 hazard.

### IN-08: `GRUG_AGENT_WORD` would flag ordinary prose such as "grug-brained"

**File:** `scripts/check-story-docs.ts:92`
**Issue:** `/(?<![\w./-])grug-(?=[a-z])/` matches any `grug-` followed by a lowercase letter. A
CLAUDE.md line about the "grug-brained developer" essay, a phrase the brand rules keep visible, would
be refused as a removed agent name.
**Fix:** Anchor to the removed agent stems, for example `grug-(?:orchestrator|[a-z]+-[a-z]+)\b`
derived from the role list, or exempt `grug-brain`.
