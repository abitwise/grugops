### WR-01: `install.js --check` (doctor) says nothing about a stale runnable, unlike stale adapters

**File:** `install/install.ts:1082-1164` (staleRunnables / retireStaleRunnables). The doctor's stale-adapter block is at `install/install.ts:3596-3604`.
**Issue:**
- **Still present, and deferred as P2 debt.** `staleRunnables` and `unrecordedStaleRunnables` are
  called only from `retireStaleRunnables`, which runs in the install run, not from `doctor()`.
- **The guide now documents the gap.** `install/README.md:258` says "`install.js --check` does not
  look for these files". A host whose plain `node --test` still runs
  `tools/grugops/test-skip-integrity.js` still gets a clean `--check`.

**Fix:** Mirror the stale-adapter block. In the doctor, report each `staleRunnables(ledgerRead)`
member through `staleRunnableText`, and each `unrecordedStaleRunnables(ledgerRead).paths` member as a
`note`. Then drop the "does not look" sentence from the guide.

### WR-02: Uninstall no longer names an unrecorded `tools/grugops/test-skip-integrity.js`

`RUNNABLES_MIRROR` destination nor a ledger entry. Report only; never remove it.

### WR-08: The OIDC condition does not require the token subject to name the repository, so an organization-wide trust policy meets it

**File:**
- **The prose restatements:**
  - `install/README.md:1822` (C-28-089)
  - `AGENTS.md:106`
  - `agent-factory/README.md:18-20`
  - `agent-factory/_commit-convention.md:77-78`
  - `agent-factory/config/factory.config.md:232`
  - `agent-factory/packaging/adapters.md:162-166` and `:180-185`
  - `agent-factory/workflows/05-pr-quality-gate.md:31`
  - `agent-factory/workflows/12-release.md:9`
  - `docs/concepts.md:8` and `:41`
  - `docs/faq.md:32-34`
  - `docs/how-it-works.md:73`
  - `docs/dogfood-human-runbook.md:51-53`
- **The generated and model text:** `scripts/audit-model.ts:336` and `:339`,
  `scripts/generate-guarantees.ts:752-757`, and `docs/GUARANTEES.md:35-40` and `:53`.
- **The main clause of the checklist item:** `install/README.md:1891` and
  `scripts/runnable-ref/host-protection.ts:1652`.

**Issue:**
- **What the words require.** Every restatement says the floor holds when "an OIDC trust policy
  accepts only tokens whose subject names that environment".
- **The words do not exclude other repositories.** A policy pinned to
  `repo:my-org/*:environment:production`, or to `*:environment:production`, "names that
  environment". It still accepts a token from any other repository in the organization (or, in the
  second case, any repository on GitHub) that has an environment called `production`.
- **Such an environment is easy to make.** GitHub creates a referenced environment that does not yet
  exist, with no protection rules. So anyone with write access to any repository in the
  organization can get a matching token with no reviewer. That defeats the floor the sentence
  vouches for.
- **Only two places pin the repository.** The checklist item's parenthesized example
  (`repo:<owner>/<repo>:environment:<name>`) and the citation paragraph at
  `install/README.md:1910-1922` ("accepts only that subject") do. The governing clause and all
  sixteen prose restatements do not.
- **The failure list misses this case.** It names "a branch or the whole repository" and not
  "another repository".
- **The registry hides it.** C-28-089 and C-28-090 are `status: true` on this wording.
- **Origin.** The prior review's own suggested fix for WR-04 had the same gap, and plan 43.1-10
  adopted it.

**Fix:** Make the subject name both the repository and the environment, and add the missing failure
case. For example:
```
... and an OIDC trust policy for the deploy accepts only tokens whose subject names this repository
and this environment (`repo:<owner>/<repo>:environment:<name>`, or the immutable
`repo:<owner>@<owner-id>/<repo>@<repo-id>:environment:<name>`), not a branch, the whole repository,
or a wildcard over repositories or owners
```
The short form for the pages is "accepts only tokens whose subject names this repository and that
environment". Update `ENVIRONMENT_FLOOR`, `SAFETY_FLOORS` and the enforcement section, then
regenerate `docs/GUARANTEES.md`. Update the verbatim blocks of the affected registry rows and
re-measure them.

### WR-09: The human is told to confirm the credential item "in the environment's settings", where it cannot be seen

**File:** `install/README.md:1924-1926`; `scripts/runnable-ref/host-protection.ts:1666-1668` (the text of the environment line printed by `tools/grugops/host-protection.js`)
**Issue:**
- **What the instruction says.** The guide says "Confirm each line of the production list above
  yourself, in the environment's settings on your git host". The check's environment line repeats
  this: "confirm each production line ... in the environment's settings yourself".
- **The credential item cannot be confirmed from that page.** Plan 43.1-10 widened it. It asks the
  human to make sure that:
  - no deploy secret sits in repository or organization secrets, in CI variables, on a runner or on
    a developer machine;
  - the cloud provider's OIDC trust policy (an AWS IAM role trust policy, a GCP workload identity
    provider condition, an Azure federated credential) accepts only the environment subject.
- **None of that is shown in a GitHub environment's settings.** A human who follows the instruction
  literally sees an environment with a reviewer, finds nothing wrong there, and ticks the line.
- **That is the case WR-04 was meant to close.** The deploy floor is the one item the check
  deliberately leaves to the human (33.1 D-31), so the place the human is sent to look decides
  whether the item is checked at all.

**Fix:** Name where each line is confirmed, in both the guide and the check's environment line. For
example: "Confirm the setting lines in the environment's settings on your git host, and the
credential line in the repository and organization secrets and variables, your runners, and the
trust policy of each cloud role the deploy assumes." Keep the README sentence and the
`environmentByDesign` reason text in step. Check whether a test pins the reason text, such as
`host-protection.test.ts`.

### IN-09: The guide says `--migrate` always retires stale runnables, but `--migrate` on an already-migrated target exits before the install run

**File:** `install/README.md:238-240` and `install/README.md:515-517`; the exit is at `install/install.ts:8948-8995`
**Issue:**
- **What the guide says.** The new subsection says install compares the ledger "on every run, and so
  does `--migrate`, which continues into the install run". The touch list says "A re-install or
  `--migrate` also removes a program an earlier kit installed there".
- **One arm stops early.** The `layout.isMigrated && state !== "pre-v3"` arm of `--migrate` ends with
  `process.exit` at `install/install.ts:8995`. That is before `materializeRunnable()` and
  `retireStaleRunnables()` at `:10460-10461`.
- **The effect.** On a target already on the two-root layout and the current state layout,
  `--migrate` neither removes nor notes a stale runnable.
- **The registry does not cover this arm.** C-28-088's re-measure covers only the D66 `--migrate`
  test, which takes the continuing arm.

**Fix:** Say "a `--migrate` that continues into the install run (one that has a layout to move)". An
alternative is to run `retireStaleRunnables()` in the already-migrated arm too.

### IN-10: The two-part definition reads as complete, but both parts hold trivially for a deploy that no Actions job runs

**File:** `install/README.md:1820-1824`, `install/README.md:1891`, and the restatements listed under WR-08
**Issue:**
- **The new form of the condition.** Since plan 43.1-10, "the deploy credentials live solely in the
  production environment" is followed by a colon and two parts: a stored-secret part and an OIDC
  part.
- **Two kinds of deploy satisfy both parts trivially.** One is a hosting platform's own Git
  integration, which deploys on a push to `main`. The other is a pull-based GitOps controller. Both
  hold their credential outside GitHub and use no Actions trust policy. A reader can tick both parts
  even though the environment's reviewer never sees such a deploy.
- **The earlier wording handled this case.** "Live solely in that environment's secrets" required
  the credential to be in the environment's secrets, so these deploys failed it.

**Fix:** Add a clause such as "and every production deploy runs as a job that references this
environment". Alternatively, name platform-held and pull-based deploys in the "can deploy without
its reviewer" list.
