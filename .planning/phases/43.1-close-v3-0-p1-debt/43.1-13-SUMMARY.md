## GitHub pages read (Task 1)

Both pages were fetched on **2026-11-20 at 10:06 UTC** with `curl -sS -L`. Each returned **HTTP 200 with 0 redirects**, and the final URL was the one requested. The quotes below are copied verbatim from the HTML-stripped pages.

**`https://docs.github.com/en/actions/reference/security/oidc`** (HTTP 200, 0 redirects)

- Environment subject: "Syntax: repo:ORG-NAME/REPO-NAME:environment:ENVIRONMENT-NAME" and "Example: repo:octo-org/octo-repo:environment:Production". The page introduces it with: "The subject claim includes the environment name when the job references an environment."
- Immutable default: "To help prevent this scenario, repositories created after July 15, 2026 now use an immutable default subject format that includes both the owner ID and repository ID. This rollout does not include GitHub Enterprise Server."
- Immutable branch syntax and example: "Syntax: repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/BRANCH" and "Immutable format example: repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main".
- Repo segment: "For repositories using immutable subject claims (not available on GitHub Enterprise Server), owner_id and repo_id are always included in the repo segment of the sub claim, even when you customize claims with include_claim_keys. You can't remove these IDs from the immutable format."
- Enterprise Server: "Immutable subject claims are not available on GitHub Enterprise Server."

**`https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments`** (HTTP 200, 0 redirects)

- "Deployment protection rules require specific conditions to pass before a job referencing the environment can proceed."
- Re-read for the stored-secret part: "Secrets stored in an environment are only available to workflow jobs that reference the environment. If the environment requires approval, a job cannot access environment secrets until one of the required reviewers approves it."

**How the immutable environment subject was composed.** The OIDC page prints the immutable format only for branch subjects. A count of `@123456/octo-repo@456789:environment` in the stripped page gives 0. So `repo:<owner>@<owner-id>/<repo>@<repo-id>:environment:<name>` comes from two statements:

- the immutable branch syntax, which keeps the `repo:` segment ahead of the qualifier;
- the sentence that `owner_id` and `repo_id` "are always included in the repo segment of the sub claim".

Those two are put together with the environment syntax. The install guide says this in words ("a form composed from those two statements that the page does not print as one example"). The page shows no immutable environment subject in any other shape, so row C2 stands as the human decided.

**What each quote supports:**

- The job part of L2, row J and the no-such-job sentence rest on the protection-rules quote.
- The repository part and the wildcard failure rest on the environment syntax. The subject names the owner and the repository before the environment. So a policy with a wildcard over that segment accepts a token from another repository's job. That follows from the syntax and is not a GitHub sentence. The guide says nothing about how GitHub creates environments.
- The stored-secret part still rests on the environment-secrets quote.
