# 999.14 — Upstream design sources, build requests and a universal consultant (idea)

Captured 2026-11-24 by the human, from a design discussion after the v3.0.0 release. It refines 999.13 and does not replace it.

## The problem

The human runs a separate design system that turns an idea into an approved design package. The first case is a game-studio repository of Claude Code agents. Its package holds the design, UX, technical architecture, art and audio documents, plus ledgers of decisions, questions and sources with stable IDs. A named human (the director) decides, and a locked decision changes only by supersession.

When the human creates a new repository and starts grugops to build the product, grugops cannot see that package. No role can look up, refine or change a requirement that came from upstream. A consultant inside grugops would make up answers to questions upstream has already decided, or should decide. That is fabrication, and it lets the design and the code drift apart.

## Ownership split (proposed)

- Upstream owns **what the product is**. grugops owns **how it is built**. BA/PM translates between them.
- A change to what the product is goes back upstream as a build request. grugops never decides it.
- A human carries requests across, because in both systems a human decides. grugops never writes into the upstream repository.

## Scope (grugops side)

1. **Declared upstream sources.** A config key (name TBD) declares one or more read-only design sources. Each source is pinned by commit, with a blob hash for its entry file. Roles read the source in place and never copy it into `memory-bank/` state: a package runs to hundreds of KB, far over the state byte budgets. The Orchestrator reports a pin that no longer matches the source.
2. **Traceability upstream.** BA/PM tickets cite upstream IDs, so the trail runs from the upstream decision to the requirement, the code, the test and the release.
3. **Build requests.** A role may need something the sources do not answer, or a requirement changed. It writes a build request file in the grugops repository and reports a new status (name TBD). The file holds the question, the upstream IDs it touches, the options with a recommended default, and what is blocked. The ticket stays blocked until a new pin answers it. An upstream answer enters the shared context as a `claim` note that cites the upstream ID and the pin, never as a `finding`.
4. **Universal consultant.** One parameterized role takes a topic and a lens.
   - **Dispatch.** Only the Orchestrator dispatches it, on a `CONSULT` request from BA/PM, the System Analyst, the Architect or the Designer, or on a human's request. Engineers, QE and Release do not request it.
   - **Order.** It first answers from the declared sources and cites them. Beyond them it answers only questions outside the upstream owner's scope, such as platform certification, privacy, store rules or implementation tradeoffs. Each answer has a source or is marked `UNKNOWN - verify`, and is written as a `claim` or `observation` note.
   - **Upstream questions.** A question in the upstream owner's scope becomes a build request, never an opinion.
   - **Panel mode.** Several lenses each argue a stated position, such as customer, operator, finance, regulator or skeptic. The output ends with where they disagree and why, not with an averaged consensus. Copies of one model with different personas give correlated answers, so the disagreement section is the deliverable. Panel members may run on different tiers through the `models` dial.
   - **Dial.** A single consult in lean mode and a panel in enterprise mode (dial name TBD). With no config, a consult runs only on request.
5. **Architecture as input.** When upstream sources include a stack or architecture decision, the Greenfield Mapper and the Architect take it as given input. A deviation from it is a build request.

## Constraints to settle first

- **Role byte budget.** All role text is about 61 KB (`wc -c agent-factory/roles/*.md`, 2026-11-24), against the guard's warning at 64,000 B and its fail at 67,383 B. The consultant role must stay near 2 KB, with its procedure in a new workflow, as Phase 40 D-05 prescribes for detail.
- **New board status.** The new status needs support in the validator and in `state-check`. It is additive, so existing repositories stay valid.
- **Files first.** The first version is file-based and works on all six host CLIs. A live link (an MCP server or CLI exposed by the upstream system) is out of scope until carrying files becomes a burden.
- **Relation to 999.13.** This item keeps 999.13's advisory-only rule. It replaces "one consultant per purpose" with one parameterized role; on 2026-11-24 the human leaned towards a universal consultant, which is not yet a decision. Packs (ratified domain content, which needs the PROJECT.md Out of Scope line amended) stay in 999.13 and can follow later.
- **The upstream side is not grugops work.** The upstream system needs a build handoff (an export manifest of approved artifacts, pinned by commit) and a way to take in build requests. Its format should settle before grugops fixes the shape of the source declaration.

## Open decisions for the human

- Who owns the technical architecture when upstream provides one. Proposed: upstream, with grugops taking it as input.
- Whether to start building before upstream's final go/no-go gate. One option: a prototype built only on decisions locked at upstream's first gate.
- The names of the new status and the config keys.

## Release sizing

The change is additive: a new role, a new workflow, a new status and new config keys, with no change to the state layout. Under SemVer that is MINOR, `3.1.0` (tag `v3.1.0`). One v3.1 milestone can hold this item together with 999.13's consultant core; packs can split out.
