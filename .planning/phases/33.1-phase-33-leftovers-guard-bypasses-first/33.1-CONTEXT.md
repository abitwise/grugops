## Implementation Decisions

These decisions bear on production-deploy and protected-merge safety, so they use clear professional voice.

### Guard retirement (2026-09-26, supersedes D-01 to D-05 and D-08)
- **D-17:** RETIRE the Bash command-parsing guard entirely. grugops no longer decides, from a
  shell string, whether a command is a production deploy or a protected merge. Thirty-three phases
  showed that approach cannot be closed: each round of per-arm fixes, and the canonical-form
  cutover in progress, produced new bypasses (CR-01, CR-02, the alias and spliced-variable forms).
  Removed: the `Bash` PreToolUse matcher in `hooks/hooks.json`, `hooks/guard.ts`/`guard.js` and
  its tests and corpus, the command model in `scripts/checkpoints.ts` (`COMMAND_CHECKPOINT_RULES`,
  `governedToolsNamedBy`, `classifyWords`, `failClosedCheckpoints`, `matchCommandCheckpoints` and
  what only they use), and the `GRUGOPS_PROD_DEPLOY_APPROVED` / `GRUGOPS_FLOOR_*` grant keys for
  those two checkpoints. The planner derives every consumer of the removed code (at least
  `scripts/audit-model.ts`, `generate-guarantees.ts`, `check-platform-shapes.ts`,
  `check-diff-disposition.ts`, `validate-agent-factory.ts`, `kit-model.ts`, `context-io.ts`,
  `frontmatter.ts`, `hooks/hook-entry.ts` import `checkpoints`) and counts them. It does not
  hand-list them. Checkpoint config keys (`checkpoints.protected_branch_merge`,
  `production_requires_human_confirmation`) STAY, because the installer now reads them (D-18).
  — **Reversibility:** costly — undoing it means restoring ~6k lines of guard code and corpus
  from git history, plus re-publishing guarantees the docs will no longer make.
- **D-18:** The installer translates the checkpoints config into Claude Code `permissions.ask`
  rules in `.claude/settings.json`: `protected_branch_merge` → `git push`/`gh pr merge` rules;
  `production_requires_human_confirmation` → the deploy tools the retired rule table named
  (kubectl apply/rollout/delete, helm upgrade/install, terraform apply, gcloud deploy, aws
  deploy/sync, serverless/sls, fly/flyctl deploy, vercel --prod, and the npm/yarn/pnpm publish
  forms). The installer contract holds: idempotent, additive, dry-run, reversible, never
  overwrites or deletes a user's own rules, and uninstall removes only what install added. The
  other four CLIs get per-tool documentation of their approval modes, not generated config.
  **These rules are a SPEED BUMP, not the guarantee.** Every document says so. The client-side
  protection that actually works is not allow-listing arbitrary Bash, so any command that isn't
  allowed prompts for approval.
- **D-19:** Git-host protection is the hard floor. grugops ships a setup checklist (branch
  protection or rulesets on protected branches: PR required, review required, no force push;
  deployment environments with required reviewers for prod), plus a READ-ONLY `gh api` check that
  the gate and release roles run. The check reports `protected`, `unprotected` or
  `UNKNOWN - verify` (no `gh`, no auth, no permission). grugops never configures the host itself.

  `.claude/agents/grugops-*.md`, skill `.claude/skills/grugops*/**`) that the user edited. Install
  **asks the user whether to back up the edited files and then overwrite**. The human's words: "Ask
  if user wants to back up and then overwrite. It would be risky if some kit files are updated and
  the ones that were edited are not." So the choice is **all-or-nothing for the kit**: detect every
  edited kit file first (against the `kitFiles` record; a file with no record that differs from
  the current kit source counts as possibly edited), before any kit write. Then either back up all
  of them and overwrite the whole kit, or change nothing in the kit. Never refresh the unedited
  files and skip the edited ones, because that leaves a mixed-version kit. Where no human can answer
  (no TTY, an agent-run install): the answer is not assumed. Install changes nothing in the kit and
  says how to opt in (for example an explicit flag). DRY_RUN lists the files it would back up.
  — **Reversibility:** reversible (installer behaviour; backups keep user content recoverable).
