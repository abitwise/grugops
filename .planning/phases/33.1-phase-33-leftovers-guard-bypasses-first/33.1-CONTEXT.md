<decisions>
## Implementation Decisions

These decisions bear on the prod-deploy guard, a safety surface, so they use clear professional voice.

### Guard design (CR-01, CR-02, D-33-R4-06)
- **D-01:** CR-01 and CR-02 are closed by a CANONICAL-FORM CUTOVER, not by per-arm fixes. Any
  segment that names a governed tool, directly or through the nested re-projection
  (`governedToolsNamedBy`, `scripts/checkpoints.ts`), must consist entirely of plain literal words
  separated by whitespace. Anything outside that canonical form is REFUSED ON THE NAME. That covers
  a brace list, a bare `$IFS`, any `$N`, `$var` or double-quoted run containing an unescaped `$`,
  a backslash or quote splice, and a whitespace-free nested word. The canonical form is an
  allow-list: the guard refuses everything outside it and does not enumerate bad shapes. This is
  the P27 D-64 pattern, and it closed a class that per-arm widening had failed to close for eleven
  rounds. The review's targeted fixes (a whitespace-free-word refusal; classifying `"…$…"` as
  opaque in `classifyWords`) were considered and rejected as the per-arm pattern.
  — **Reversibility:** costly — every corpus row, both hook entry points and the
  `failClosedCheckpoints` residual docblock are re-based on the canonical form.
- **D-02:** Two bypasses from Phase 33 `deferred-items.md` join the guard work and become DENY
  corpus rows: `git -c alias.p=push p` (git's own alias form of a push) and
  `bash -c 'x=g\it; $x push origin main'` (a spliced tool name assigned to a variable inside a
  nested body). Both ALLOW with zero keys today. Either one staying ALLOW after the cutover is a
  guard defect, not a residual.
- **D-03:** IN-02 (row 308) is handled inside the guard work. A launcher-shaped word (`npm`, `yarn`
  or `pnpm exec`, `git submodule foreach`, `git bisect run`, `git rebase -x`) never qualifies for
  the benign-adjacency exemption under an xargs stdin feed.
- **D-04:** The D-33-R4-06 narrowing (stop refusing an unreadable word when no governed tool is
  reachable) lands in a LATER guard wave, only after the D-01/D-02 bypass closures are red-teamed
  clean. The narrowing may exempt an unreadable word only when the COMMAND word is a literal member
  of a set of commands that cannot launch anything. That set must be DERIVED (from a source and
  counted), not hand-typed. It must exclude every launcher-shaped word (D-03), and an expansion in
  the command position is never exempt. If the set cannot be derived, the narrowing is deferred,
  row 269 stays open, and availability loses rather than safety. The narrowing must not widen any
  allow path that D-01 refuses.
- **D-05:** The proof bar before the guard is called closed:
  (a) WR-04 (row 306) is fixed FIRST: `runAll` resolves with stdout, exit code and signal, and
  every allow control also asserts code 0 and signal null;
  (b) DENY corpus rows for every mechanism (brace list, `$IFS`, positional in spelled, permuted and
  trailing-argument orders, the variants of R4-11 and R4-12, splice, alias, launcher under xargs)
  under all four wrapper families (`bash -c`, `sh -c`, `eval`, pipe-to-shell);
  (c) every row replayed through BOTH `hooks/guard.js` and `hooks/hook-entry.js`;
  (d) at least two independent opus red-team passes plus a self-reproduction of any reported
  bypass. Green tests alone are not proof (project memory: safety invariants).

### Phase structure and cap
- **D-06:** All carried work stays in one phase, 33.1, under one 4-round gap-closure cap (D-44).
  The guard is wave 1. The phase is NOT split into a separate 33.2.
- **D-07:** After the guard wave (D-01 to D-05) there is a BLOCKING HUMAN CHECKPOINT. The red-team
  results and the corpus replay go to the human, and no later wave starts without their go. A
  bypass found at that checkpoint is fixed inside the guard wave, never carried.
- **D-08:** The guard NEVER closes by human override. A reproducible prod-deploy guard bypass is
  never accepted open again, which is what happened to CR-01 and CR-02 at the Phase 33 close. If
  the cap is reached with the guard still bypassable, the phase stops, and the guard carries
  forward as the FIRST open item, unoverridden. This narrows D-20's override path for the guard
  only. — **Reversibility:** one-way — it removes an escape hatch the human would otherwise hold
  at the cap; relaxing it later needs a new recorded human decision.
- **D-09:** Every entry still marked `status: open` in Phase 33 `deferred-items.md` (11 of 22 at
  2026-09-25; the other 11 read `resolved` and are not reopened) is disposed in 33.1. Each one is
  fixed, given a WINDOWS.md row with an owner, or shown to be closed. None is silently dropped. The
  routing:
  - guard wave: `git -c alias.p=push p` and the spliced-`$x` body (D-02); the command-model
    regex throw on a large non-literal name piece; the GNU parallel stdin launcher
    `UNKNOWN - verify` (with IN-02, D-03); and the pinned-ALLOW residuals LB-08 (`help.autocorrect`)
    and RES-03 (xargs replace string assembling the tool name), re-examined against D-01. A
    residual stays pinned ALLOW only if the red-team confirms the canonical form cannot refuse it
    (computed at run time); otherwise it becomes a DENY row;
  - after the guard checkpoint: the admission-server bare-name docblock sites, the stale
    `grugops@grugops` 0.1.0 plugin rows (human-state cleanup, confirm before touching user
