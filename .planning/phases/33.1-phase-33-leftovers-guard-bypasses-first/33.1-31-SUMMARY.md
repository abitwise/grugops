# Phase 33.1 Plan 31: Kit Write All-or-Nothing Summary

**Two-phase kit write in install.js: buildKitPlan reads every kit source once, captures the rendered adapters in memory and asks one destination decision for every skill and adapter before the first kit write; any refusal (render, routing floor, source directory, or a link/FIFO/hard link/non-directory at any kit path) writes, links and unlinks no kit file, and --migrate now unlinks only install's own link, in the write phase.**

## Accomplishments

- `buildKitPlan()` (install.ts) builds the whole kit plan with no write: every skill (materialize/copy/link/missing from one `readUserFile` read), every adapter (the render is read into the plan inside the `renderAdaptersInMirror` callback, before the mirror is deleted, with the set, count, alias, routing-floor, banner and alias-set checks), then `kitDestDecision` over every destination. Every refusal is collected, not returned on.
- `executeKitPlan()` runs only when nothing refused. It writes from memory in the old order (skills, the relayed render/resolution lines, adapters). `materializeAdapter(entry)` and `copyKitFile(entry)` re-ask the same decision at the write.
- `kitDestDecision()` is the one destination rule, asked in both phases. The write bound (adapterDestHazard) comes first for a materialize entry, then readForWrite (FIFO, directory, hard link, too-large, link or non-directory on the way), then the identical-skip.
- `--migrate` Pitfall 1: migratePreSteps step 3 no longer unlinks anything. It sets `KIT_MIGRATE_OWN_LINKS`, and the plan marks `unlinkFirst` only for install's own link (`isOwnLink` against the kit source path uninstall also uses). The unlink happens in the write phase, just before that file is written. Any other link there is a refusal. This closes the dc2 carry "--migrate unlink removes ANY link at an adapter path".
- On a refusal: one counted `verify` per refusal plus a `kit` line saying no skill or adapter was written, linked or unlinked. `kitFiles` is carried unchanged by writeMarker's existing rule.

## Decisions Made

- The pre-flight includes every destination check, not only the plan's list (render, alias, slot, source directory). A link, FIFO, hard link, dangling link or non-directory at or on the way to any kit path refuses the kit (orchestrator instruction). Plan 26's per-path refusals are now decided before the first kit write.
- `--migrate` removes only install's own link (the dc2 carry from plan 27, as the orchestrator directed). "Own" is `isOwnLink(dest, <kit source path>)`: `.claude/agents/<f>` for an adapter, `.claude/skills/<s>/SKILL.md` for a slot-carrying skill. This is the same path uninstall's removeKitAdapters and removeKitSkills treat as install's link.
- Render-level refusals (the render failed, set mismatch, count mismatch) still stop the per-member checks, which would be meaningless after them. Per-member refusals are all collected. The alias-set cross-check runs only when every member produced an alias.
- The nested-adapter findings (flat contract, cycles, unreadable nested directory, work bound) stay per-path verifies after the kit step. They name files outside the flat install set, so they cannot produce a mixed kit.
- `srcCarriesSlot(path)` became `carriesSlot(text)`, so each source is read once and routed on those bytes. `linkOrCopy` lost its `isKitFile` parameter, and its only caller now is AGENTS.md.

## Residual risk

- **The write phase (stated, T-33.1-312 accepted):** a filesystem error while the kit is written (EACCES on one file) leaves a partly written kit. It is a counted verify naming the file, and the next run's pre-flight sees the state.

### Decisions

- **Non-kit migration steps are gated (the question the orchestrator asked).** A `--migrate` whose pre-check refuses performs none of them. Two other options were rejected. Running them and letting the re-run recover would have needed a new marker field or a change to `isMigrated`. Running them without writing the marker would have left the created files unrecorded. The pre-check covers everything knowable before the first change: the config carry's refusals and every kit refusal. So a blocked legacy config or a FIFO at the seeded config now stops the migration too, and their "re-run --migrate" remedy is true.
- **The observation (a refused run's kitFiles).** The behaviour is kept, and the truth is made precise in the README instead. A run that refuses the kit carries forward every earlier `kitFiles` entry whose file still holds what install wrote. It drops only an entry this run proved stale; the red-team's example was a hard-linked skill, 24 entries down to 23. That is the rule every other run applies. It is the safe direction, because uninstall would leave that file anyway. Carrying the stale entry unchanged would keep a record that proves nothing. Plan 33.1-32's truth "kitFiles keeps its previous state" should be read with this precision.
  - **Superseded by the plan 33.1-32 red-team fixes (B1, 2026-09-30).** A run that writes no kit file, for any reason, now writes `kitFiles` back verbatim; nothing is dropped. The staleness proof of a refused run can be wrong about a file the user will then restore: with an edited adapter and a directory at another adapter, the refused run dropped both entries (24 → 22), and after the user removed the directory and restored the edit, uninstall left the restored file with "no record", so the remedy the verify gave was false. Keeping the entry is not a carry by presence at uninstall, which still removes a kit file only while it holds its record. Dropping remains the rule only in a run that writes the kit, where the entry is replaced. See 33.1-32-SUMMARY.md, "Red-team fixes (brief §3)".
- A seventh mid-script `process.exit` (the refused `--migrate` must stop before the handoffs backup and the install run). The pinned count in install.test.ts is now 7, and 8 counting the mention in prose.

### Residual

- The write phase can still fail on something the checks cannot see, such as a full disk, an ACL access(2) does not reflect, or a change between the plan and the write. It is still the stated T-33.1-312 residual: a counted verify naming the file.
- In a `--migrate`, the kit is rendered with the legacy config before the pre-steps run. If the carry's own write then fails, the adapters carry that config while `.grugops/factory.config.json` is absent. That is a counted verify, and the next install re-renders.
- A collision is refused on a case-sensitive target too, where the two names would be two files. This is deliberate: the target is not probed.
- On platforms other than Linux, PATH_MAX is the conservative 1024.
- `--check` still reports install's own link at an adapter path through adapterDestHazard (a link hazard). The remedy it prints (re-run) is correct, because install now replaces that link.
