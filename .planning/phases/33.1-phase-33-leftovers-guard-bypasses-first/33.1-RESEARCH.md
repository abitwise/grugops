## Research question answers

### Q1. Do CC `permissions.ask` Bash rules match through wrappers, compound commands and nested shells?

**Partly, and the docs say exactly where the edge is.** [CITED: code.claude.com/docs/en/permissions, "Compound commands", "Wrappers", "What a Bash rule doesn't match"]

- **Matched:** each subcommand of `&&`, `||`, `;`, `|`, `|&`, `&`, newline; "a command nested inside a subshell, a command substitution, or a control-flow body such as a `for` loop"; after stripping `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, and bare `xargs` (no flags); and "A deny or ask rule matches past any leading assignment".
- **Not matched:** "the same program invoked in a different form" — a path-qualified program, a `sh -c`/`bash -c` body, options before the subcommand, a quoted subcommand. The docs conclude that such a rule "covers the invocation Claude usually produces and isn't a security boundary around the program."
- Ask rules win over allow rules: "a matching ask rule prompts even when a more specific allow rule also matches the same call."
- Hooks cannot override them: "a matching ask rule still prompts even when the hook returned `"allow"`."
- `deny` and `ask` rules in a project `.claude/settings.json` are NOT gated by workspace trust ("`deny` and `ask` rules aren't affected, since they only restrict"). Allow rules are.

**Measured this session (zero tokens, stub binaries first on `PATH`, CC 2.1.283, `-p --permission-mode default`, the command allowed by `--allowedTools` so that only the ask rule can stop it):**

| Rule shape | Command shape | Result |
|------------|---------------|--------|
| `Bash(helm upgrade *)` | leading `FOO=bar` assignment | denied (matched) |
| `Bash(helm upgrade *)` | `timeout 30` wrapper | denied (matched) |
| `Bash(npm publish *)` | second half of `&&` | denied (matched) |
| `Bash(npm publish *)` | inside `$( )` | denied (matched) |
| `Bash(kubectl apply *)` | a flag between tool and verb | **ran** (not matched) |
| `Bash(kubectl * apply *)` | a flag between tool and verb | denied (matched) |
| `Bash(kubectl * apply *)` | `kubectl apply -f x.yaml` | **ran** (not matched) — the mid form needs a word between |
| `Bash(gcloud * deploy *)` | `gcloud run deploy svc` | denied |
| `Bash(gcloud * deploy *)` | `gcloud run deploy` (nothing after) | **ran** |
| `Bash(gcloud * deploy)` | `gcloud run deploy` | denied |
| `Bash(gcloud * deploy)` | `gcloud run deploy svc` | **ran** |
| `Bash(terraform * apply)` | `terraform -chdir=infra apply` | denied |
| `Bash(vercel *--prod*)` | `vercel --prod`; `vercel deploy --prod` | denied (both) |
| `Bash(git push *)` | bare `git push` | denied |

Consequence: each governed verb needs three rule forms (§ Installer design). The wording "speed bump" is accurate at every strength of this answer.

### Q3. Settings precedence and merge semantics

[CITED: code.claude.com/docs/en/settings, "Settings precedence", "Lists merge instead of overriding"; code.claude.com/docs/en/permissions, "Settings precedence"]

- Precedence, highest first: managed → command-line arguments → `.claude/settings.local.json` → `.claude/settings.json` → `~/.claude/settings.json`.
- **Permission lists merge across scopes** ("each file can add entries without removing another file's"); deny then ask then allow, first match wins, across all scopes.
- So an installer rule in `.claude/settings.json` cannot be neutralised by a user's `allow` in any file; only removing the ask entry (or a managed `allowManagedPermissionRulesOnly`) removes it.
- CC reads the shared `.claude/settings.json` "from the session's primary working directory"; it reloads settings on change mid-session.
- `.claude/` is a protected path: agent writes to it prompt in `default`, go to the classifier in `auto`, are allowed in `bypassPermissions` [CITED: permission-modes#protected-paths]. So an agent can remove the rules only through a prompt (default) or a classifier decision (auto). This is a speed-bump property, stated as such.

**For install/uninstall this means:** write only into `permissions.ask` of the target's `.claude/settings.json`; never touch `settings.local.json` or user settings; never remove an entry the install did not add.

## Common Pitfalls

### Pitfall 1: The hook manifest makes every admission call deny
`hooks/hook-entry.ts` carries a generated SHA-256 manifest of each decider's import closure. `hooks/admission-guard.js`'s closure includes `scripts/checkpoints.js` and `scripts/context-io.js` (`hooks/hook-entry.ts:252-266`). Editing either and rebuilding with `npm run build` alone leaves stale hashes, and the wrapper then denies every MCP admission call. **Avoid:** after any edit, run `npm run generate:hook-manifest` (it rebuilds), then `npm run freshness:hook-manifest`; commit `hook-entry.ts/.js` with the change.

### Pitfall 2: Tests that index `PreToolUse[0]` silently change meaning
After the Bash entry goes, index 0 is the MCP matcher. These sites assume Bash at index 0 or look it up by name: `scripts/check-uat-oracles.ts:428-440`, `scripts/check-uat-oracles.test.ts:256,267`, `scripts/check-foundation-guards.test.ts:7977`, `scripts/nonblocking-reader-parity.test.ts:706`, `scripts/floor-invariance.test.ts:824`, `scripts/context-io.test.ts:12173-12178`. A mutation test that "breaks" index 0 now breaks the admission wiring, and may still go green for the wrong reason. Re-derive each assertion's intent.

### Pitfall 3: The installer ledger is overwritten on re-install
See § Installer design. Test 4 there catches it.

### Pitfall 4: The retirement orphans the two-key floor for all four floors
`evaluateMatrix`, the banner and `emitCheckpointNote` have no production caller after `hooks/guard.ts` goes. Docs that keep describing `GRUGOPS_FLOOR_OPEN_PR` or a printed banner then describe a mechanism nothing runs, which violates D-20(b). Resolve Open Question 1 before the doc wave.

### Pitfall 5: `gh api` turns a read into a write
Passing `-f`/`-F` makes it a POST. The runnable passes no fields, pins `--method GET`, and a test asserts the argv.

### Pitfall 6: Ask rules exist only where the installer ran
The plugin form cannot ship permission rules (plugin `settings.json` honours `agent` and `subagentStatusLine` only). The four other CLIs get docs. `install/README.md` §5 must say which install path gets the speed bump and which gets none.

### Pitfall 7: The CLAUDE.md regeneration trap
The project block is generated from `.planning/PROJECT.md`, and the stack block names a source whose content has moved on. Edit PROJECT.md:218 with CLAUDE.md:15. Hand-edit the stack block, and never run a stack regeneration in this phase.

### Pitfall 8: The executor's roadmap update marks 33.1 Complete early
Project memory. The last plan of each wave checks the ROADMAP 33.1 line and reverts it on `gaps_found`.

### Ask-rule forms from one table

```ts
// install/checkpoint-ask-rules.ts (sketch; the row data is transcribed from the retired table, scripts/checkpoints.ts:785-843)
type Row = { checkpoint: "protected_branch_merge" | "production_requires_human_confirmation"; tool: string;
             verbs?: readonly string[]; flags?: readonly string[]; midOnly?: boolean };
export function askRulesFor(rows: readonly Row[], checkpoint: Row["checkpoint"]): string[] {
  const out: string[] = [];
  for (const r of rows.filter((x) => x.checkpoint === checkpoint)) {
    for (const v of r.verbs ?? []) {
      if (!r.midOnly) out.push(`Bash(${r.tool} ${v} *)`);   // A: also matches the bare "<tool> <verb>"
      out.push(`Bash(${r.tool} * ${v} *)`);                  // B: flags before the verb, args after
      out.push(`Bash(${r.tool} * ${v})`);                    // C: flags before the verb, nothing after
    }
    for (const f of r.flags ?? []) out.push(`Bash(${r.tool} *${f}*)`);
  }
  return out;
}
```

## Security Domain

`security_enforcement` is on (ASVS L1, block on high). The phase **removes** a defensive control and replaces it with two others. The security argument must therefore be explicit about what each tier does and does not do.

### Applicable ASVS Categories

| ASVS category | Applies | Control in this phase |
|---------------|---------|-----------------------|
| V1 Architecture | yes | Enforcement moves to the system that owns each action: git host for merge/push, deployment environments for deploy. Tiers published honestly (D-20(b)). |
| V2 Authentication | no | — (the host check uses the operator's existing `gh` auth, read-only) |
| V4 Access control | **yes** | Hard floor: host branch protection/rulesets and environment required reviewers. Speed bump: CC ask rules. Admission gate unchanged (D-24). |
| V5 Input validation | yes | Installer parses a user-owned JSON file fail-closed (unparseable → untouched + `verify`). The host check parses `gh` JSON output fail-closed (anything unexpected → `UNKNOWN - verify`). |
| V6 Cryptography | no (reused) | The hook manifest's SHA-256 (`node:crypto`), regenerated, not changed. |
| V7 Error handling/logging | yes | The host check never reports `protected` on an error. The installer reports every rule it did not add or did not remove. |
| V14 Configuration | **yes** | `.claude/settings.json` is now a grugops-written security configuration. Protected path in CC (agent edits prompt in `default`). Ledger-based reversal. |

### Threat patterns and mitigations

| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Agent spells a governed command in a form an ask rule does not match | Elevation of privilege | Accepted by design (vendor-documented). The host floor refuses the push or merge, or holds the deploy job. Docs say "speed bump". |
| Agent removes the ask rules from `.claude/settings.json` | Tampering | CC protected path: a prompt in `default`, the classifier in `auto`, allowed only in `bypassPermissions`. The host floor still holds. |
| Operator runs with no host protection configured | Elevation of privilege | The host check reports `unprotected` / `UNKNOWN - verify` at every gate and release run; the checklist ships; grugops never claims the floor exists without the check. |
| Host check mis-reports `protected` | Spoofing (false proof) | Only positive evidence yields `protected` (ruleset rule types, or admin-visible PR/review/no-force-push). Every ambiguous status maps to `UNKNOWN - verify`. The stub-`gh` tests cover both 404 bodies. |
| Host check performs a write | Tampering | No field flags, `--method GET` pinned, argv asserted in tests. |
| Installer deletes a user's own rule | Tampering / repudiation | Ledger of added rules; uninstall removes `ledger ∩ present` only. Test 3 in § Installer design. |
| Self-set grant visibility lost for `GRUGOPS_ADMISSION_APPROVED_BY` | Repudiation | The guard's inline self-set refusal was a visibility control, not the access control (`scripts/checkpoints.ts:241-246`). Access control is unchanged: the hook's own process environment. GUARANTEES residual row 9 (settings-file `env` injection) still applies to the admission grant; keep it, re-scoped. |
