## Summary

Every named bypass reproduces on HEAD `e81b533b` through both hook entry points with a scrubbed environment. Each is also executable: under bash, a stub binary received the full governed argv, and a real `git` pushed to a scratch bare remote. The committed `.js` files are a faithful build of their `.ts` sources.

Three facts matter most for planning, and each changes what the plan must contain.

**First, D-01 as worded is necessary but not sufficient.**
- D-01 triggers on "a segment that names a governed tool". Two locked D-02 rows never trigger it:
  - `bash -c 'x=g\it; $x push origin main'`: no segment at any depth names a tool. The only tool name sits inside an assignment value, which `governedToolsNamedBy` does not read as a name. The tool actually runs from `$x` in the command position.
  - `git -c alias.p=push p`: every word is already a plain literal.
- So the plan needs two rules beside the canonical-form shape rule:
  - a command-position expansion rule (C3);
  - a git config-injection rule (C4), because git's alias surface is wider than one `-c`: `--config-env`, `GIT_CONFIG_COUNT/KEY/VALUE`, `GIT_CONFIG_PARAMETERS`, case-folded `ALIAS.p`, the `alias.p.command` subsection form, a deprecated-command alias, and `git config alias.x push && git x`. All nine measured forms pushed `main`, and all nine ALLOW today.

**Second, the fix direction is cheap in availability. This is measured, not argued.**
- The corpus: all 236 real agent Bash commands from the two committed live captures (rounds 1 and 4, paths A and B).
- The two canonical-form refusals D-01 names add **zero** new denials:
  - a double-quoted run holding an unescaped `$` in a segment that names a governed tool;
  - re-reading a whitespace-free quoted value that names a governed tool.
- The command-position expansion rule adds 4 or 5 of the 216 currently allowed commands (C3a). An "expansion plus a literal governed verb" rule adds 2 (C3b). A broad "any expansion" rule would add 57, so it is rejected.

**Third, the D-04 narrowing cannot meet its own derivation bar.**
- The only authoritative source for "commands that cannot launch anything" is Claude Code's read-only list. It is published as "The set includes …", which is non-exhaustive. It contains exec-capable members (`find`, `git`).
- Even granted that list, the narrowing recovers **1 of 17** measured over-denials. The other 16 name `npm` or `git` directly, so no "no governed tool reachable" rule can recover them.
- Recommendation: defer D-04 by D-04's own rule. Row 269 stays open.

Two items outside the guard were settled at zero tokens this session:
- **The permission mode.** A local mock of the Messages API was used, so no model call and no spend. With the operator's real config (`defaultMode: "auto"`), `claude -p --permission-mode default` DENIES an out-of-target `Write`:
  - on the main thread, and in a spawned subagent;
  - without the flag, the session inherits `auto`;
  - an in-target `Write` is allowed by the runner's scoped `Edit(//…/**)` rule.
  - This is the measurement D-11(a) requires.
- **The nesting correction.** `code.claude.com/docs/en/sub-agents` states that subagents nest three layers deep by default. So row 309 is corrected from a primary source, and there are three CLAUDE.md sites, not one.

**Primary recommendation:** do these in order.
1. Fix WR-04 first, across all 16 stdout-only allow sites, not only `runAll`'s 3.
2. Land one canonical-form authority in `scripts/checkpoints.ts`, made of rules C1 to C5 below.
3. Re-base the corpus on a derived matrix of mechanism × family × arm (clean body and trailing-opaque body), plus pipe-to-shell.
4. Replay through both entry points with positive allow proof (exit 0, signal null, and the fd-3 allow token on the direct run).
5. Red-team twice.
6. Stop at the D-07 checkpoint.

## Architecture Patterns

### How a command reaches the decision (every arm, and what the input is built from)

```
Claude Code PreToolUse(Bash)
        │  stdin JSON: {tool_name, tool_input.command, session_id, …}
        ▼
hooks/hook-entry.js guard.js ──► verify decider-closure manifest (hash of every .js in guard.js's import closure)
        │                          mismatch / FIFO / unreadable ─► wrapper's own fail-closed DENY
        ▼ spawnSync(node guard.js), stdin passed through, fd 3 = private allow channel, bounded timeout
hooks/guard.js
  1. read stdin → cmd (string) [malformed → "" → allow-only-non-deploys]
  2. read governance config (trustedRepoRoot) → matrix; banner → stderr
  3. SELF_APPROVE regex over cmd (grant vars) ─► DENY
  4. modelled = matchCommandCheckpoints(cmd)        ◄── the ONE model (scripts/checkpoints.js)
  5. per checkpoint group: byPattern (literal regexes over cmd) OR byModel ─► matrix/two-key ─► DENY | continue
  6. allow(): write "grugops-hook-allow" on fd 3, exit 0
```

**The model's input is `tool_input.command` and nothing else.** It sees no environment, no cwd contents, no git config and no earlier commands. Every class whose value comes from outside the string is out of reach by construction:
- host `~/.gitconfig` aliases and `help.autocorrect`;
- an alias persisted by an earlier call;
- a file written with the Write tool and then executed;
- `PATH` shims.

**`matchCommandCheckpoints` has these arms, all verified in `scripts/checkpoints.ts:1768-1922`:**
1. `commandSegments(cmd) === null` means unbalanced input or depth > 3. The segment is refused on the whole text.
2. **Fail-closed arm.** A segment is `opaque` when any word is opaque or `UNRESOLVABLE_SHELL_RE` matches. It is refused on `failClosedCheckpoints(seg.raw)`, which is the union of `governedToolsNamedBy` and a raw whole-word regex per tool.
3. **Readable arm.** For every canonical non-flag word `w`:
   - (3a) **nested re-tokenization, only when the value has whitespace:** `if (/\s/.test(w.value)) {` (`:1866`). ← CR-01 lives in this gap.
   - (3b) `named = governedToolsNamedBy(w.raw)`.
   - (3c) the xargs feed. An adjacent benign word decides unless a replace flag is present (`:1880-1886`). ← IN-02 lives here.
   - (3d) `verbCandidates(words, i + 1)`, which reads only the words after the naming word. It reads `-c alias.` values through `/^alias\.[^=]+=(.+)$/` (`:1512`), which is lowercase-only. ← R-30.
   - (3e) benign adjacency, (3f) flag rows, and (3g) git: `update-ref` and `gitPushIsGoverned`. The ref is the **last** candidate: `const ref = after[after.length - 1] as string;` (`:1594`). ← CR-02 lives here.
   - (3h) `spelledVerb` prefixes.

**The classifier admits a double-quoted run as canonical whatever it holds** (`:496`: `kind = runs[0]!.quoted || CANONICAL_WORD_RE.test(runs[0]!.text) ? "canonical" : "opaque";`). That is how `"$1"` became the literal `$1` in R-19..R-23.

### The canonical-form cutover: recommended rules (one authority, `scripts/checkpoints.ts`)

These are Claude's discretion (the grammar and its home). Every rule is an allow-list or a derived set. None enumerates bad shapes.

**C1: a literal word is one of a closed set of spellings. Everything else is opaque.**
- An unquoted run of `CANONICAL_CHARS`. Verbatim from `scripts/checkpoints.ts:358`: `const CANONICAL_CHARS = "A-Za-z0-9._/@:+=,~%^-";`
- A single-quoted run with any content.
- A double-quoted run whose content has **no** `$`, backtick or backslash.
- The existing prefix+quoted flag or assignment shape (`:497-505`), under the same content rule.

C1 closes R-19..R-23, the top-level `git "$@"`, and R-44. It is the review's `"…$…"` fix, but stated as membership in the allow-list rather than as one more refused shape.

**C2: a quoted value is re-read as shell text when it has whitespace OR when its next-shell reading names a governed tool.**
- Change the trigger at `:1866` from "has whitespace" to "has whitespace, or `governedToolsNamedBy(w.value)` is non-empty".
- The re-read value then goes through the same `commandSegments`, so `{git,push,origin,main}` and `"git"$IFS"push"…` become opaque nested segments. They are refused on the name `git`.

C2 closes R-01..R-09, R-11..R-14 and R-16. It is recursive by construction: C1 and C2 apply at every depth, because the nested segment is queued like any other.

**C3: a command word is literal.** An expansion in the command position is never readable.
- **C3a.** The first word of a segment, after skipping leading `NAME=value` assignments, redirections and **shell reserved words** (`do`, `then`, `else`, `if`, `while`, `until`, `!`, `{`, `time`), must be a C1 literal. Otherwise the segment is refused on **every** governed checkpoint, because the command it runs is unknowable.
  - The reserved-word skip is load-bearing. The measurement script missed R-46 (`do $x push …`) until it was added.
- **C3b.** A segment that holds any expansion word **and** a word equal to a governed verb or flag of any rule (derived: `COMMAND_CHECKPOINT_RULES.flatMap(r => [...r.verbs, ...(r.flags ?? [])])`) is refused on that verb's checkpoint(s). This covers the wrapper positions C3a cannot see: `env $x push origin main` and `nice -n 5 $x push origin main`.
- **What stays open, stated plainly.** A tool **and** its verb both computed at run time behind a launcher word (`x=git; y=push; env $x $y`). Closing it needs "any expansion in any word refuses unless the command word is a provable non-launcher", which is C3d. C3d costs 57 of 216 measured commands, and it needs the same non-derivable set D-04 needs. Record this as the one residual, computed at run time, and have the red-team confirm it.

C3 closes R-41..R-48 (including RES-01) and D-02 (b).

**C4: git config injection is refused on the name.**
- For a segment that names `git`, refuse (fail-closed on `protected_branch_merge`) when any of these appear:
  - `-c <key>=…` or `--config-env=<key>=…` whose key, compared **case-insensitively**, is outside a small declared allow-list of keys that cannot change which command git runs. Recommended starting allow-list: `user.name`, `user.email`, `color.*`, `core.pager`, `commit.gpgsign`. An allow-list that is missing a member over-refuses, which the file's own rule at `scripts/checkpoints.ts:665-673` admits. At minimum, the refused keys include `alias.*` (and its subsection form), `include.*`, `includeIf.*` and `help.autocorrect`.
  - a leading environment assignment on the same segment whose name starts with `GIT_CONFIG` (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`) or equals `GIT_EXEC_PATH`. The git docs say the `GIT_CONFIG_*` pairs "will be added to the process's runtime configuration". [CITED: git-scm.com/docs/git-config]
  - a `git config` write (any non-flag operand after `config` besides a read) of an `alias.*`, `include.*` or `includeIf.*` key, because it persists into `.git/config` for later calls (R-36).
- Delete the partial alias reader in `verbCandidates` (`/^alias\.[^=]+=(.+)$/`, `:1512`). The rule above replaces it. Keeping both would leave two grammars for one question, which is the Phase 29 lesson. A deleted reader also cannot keep the refspec-count defect the deferred entry describes (the definition word counted as a refspec).
- **Option (ii), a human decision:** a git verb-slot allow-list. The word adjacent to `git` (no flag between) must be a member of a **derived** set of known, non-deprecated git commands, or the segment fails closed. Derive the set from git's own `git --list-cmds=main,others,nohelpers` at generate time, minus the deprecated category, and assert the count. This is the only rule that refuses host-config classes: bare LB-08 under a global `help.autocorrect`, and an alias persisted by an earlier call or written with the Write tool. The cost is that a user's own git aliases are refused. It needs its own availability measurement and its own go. **Aliases can override deprecated commands (R-38), so the derived set must exclude them.**

C4 closes R-27..R-37, R-38 when the alias is inline, and LB-08's `-c` form. It does not close classes that live only in host config unless option (ii) is adopted.

**C5: under a stdin feed, no adjacent word earns an exemption.**
- Remove the benign-adjacency exemption under an xargs feed entirely (`scripts/checkpoints.ts:1880-1886`), rather than subtracting a hand list of launcher words. This is a strict superset of D-03: every launcher-shaped word D-03 names is refused, and so is any launcher the list would have missed (R-56, R-57).
- Measured cost: 1 of the 236 captured commands uses xargs at all, and it names no governed tool, so the measured cost is 0.
- Under a replace flag (`XARGS_REPLACE_FLAG_RE`, `:1635`), treat a word that contains the replace string as an expansion for C3. This moves RES-03's literal-verb form into C3b.
- **Option (b) for GNU parallel (`UNKNOWN - verify`, not installed here):** treat any segment on the right of a single `|` that names a governed tool as stdin-fed, instead of keying on the `xargs` basename. That covers any stdin-to-argument launcher without listing launchers. Measured cost over the captures: 0 real hits (4 regex false positives, all a `.git` path inside a quoted grep, which the projection does not name as `git`). The planner decides whether to include it in wave 1 or ledger it with the owner stated.

## Common Pitfalls

### Pitfall 1: The corpus sweeps only one arm
**What goes wrong:** every committed family carries a trailing opaque word or `<<<`, so the sweep only ever reaches the fail-closed arm. CR-01 lived in the readable arm and stayed green for a whole round.
**How to avoid:** build the family matrix with an explicit **arm** axis: a clean body (readable arm) and a body with a trailing `$X` (fail-closed arm), under each family. Add pipe-to-shell as a family. Keep here-string, which the fixture has now. Update the four-name pin at `scripts/checkpoints.test.ts:2605-2607` in the same commit.

### Pitfall 2: A stale decider manifest makes `hook-entry` deny everything
**What goes wrong:** `hooks/hook-entry.ts` carries a generated hash manifest of every `.js` in the decider's import closure. The region is marked `// <hook-manifest> GENERATED — do not edit by hand; run \`npm run generate:hook-manifest\`` at `hooks/hook-entry.ts:250` and closes at `:283`. On a mismatch the wrapper refuses with "does not match the frozen manifest" (`:326`), or with "carries no manifest entry" (`:289`). The closure of `hooks/guard.js` includes `scripts/checkpoints.js`. So any edit to `scripts/checkpoints.ts` or `hooks/guard.ts` that is rebuilt without regenerating the manifest makes every row replayed through `hook-entry.js` DENY, including every allow control. [VERIFIED: hooks/hook-entry.ts:234-252, :283, :289, :326, read this session]
**Why it happens:** `npm run build` (`tsc`) rebuilds the `.js` but does not touch the manifest region. The script is `"generate:hook-manifest": "tsc --outDir .tmp-build && node scripts/generate-hook-manifest.js && npm run build"`. It regenerates the region in `hook-entry.ts` and then rebuilds, so the wrapper's own `.js` picks up the new hashes. [VERIFIED: package.json scripts, read this session]
**How to avoid:** every guard task runs in this order: edit `.ts`, then `npm run generate:hook-manifest`, then the offline tests, then `npm run freshness:hook-manifest`. It commits `scripts/checkpoints.{ts,js}`, `hooks/guard.{ts,js}` and `hooks/hook-entry.{ts,js}` together. `scripts/floor-invariance.test.ts` also asserts that the manifest's file set equals a freshly derived closure (docblock `hooks/hook-entry.ts:238-246`). Run it in the wave gate.
**Warning signs:** the `guard.js` half of a replay is green while the `hook-entry.js` half denies uniformly, and the deny text names the manifest rather than a checkpoint. A mismatch fails in the deny direction. Before WR-04 is fixed, a mismatch still shows (a deny envelope is non-empty stdout). A wrapper crash that produces no stdout would not show, which is why WR-04 comes first.

### Pitfall 3: The AUTO-07 whole-run differential goes red, or is re-pinned to make it green
**What goes wrong:** `scripts/autonomy-zero-config.test.ts` diffs the full output of the current `hooks/guard.js` against a pre-Phase-30 guard pinned **by blob**: `const PRE_PHASE_GUARD_JS_BLOB = "e86da3f8b2262d7846d6f937fd149d21d8640203";` (`:43`). For every entry in `PAYLOADS` (`:142`) it requires exactly one added line (the banner) and zero removed or changed lines. A C1-C5 change that alters the decision **or the deny wording** for any roster payload turns it red. [VERIFIED: scripts/autonomy-zero-config.test.ts:1-43, :142, :347-375, read this session]
**Why it happens:** the test is deliberately a line-level diff, not a substring probe (its header, `:9-16`). A new refusal reason, or a reworded deny for a shape the pre-phase guard already denied, counts as a removed line plus an added line.

## Security Domain

`security_enforcement` is not disabled, so this section applies. The phase hardens a **defensive control**: the PreToolUse hook that stops an agent from pushing to a protected branch or deploying to production without a named human. This section names threat classes only. The mechanisms are recorded by ID in § Reproductions and are not repeated here.

### Applicable ASVS Categories

| ASVS category | Applies | Standard control in this phase |
|---------------|---------|--------------------------------|
| V1 Architecture (secure design) | yes | One canonical-form authority in `scripts/checkpoints.ts`, used by both entry points. The wrapper (`hooks/hook-entry.js`) verifies a derived hash manifest and fails closed. |
| V2 Authentication | no | No identities are authenticated. The human grant is an environment value the hook reads, and this phase does not change it. |
| V3 Session management | no | — |
| V4 Access control | **yes** | The guard *is* the access control on merge and deploy. Allow-list (canonical form) plus deny by default outside it. The matrix and two-key floor are unchanged. |
| V5 Input validation | **yes** | The command string is untrusted input from the agent. Validation is an allow-list of word spellings (C1), not a deny-list of bad shapes. Anything outside the list is refused on the name. |
| V6 Cryptography | no (reused only) | The manifest uses SHA-256 hashes from `node:crypto`. Nothing is hand-rolled, and nothing changes. |
| V7 Error handling and logging | yes | Every decider failure (crash, timeout, regex throw, manifest mismatch) resolves to DENY. The deny text is safety output in clear voice and names the unreadable word. |
| V14 Configuration | yes | git's runtime configuration channels (C4) and the Claude Code permission mode (D-11(a)) are configuration surfaces that change what executes. |

### Threat classes addressed

| Class | STRIDE | Where it lived | Standard mitigation in this phase |
|-------|--------|----------------|-----------------------------------|
