# Phase 33.1 Plan 19: CR-01 non-bypassability Summary

A branch now reads `protected` only through sources the checked account cannot bypass. A ruleset rule
counts only when `GET rulesets/<id>` reports `current_user_can_bypass: "never"`. Classic protection
counts only with `enforce_admins.enabled === true` and, for the pull-request and approval items, no
pull request bypass allowance. The qualifier is the fifth row of the one canonical table and the fifth
line of the one published checklist.

## What was built

- **Task 1 (tracer), commit `ff8a298b`.** `BRANCH_FLOOR` became a table of four items plus the
  `no_bypass` qualifier, which comes last, with the wording "does not let administrators or the
  account the agent works under bypass it" (D-30, no wording change). The ruleset arm collects the
  distinct `ruleset_id` values of rules that could show an item. It accepts an id only when
  `Number.isSafeInteger(id) && id > 0`, reads each one once per run (a cache shared across branches),
  and reads at most `MAX_RULESET_READS = 20` per branch. `never` binds. `always`,
  `pull_requests_only` and `exempt` are read as bypassable. Any other answer, including a 404, a
  missing field, a non-string or a 200 about a different ruleset, is unknown. An item is `held` on the
  ruleset arm only when a rule shows it and that rule's ruleset binds.

  The same task changed install/README.md §5(a). The checklist gained the fifth line, and a short
  paragraph after the list says how to meet it (include administrators, list no pull request bypass
  actors, keep the agent's account off ruleset bypass lists). It also states the cost on a
  single-identity repository: the author of a pull request cannot approve it, so the owner cannot merge
  their own pull requests, and adding yourself to a bypass list makes the check report `unprotected`.
  The 33.1-17 README drift case stays two-sided and passes.
- **Task 2 (TDD), commit `82eea6d1`.** `classicBinding()` reads `enforce_admins`. `false` makes every
  classic item bypassable (failed). Missing, non-object or a non-boolean `enabled` makes it unknown.
  For the pull-request and approval items, `bypass_pull_request_allowances` must be absent or an
  object whose `users`, `teams` and `apps` are all empty arrays. A non-empty list is unknown, and its
  evidence gives only the number of listed actors, never their names. Any other shape is unknown. The
  33.1-17 union rule is unchanged. The task also added the union matrix (a)-(g), the `no_bypass`
  weakening in `WEAKEN_BRANCH`, and the six-shape endpoint allow-list in the read-only proof.
  33.1-COVERAGE.md gained the `GET repos/{owner}/{repo}/rulesets/{ruleset_id}` INTEGRATE row (153
  characters) and updated reasons for the rules row (133) and the protection row (148). All five
  OPT-OUT rows are still there.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] WEAKEN_BRANCH no_bypass entry staged across the two tasks**
- **Found during:** Task 1
- **Issue:** The 33.1-17 two-sided test requires a `WEAKEN_BRANCH` key for every `floor.branch` row,
  so adding `no_bypass` in Task 1 needed a weakening at once. The planned weakening (classic
  `enforce_admins.enabled: false`) only takes effect after Task 2.
- **Fix:** In Task 1 the entry was ruleset `always` with classic 404 `Branch not protected`. Task 2
  changed it to the planned weakening: ruleset `always` with classic `enforce_admins.enabled: false`
  on an otherwise strong body.
- **Commits:** ff8a298b, 82eea6d1

**2. [Rule 2 - Correctness] A ruleset answer must be about the ruleset asked for**
- **Found during:** Task 1
- **Issue:** The plan binds a rule on a 200 with `current_user_can_bypass: "never"`, but it does not
  say that the 200 must describe the requested ruleset. The branch arm already refuses an answer
  about a different branch (the renamed-branch measurement).
- **Fix:** `body.id === id` is required. Any other 200 is unknown. This is tested ("a 200 describing a
  different ruleset → UNKNOWN - verify").
- **Commit:** ff8a298b

**3. [Rule 3 - Blocking] Existing strong classic fixtures now state enforce_admins**
- **Found during:** Task 2
- **Issue:** Before this plan, classic bodies expected to be `protected` did not carry
  `enforce_admins`. Under D-30 such a body is unknown.
- **Fix:** `CLASSIC_STRONG` and the three inline strong classic bodies gained
  `enforce_admins: { enabled: true }`. `CLASSIC_STRONG` also carries explicit empty allowances.
  No assertion was weakened.
- **Commit:** 82eea6d1

**4. [Scope note] Row mutations are applied at the arm reading, not inside fromRule / fromClassic**
- A rule-level reader is never called when no rule of its type is present, so forcing only
  `fromRule` would not be a mutation of the row. Forcing `rulesetReading` and `classicReading` for
  the row id is the faithful form of "force its readers to held".
