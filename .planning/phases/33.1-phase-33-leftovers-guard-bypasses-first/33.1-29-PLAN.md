<objective>
Close the last "delete by presence, not by record" path on the uninstall side, which the plan checker found
in the round-2 plan set. Today uninstall removes every grugops skill and adapter file at a kit-derived path
without comparing its content, so a user's edit to one of those files is deleted with it. That is the same
defect class Gap B in 33.1-VERIFICATION.md names, and the project's hard rule (D-18: never delete user
content) does not bend for grugops-named files. This is gap-closure round 2 of the 4-round cap (D-06).

The fix is the ledger mechanism once more, and it needs no new decision. Install already knows the exact
bytes it writes (materializeAdapter builds them, and linkOrCopy copies or links a known source), so it
records a content hash (or the link target) per kit file. Uninstall removes a kit file only while it still
matches. For installs made before this record, uninstall falls back to a content record the kit already
has, byte identity with the kit source, which is the rule it already applies to AGENTS.md and the runnables.
Everything else is left and reported, never guessed. So an old install leaves its rendered adapters behind
for the user to remove by hand. That is the safe answer under "never delete user content", and plan 33.1-32
publishes it.

This plan runs before plans 33.1-30 and 33.1-31 on purpose. D-32's re-install rule (plan 33.1-30) reads this
record to tell an edited kit file from one install wrote, and the ownership census (plan 33.1-31) classifies
the kit passes by their checked record (`kit-record`), not by their name. Both the uninstall decision here and
the D-32 pre-flight are DC-2 of the gap-planning brief: act on a record, never on a name.

Purpose: uninstall never deletes a kit file the user changed.
Output: the `kitFiles` record on both sides, ownsKitFile, the two named kit removal passes, and their tests.
</objective>
