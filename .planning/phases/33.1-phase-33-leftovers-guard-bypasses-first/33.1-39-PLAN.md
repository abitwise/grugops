No failing input is known; the order is fixed so they cannot.

Deviation from D-33 (b)'s wording, named for the human. D-33 (b) says uninstall "keeps the marker while any
recorded entry is left". This plan narrows that: file, block, gemini and ask-rules entries keep the marker, and
directory and backup entries do not. Reasons: `tools/` is never removed by design, so a directory entry would keep
the marker after every clean round trip; a recorded directory left non-empty holds someone else's files; and a
backup holds the user's content, which uninstall never removes, so a backup entry would keep the marker until the
user prunes or deletes it by hand. Side effect: once uninstall removes the marker, recorded backups lose their
record, so `--prune-old-kit` can no longer remove them and reports them as unrecorded; plan 33.1-40's README tells
the user to prune before uninstall. The alternative the human may choose: backup entries keep the marker (prune
then still works after uninstall), at the cost that a marker stays after uninstall whenever a handoffs or
edited-kit-file backup exists, because prune never removes those. The SUMMARY and the CHANGELOG carry this, the
SUMMARY lists it under `## Decisions needed from the human`, and plan 33.1-43 collects it.

Purpose: reversible means a later run can finish what an earlier run could not, and the reversal removes all of
what install wrote.
Output: the marker rule, the kept-marker rewrite, the Gemini created-file arm, the IN-02 reorder, tests,
README "Undo", CHANGELOG, and replay cases.
