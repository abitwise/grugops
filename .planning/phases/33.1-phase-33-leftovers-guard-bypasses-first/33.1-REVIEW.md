## Summary

The review covered the diff from `3be289f0^` to HEAD across all 64 listed files. The main focus was
the new enforcement surfaces: the installer-written ask rules (`install/checkpoint-ask-rules.ts`,
`install/install.ts`, `install/uninstall.ts`), the read-only host check
(`scripts/runnable-ref/host-protection.ts`), the `context-io.ts` WR-01/WR-02 fixes (the `stored`
parameter on `admit()` and `publishNoteExclusive`), and the `capture-live.ts` runner changes. The
compiled `.js` twins were not reviewed, because they are freshness-checked against their `.ts` source.

Most of the ask-rule merge is sound. I exercised it end to end against the committed `.js` in a
scratch target. A first install, a byte-identical re-install and an uninstall all did the right
thing: a user rule identical to one of ours was kept and reported, the other keys and values
survived, and 54 rules were added and then removed. The `publishNoteExclusive` hard-link publish
behaves correctly on EEXIST, on non-EEXIST errors and on temp cleanup. The coordinator exemption in
`capThreePredicate` is correctly gated on a non-null derived key.

The phase does have two defects that must be fixed before it ships:

1. The host check answers `protected` on evidence weaker than the floor it publishes. It never
   reads the approving-review count, admin enforcement, ruleset bypass actors, or environment
   self-review and admin-bypass settings. The phase moved the hard floor for merge and deploy onto
   the git host, and this check is how the gate and release workflows record that floor.
2. `uninstall.js` deletes directories during a `DRY_RUN=1` preview. It also deletes empty
   directories that grugops never created. This was reproduced against the committed `.js`. The
   defect predates this phase, but it sits on the reversal path this phase extended.

Several warnings are overclaims or reversibility gaps of the kind this repository's history keeps
producing when one arm of a pair is fixed and the other is not:

- Install fails open on a malformed ledger, while uninstall fails closed on the same input.
- The docs name a config fallback that the code never reads.
- A test seam in the shipped tool is signalled only on stderr.

Retired guard bypass rows are not relevant to any finding below, so none are cited.

## Critical Issues

### CR-01: host-protection reports `protected` without the evidence the published floor requires (fail-open verdict)

**File:** `scripts/runnable-ref/host-protection.ts:220-248, 334-346`
**Issue:** The documents that consume this check define the hard floor as:

- "pull request and approving review required, force pushes blocked, deletions restricted", at
  `scripts/audit-model.ts:325`, `agent-factory/packaging/adapters.md:100` and the
  `install/README.md` §5 checklist (lines 416-419);
- "a production deployment environment with at least one required reviewer", at
  `scripts/audit-model.ts:313`.

Each of them says `tools/grugops/host-protection.js` reports that floor. The code accepts much
weaker evidence:

- **Ruleset arm (lines 220-228):** it answers `protected` from the mere presence of a rule of type
  `pull_request` plus one of type `non_fast_forward`. It never reads the rule's
  `parameters.required_approving_review_count`, which defaults to 0 on a ruleset. A ruleset that
  requires a pull request with zero approvals lets an agent holding the human's token open and
  merge its own pull request. The check calls that branch `protected` and exits 0.
- **Classic arm (lines 232-248):** it treats `isObject(required_pull_request_reviews)` as "requires
  pull request reviews". It does not read `required_approving_review_count`, which may be 0. It
  does not read `enforce_admins.enabled` either. With admin enforcement off, an admin token can
  push to or merge the branch past every requirement. On a solo builder's personal repository the
  owner's token is that admin token.
- **Neither branch arm** checks deletion restriction (the `deletion` rule type, or classic
  `allow_deletions`), although the checklist and the audit model both list it.
- **Ruleset bypass actors** are never consulted. A `pull_request` rule the current user can bypass
  is reported as protecting against that user.
- **Environment arm (lines 334-346):** it answers `protected` for any `required_reviewers` rule
  with a non-empty list. It ignores `prevent_self_review` and the environment's
  `can_admins_bypass`. With self-review allowed, the same identity that triggered a deployment can
  approve it through the REST API. That is not a "named human confirmation".

Why this is a blocker: workflow 05 step 3 records an `observation` note "naming each protected
branch" on exit 0, and workflow 12 step 6 treats `protected` as "the host gates the deploy". The
phase retired the command guard on the premise that this host floor holds. A `protected` verdict
that is reachable while the host allows an agent-performed merge is a fabricated passing gate,
which CLAUDE.md "No fabrication" forbids. The docblock's own rule at lines 16-17 ("NEVER answers
`protected` without positive evidence") is not met for the requirements the check claims to
report.

**Fix:** Require positive evidence for every published requirement, and downgrade to
`unprotected` (when the field was read and is weak) or `UNKNOWN - verify` (when it could not be
read):

```ts
// ruleset arm: count only pull_request rules that demand an approval
const prRule = rules.body.find((r) => isObject(r) && r.type === "pull_request");
const rulePr =
  isObject(prRule) && isObject(prRule.parameters) &&
  typeof prRule.parameters.required_approving_review_count === "number" &&
  prRule.parameters.required_approving_review_count >= 1;
const ruleNoDelete = types.has("deletion");
// ...and consult each ruleset's bypass actors (GET repos/{owner}/{repo}/rulesets/<ruleset_id>,
// `current_user_can_bypass`); anything other than "never" -> UNKNOWN - verify, naming it.

// classic arm
const rpr = prot.body.required_pull_request_reviews;
const classicPr = isObject(rpr) && typeof rpr.required_approving_review_count === "number"
  && rpr.required_approving_review_count >= 1;
const adminsEnforced = isObject(prot.body.enforce_admins) && prot.body.enforce_admins.enabled === true;
const classicNoDelete = isObject(prot.body.allow_deletions) && prot.body.allow_deletions.enabled === false;
// protected only when pr && noForce && noDelete && (adminsEnforced || the rule came from a ruleset
// the current user cannot bypass)

// environment arm
const reviewersOk = isObject(reviewers) && reviewers.prevent_self_review === true
  && env.can_admins_bypass === false;
```

Add stub fixtures to `scripts/runnable-ref/host-protection.test.ts` for each weak shape: zero
approvals in both the ruleset and classic forms, admins not enforced, deletions allowed, a
bypassable ruleset, self-review allowed, and admin bypass on the environment. Assert that none of
them yields `protected`.

### CR-02: uninstall deletes directories under `DRY_RUN=1`, and deletes empty directories grugops never created

**File:** `install/uninstall.ts:250-263` (called at 716, 718, 737, 739, 781, 792, 848, and at 587 from the new `removeAskRules`)
**Issue:** `rmdirIfEmpty` has a DRY_RUN branch that calls `rmdirSync(d)` for real, then reports
`would-rmdir`. Its comment says "just narrate the attempt", but the deletion happens. It also has
no ownership check: any empty directory at those paths is removed, whoever created it. I
reproduced this against the committed `install/uninstall.js`. In a fresh git repository holding
only a user-created empty `.github/` and `.gemini/`, a `DRY_RUN=1` uninstall printed
`would-rmdir` for both, then `== uninstall complete (DRY_RUN — nothing changed) ==`, and both
directories were gone afterwards.

This breaks the documented contract at `install/uninstall.ts:32` ("Honors DRY_RUN=1"), the
`install/README.md` promise, and the CLAUDE.md hard constraint on installers: "dry-run-capable,
reversible; never overwrite or delete user content". The defect predates 33.1. It is recorded here
because the phase extended this reversal path (`removeAskRules` reaches `rmdirIfEmpty` at line
587), and because the orchestrator asked for it to be confirmed and classified.

**Fix:**

```ts
function rmdirIfEmpty(d: string): void {
  if (isProtected(d)) return;
  if (!isDir(d)) return;
  let empty = false;
  try { empty = readdirSync(d).length === 0; } catch { return; }
  if (!empty) return;
  if (DRY_RUN) { report("would-rmdir", d); return; } // never touch the filesystem in a preview
  try { rmdirSync(d); report("rmdir", d); } catch { /* raced non-empty */ }
}
```

Also record in the install marker which of these directories install created (as the ask-rule
ledger already does with `createdFile`), and pass that through. Then an empty `.github/` or
`.gemini/` the user made is never removed.

## Warnings

### WR-01: The production "hard floor" is overstated — an environment reviewer only gates deploys that run through the environment

**File:** `CHANGELOG.md:70`, `agent-factory/workflows/12-release.md:9`, `scripts/audit-model.ts:313`, `agent-factory/_commit-convention.md:72`
**Issue:** The CHANGELOG Security entry says the environment with a required reviewer is "what
stop[s] an unapproved merge or deploy, whatever the agent types". Workflow 12 states flatly that
"the git host's production deployment environment, with a required reviewer, is the hard floor".
A deployment environment only gates jobs that reference it. A deploy tool run from the agent's
own shell, with credentials held locally, never touches the git host. So the host floor for
`production_requires_human_confirmation` holds only when production credentials exist nowhere
except that environment's secrets. No reviewed document states that precondition; a grep for
"credential" or "secret" across the README, GUARANTEES, the factory config doc and workflow 12
finds none. `install/README.md` §5 and the GUARANTEES preamble scope the claim correctly ("every
deployment that runs through its deployment environments"). The CHANGELOG, workflow 12 and the
audit-model `hardFloor` string do not.
**Fix:** Add the precondition wherever the production hard floor is named. For example: "This
holds only if production credentials are held solely as that environment's secrets. A deploy run
with locally held credentials never reaches the host, and only the speed bump and the prose rule
stand in front of it." Also add a checklist item to README §5: "keep production deploy
credentials only in the environment's secrets, never on a developer or agent machine". Change the
CHANGELOG's "whatever the agent types" to the scoped wording.

### WR-02: The shipped host check carries a `--gh-script` seam whose use is invisible in stdout and in `--json`

**File:** `scripts/runnable-ref/host-protection.ts:121-126, 139-142, 433-444`
**Issue:** The materialized production tool (`tools/grugops/host-protection.js`) accepts
`--gh-script <path>` and then takes every "host" answer from an arbitrary Node script. The only
signal is a stderr line. The stdout lines, the summary line and the `--json` record (whose
`calls` array holds the gh argv, not the script) are identical to a real host reading. The gate
and release workflows tell the agent to record these results in `observation` notes, so an
agent-run check can produce a `protected` record that no host reading stands behind. The header
says the workflows "never pass it", but nothing enforces that.
**Fix:** Make the seam visible in the evidence itself. Prefix every stdout target line and the
`HOST-PROTECTION:` summary with `TEST SEAM — not a host reading`, add `"source": "gh-script"` to the
JSON, and force the exit code to 2 whenever the seam is in use. A better option is to gate the
seam on an environment variable that only the test harness sets, so the shipped artifact cannot
reach it from argv.

### WR-03: `admit()` accepts a caller-asserted `stored` fact that it could derive itself

**File:** `scripts/context-io.ts:3974, 4169`
**Issue:** The exported authority `admit()` gained a boolean `stored` parameter. When it is true,
`admit()` skips the GOV-02 append if the ledger already carries the id. `admit()` never checks
the claim, although it holds every input needed to decide it (`task`, `text`, `contextRoot`, and
`scalars.id` for `decideNoteDestination`). Inside the module, both callers compute it correctly.
Any in-process importer, though, can pass `true` for a note that is not at the destination, and
the ledger line is then suppressed whenever the id is already recorded. The ledger key is the id
alone, not task plus id, and `promoteAdmitted` legitimately persists the same id into a second
task. This is the "decide the same question in two places" shape the repository keeps
retiring: the destination question is now answered by the caller and trusted by the authority.
**Fix:** Derive the flag inside `admit()` instead of accepting it:

```ts
const dest = decideNoteDestination(join(contextRoot, task, "notes"), scalars.id ?? "", text);
const stored = dest.existing !== null && dest.existing === text;
```

If the extra read is unwanted, keep the parameter off the exported signature. Route the two
internal callers through a non-exported variant, and add that variant to the derived writer-set
test.

### WR-04: The installer's settings rewrite is non-atomic and writes through a symlink

**File:** `install/install.ts:3077` (and `install/uninstall.ts:590`)
**Issue:** `writeFileSync(file, …)` rewrites the user's existing `.claude/settings.json` in place.
If the process is interrupted mid-write, the file is left truncated. That destroys the user's own
permission rules and keys, and the next install then refuses the file as invalid JSON rather than
repairing it. `writeFileSync` also follows a symlink. If `.claude/settings.json` points at a shared
dotfile, the installer writes rules into a file outside the repository, and the ledger then
records a reversal against that out-of-repo file. Uninstall has the same two properties.
**Fix:** `lstat` the path and refuse a symlink with a `verify` finding. Write a temp sibling with
flag `wx` and `renameSync` it onto the path (the same-directory rename is atomic on POSIX). Do the
same in `removeAskRules`.

### WR-05: Install silently discards a malformed ask-rule ledger and loses reversibility (fails open where uninstall fails closed)

**File:** `install/install.ts:2961, 3030-3040, 3060-3066` (with `readAskLedger` at 628-643)
**Issue:** When `.grugops/install.json` is unreadable, or its `claudeAskRules` field has any shape
defect, `readAskLedger` returns `null` and install treats that as "no previous install". Every
grugops rule already present is then re-labelled "kept as the user's own rule", `ASK_LEDGER` is
rebuilt with `added: []`, and `writeMarker()` overwrites the marker. Reproduced against the
committed `.js`: after one field was deleted from the ledger, a re-install exited 0 and reported
55 rules as the user's own. The marker's ledger became empty, and the following uninstall left
all 55 rules and the grugops-created `.claude/settings.json` in place. Uninstall's reading of the
same malformed ledger is a `verify` refusal (`install/uninstall.ts:505-515`). The two binaries
disagree, and the install side is the one that makes the loss permanent.
**Fix:** Tell "no ledger field" apart from "a field that is present but malformed or unreadable".
In the second case, report a `verify` finding naming the marker, leave `ASK_LEDGER` as the raw
prior value (or skip writing the field), and add no rules. That matches uninstall's fail-closed
behaviour.

### WR-06: The documented kit-default config fallback is never read by the installer or the host check

**File:** `install/install.ts:2938-2955`, `scripts/runnable-ref/host-protection.ts:297-316`, `install/README.md:425, 455-456`
**Issue:** README §5 says the installer reads the checkpoints "from `.grugops/factory.config.json`
(or, when that file is absent, from the kit's default config)". It says the same of the host
check's environment name ("then the kit's default config"). Both code paths read
`agent-factory/config/factory.config.json` relative to the target or working directory. Under the
shipped two-root layout, the kit lives at `$GRUGOPS_HOME/agent-factory` and the repository has no
`agent-factory/`, so the documented fallback is never consulted. Consequences:

- The host check falls straight to `production`, not to the kit default's last entry (`prod`).
- The host check's lookup is relative to `process.cwd()`, so running it from a subdirectory
  silently drops even `.grugops/factory.config.json`, while `gh` still resolves the repository.

Both failures land on `UNKNOWN - verify` or on the wrong environment name, which is fail-safe, but
the published sentence is false.
**Fix:** Either correct the README to name the code's actual order (`.grugops/factory.config.json`,
then an in-repo `agent-factory/config/factory.config.json` for the old layout, else all rules or
`production`), or make both code paths consult `KIT_ROOT`. For the host check, resolve the config
against `git rev-parse --show-toplevel` rather than `process.cwd()`.

## Info

### IN-01: The doctor calls a missing settings file "could not be read as JSON"

**File:** `install/install.ts:1022-1040`
**Issue:** An absent `.claude/settings.json` throws inside the same `try` as a parse failure, so a
user who deleted the file is told it "could not be read as JSON".
**Fix:** Check `existsSync(askFile)` first and warn "absent" separately.

### IN-02: Uninstall removes every occurrence of a ledgered rule, including a duplicate the user added later

**File:** `install/uninstall.ts:545-546, 564`
**Issue:** `isLedgerRule` filters by string membership, so a user's own later copy of a
grugops-added rule is removed together with ours. The README's "removes exactly the rules install
added and nothing else" is slightly overstated.
**Fix:** Remove only one occurrence per ledger entry, or document the behaviour.

### IN-03: Workflow 05 exit-1 text asserts a branch fact when only the environment may be unprotected

**File:** `agent-factory/workflows/05-pr-quality-gate.md:31`
**Issue:** Exit `1` means "at least one target is unprotected", and that target may be the
production environment alone. The step still tells the agent to "State in the recommendation that
the git host does not enforce review before merge", which is false in that case.
**Fix:** Tell the agent to state what each `unprotected` line names, per target kind.

### IN-04: The host check's crash handler prints an unsanitized message

**File:** `scripts/runnable-ref/host-protection.ts:76-79`
**Issue:** The `uncaughtException` handler interpolates `err.message` raw. Every other untrusted
value goes through `printable()`, and an exception message can carry host-supplied text.
**Fix:** Wrap it: `printable(err instanceof Error ? err.message : String(err))`.

### IN-05: Ask rules are written regardless of which host tools were detected

**File:** `install/install.ts:3098-3101`
**Issue:** `writeAskRules()` runs unconditionally, so a repository used only with Codex, Gemini,
OpenCode or Copilot gains a `.claude/settings.json` (and a `.claude/` directory). This is additive
and reversible, but it is not what README §5 heading (b) ("standalone install only") suggests to a
non-Claude user.
**Fix:** Gate the step on Claude Code being among the detected tools, or say in README §5 that it
always runs.

### IN-06: The capture-live coordinator exemption matches through prefix stripping

**File:** `scripts/capture-live.ts:786-788, 931, 947`
**Issue:** `roleKey` strips the adapters' longest common prefix, so a spawn whose
`subagent_type` is the coordinator's bare, unprefixed name (for example a user-level agent with
that name) also matches `coordinatorKey` and is exempted. Granted keys already had this ambiguity.
The exemption inherits it, and it is the one clause that skips the membership check entirely.
**Fix:** Compare the exemption against the full coordinator name
(`o.role === grant.coordinator`, or the one plugin-namespaced spelling) rather than the stripped
key.
