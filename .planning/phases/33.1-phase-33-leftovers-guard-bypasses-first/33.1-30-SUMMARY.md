# Phase 33.1 Plan 30: Kit-file ownership (kitFiles) Summary

**Uninstall now removes a grugops skill or adapter only while it still holds the sha256 (or link target) install recorded in `kitFiles`. For an install made before this record, it falls back to byte identity with the kit source. A target with no marker loses nothing.**

## Accomplishments

- `kitFiles` in the marker, written after `geminiSettings`. materializeAdapter records `sha256:` of the final bytes (written or found identical). The skills `linkOrCopy` call (new `isKitFile` argument) records `sha256:` of a copy or identical copy, or `link:<src>` of install's own link. DRY_RUN, refusals and foreign links record nothing.
- writeMarker applies the one absent-ledger rule. A fresh install writes the field, possibly `{}`. An `ok` previous record is carried, and each entry survives only while it holds its record (recordHolds), with this run's entries laid over the top. A legacy marker gets the field only when this run recorded kit files. A malformed record is written back with a verify.
- `ownsKitFile(rel, path, src)` gives these answers:
  - An `ok` record wins.
  - `ok` without an entry: left.
  - Malformed ledger, or an unreadable marker: fail closed.
  - Marker without the field: the legacy fallback, `sameFileBytes(path, src)`.
  - No marker: left.
- The two top-level passes became `removeKitSkills()` / `removeKitAdapters()`. They call `removeFile(f, rel, src, () => ownsKitFile(rel, f, src))`. The ownership question comes after removalDecision and before the DRY_RUN branch.
- `kitFiles` joined `malformedLedgers()` and `updateKeptMarker`. The unreadable-marker verify names the kit-file ledger.
- install/README.md's uninstall section now states the kitFiles rule, the no-marker and legacy answers, and that an own-shape link at a copy-recorded path is left.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - D-18 / brief DC-2] No marker at all removes no kit file**
- **Found during:** Task 2
- **Issue:** The plan's no-marker bullet removed a skill byte-identical to the kit source. That would delete kit copies from a never-installed target, which is the carry item 3 shape. It also breaks the brief's rule that a never-installed target changes by zero bytes, and it contradicts plan 28's rule for AGENTS.md and the runnables.
- **Fix:** When MARKER is absent, ownsKitFile answers left ("there is no install marker…"). The byte-identity fallback applies only to a marker without `kitFiles`. Mutation (h) proves the tests tell the two rules apart.
- **Files modified:** install/uninstall.ts
- **Committed in:** a7d9f899. The ledger entry is WINDOWS.md #313 (deviation).

**2. [Rule 1 - carry-forward rule] kitFiles is carried by recordHolds, not by lstat presence**
- **Found during:** Task 1
- **Issue:** The plan text said to start from previous entries "whose path still exists (lstat succeeds)". That is carry by presence, which plan 28's red-team found as a bug.
- **Fix:** A previous entry survives only while recordHolds. Mutation (e) turns the carry case red.
- **Committed in:** c854331a

**3. [Rule 3 - one authority] No node:crypto import in install.ts or uninstall.ts**
- **Found during:** Task 1
- **Issue:** The plan asked both binaries to import createHash. The dispatch forbids a second hash helper.
- **Fix:** Both binaries use contentRecord / linkRecord / recordHolds from install-marker.ts. readKitFiles shares readPathRecords with readCreatedFiles. The module headers were updated rather than the builtin lists.
- **Committed in:** c854331a

**4. [Rule 1 - superseded test expectation] uninstall-removal own-link case**
- **Found during:** Task 1 (install/ run: 1 failed)
- **Issue:** The case put the own-shape link at every kit path of a COPY install and expected removal. The copy's sha256 is now the record, so the link is left. This is the same rule plan 28 applied to AGENTS.md in that case.
- **Fix:** The kit paths now join AGENTS.md in the `left` arm. A new case proves that a real `--symlink` install's links are removed and gone, and that the real run and DRY_RUN decide alike.
- **Files modified:** install/uninstall-removal.test.ts
- **Committed in:** c854331a

**5. [Rule 2 - completeness] ledger-provenance R2 covers kitFiles; README corrected**
- **Found during:** Task 2
- **Issue:** The R2 class test garbled 4 ledgers. install/README.md said uninstall removes the skills and adapters with no condition, which is now false.
- **Fix:** `kitFiles` joins LEDGERS, the kept marker must name no removed kit file, and the user's re-made verbatim skill must survive the second uninstall. The README uninstall section was updated. Plan 34 still owns § Undo.
- **Committed in:** a7d9f899

**6. [Rule 2 - test the stated truth] An absent kitFiles stays absent over a legacy marker**
- **Found during:** Task 2 (self-check of the must_haves)
- **Fix:** Added the test in aeace65f. Mutation (i) turns it red.
