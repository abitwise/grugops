## Accomplishments

- **SIBLING_PAIRS (Task 1).** Every unordered pair of evidence (non-inert) walked paths that share a parent, each in its body's baseline, derived from plan 33.1-23's walk. There are 62. Each pair gets one `it` that loops over absent+absent, absent+wrong, wrong+absent and wrong+wrong, using section 5's mutations through the shared `applyMutation()`. The class rule: every row either field feeds is not held, every row fed by neither stays held, a fed target is not protected, and the exit is not 0.
- **A pair defect, found and fixed (DC-1).** 12 sibling pairs were red on the first run. A rule entry's `ruleset_source` (or `ruleset_source_type`) broken alone makes ruleset 1 bind nothing, so every branch row reads unknown. Broken together with the entry's `type` (so the entry is no longer a readable rule) or its `ruleset_id` (so it names no ruleset), the entry dropped out of the source-agreement check. Ruleset 1's other rules then bound again, and no_force_push / no_deletion read held: more broken input gave a stronger reading. `sourceDisagreement()` now asks every entry of the rule list that does not name another ruleset by a usable id, readable or not.
- **Sibling search (the same shape elsewhere).** The file has two other "exactly one?" checks over host lists. Both dropped unreadable entries, so garbling one field of a duplicate turned "which one applies is not readable" into a pass. Both are fixed. `ambiguousReviewerRules()` is asked by both reviewer rows. environmentVerdict now counts an entry with no readable name as a possible second environment of the configured name.
- **ROW_PAIRS and CROSS_TARGET_PAIRS (Task 2).** Row ids come from the CLASSIC_ARM and RULESET_ARM baseline runs' facts. ROW_PAIRS is C(10, 2) = 45, asserted against both n(n-1)/2 and the pin. CROSS_TARGET_PAIRS is 5 branch rows x 5 protected-branch evidence paths (the list's 4 evidence paths and the listed branch's classic root) = 25, asserted against the product and the pin. Every pair is green on HEAD.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - DC-1 defect found by a pair] Source agreement ignored unreadable and unattributed entries**
- **Found during:** Task 1, first run (12 of 62 sibling pairs red)
- **Issue:** `sourceDisagreement()` read only readable entries (a string `type`) that name the ruleset's id. A second broken field removed the disagreeing entry from the check.
- **Fix:** RulesetArm carries the raw `entries`. The check asks every entry whose `ruleset_id` is this id, or is not a usable id.
- **Files modified:** host-protection.ts / .js, host-protection-floor.test.ts (LEAVES), host-protection.test.ts
- **Verification:** 21 RED cases, then green, with 3 controls. The single-field `rules:$[0].ruleset_id` case still feeds only PR, because the entry's source is present and agrees.
- **Committed in:** `9106ad57` (RED), `c1bfa83a` (fix)

**2. [Rule 2 - DC-1 siblings] Uniqueness checks dropped unreadable entries**
- **Found during:** the sibling search after deviation 1 (brief §2.3). The file was read for every check over a host list that selects or counts entries.
- **Issue:** `[<strong reviewer rule>, <the same rule with type 7>]` read held, while two readable rules read unknown. `[<production>, {name: 7}]` read protected (the pre-plan build exits 0), while two productions read unknown.
- **Fix:** `ambiguousReviewerRules()` (both reviewer rows ask it) and the unnamed-entry count in environmentVerdict. A readable entry of another type or another name still reads as provably different, and the controls keep `wait_timer` and `staging` protected.
- **Committed in:** `3880d960` (RED), `8bf5386f` (fix)

**3. [Changed expectations, with reasons]**
- LEAVES `rules:$[0]`, `$[1]` and `$[2]` changed from PR/NFF/DEL to all five branch rows. A whole entry that is null or garbled names no ruleset and no source, so it may belong to ruleset 1. Removing the element is still checked with the removal rule.
- The plan 33.1-22 case `[null, non_fast_forward, deletion]` expected force pushes held. It now expects every branch row unknown, for the same reason.
- The plan 33.1-22 case `protection_rules [null, <strong reviewer rule>]` expected both reviewer rows held. It now expects them unknown, because the null entry may be a second required_reviewers rule.
- In pairs, a removed array element uses section 5's removal rule: some row it feeds stops being held. Without this, `rules:$[0] + rules:$[1]` both removed would demand that no_deletion (still shown by `rules[2]`) is not held.

**4. [Plan interpretation] Row representatives**
- The plan's literal rule is "the first evidence path in walk order". That picks `classic:$` for every branch row and `environments:$` for every environment row, so the 45 row pairs would be three distinct fixtures.
- The representative is now the evidence field that feeds the fewest rows, then the deepest, then the first in walk order. It is still derived from LEAVES and the walk, never typed, and it is printed and asserted: it belongs to the baseline and feeds its row.
