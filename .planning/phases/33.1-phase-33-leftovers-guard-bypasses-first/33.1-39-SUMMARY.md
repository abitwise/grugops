# Phase 33.1 Plan 39: The install marker outlives an unfinished uninstall; a created Gemini file is reversed whole Summary

**Uninstall now removes `.grugops/install.json` only when the run counted no verify for a recorded path and every file, block, gemini and ask-rules entry was removed, reversed, found gone, or claims nothing. Otherwise it keeps the marker, rewritten from OUTCOMES to list only what is still there, so "fix the cause and re-run" finishes the reversal (WR-02). A Gemini settings file install created is reversed whole, with the user's keys kept byte for byte (WR-03). writeAskRules decides its splice oracle before its DRY_RUN return (IN-02).**

## Accomplishments

- **The marker rule (`install/uninstall.ts`).**
  - `RECORDED_VERIFIES` counts the verify lines raised inside `walkLedger`, as a delta of `VERIFY_FINDINGS` across the walk.
  - `heldEntries()` lists the file, block, gemini and ask-rules entries whose outcome is not removed, gone or reversed. An entry that claims nothing (`entryClaimsNothing`) is skipped.
  - `markerDischarged()` is true only when `RECORDED_VERIFIES` is 0 and `heldEntries()` is empty.
  - `removeMarker` keeps the marker whenever `markerDischarged()` is false. It prints a `left` line naming the held paths and calls `updateKeptMarker`. It sets `KEPT_FOR` only when there was no recorded verify.
  - The header now states the rule and the narrowing.
- **`updateKeptMarker` rewrites from OUTCOMES.**
  - Removed and gone entries are dropped.
  - A reversed file or block entry is dropped. A reversed gemini or ask-rules entry is replaced by its after-record.
  - Left and verify entries are kept exactly as found.
  - Dir and backup entries are kept while their path is still there.
  - The guards are unchanged: a same-bytes re-read through `readForWrite`, the write through `rewritePath`, a verify naming the stale entries when the write fails, and `would-edit` under DRY_RUN. `BLOCKS_GONE` is deleted because OUTCOMES carries the same fact.
- **The pointer-file outcome.** `removeOwnedEmptyFile` now returns an outcome in each of these cases:
  - `gone` when the block entry is gone.
  - `left` when the block is still there.
  - `reversed` when this run removed the block and the file still holds the user's lines.
- **Three closing outcomes, each with its banner and exit status on the same branch:**
  - complete: marker removed, exit 0.
  - complete with recorded items left: exit 0, `== uninstall complete — <n> recorded item(s) left in place; .grugops/install.json kept to record them ==`, plus one line naming the two ways forward.
  - INCOMPLETE: exit 3, as before.

  The last statement still sets `process.exitCode`.
- **WR-03 (`unmergeGemini`).** When the file was created by install and `context.fileName` is still the recorded list, `fileName` is removed whole. `context` is removed too when nothing else is in it. If `{}` is left, the file is deleted only when it is byte for byte install's emptied shape (`emptiedCreatedGeminiText`) and has the recorded mode. Otherwise the content is taken out through the existing text edit and oracle, the file is kept, and the line says why. The appended-entry arm (`createdFile` false) is unchanged. `install-marker.ts` exports `createdGeminiText` and `GEMINI_CREATED_FILE_NAME`, and `install.ts mergeGemini` writes through them, so both binaries share one created text.
- **IN-02 (`install.ts writeAskRules`).** The `if (DRY_RUN)` block now sits after the splice and its oracle. No other line changed.

## Decisions Made

- **The pointer-file outcome.** In a `CLAUDE.md` or Copilot file install created, the content install wrote is the block. If this run removed the block and the file still holds lines of the user's, the file entry is `reversed`, and it does not hold the marker. Otherwise every user who added lines to an install-created `CLAUDE.md` would get a marker that never goes away. Before this change the file entry was `left` silently, with no line naming it. This follows the plan's truth: "every entry whose content install wrote … was removed, reversed". A blank pointer file left only for a mode change, or because its unlink failed, still holds the marker.
- **The emptied Gemini file.** The plan says to delete a `{}` result through unlinkPath. The existing red-team L1 test (`record-truth.test.ts`, plan 33.1-34) requires that a whitespace or line-end edit, or a chmod, keeps a file install created. The repository's rule against deleting user content takes precedence, so the rule `removeAskRules` uses was applied here as well: delete only when the result is byte for byte install's emptied shape and has the recorded mode. Otherwise the list install wrote is taken out and the file is kept, and the line says why. `createdGeminiText` was moved into install-marker.ts, so both binaries share that one text.

## Decisions needed from the human

Plan 33.1-43 collects these.

1. **D-33 (b) narrowing: directories and backups do not keep the marker** (reversible; it is installer behaviour).
   - **What D-33 (b) says:** uninstall keeps the marker "while any recorded entry is left".
   - **What this plan does:** file, block, gemini and ask-rules entries keep the marker. Directory and backup entries do not. They are still reported, and a kept marker still lists the ones that are present.
   - **Why:** a directory holds no content of install's own, because its files are their own entries. `tools/` is never removed by design, so counting directories would keep the marker after every clean round trip. A recorded directory left non-empty holds someone else's files. A backup holds the user's content, which uninstall never removes.
   - **Side effect:** once uninstall removes the marker, recorded backups lose their record, so `--prune-old-kit` can no longer remove them and reports them as unrecorded. README and CHANGELOG tell the user to prune before uninstalling.
   - **Alternative:** backup entries keep the marker, so prune still works after uninstall. The cost: a marker stays after uninstall whenever a handoffs backup or an edited-kit-file backup exists, because prune never removes those.
2. **Pointer files count as `reversed` once their block is removed** (reversible). In a `CLAUDE.md` or Copilot file install created, the file entry stops holding the marker once this run has removed the block and the user's lines remain. The alternative is that the file entry holds the marker too. Then every user who edited an install-created `CLAUDE.md` keeps a marker until they delete it by hand.
3. **The emptied created Gemini file follows the L1 rule** (reversible). The plan's wording says a `{}` result is always removed. This plan removes it only when it is byte for byte install's emptied shape with the recorded mode. That keeps the plan 33.1-34 L1 tests green and matches `.claude/settings.json`. A user's chmod or whitespace edit therefore leaves a `{}` file in place with nothing of install's in it.
4. **Residual found in the sibling search (plan 37 surface, not changed):** when `writeKitHomeRecord`'s write fails after `copyKit` made a backup, the verify line does not name that backup, so the backup stays unrecorded and unnamed. Candidate for 33.1-43 or backlog 999.1.
