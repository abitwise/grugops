# D-20 part (d): what an installed Claude Code `ask` rule does in `claude -p` mode

This record is the committed, re-runnable evidence for part (d) of the D-20 proof bar. Every value in
the result table was printed by the harness named in `precheck:`. Nothing in it was typed by hand.

## What is being checked

D-20 part (d) asks for a zero-token measurement of how a Claude Code `permissions.ask` rule behaves
in non-interactive `-p` mode. The question matters because grugops now relies on those rules as the
client-side speed bump for protected merges and production deploys (D-18): an ask rule that silently
let a command through in `-p` mode, or hung waiting for a prompt nobody can answer, would be a
different control from the one the documentation describes.

The specific claim measured: with the rule the grugops installer writes for the
`protected_branch_merge` checkpoint (`Bash(git push *)`), a `git push` that Claude Code proposes in a
`-p` run is denied in every permission mode, even when the same command is explicitly allow-listed.

## How it was measured

- **The real installer wrote the rule.** For each case the harness creates a scratch git target (one
  commit on `main`) with a bare remote named `origin`, then runs this checkout's committed
  `install/install.js --yes` into it (`INSTALL_MODE=copy`, a temporary `GRUGOPS_HOME`). The installer
  writes the target's `.claude/settings.json`; the harness checks that `Bash(git push *)` is in it.
- **No model was called.** `mock-api.mjs` stands in for the Messages API on `127.0.0.1` only. It
  answers the first tool-bearing request with one `Bash` tool use, `git push origin main`, and every
  later request with an `end_turn` text. `claude` runs with `ANTHROPIC_BASE_URL` pointed at the mock,
  a placeholder API key, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, a temporary
  `CLAUDE_CONFIG_DIR`, and every inherited `CLAUDE*` / `ANTHROPIC*` variable removed (so no OAuth
  token and no parent session reaches it). A case whose mock log shows no `POST /v1/messages` is
  refused with exit 2 rather than reported; no case was refused.
- **Only project settings apply.** The invocation is
  `claude -p push --setting-sources project --output-format stream-json --verbose [--permission-mode <m>] --allowedTools "Bash(git push *)"`,
  with the scratch target as the working directory and stdin empty. The `none` row passes no
  `--permission-mode` flag (the built-in `-p` default).
- **Only the ask rule can stop the push.** The command is allow-listed on the command line, so in the
  ask rows the one thing that can refuse it is the installed ask rule. Claude Code documents that an
  ask rule wins over a matching allow rule.
- **The config-off control proves the cause.** Each control row repeats the run with
  `.grugops/factory.config.json` setting `checkpoints.protected_branch_merge` to `off`. The installer
  then writes no merge rule (the harness checks `Bash(git push *)` is absent), and the push must run.
- **Two observables decide each row.** The `permission_denials` array of the `result` frame, and
  whether the bare remote has `refs/heads/main` after the run.

## What this does not show

- **The rules are a speed bump, not a security boundary.** A Bash ask rule matches the command
  spellings Claude usually produces. It does not match the same program invoked another way: a
  path-qualified program, a `sh -c` body, options before the subcommand, or a quoted subcommand.
  Claude Code's own documentation says such a rule "covers the invocation Claude usually produces and
  isn't a security boundary around the program"
  (https://code.claude.com/docs/en/permissions, "What a Bash rule doesn't match"). This record
  measures one spelling, `git push origin main`, and says nothing about any other spelling.
- **The git host is the hard floor.** Branch protection or rulesets on protected branches, and
  deployment environments with required reviewers for production, are what actually hold
  (install/README.md §5, plans 33.1-04 and 33.1-08). This record does not measure them.
- **Interactive mode is not measured.** In an interactive session an ask rule prompts the human
  instead of denying; this record covers `-p` mode only.
- **The plugin form carries no permission rules.** Only the scripted installer writes
  `.claude/settings.json`; a plugin-only install gets none of these rules. The other four CLIs get
  documentation only (D-18).
- **One Claude Code version.** The result is for 2.1.283 on one macOS host. A later version can
  change the behaviour; re-run the harness after an upgrade.
- **One rule measured end to end.** The other 54 installed rules share the same mechanism and the rule
  shapes measured in 33.1-RESEARCH § Q1, but only the `git push` rule was driven through `-p` here.
