<objective>
Close the validator fail-closed blocker (CR-03). The file header promises "every read/JSON.parse is wrapped in try/catch so a missing or garbled file becomes a finding, never an unhandled throw." But `JSON.parse('null')` is valid ECMAScript that returns `null` WITHOUT throwing, so the try/catch passes silently — then `cfg[key]` (checkConfig) and `manifest.name` (checkPackaging) crash with `TypeError: Cannot read properties of null`. The validator prints a Node stack trace instead of the documented greppable finding, and every check after the crash is skipped (the finding set becomes incomplete and order-dependent).

Fix: after `JSON.parse(raw)` succeeds in both checkConfig and checkPackaging, reject any non-object result (null, array, or primitive) before dereferencing — emitting a greppable finding consistent with the validator's existing `err(\`${rel}: not valid JSON\`)` style. Then add null-literal regression fixtures for BOTH factory.config.json and plugin.json to validate.test.sh so the crash can never silently return.

Purpose: the fail-closed invariant is the validator's stated correctness contract — untrusted/garbled local file content (here a valid-but-null JSON literal) must degrade to a finding, never a crash. This is the security-relevant robustness fix for the validator: a file that is technically valid JSON but structurally wrong must not take the validator down.
Output: a null-object guard in checkConfig and checkPackaging, plus two new validate.test.sh checks proving a null-literal config and a null-literal plugin.json each yield a finding (not a TypeError) and a nonzero exit.
</objective>
