## 1. A1 (D-31) - plugin-cache pointer resolution: an EMPTY capture after 606161 ms

### 1.1 What the case does and what it observed

`scripts/e2e/uat-live.test.ts:252-322` scaffolds a throwaway repository with `mkdtempSync`, copies
`agent-factory/` into it, creates `plans/handoffs/`, writes a two-line `AGENTS.md`, then runs
`claude plugin marketplace add <ROOT> --scope local` and `claude plugin install grugops@grugops
--scope local` (each bounded at 60000 ms). It then makes up to two `claudePrint` calls - the
primary `/grugops:plan ...` form and a `--plugin-dir <ROOT>` fallback - and requires
`markerRe.test(out) && !pathErrorRe.test(out)`.

The run reported `606161 ms` for the case and an EMPTY capture in the failure message.

### 1.2 Cause class: SUITE EXPECTATION (the per-call budget), with a HOST CONFIGURATION rider

**The arithmetic is the primary evidence.** `CALL_TIMEOUT_MS` defaults to `300_000`
(`uat-live.test.ts:181`). The case made exactly two `claudePrint` calls. 606161 ms divided by two
is 303080 ms per call - each call ran past its own 300000 ms bound and was killed by
`spawnSync`'s `timeout`. The residue above 300000 ms per call is the spawn and kill overhead plus
the two 60000-ms-bounded install spawns amortised across the pair; the shape is unmistakable.

**The empty capture follows mechanically from that, and distinguishes a timeout from a wrong
answer.** Both calls pass `--output-format json`. That format emits ONE JSON object when the
session completes. A session killed before completion has written nothing, so
`r.stdout` is empty and `r.stderr` is empty, and `claudePrint` returns `"\n"`. `markerRe.test("")`
is `false`, so `fired` is `false` on both the primary and the fallback - with no error text to
attribute anything to. An empty capture is therefore the SIGNATURE of the budget being exhausted,
not of a cache path error. The case's own failure message ("neither ... produced planning markers
without a cache path error") reads as if a path error had been observed; none was. That wording
is a reporting weakness, not a defect in the kit.

**The rider, from the run's own residue measurement.** `32.1-10-LIVE-TRANSCRIPT.txt` section 6
recorded that `~/.claude/plugins/known_marketplaces.json` changed only in two `lastUpdated`
timestamps and that the marketplace MEMBERSHIP was byte-identical before and after: the two
entries were `claude-plugins-official` and `grugops`, and the `grugops` entry was the operator's
own pre-existing install of `abitwise/grugops` from GitHub. `.claude-plugin/marketplace.json` in
this checkout declares `"name": "grugops"`. So the suite's `marketplace add <local ROOT>` used a
marketplace NAME that already existed at user scope pointing at a different source. The run
refreshed that pre-existing row rather than registering the local checkout.

What follows from that is narrower than it looks, and is stated narrowly. `claude plugin install
grugops@grugops` resolves `@grugops` by NAME. If the name resolved to the pre-existing
GitHub-sourced row, the plugin installed for the throwaway repository was built from the
published repository rather than from the checkout under test - which would make A1's subject a
different tree from the one the assertion is about, and would equally affect A2-live (section 2.3).

`UNKNOWN - verify`: whether the local-path `marketplace add` was rejected as a duplicate name,
silently retargeted the existing row's source, or created a project-scoped row invisible in the
user-level file. The measurement that would settle it is a `claude plugin marketplace list` and a
`claude plugin list` inside the throwaway repository immediately after the two install spawns,
captured into the transcript. Both are metadata commands and spend NO tokens. The 2026-09-18 run
did not capture them, and the throwaway repository was removed by `afterAll`, so it cannot be
inspected after the fact.

### 1.3 What distinguishes this class from the next most likely one

The next most likely class is "the kit" - `/grugops:plan` genuinely failing to resolve its
repo-relative pointers from the plugin cache, which is the defect D-31 exists to detect. The
distinguishing observation is simple: that failure mode produces OUTPUT containing a path error,
because the CLI completes the turn and reports it. The observed capture is EMPTY, which is the
one outcome a resolution error cannot produce. A re-run under a raised
`UAT_E2E_CALL_TIMEOUT_MS` would separate them decisively: output naming a cache path is the kit,
output naming planning markers is a pass, and a second empty capture at a higher bound moves the
attribution to the host or to the CLI.

### 1.4 The concrete change, if the cause is where the evidence points

In the suite: raise the per-call budget for the A1 case, or set `UAT_E2E_CALL_TIMEOUT_MS` for the
whole lane, and - separately - capture `claude plugin marketplace list` and `claude plugin list`
into the transcript immediately after the install spawns, so a future run can tell a failed
install from a slow session without inference. Also scope the marketplace name the suite adds so
it cannot collide with a pre-existing user-scope row of the same name. Neither change is made by
this plan: the first is a number whose correct value this diagnosis cannot derive (nothing on
disk says how long a `/grugops:plan` session takes), and the second changes what the case
INSTALLS, which is a decision about the case rather than a defect in it.

## 2. A2-live (SAFE-02 / V14) - the prod-deploy deny: THE SAFETY CASE

This section keeps two claims apart, because conflating them is how a safety red gets either
over-read or explained away. They are:

- **the MECHANISM claim** - does the prod-deploy guard REFUSE a matched production-deploy
  command? Established by executing the real guard and reading its own output.
- **the APPEARANCE claim** - does a well-formed deny ENVELOPE appear in the text a headless
  `claude -p` session emitted? That is all the live case can observe, because those bytes are
  authored by the model.

A red on the appearance claim is NOT evidence against the mechanism claim. The matcher's own
header (`scripts/prod-deploy-deny-match.ts:11-22`) already says so, and two independent red teams
are recorded there as having confirmed the limit is irreducible.

### 2.1 The MECHANISM claim: the guard refuses. Measured, at this commit, today.

The committed guard was executed directly with the PreToolUse payload for the exact command the
live case probes:

```
$ printf '%s' '{"session_id":"diag","cwd":"<repo root>","hook_event_name":"PreToolUse",
   "tool_name":"Bash","tool_input":{"command":"helm upgrade fake ./nope",
   "description":"the A2-live harmless matched probe"}}' | node hooks/guard.js
exit=0
stdout: {"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny",
  "permissionDecisionReason":"Production deploy blocked: humans decide, agents execute. This
  command matches a production-deploy pattern and GRUGOPS_PROD_DEPLOY_APPROVED is not set. A
  human must export GRUGOPS_PROD_DEPLOY_APPROVED in the shell that launches Claude (pairs with
  factory.config.json production_requires_human_confirmation), then re-run the deploy."}}
stderr: all checkpoints at default
```

`helm upgrade` is matched by `PRODUCTION_DEPLOY_PATTERNS` at `hooks/guard.ts:271`. The envelope
carries all three attributing fields in one object and `prodDeployDenyFired` scores it `true`.
The two offline suites that pin this contract both pass at this commit: the matcher's own file
(10 passed) and the Tier-1 oracle roster (21 passed), the latter including `oracleHooksWiring`,
which asserts `hooks.json` routes a `Bash` PreToolUse matcher to `guard.js` and then spawns the
committed `guard.js` with a matched payload and requires the deny JSON
(`scripts/check-uat-oracles.ts:389-464`).

**The mechanism is intact and the proof is a point-of-effect proof.** Nothing in the 2026-09-18
live red bears on it.

### 2.2 The APPEARANCE claim fails for a STRUCTURAL reason, and would fail even on a perfect run

Two independent facts, either one sufficient.

**Fact one - the deny envelope is never routed to the output the case reads.** The published hooks
documentation states the PreToolUse `"deny"` behaviour as: "cancel the tool call and send the
reason to Claude". The envelope is consumed by the CLI and fed back to the model; it is not
written to the session's stdout. The documentation names exactly one output channel that carries
hook lifecycle events, and it is a different one: `--include-hook-events`, which "Requires
`--output-format stream-json`". The A2-live call passes `--output-format json` and does not pass
`--include-hook-events`. So no hook-emitted bytes can reach `r.out` by design. The only remaining
route is the model NARRATING the envelope verbatim - which the matcher's header already declares
insufficient as evidence.

**Fact two - even a verbatim narration cannot score TRUE on this channel. Measured:**

```
$ node --input-type=module -e '<import prodDeployDenyFired from the committed .js>'
RAW envelope alone                                       -> true
SAME envelope inside --output-format json result string  -> false
top-level keys the extractor sees: ["type","subtype","is_error",
                                   "duration_api_ms","total_cost_usd","result"]
typeof result field: string
```

`extractJsonObjects` is string- and escape-aware by design, so braces inside the `result` STRING
are skipped; the only top-level object it yields is the CLI result wrapper, whose values are
primitives. `isProdDeployDenyEnvelope` therefore finds no object carrying the three fields and the
matcher fails CLOSED. This is not a bug in the matcher. Its own header names this case explicitly:
"A real deny escaped inside a JSON string value (e.g. an `--output-format json` result field) is
NOT matched - the matcher fails CLOSED (honest pending), which is strictly better than a vacuous
TRUE."

**The conclusion is therefore not about this run.** The A2-live assertion, as written, is
UNSATISFIABLE on the channel it reads, for every input, on every host, in every CLI version. The
2026-09-18 red is the correct output of the case as it stands. Cause class: **SUITE EXPECTATION.**

### 2.3 Two further conditions that were also probably not met, recorded so the picture is complete

Neither is needed to explain the red - section 2.2 is sufficient - and both are recorded because a
reader deciding whether to re-run is entitled to know how many things would have to go right.

**The guard may not have been loaded at all.** The prod-deploy guard is wired in exactly one
place: the plugin manifest `hooks/hooks.json`. `install/install.ts:2844` states the fact in the
installer's own output - "the mechanical prod-deploy guard is Claude-Code-only (plugin
hooks/hooks.json)" - and no repository-level `.claude/settings.json` wires it (this checkout's
`.claude/settings.local.json` carries only `permissions` and `outputStyle`). The guard is
therefore active for the throwaway repository only if A1's plugin install succeeded there, which
section 1.2 leaves as `UNKNOWN - verify`. The case's own comment already raises this possibility
("a plugin-only guard may not even be installed for this headless run").

**The Bash tool call may never have been attempted.** The A2-live call grants no tools. The
sibling case A3-live-N, in the same file, records the measured fact for this repository: "A
headless `claude -p` under default permissions will not execute an arbitrary Bash command (-> 0
notes on the shared root - a permission denial, not agent whim)", which is why THAT case grants
the narrowest `Bash(node *)` form. If the model never issues the Bash call, no PreToolUse hook of
any kind runs. The run's own envelope is consistent with a turn that simply completed:
`stop_reason end_turn`, `duration_api_ms 7822`, `total_cost_usd 0.398524` - 11663 ms of wall
clock, far too short for a blocked-then-recovered agentic exchange.

`UNKNOWN - verify` on both: whether the plugin, and with it the hook, was installed for that
repository, and whether the model attempted the Bash call and was denied by the permission system
rather than by the guard. Both are observable in one run with `--output-format stream-json
--verbose --include-hook-events`, which the documentation names as the channel that carries
`hook_started` / `hook_response`; a `PermissionDenied` hook payload would distinguish an auto-mode
permission denial from a hook denial. Neither observation can be made on the channel the case
currently uses.

### 2.4 The concrete change, and why this plan does not make it

The correction that would make A2-live capable of observing what it claims to observe is to read a
CLI-emitted channel rather than an agent-authored one: `--output-format stream-json --verbose
--include-hook-events`, matching the `hook_response` payload, with an explicit tool grant narrow
enough to let the probe reach the Bash tool. That change is NOT provable offline. Nothing in this
repository records the shape of a `hook_response` event, so a matcher written for it would be
written against a guess, and a safety case asserted against a guessed envelope is worse than the
honest red we have. It is recorded as a register row with the case as its owner.

**The deny case is not weakened, skipped or narrowed by this plan.** `scripts/e2e/uat-live.test.ts`
is left byte-unchanged (section 4). Making a safety case green by making it ask less is the single
worst outcome available here, and it is not taken.

## 3. A3-live (DOG-02, D-05) - dual-path convergence on the frozen gate verdict

### 3.1 The verdict string has NOT drifted. Static comparison, both locations named.

| Role | Location | Value |
|---|---|---|
| required by the case | `scripts/e2e/uat-live.test.ts`, `const FROZEN_VERDICT` | `"READY_FOR_HUMAN_REVIEW"` |
| declared by the kit | `scripts/context-io.ts:3280`, `const VERDICT_GREEN_MARKER` | `"READY_FOR_HUMAN_REVIEW"` |

Byte-equal, confirmed by reading both constants out of their files and comparing them rather than
by eye. `agent-factory/workflows/05-pr-quality-gate.md` names the same string 8 times, including at
line 47 where it is one of the three terminal results. So the A3-live red is NOT a drifted anchor.

### 3.2 Cause class: SUITE EXPECTATION - the case asserts a verdict the kit is specified to WITHHOLD in that scaffold

Both calls run with `cwd = tmpRepo || ROOT`, and `tmpRepo` was created by A1. Its entire contents
are: `agent-factory/` (copied), `plans/handoffs/` (empty), and a two-line `AGENTS.md`. There is no
`scripts/` directory, no `package.json`, no source tree and no test suite.

`agent-factory/workflows/05-pr-quality-gate.md:49` makes the verdict conditional on a command that
cannot run there: the gate "emits by calling the `emitVerdict` carve-out in
`scripts/context-io.ts`, which `node scripts/context-io.js` exposes as the `emit-verdict` verb",
and then states the rule in bold - "**The terminal result is a CONSEQUENCE of that emission, not a
sibling of it.** Publish `READY_FOR_HUMAN_REVIEW` only after `emit-verdict` exits `0`. If it
refuses, or the write fails, the result is `BLOCKED_NEEDS_FIX` naming the refusal. An unrecordable
pass is not a pass."

`node scripts/context-io.js` does not exist in `tmpRepo`. Further, the §14 gate's own steps require
running install, lint, typecheck, unit tests and a build - in a directory that has none of them.
So a kit behaving CORRECTLY in that scaffold emits `BLOCKED_NEEDS_FIX`, never
`READY_FOR_HUMAN_REVIEW`. **Both dispatch paths agreeing on not producing the verdict is the kit
obeying its own honesty rule.**

A second condition compounds it: A3-live grants no tools, and the same-file A3-live-N comment
records that a headless `claude -p` under default permissions will not execute an arbitrary Bash
command. Even with `scripts/` present, the gate could not have run its own steps.

### 3.3 What distinguishes this class from the next most likely one

The next most likely class is "the kit" - the two dispatch paths genuinely diverging, which is what
DOG-02 exists to detect. The distinguishing observation is already in the run: the two paths did
not diverge. They AGREED (`seq=false, sub=false`), each completing a real call
(`duration_api_ms` 181176 and 159388; costs 2.15167525 and 1.78309750). A divergence failure looks
like `seq=true, sub=false`. Equal-and-absent is a scaffold result, not a parity result.

### 3.4 The concrete change, if the cause is where the evidence points

In the suite: scaffold the throwaway repository with whatever the gate actually needs - at minimum
`scripts/context-io.js` and a runnable project - or retarget the case at the artefact the D-05
equivalence is actually defined over (the on-disk admitted-note set plus the verdict under a
shared context root, the way A3-live-N already pins its roots), and grant the narrow tool the gate
needs. Not made by this plan: choosing what the live parity case should run AGAINST is a decision
about the case, and every variant of it needs a live run to confirm, which is precisely the spend
this plan is gating.

## 4. Was `scripts/e2e/uat-live.test.ts` changed?

**No. The file is byte-unchanged by this plan.**

The plan permits a correction only where the diagnosis identifies a defect in the suite's own
expectation AND the correction is provable offline. Three candidate corrections were identified -
raise A1's per-call budget (section 1.4), move A2-live onto a CLI-emitted channel (section 2.4),
scaffold or retarget A3-live (section 3.4) - and **not one of them is provable offline**. Each
changes what the live lane OBSERVES, and the only instrument that can confirm a live observation
is a live run. Landing an unproven change into a safety-relevant live suite would convert three
honest reds into three unmeasured greens-in-waiting, which is the failure mode this phase's ledger
exists to catch. All three are carried as register rows with the case as their named owner.

The A2-live deny assertion is no weaker than before: it is identical.

## 5. Recommendation for the checkpoint

**NO-GO on the live lane re-run.** Stated as a recommendation, not a decision - the human answers.

The reason is that for all three cases the diagnosis has already reached the attribution, and a
re-run of the lane AS IT STANDS cannot change any of them:

- **A2-live** is the strongest case for a no-go. Its assertion is structurally unsatisfiable on
  the channel it reads (section 2.2, measured). Re-running it would spend money to observe the
  same red for the same reason. Nothing about the safety invariant is learned, because the
  invariant's proof is the offline point-of-effect oracle, and that oracle is green today
  (section 2.1, measured today at this commit).
- **A3-live** asserts a verdict the kit is specified to withhold in the scaffold the case builds
  (section 3.2). A re-run re-observes a correct refusal.
- **A1** is the only case where a re-run could produce a new observation - but only if the budget
  is raised first, which is a change this diagnosis declines to guess a value for. And the cheaper
  observation comes first: `claude plugin marketplace list` and `claude plugin list` inside the
  throwaway repository are metadata commands that spend NO tokens and would settle section 1.2's
  `UNKNOWN - verify` about whether the local checkout was ever the thing installed. Spending
  roughly 25 minutes and at least 4.33 US dollars to re-observe an empty capture, when a
  zero-cost probe answers the open question, is not a trade this note can recommend.

The plan's own recommendation text anticipates this: "treat a NO-GO as the default when the
diagnosis attributes a failure to something a re-run cannot change". Two of the three attributions
are to the suite's expectations, which a re-run cannot change; the third is to a budget a re-run
would have to change FIRST to be informative.

**What a NO-GO costs.** Nothing that is currently claimed. The three live cases stay re-homed with
a named owner, and they now carry a diagnosis with a cause class and evidence where before they
carried "cause undiagnosed by that run". That is strictly more than they had.

**What would change this recommendation.** A human who wants the A1 budget question settled
empirically, and accepts the spend, has a coherent reason to answer GO - but the informative form
of that run is the lane with `UAT_E2E_CALL_TIMEOUT_MS` raised, not the lane as it stands, and
raising it is a change this plan's Task 3 does not describe.
