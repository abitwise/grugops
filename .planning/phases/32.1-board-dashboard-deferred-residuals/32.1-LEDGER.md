# Phase 32.1 completion ledger

**What this file is.** The artefact a verifier reads to decide whether phase 32.1 is done. Phase 32
spent its four-round gap-closure cap and ended at a human decision (`32-41`, Option C,
`defer-to-next-phase`, 2026-09-17) precisely because completion had become arguable. This phase's
answer is to make completion a **count equality** whose denominator a reader can re-derive: every
item is enumerated from a named source, every item carries exactly one terminal disposition, and the
two counts are compared by a script rather than by this document's prose.

The equality is measured by `32.1-ledger-check.mjs`, filed beside this file, and its output is in
`32.1-11-GREEN-proof.txt`. If you are checking this phase, run the script; do not read the number
out of a sentence.

### 1.1 The nineteen-versus-twenty reconciliation

Three documents on this tree count this phase's work three different ways. All three numbers are
correct about what they count, and they count different things. D-16's rule applied to D-16 is that
the number is a measurement, so the disagreement is reconciled here rather than resolved by picking
a favourite.

**Twenty** — `32.1-CONTEXT.md` `<domain>`, and `32.1-CONTEXT.md` D-16. The prose says "the 20 items"
and "the eight carried or undecidable ledger rows re-homed here". Its own list then enumerates seven
row identifiers (176, 183, 184, 194, 208, 209, 210) and adds "plus row 207's nested-runner half
which is F-21". That eighth entry is F-21, which the same sentence has already counted among the
eight round-4 findings. Twenty is therefore **nineteen distinct items with F-21 counted twice** —
once as a finding and once as the carried nested-runner half of the ledger row it occupies.
`32.1-RESEARCH.md` §Contradictions row 14 measured exactly this and graded it MEDIUM, and
§Open Questions item 3 asked for the denominator to be defined before a line was written. It is
defined above.

**Nineteen** — this file, per D-22. Eight findings, seven ledger row identifiers, four review
warnings. Each item appears once. This is the count the check measures.

**Eighteen** — `deferred-items.md` § "The 18 open items and the owner each now carries", whose
numbering and homes column come from `32-41-OVERRIDE-DRAFT.md` § 3. That table counts **homes**, not
items: it maps each open item to an override block, a `deferred-items.md` row, or a `WINDOWS.md`
ledger row, and its purpose was to prove that no item was left without a home. Three differences
account for the gap, and they run in both directions:

- it **includes two items this phase does not own** — items 11 and 16, the two halves of the
  `windows-latest` measurement, homed to ledger rows 186 and 193 and kept with Phase 33 by that
  table's own stated reason (`32.1-CONTEXT.md` names them out of scope);
- it **gives F-21 a second home** — item 8 is F-21 at row 207, and item 17 is the nested-runner half
  of the same row, carried separately in `deferred-items.md` and marked `207 (= F-21)` in the table
  itself. Counting homes, that is two rows; counting items, it is one item;
- it **omits WR-01 .. WR-04 entirely** — a review warning carries no ledger row, so under a
  homes-based accounting it has nothing to be homed to. All four are nevertheless work this phase
  did, and all four are in the enumeration above.

The arithmetic closes: `18 - 2 (Phase 33) - 1 (F-21's second home) = 15`, which is this file's
fifteen non-warning items, and `15 + 4 = 19`.

### 1.3 The nineteen-versus-twenty-nine reconciliation (plan 32.1-15, D-16 and D-22)

The denominator moved from nineteen to twenty-nine. Section 1.1 exists to reconcile counts that
disagree, and this one is recorded the same way, because a denominator that moves without a
reconciliation is indistinguishable from a goalpost that moved.

**What nineteen counted.** Phase 32's unfinished work, as phase 32 left it: its eight round-4
findings, its four round-4 review warnings, and the seven ledger rows it carried forward. Every
item in that set was authored before phase 32.1 opened. That is a complete and correct count of
**the work this phase inherited**.

**What twenty-nine counts.** The same nineteen, plus the ten items **this phase's own code review**
raised against the code this phase wrote — `32.1-REVIEW.md`'s three warnings and seven information
items. Those ten were real findings against real modules, and every one of them was dispositioned
by plans 32.1-12 through 32.1-14 *before* this widening; what they were not, until now, was
**inside the count that decides whether the phase is done**.

**Why that is a change of scope and not a moved goalpost.** A moved goalpost makes a target easier
to reach. This widening makes it strictly harder: ten items were added to the denominator and the
completion equality must now hold over all of them, so the phase cannot read as complete on the
strength of the nineteen alone. The direction is the test. A denominator that grows when the
evidence grows is a measurement; one that shrinks when the evidence is inconvenient is the failure
this file exists to prevent. Concretely: before the widening, `32.1-REVIEW.md` could have contained
a critical finding nobody addressed and this ledger would still have printed a clean equality over
nineteen, because the review was not one of its sources. That is a completion equality over the
wrong set.

**One defect observed twice is ONE item.** `32.1-VERIFICATION.md`'s single **failed** must-have
truth — D-07, "the `spelled` refusal-sentence builder owns every content-derived interpolation
across all three board modules" — and `32.1-REVIEW.md`'s **first warning**, `WR-01` ("a composed
path carrying a listing entry's name reaches a published sentence unescaped"), are **the same
defect**, seen by two instruments. The verifier found it by asking whether the phase's own must-have
held; the reviewer found it by tracing `childPath` through `board-read.ts` to eleven message sites.
Both name the same unbuilt substitutions in the same module. It is therefore enumerated **once**, as
`32.1-WR-01`, and the verifier's failed truth is **not** a separate item. Recording it twice would
have inflated the denominator by one and then satisfied both copies with a single closure — the
exact double-count shape § 1.1 exists to catch, arriving from a new direction.

Its single closure is correspondingly doubled-checked: plan 32.1-12 reproduced the defect end to end
at three channels, and plan 32.1-13 closed it by deleting the classification rather than redrawing
it, moving **all 42** unowned published substitutions in the three board modules rather than the 16
of the path class that plan 32.1-12 had scoped.

`waived-with-reason`: there is no structural limit here — `git status --porcelain -- '*.js'` would
see both the modified and the untracked file, and the remedy is known and cheap. What is missing is
a decision, so the honest disposition is a named owner carrying the measurement.

### 3.5 `32.1-IN-06` — guardedness decided per enclosing function

**Owner:** the F-19 / IN-03 computed-key census rule in `scripts/check-foundation-guards.test.ts`,
together with `.planning/WINDOWS.md` row 223.

**The measurement that made re-homing the honest answer.** A computed-key read counts as guarded
when any `Object.hasOwn(REGISTER, …)` call resolves to the same register **inside the same
function**, so `Object.hasOwn(R, a) ? R[b] : undefined` passes. Two facts bound it, and both are
measured rather than assumed: the `scattered` assertion holds one function per register, which
bounds the blast radius to a single function, and the text-based rule this replaced had the **same**
granularity, so it is not a regression. Closing it is therefore a tightening rather than a repair,
and the remedy is already written down — require the `hasOwn` call to be an ancestor condition of
the read, by walking `read.parent` for a `ConditionalExpression` or `IfStatement` whose test
contains the guard. Why not `closed-with-reproduction`: nothing was closed. Why not
`waived-with-reason`: a waive records what an instrument **cannot** observe, and this one can — the
parent walk is available to it. The gap is a scope decision, so it carries an owner.
