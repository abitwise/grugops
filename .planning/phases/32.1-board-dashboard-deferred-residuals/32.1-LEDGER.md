# Phase 32.1 completion ledger

**What this file is.** The artefact a verifier reads to decide whether phase 32.1 is done. Phase 32
spent its four-round gap-closure cap and ended at a human decision (`32-41`, Option C,
`defer-to-next-phase`, 2026-09-17) precisely because completion had become arguable. This phase's
answer is to make completion a **count equality** whose denominator a reader can re-derive: every
item is enumerated from a named source, every item carries exactly one terminal disposition, and the
two counts are compared by a script rather than by this document's prose.

The equality is measured by `32.1-ledger-check.mjs`, filed beside this file, and its output is in
`32.1-11-GREEN-proof.txt`. If you are checking this phase, run the script; do not read the number
out of a sentence.

### 1.1 The nineteen-versus-twenty reconciliation

Three documents on this tree count this phase's work three different ways. All three numbers are
correct about what they count, and they count different things. D-16's rule applied to D-16 is that
the number is a measurement, so the disagreement is reconciled here rather than resolved by picking
a favourite.

**Twenty** — `32.1-CONTEXT.md` `<domain>`, and `32.1-CONTEXT.md` D-16. The prose says "the 20 items"
and "the eight carried or undecidable ledger rows re-homed here". Its own list then enumerates seven
row identifiers (176, 183, 184, 194, 208, 209, 210) and adds "plus row 207's nested-runner half
which is F-21". That eighth entry is F-21, which the same sentence has already counted among the
eight round-4 findings. Twenty is therefore **nineteen distinct items with F-21 counted twice** —
once as a finding and once as the carried nested-runner half of the ledger row it occupies.
`32.1-RESEARCH.md` §Contradictions row 14 measured exactly this and graded it MEDIUM, and
§Open Questions item 3 asked for the denominator to be defined before a line was written. It is
defined above.

**Nineteen** — this file, per D-22. Eight findings, seven ledger row identifiers, four review
warnings. Each item appears once. This is the count the check measures.

**Eighteen** — `deferred-items.md` § "The 18 open items and the owner each now carries", whose
numbering and homes column come from `32-41-OVERRIDE-DRAFT.md` § 3. That table counts **homes**, not
items: it maps each open item to an override block, a `deferred-items.md` row, or a `WINDOWS.md`
ledger row, and its purpose was to prove that no item was left without a home. Three differences
account for the gap, and they run in both directions:

- it **includes two items this phase does not own** — items 11 and 16, the two halves of the
  `windows-latest` measurement, homed to ledger rows 186 and 193 and kept with Phase 33 by that
  table's own stated reason (`32.1-CONTEXT.md` names them out of scope);
- it **gives F-21 a second home** — item 8 is F-21 at row 207, and item 17 is the nested-runner half
  of the same row, carried separately in `deferred-items.md` and marked `207 (= F-21)` in the table
  itself. Counting homes, that is two rows; counting items, it is one item;
- it **omits WR-01 .. WR-04 entirely** — a review warning carries no ledger row, so under a
  homes-based accounting it has nothing to be homed to. All four are nevertheless work this phase
  did, and all four are in the enumeration above.

The arithmetic closes: `18 - 2 (Phase 33) - 1 (F-21's second home) = 15`, which is this file's
fifteen non-warning items, and `15 + 4 = 19`.

## 3. The two re-homed items, with their owners and the measurements behind them

`re-homed-with-named-owner` is not a deferral. It is the disposition for an item where a measurement
established that the remedy the phase set out to apply does not apply, and the honest answer is a
named owner carrying the measurement rather than a closure nobody can reproduce. The residual ledger
has no status for re-homing, so both rows stay `open` in `.planning/WINDOWS.md` by design, and this
file carries the owner. A later reader must not read that `open` as an oversight.

### 3.1 Row 183 — the live claude-CLI end-to-end lane

**Owner:** `scripts/e2e/uat-live.test.ts`, together with the register rows this plan appends for the
three failing cases and for the file's stale docblock (§ 4.3; the assigned ids are recorded in
`32.1-11-GREEN-proof.txt`).

**The measurement that made re-homing the honest answer.** The row read "the live claude-CLI e2e
lane was not run for plan 32-17 ... its state is UNKNOWN - verify". Plan 32.1-10 answered it: behind
a `blocking-human` checkpoint the human answered **go**, the lane was run **once**, from 09:41:34Z to
10:06:37Z on 2026-09-18, and it reported `Test Files 1 failed | 75 passed (76)` and
`Tests 3 failed | 5227 passed | 2 skipped (5232)`. The outcome is recorded as `fail`.

The state is therefore known and it is bad. Three live cases failed against the real CLI:

- **A1** (D-31, plugin-cache pointer resolution) — 606161 ms, capture **empty**;
- **A2-live** (SAFE-02 / V14, the prod-deploy deny) — 11663 ms, the call completed with
  `stop_reason: end_turn` and the guard's structured deny envelope never appeared. **This is a
  safety case.**
- **A3-live** (DOG-02 / D-05, dual-path convergence) — 370297 ms, both paths completed and neither
  produced the frozen verdict.

Why not `closed-with-reproduction`: nothing was reproduced closed. Why not `waived-with-reason`: a
waive rests on a structural limit, and there is none here — the instrument worked, it was pointed at
the question, and it returned a red. Whether the cause is the kit, the suite's expectations, the CLI
version on that box (2.1.275) or that host's configuration is **not determined by that run**, and
`32.1-10-SUMMARY.md` attaches no diagnosis. The go covered one occasion and explicitly not a re-run,
so this phase cannot measure further; D-17 forbids an adversarial round inside it and the standing
four-round cap bounds anything after it. The honest disposition is a named owner carrying the red.

Two further facts the transcript records rather than smooths: the exit code is **derived** from the
runner's own summary and not captured by `wait()` (the reason is named in
`32.1-10-LIVE-TRANSCRIPT.txt` § 7), and the visible `total_cost_usd` values sum to 4.33 USD, which
is a **floor** rather than a total.

### 3.2 Row 210 — the ninth `NOT_A_SECOND_AUTHORITY` exemption

**Owner:** the ninth entry of the `NOT_A_SECOND_AUTHORITY` registry in `scripts/validate.test.ts`,

## 4. What this phase did to `.planning/WINDOWS.md`

Every mutation ran through the ledger tool's own verbs. Both of the ledger's representations are
rendered by the tool from one set of entries and its frontmatter counters are cross-checked against
those entries, so a hand edit throws rather than landing. The reconciliation between the two
representations is by **row identifier** with a symmetric difference of zero, never by column
position (at least three descriptions carry an escaped separator that shifts a positional tally by
three) and never by row count. The measurements are in `32.1-11-GREEN-proof.txt`.

### 4.1 Rows set to `fixed`

`176`, `194`, `209`, and `200` through `207` — the eight finding rows, in F-number order. Eleven
rows, one verb call each, each against the evidence its row in § 2 names.

### 4.2 Rows set to `waived`

`184` and `208`, with the final reason sentences `32.1-08-GREEN-proof.txt` § 3 measured. Each reason
states a **structural limit** — what an instrument over this corpus cannot observe, and why — rather
than a schedule. The waive verb is one-shot and overwrites the reason cell, which is why those
sentences were finalised a plan earlier and are passed verbatim. Row 208's reason is the **composed**
sentence covering both of its structural halves, because the row has one reason cell.

This is the first use of `waived` on this ledger. Nothing was implemented for it: the tool's status
vocabulary already declares `waived` beside `open` and `fixed`, its waive verb already requires a
non-empty reason, and its counter cross-check already recomputes all four totals. This phase is that
verb's first caller.

### 4.3 Rows appended

Nine rows, for defects this phase's own plans named and no plan closed. They are appended rather
than left in prose so each is OPEN in the register rather than ABSENT from it; `32.1-10-SUMMARY.md`
explicitly deferred the first four to this plan. The assigned identifiers are recorded in
`32.1-11-GREEN-proof.txt`.

- the three live cases that failed on 2026-09-18 (A1, A2-live, A3-live) — row 183's re-home owners;
- the stale docblock in `scripts/e2e/uat-live.test.ts` claiming the live lane is kept out of the
  default `npm test` path, which is false of this tree;
- `R-32.1-01-A` — IN-05, the presence-spelling walk in `scripts/board-model.test.ts` reading
  untracked files, not closed by plan 01's tracked-set floor (§ 3.3);
- `R-32.1-01-B` — `(r-class-authority)` classifies a `*.test-support.ts` file as shipped;
- `R-32.1-01-C` — the walker-importer derivation is still a text match rather than a checker
  resolution;
- plan 32.1-07's two named residuals — `conflicts[].ticketId` still publishes the byte deleted, and
  the census's declaration key is `<file>#<name>` so two declarations sharing a name in one file
  share a class.

### 4.4 The governance effect, named rather than discovered later

`open_count` gates `/gsd-ship` when `workflow.windows_enforce` is on. Fixing a row and waiving a row
both **lower** it; appending a row raises it. The before and after numbers, and the net movement, are
recorded in `32.1-11-GREEN-proof.txt` so the change is attributed here rather than found by somebody
later wondering why a gate stopped blocking. On this tree `workflow.windows_enforce` is `false`
today, so the gate is not currently blocking either way — which is itself a reason to record the
movement rather than rely on a gate to surface it.

## 5. The posture this phase deliberately took (D-17)

**No adversarial red-team round ran inside phase 32.1.** Verification is `gsd-code-review` plus the
verifier against the count equality in § 2, and the standing four-round gap-closure cap bounds any
gap-closure that follows. Phase 32 spent that cap; this phase did not open a new one by running
rounds of its own.

**The eight requirements are not re-verified from scratch.** DASH-01 .. DASH-08 were Complete before
this phase opened. The requirement column in § 2 says which residual bore on which requirement and
nothing more.

**The completion equality is this plan's gate, not a permanent suite case.** A permanent case that
reads a phase document under the planning directory turns the suite red on the commit that writes
that document — this repository has already paid for that shape once, in a phase whose coverage case
read a review file. `32.1-ledger-check.mjs` is a small derived check filed beside the phase; the
suite stays about the code.
