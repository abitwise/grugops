# Phase 32.1: Code Review Report

**Reviewed:** 2026-09-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 29
**Status:** issues_found

## Summary

The phase touches four shipped modules (`board-model.ts`, `board-read.ts`, `board-dashboard.ts`, `js-import-closure.ts`), adds one gate module (`check-build-parity.ts`) and two un-emitted test-support modules, rewrites the module-specifier extractor from a hand-written scanner to a TypeScript-parse walk with a lazily acquired parser, moves the F-20 liveness probe onto the resolved path, introduces the `spelled` tagged template for content-derived values, and lands two disposition registers. The committed `.js` files were verified rather than assumed: every in-scope `.js` is byte-identical to a fresh `tsc` rebuild into a scratch directory, the `*.test-support.ts` modules are not emitted, and the `check-diff-disposition.js` hash carried in `hooks/hook-entry.ts` matches the committed file.

The safety surfaces stand. The prod-deploy guard is untouched except for a regenerated manifest hash; the dashboard's read-only posture is unchanged (the loader oracle asserts a before/after `git status --porcelain` equality, and vitest runs files serially so that snapshot cannot race another file); containment on the watch path became strictly tighter (`deps.exists(decision.real)` replaces `deps.exists(dir)`, and `deps.watch` already opened `decision.real`). The lazily acquired `typescript` in `js-import-closure.ts` follows the sanctioned D-20 pattern: memoized, behind `createRequire`, with a named `ImportClosureError` on absence, and no top-level non-builtin import anywhere in `scripts/*.ts` shipped output. `spelled` is idempotent by construction (`visible` emits only printable ASCII), so the nested application at `board-dashboard.ts:1266` does not double-escape.

Three warnings. The first is the F-14 class one register over: `spelled`'s docblock declares PATH-DERIVED values out of scope on the argument that the entry name inside a composed path "is itself content-derived and escaped above", and that argument is false at seven `board-read.ts` message sites where the sentence carries only the composed path. The second is that the new tokenizer never consults parse diagnostics, so a source with an unterminated block comment or template literal yields a silently short closure at exit 0, which is the exact outcome the module's header says it refuses. The third is a test-reliability hazard in the loader oracle: the child load has no timeout, so the failure mode of the premise it guards is a hung suite rather than a red one.

## Warnings

### WR-01: A composed path carrying a listing entry's name reaches a published sentence unescaped, and the carve-out's stated reason does not hold at those sites

**File:** `scripts/board-model.ts:1114-1125` (the PATH-DERIVED carve-out), with the reachable sites at `scripts/board-read.ts:1041` (predicate), `:1591`, `:1609`, `:1753`, `:1771`, `:240`, `:292`, `:381`, `:730`, `:742`, `:757`
**Issue:** `spelled`'s docblock excludes path-derived values from the builder on the reasoning that "an author reaches it only by creating a filesystem entry, and the entry NAME that lets them is itself content-derived and escaped above." Traced through `board-read.ts`, that is not what the code does. `childPath` (line 1041) refuses a segment only when it is empty, `.`, `..`, or carries `/` or `\`; a C1 code point such as U+0085 in a directory entry's name is a plain segment and is joined into `taskDir` (line 1535) and `claimMd` (line 1551). The `tampered` (line 1591) and `no-at` (line 1609) messages then interpolate `claimMd` and nothing else, so the only place the entry's name appears in the published sentence is inside the composed path, raw. `RENDER_STRIPPED` deletes the byte at every channel, and the `--json` document states that `.grugops/queue/claimed/X<U+0085>Y/claim.md carries no at: line` with the byte gone: a path that does not exist on the tree. The same shape holds for `taskDir` at lines 1753 and 1771 (context entry name), `absPath` at lines 240 and 292 (ticket entry name), `path` at line 381, and `target` in the three `insideRoot` refusals at lines 730, 742 and 757 (`childPath` passes the composed target at line 1055). The derived census in `board-model.test.ts` pins `board-read.ts#claimMd`, `#taskDir`, `#absPath`, `#path` and `#target` as `"path"`, which records the gap as a decision but does not close it. This is F-14's own defect on the path axis, and the phase's remedy for F-14 (spell, never delete) applies unchanged.
**Fix:** Treat a path composed from a listing entry as content-derived. `spelled` is idempotent, so the cheapest closure is to route every `message:` sentence in `board-read.ts` through it and move the affected keys from `NOT_CONTENT_DECLARATIONS` to `CONTENT_DECLARATIONS` in `scripts/board-model.test.ts`, then re-derive the three pinned counts. If the carve-out is kept, its docblock should state the true bound: a composed path is escaped only where the same sentence separately quotes the escaped name, and the seven sites above do not.
```ts
// scripts/board-read.ts:1609 — before
message:
  `${claimMd} carries no \`at:\` line and a claim record is written with exactly one. ` + …
// after
message:
  spelled`${claimMd} carries no \`at:\` line and a claim record is written with exactly one. ` + …
```

### WR-02: The parse walk never consults parse diagnostics, so a malformed source yields a silently short closure at exit 0

**File:** `scripts/js-import-closure.ts:446-507` (`moduleSpecifierFacts`), `:489-494` (declaration arm)
**Issue:** The header states the module "REFUSES RATHER THAN RETURNS SHORT" and that a slot it cannot read is "never silently treated as 'no edge here'". `ts.createSourceFile` never throws on a syntax error; it recovers and returns a partial tree, and the walk reads that tree without asking whether the parse was clean. Probed against the committed `scripts/js-import-closure.js`: `import a from "./a.js";\n/* never closed\nimport b from "./b.js";` yields `["./a.js"]` with an empty `unreadable` list, and the same for an unterminated template literal. A closure built from that answer is short by `./b.js` with no throw and no diagnostic, which is the precise outcome the header calls the failure it exists to prevent. Separately, the import/export declaration arm at lines 493-494 calls `readValue`, which pushes only when the specifier is string-literal-like; `import a from foo;` therefore records neither a specifier nor an unreadable site (probed: `[]` / `[]`). That is a syntax error rather than a live shape in `tsc` output, but it is the one arm where the "recorded, never dropped" rule is not implemented, and mirrors in this repository append author-written source to committed modules before walking them.
**Fix:** Refuse a source whose parse produced diagnostics, and record a non-literal declaration specifier into the D-11 seam. Every `SourceFile` carries `parseDiagnostics` at run time; declare it optionally on the structural surface so no `typescript` type is imported.
```ts
interface TsSourceFile extends TsNode {
  readonly parseDiagnostics?: readonly { readonly messageText: unknown }[];
}
// in moduleSpecifierFacts, after createSourceFile:
const faults = (sourceFile as TsSourceFile).parseDiagnostics ?? [];
if (faults.length > 0) {
  throw new ImportClosureError(
    `js-import-closure: the source did not parse cleanly (${faults.length} syntax diagnostic(s)), ` +
      `so the walk cannot vouch that every import was seen. A closure read off a recovered parse ` +
      `is short by an unknown amount; the walk refuses instead.`,
  );
}
// declaration arm: record what readValue declines
if (specifier !== undefined && !api.isStringLiteralLike(specifier)) {
  unreadable.push({ form: "declaration", nodeKind: specifier.kind, nodeKindName: nodeKindName(api, specifier.kind) });
}
```
(`UnreadableSpecifierSite["form"]` gains `"declaration"`; the `D11_ARGUMENT_SHAPES` table in `board-readonly.test.ts` is unaffected because it enumerates dynamic-import shapes.)

### WR-03: The loader oracle's child process has no timeout, so the premise it guards fails as a hung suite rather than a red one

**File:** `scripts/loader-oracle.test-support.ts:151-155`
**Issue:** The module's header records, from measurement, that when `process.argv[1]` is the dashboard entry the dashboard "RUNS ITS MAIN". `board-dashboard.js` without `--once` is a live watch loop that never exits, and the child's stdout is piped. The current shaping (a real script file as `argv[1]`) avoids that today, but the assertion that protects it is the `treeBefore === treeAfter` equality in `board-readonly.test.ts`, which is only reachable after `execFileSync` returns. If `is-entry` ever mis-detects (the very case the header discusses), `execFileSync` blocks forever, the vitest worker hangs, and CI reports a timeout with no message naming the cause. A guard whose failure mode is silence is the shape this repository's ledger records repeatedly.
**Fix:** Bound the child and turn a timeout into a named premise failure.
```ts
execFileSync(process.execPath, [scriptPath, join(root, entryRel), resultPath], {
  cwd: root,
  encoding: "utf8",
  stdio: ["ignore", "pipe", "pipe"],
  timeout: 60_000,
  killSignal: "SIGKILL",
});
```
and in the consumer, catch `error.signal === "SIGKILL"` / `error.code === "ETIMEDOUT"` and fail with: "the corpus load did not return — the entry's main most likely ran, which is the is-entry premise this oracle rests on".

## Info

### IN-01: A spawn failure of the build is reported with an empty detail

**File:** `scripts/check-build-parity.ts:115-121`
**Issue:** `spawnSync("npx", ["tsc"])` without `shell: true` fails with `ENOENT` on Windows (the binary is `npx.cmd`); `build.status` is then `null`, the `!== 0` test correctly fails closed, but `build.error` is never surfaced, so the operator reads "the build did not complete" with no cause. `freshness.ts:236-245` has the same shape, so this is consistent with its sibling; CI scopes the step to ubuntu.
**Fix:** Append `build.error?.message` to `detail` when present.

### IN-02: The parity oracle inherits the `git diff`-ignores-untracked blind spot the workflow itself documents

**File:** `scripts/check-build-parity.ts:93-95`; `.github/workflows/ci.yml:231-237`
**Issue:** `git diff --name-only -- '*.js'` cannot see a `.js` the build produced for a new `.ts` that has no committed twin; the module's header is honest that this is "the same set the inline command asked about, moved rather than reinterpreted". The workflow records at lines 231-237 that exactly this class let an untracked adapter through, and replaced it with a `git status --porcelain` pair. On this tree the case is caught downstream only because the second freshness block (line 188) runs after the build and its `workingOnly` arm sees the file on disk; the parity gate's PASS line is therefore correct but ordering-dependent.
**Fix:** Derive `movedBuildOutputs` from `git status --porcelain -- '*.js'` (modified and untracked alike) so the parity gate does not depend on a later step to hold its own subject, or record the ordering dependency in the module header.

### IN-03: `check:build-parity` compiles the tree twice

**File:** `package.json:15`
**Issue:** The declared command shape prefixes `tsc --outDir .tmp-build`, and the module then runs `npx tsc` into `./` itself. Two full compiles per invocation; harmless, and forced by the zero-exemption shape rule in `check-foundation-guards.test.ts`.
**Fix:** None required. If the cost matters, have the module accept a `GRUGOPS_SKIP_TYPECHECK` style flag is the wrong move; the honest fix is a third declared shape, which the test deliberately refuses. Leave as is and note it.

### IN-04: `module.registerHooks` needs Node 22.15+, but `engines` promises only `>=22`

**File:** `scripts/loader-oracle.test-support.ts:96`; `package.json:6`
**Issue:** On Node 22.0 through 22.14 the oracle child fails at import time with a `SyntaxError` about a missing named export, surfaced to the test as an opaque `execFileSync` throw. CI resolves `22` to the latest patch so it is green there; a contributor on an older 22.x gets a failure that does not name the cause.
**Fix:** In the oracle script, `import * as m from "node:module"` and refuse by name when `typeof m.registerHooks !== "function"`, or raise `engines.node` to `>=22.15`.

### IN-05: `freshness:hook-manifest` is invoked by no CI step

### IN-06: "Guarded" is decided per enclosing function, not per read

**File:** `scripts/check-foundation-guards.test.ts:1176-1183` (diff numbering; the F-19 / IN-03 census)
**Issue:** A computed-key read counts as guarded when any `Object.hasOwn(REGISTER, …)` call resolves to the same register inside the same function, so `Object.hasOwn(R, a) ? R[b] : undefined` passes. The `scattered` assertion (one function per register) narrows the blast radius, and the prior text-based rule had the same granularity, so this is not a regression.
**Fix:** If tightened later, require the `hasOwn` call to be an ancestor condition of the read (walk `read.parent` chain for a `ConditionalExpression`/`IfStatement` whose test contains the guard).

### IN-07: The runtime module set is relativised against an unresolved root

**File:** `scripts/loader-oracle.test-support.ts:167-173`
**Issue:** Node's ESM resolver reports real paths (symlinks resolved) unless `--preserve-symlinks`; `relative(root, fileURLToPath(...))` uses the caller's spelling of `root`. A checkout that lives under a symlinked directory (macOS `/tmp` is one) produces `../…` entries and reds the three-authority equality for a reason unrelated to the closure. The module's own comment treats a `../` spelling as a deliberate loud outcome, which is right for an escape and wrong for a symlinked checkout.
**Fix:** `const realRoot = realpathSync(root)` once, and relativise against it.
