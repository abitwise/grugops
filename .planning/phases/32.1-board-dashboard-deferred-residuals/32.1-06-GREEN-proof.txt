§ 3 — THE ABSENT-PARSER REFUSAL, MEASURED RATHER THAN SIMULATED
----------------------------------------------------------------

The refusal route cannot be reached by injection — injecting a parser is what bypasses acquisition.
So the committed build output is mirrored into a directory with no `node_modules` anywhere above it
and Node is spawned there. `createRequire` resolves from the MODULE'S own location, so the mirror
genuinely has no parser to find.

  $ M=$(mktemp -d) && mkdir -p "$M/scripts" && cp scripts/js-import-closure.js "$M/scripts/" \
      && printf '{ "type": "module" }\n' > "$M/package.json" \
      && cat > "$M/probe.mjs" <<'PROBE'
  import { moduleSpecifiers } from "./scripts/js-import-closure.js";
  try { moduleSpecifiers('import x from "./a.js";'); console.log("NO-REFUSAL"); }
  catch (error) { console.log(`${error.name}: ${error.message}`); }
  PROBE
  $ node "$M/probe.mjs"

  ImportClosureError: js-import-closure: the module specifier extractor could not acquire
  "typescript", so moduleSpecifiers cannot read a source and the closure walk cannot start. This
  module is a DEVELOPMENT and CONTINUOUS-INTEGRATION tool — it is run from a checkout by the
  freshness gates, the hook-manifest generator and the platform-shape check, never by a host running
  the installed kit — so the fix is to install this repository's dev dependencies. It refuses rather
  than falling back to a pattern match: a second grammar for JavaScript is exactly what 32.1-06
  deleted, and a fallback that reads SOME imports hands back a closure missing precisely the file the
  walk could not see.

  It is a NAMED refusal, not a crash and not an empty result: it says which module could not be
  acquired, which function needed it, what kind of program this is, and therefore what to do. The
  case asserts all four of those substrings, so a message that degrades into "cannot find module"
  reds rather than passes. T-32.1-06-03 is mitigated by this, measured.

§ 5 — THREE AUTHORITIES, ONE QUESTION
--------------------------------------

Asserted in one case, per entry, over `scripts/board-dashboard.js`:

  1. the STATIC WALK          — `jsImportClosure(ROOT, DASHBOARD_ENTRY)`, the subject;
  2. an INDEPENDENT PARSE     — the closure rebuilt over `parsedSpecifiers`, a second implementation
                                of the stated node set written out in the test file;
  3. NODE'S OWN RESOLVER      — `recordRuntimeAcquisitions`, which shares neither this code nor this
                                parser.

  The third is the one F-17 proves is load-bearing: two parsers asking one question are blind to the
  same shape, which is exactly how the old two-sided oracle stayed green over a hole. Both premises
  are floored (the static closure has more than one module; the runtime recorded more than one), so
  neither equality can hold over an empty set.

  `parsedSpecifiers` deliberately does NOT re-implement `classifySpecifier`. The suite's own rule
  "this file decides no specifier's class itself — it asks the one authority" caught the first draft,
  which tested `startsWith("./")` inline — the exact fourth-arm shape 32-31 removed. The oracle is
  independent in traversal and value extraction and asks the one authority about class, because what
  is being cross-checked here is the CLOSURE, not the partition.
