Section 2 -- the reconciliation, BY ROW IDENTIFIER
-------------------------------------------------------------------------------

The comparison is between the identifier SET of the markdown table and the
identifier SET of the fenced JSON array. It is NOT a row count and it is NOT a
column-position tally. Both of those refusals are measured below rather than
asserted.

  $ node reconcile.mjs

  === reconciliation of .planning/WINDOWS.md's two representations, BY ROW IDENTIFIER
  table  representation: 219 distinct identifier(s)
  array  representation: 219 distinct identifier(s)
  only in table : []
  only in array : []
  SYMMETRIC DIFFERENCE = 0

  per-identifier STATUS agreement: every identifier carries the same status in both representations

  frontmatter counters : {"open":193,"waived":2,"fixed":24,"total":219}
  derived from entries : {"open":193,"waived":2,"fixed":24,"total":219}
  counters agree       : true

  === why the comparison is BY IDENTIFIER and not by column position or by row count
  naive positional tally of status==open (split on EVERY '|') : 191
  tally over UNESCAPED separators, keyed by identifier        : 193
  the array's own open count                                  : 193
  the two disagree by 2, because descriptions carry an escaped separator that shifts a positional index.
  rows whose description carries an escaped separator: 4

  RECONCILED: symmetric difference 0, statuses agree per identifier, counters re-derive.

WHAT THE LAST BLOCK IS FOR. A naive `split("|")` over the table returns 191 open
rows where the array says 193, because four descriptions carry an escaped
separator that shifts every column index to its right. A reader who reconciled
that way would find a two-row disagreement and go looking for two missing rows
that do not exist. `32.1-RESEARCH.md` section D-14 measured the same hazard
before this phase began and reported it at THREE on the pre-transition ledger;
it measures TWO here because the open SET is different after eleven fixes, two
waives and nine appends. The hazard is the same, the number is a function of
which rows are open, and that is exactly why the comparison is not a tally.

A ROW-COUNT comparison is refused for the weaker reason: two representations
can carry the same number of rows and disagree about which rows. The identifier
sets are the comparison; the count falls out of them.

The per-identifier STATUS agreement is a second assertion on top of membership.
Equal identifier sets would still permit a row that reads `fixed` in the table
and `open` in the array. It does not happen, and what says so is a join over all
219 identifiers rather than a reading.

Section 3 -- the open-count movement, and its governance effect
-------------------------------------------------------------------------------

BEFORE (HEAD at plan base ae001aef, frontmatter and entries agreeing):

    open 197    waived 0    fixed 13    total 210

AFTER:

    open 193    waived 2    fixed 24    total 219

THE MOVEMENT, attributed rather than left to subtraction:

    open  197  - 11 fixed  - 2 waived  + 9 appended  =  193      (net  -4)
    fixed  13  + 11                                  =   24      (net +11)
    waived  0  +  2                                  =    2      (net  +2)
    total 210  +  9 appended                         =  219      (net  +9)

THE GOVERNANCE EFFECT, NAMED HERE SO IT IS NOT DISCOVERED LATER.
`open_count > 0` blocks `/gsd-ship` when `workflow.windows_enforce` is on.
Fixing a row and waiving a row both LOWER that number; appending a row raises
it. This plan lowered it by thirteen and raised it by nine, for a net fall of
four -- from 197 to 193.

Two things a reader should take from that, and neither is comfortable:

  1. The gate is NOT currently blocking either way. Measured on this tree:

       $ gsd-tools query config-get workflow.windows_enforce --raw
       false

     So nothing about this movement changed what ships today. That is a reason
     to record the movement HERE rather than to rely on a gate to surface it --
     a number that no gate is reading is a number nobody will notice moving.

  2. 193 is still a long way above zero. This phase closed thirteen rows and
     opened nine; it did not drain the register and does not claim to. What it
     claims is that the rows it touched moved for a recorded reason, and that
     the nine it opened are defects that were already true of the tree and were
     sitting in prose rather than in the register.
