SECTION 2 — WR-03 / IN-04 / IN-07: the oracle's child (scripts/loader-oracle.test-support.ts)
=================================================================================================

2.1  THE BOUND, AND THE SENTENCE A BOUNDED-OUT CHILD BECOMES

  ORACLE_CHILD_OPTIONS = {"timeout":60000,"killSignal":"SIGKILL"}   (frozen, spread by the call)

  the corpus load did not return within 60000 ms and was killed with SIGKILL. The entry's main most
  likely RAN - which is the is-entry premise this oracle rests on - so the recording proves nothing.
  Reported here, by name, rather than as a worker that hangs and a run that times out naming nothing.

  The bound is held in ONE frozen object that the invocation spreads, so the case asserting it
  asserts the value really passed. The consumer's arm is ONE function, `withLoadPremise`, and every
  recording in scripts/board-readonly.test.ts goes through it - four call sites, no exceptions.

  The predicate is driven with a REAL bounded-out error from a REAL non-returning child at a 1500 ms
  bound, because the two fields it reads are platform behaviour: code === "ETIMEDOUT" and
  signal === "SIGKILL", both measured in RED S 2.2 and re-measured by the case each run. A
  hand-built error object would prove the predicate matches a literal somebody typed.

2.2  THE ABSENT-REGISTRATION REFUSAL

  loader-oracle: this runtime (<process.version>) does not provide module.registerHooks, so the
  runtime-acquisition oracle cannot observe Node's own ESM resolver and refuses rather than loading
  the corpus with nothing watching. It is available from Node 22.15 onward. The declared engines
  floor is deliberately NOT raised to match: a named refusal at the fact is the cheaper and more
  honest of the two fixes, because it costs a contributor on a supported runtime nothing.

  The absence cannot be created on a runtime that HAS the function, so the guard's own bytes are
  executed against a stub namespace - the exported ORACLE_REGISTRATION_GUARD is the string the
  shipped child is built from, asserted by its own case, so the proof is about the text that runs.
  Discrimination: the same bytes against a namespace that DOES carry the function print NO-REFUSAL.

  The import is a NAMESPACE import. A named import of an absent export is a LINK-time SyntaxError,
  so a named import can never be the thing that checks whether the export is there - the guard would
  be unreachable on exactly the runtimes it exists for. Asserted in both directions.

  package.json is byte-unchanged: `git diff --exit-code -- package.json` exits 0.

2.3  THE REALPATH-RESOLVED ROOT

  RED   symlinked checkout: 5 of 5 modules spelled ../../../../../../../Users/.../scripts/<x>.js
  GREEN symlinked checkout: identical to the direct recording, 0 leading-parent entries

  The loud outcome is NOT removed, only the false one. A path outside the REAL root still
  relativises to `../...` and still reds the consumer's equality by name; what stopped happening is
  an ordinary symlinked checkout impersonating an escape.

3.2  THE THREE ROWS PLAN 32.1-15 APPENDS, IN FINAL TEXT

Row A - owner `scripts/check-build-parity.ts`:
  The build-parity gate derives its moved-outputs set from `git diff --name-only -- '*.js'`, which
  cannot see a `.js` the build produced for a `.ts` with no committed twin. The gate's result is
  correct on this tree only because a later workflow step's working-tree arm sees the file; the
  ordering dependency is recorded in the module header by plan 32.1-14. Deriving the set from
  `git status --porcelain -- '*.js'` instead would make the gate hold its own subject, and is a
  decision about what the gate's subject set contains rather than a defect fix.

Row B - owner `scripts/check-foundation-guards.test.ts` (the F-19 / IN-03 census rule):
  The computed-key census decides guardedness per ENCLOSING FUNCTION rather than per read, so a
  guarded call and an unguarded read of the same register in one function both pass. Bounded by the
  `scattered` assertion (one function per register) and no worse than the text rule it replaced.
  Remedy if tightened: require the `Object.hasOwn` call to be an ancestor condition of the read.

Row C - owner `package.json` `check:build-parity` / the declared command-shape rule:
  `check:build-parity` compiles the tree twice per invocation - once through the declared shape's
  `tsc --outDir .tmp-build` prefix and once inside the module. ACCEPTED: the honest alternative is a
  third declared command shape, which `scripts/check-foundation-guards.test.ts` deliberately
  refuses, and a declared shape with a named exception is a declared shape that has started widening.

  Each row states a LIMIT or a DECISION and none states a schedule. A row whose reason is "later"
  is a row nobody will ever close.
