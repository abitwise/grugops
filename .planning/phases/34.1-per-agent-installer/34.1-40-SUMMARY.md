## Accomplishments

- **MARKER_REMEDY_CALLS** (describe "D-35: the markerRemedy call sites (34.1 review CR-04)"). `markerRemedyWalk` uses productModules (git ls-files) and the TypeScript parser to find every `markerRemedy` identifier in the product modules.
  - Each call is keyed by module and enclosing function. The result must equal the table both ways, with per-module counts `{install.ts: 4, uninstall.ts: 4}`.
  - Every other mention must be the declaration in install-marker.ts or a plain (not renamed) import. So an alias, a renamed import or a namespace call cannot stay outside the count.
- **Converse**: the owner-tagged sites of the remedy census (owner "yes" or "no"), grouped by module and function, must each hold a markerRemedy call. The census tags 9 readings in 6 functions:
  - install.ts: markerUnreadable, writeAskRules, askRulesStep;
  - uninstall.ts: `<module>`, removeMarker, keepWithoutRecord.

  The count of 6 is pinned. writeMarker calls the owner only for ledgerWellFormed, so it has a call but no owner-tagged reading.
- **Unit table** (one `it` in the D-35 describe). 12 shapes, each written as a real `.grugops/install.json` in its own scratch target under SCRATCH and read through readInstallMarker. Every shape is asked for "install", "uninstall-full" and "uninstall-partial", giving 36 cells.
  - Each row first checks that the file reads as the shape it names: the state, whether an object was parsed, the duplicated key, the ledger state for `ok`, and unboundBy for `unbound`.
  - The expected mayRemove comes from the docblock rule, stated once in `ruleMayRemove`. The expected ledgerWellFormed is the row's own. The expected `fix` is the read's problems exactly when the read is unreadable with an object, and `[]` otherwise.
  - Every never-remove answer's markerFixText must contain "never delete the marker", name each fix entry, and match neither offersRemoval nor REMOVAL_OFFER. The premise is that 5 shapes have a fix to name.
- **README** (install/README.md, after the paragraph ending "named in a `FAIL` line with the entry and the reason."): one paragraph of 4 sentences. See the claim table below.

## Deviations from Plan

### Plan wording adjusted for DOC-1

**1. [Rule 1 - DOC-1 accuracy] README wording narrowed from the plan's draft**
- **Found during:** Task 1
- **Issue:** The plan's draft sentences said "after the fix, run the command the line prints" for all three binaries, and that a not-JSON or malformed-ledger marker "can still be fixed or removed". The installer's never-remove verify prints no command ("then re-run the installer."). The uninstaller's left line for a JSON-object marker with a malformed ledger offers neither fix nor removal, and on a partial run U4 says never to remove an `ok` marker with a malformed ledger.
- **Fix:** The README says to run the command the `--check` or uninstall line prints, or to run the installer again. The fix-or-remove sentence names only `--check` and the installer.
- **Files modified:** install/README.md
- **Committed in:** 1c8ea88d

**2. M2's census red is the class rule and the global rule, not a changed I1 variant**

The class rule ("no well-formed ledger: fix or remove" requires owner yes), the global D-35 rule, R36 and the converse premise go red. This matches the plan's expected reds except "an I1 variant changed".
