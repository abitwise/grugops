## Summary

This review covers gap round 2 (plans 34.1-19 to 34.1-32). Those plans added the invocation context to

The round-1 fixes I checked hold. `keepWithoutRecord` offers deleting the marker only on a FULL run.
`finishCommand` never returns the flag-less command on a partial run. `agentsToRecord` is the only

The CR-03 and WR-19 classes still have open sites one step over:

I ran the reproductions with HOME and GRUGOPS_HOME set to scratch directories. I did not run `npm test`.

Already recorded for triage and not filed again: DI-05, DI-11, DI-12, DI-13, DI-14, DI-15.

## Critical Issues

### CR-04: "Fix or remove the marker" destroys a record that fixing one field would recover (CR-03 class, one step over)

**File:** `install/install.ts:1249-1256` (markerUnreadable), `install/install.ts:6696`, `install/install.ts:6940`; `install/uninstall.ts:2559` (the module-top unusable-marker verify); the census rows at `install/agents-record.test.ts` (class "not a usable record", I1/I5/I6)

**Issue:** `readInstallMarker` answers `unreadable` for any `installMarkerProblems` hit. That includes a
hand-edit typo in one field, for example `"agents": ["Codex", "claude-code"]`, which fails
`AGENT_ID_SHAPE`. The install ledger beside it can be complete and well-formed. Three remedies then
print "Fix or remove the marker, then re-run": the doctor's `markerUnreadable`, `writeAskRules` and
`askRulesStep`. Plan 34.1-20's census classes them "not a usable record", with the rationale "no run
reads a record from it, before or after the remedy". That rationale is false: fixing the field gives
back a usable marker holding the whole ledger.

Removing the marker, which the text offers as an equal choice, destroys the only record of every agent.
This is exactly the harm CR-03 was about, reached through the doctor instead of the uninstaller's kept
line. The uninstaller's matching verify (uninstall.ts:2559) never mentions fixing the field. Its only
remedy is "remove them by hand".

Reproduced in scratch:

1. `install --codex --claude` recorded 57 ledger entries.
2. `agents` was edited to `["Codex","claude-code"]`. `--check` printed the FAIL with "Fix or remove the
   marker, then re-run install.js `...`".
3. Following the "remove" branch: the marker was deleted, then the printed install command was run. The
   new ledger held 1 entry and `agents` was `["claude"]`. The earlier files were now unrecorded user
   files, so install did not adopt them.
4. A flag-less uninstall then exited 0 with 87 `left` lines and removed none of grugops' files.

The install is no longer reversible, and the printed text led there.

**Fix:** Split the remedy by cause, the same way `keepWithoutRecord` splits by FULL. When the object
parses as JSON, its ledger is well-formed, and only field problems are reported, print one line and never
offer removal:

```ts
// install.ts markerUnreadable (and the writeAskRules / askRulesStep siblings, and uninstall.ts:2559)
const fieldOnly = read.jsonObject && ledgerOf(rawObject).state === "ok";
const remedy = fieldOnly
  ? `fix ${problems.join(", ")} by hand; never delete the marker: its install ledger is still the record of every agent installed here`
  : "fix or remove the marker";
```

Then re-class those census rows under a rule that rejects "remove" whenever a well-formed ledger is
present. Add a row that follows the printed alternative, then uninstalls, and asserts that grugops'
files are removed.

## Warnings

### WR-21: The doctor's printed install commands use the doctor run's kit home and mode, not the record's; following them writes a second kit and moves the install (WR-19 class)

**File:** `install/install.ts:353-358` (COMMAND_CONTEXT), `install/install.ts:489-496` (doctorInstallCommand / doctorCheckCommand); `CHANGELOG.md:435-438`; `install/README.md:76-82`

**Issue:** `COMMAND_CONTEXT` in install.ts comes from this run's `GRUGOPS_HOME` and `INSTALL_MODE`. Under
`--check`, every doctor remedy uses it. A target installed with `GRUGOPS_HOME=/opt/kit` and checked with
a plain `install.js --check` therefore prints install commands with no `GRUGOPS_HOME=` prefix.

Reproduced in scratch:

1. Install with a custom kit home.
2. Delete `AGENTS.md`.
3. Run `--check` without `GRUGOPS_HOME`. It printed `FAIL kit-root sources DISAGREE` and, in the same
   output, "Re-run install.js, which writes it where nothing is: `node /…/install/install.js --target …`".
4. Run that command as printed, from `/`. It copied a new kit into `$HOME/.grugops` and rewrote the
   marker's `grugopsHome` and `kitRoot` to point there.

That is the harm WR-19 named. The uninstaller already reads the marker's `grugopsHome` and
`installMode` to word its install commands (uninstall.ts:2513-2529), so the two binaries hold two
derivations of one context and disagree.

`CHANGELOG.md:438` says "following it never writes a second kit there or changes the install mode".
That is false for every `--check` remedy (DOC-1). README:81-82 mentions the symlink half only.

**Fix:** Build the doctor's context from the record it is checking. When the marker reads `ok`, use its
`grugopsHome` and `installMode`, as uninstall.ts does. Use the run's own values only when there is no
usable marker. One helper shared by both binaries, for example `commandContextFromRecord(markerRead,
env)` in host-tools.ts, removes the second derivation. Correct the CHANGELOG and README sentences, and add
a row that runs `--check` without the custom `GRUGOPS_HOME`, follows a printed remedy, and asserts that
the default kit home does not exist afterwards.

### WR-22: The uninstaller's printed install command uses the kit home of a marker it says belongs to another directory

**File:** `install/uninstall.ts:2513-2529` (COMMAND_CONTEXT, `MARKER_READ.state === "unbound" ? MARKER_READ.object`), `install/uninstall.ts:2536-2544`

**Issue:** For an `other-directory` marker, the verify says "none of its records is used here", yet
`COMMAND_CONTEXT` takes its `grugopsHome` (and `installMode`) to build `reinstallCommand()`. The common
way to get such a marker is a cloned repository with a committed `.grugops/install.json`. There, the
recorded home is another user's or another machine's path.

Reproduced: with a marker recording `grugopsHome: /Users/alice/.grugops`, the uninstaller printed
`` `GRUGOPS_HOME=/Users/alice/.grugops node /…/install/install.js --target …` ``. Run as printed, that
tries to create a kit under another user's home directory, which fails (EACCES or no parent), so the
remedy does not finish (MSG-1). For the same marker, the doctor (install.ts) prints the run's own home,
so the two binaries give different commands for one marker.

**Fix:** Use a recorded `grugopsHome` only from an `ok` marker. For an `unbound` one, fall back to the
run's `GRUGOPS_HOME` or the default. Alternatively, use the recorded home only when its `agent-factory/`
exists (lstat only). The marker-supplied text reaches a printed shell command, so keep it out unless it
can be shown to be this machine's kit.

### WR-23: No printed command carries `GRUGOPS_SRC`; the stale-adapter remedy compares one checkout and re-renders from another

**File:** `install/install.ts:2329-2337`; `install/host-tools.ts` (CommandContext)

**Issue:** `GRUGOPS_SRC` is a documented usage knob (install.ts header:
`GRUGOPS_SRC=/path/to/grugops TARGET=/path/to/repo node install/install.js`). `CommandContext` has no
field for it. Every printed install command therefore renders from `dirname(scriptDir)`, not from the
checkout the run used.

The stale-adapter WARN shows the contradiction in one line. It says each adapter was compared against "a
fresh render of the kit checkout at ${GRUGOPS_SRC} … so what differs here is what a re-run would
change", then prints `doctorInstallCommand()` "which renders from the checkout at
${resolve(SCRIPT_DIR, "..")}". With `GRUGOPS_SRC` set, those are different checkouts, and the printed
re-run changes something other than what was measured. The second path is also not passed through
`canonicalPathSpelling` (WIN-1), unlike every other path in the line.

**Fix:** Add `src: string | null` to `CommandContext` (null when it equals `dirname(scriptDir)`), and have
`scriptCommand` prefix `GRUGOPS_SRC=<word>` for install.js. Alternatively, have the doctor print no
command when `GRUGOPS_SRC` differs from the script's checkout and name the checkout instead. Spell the
path with `canonicalPathSpelling`.

### IN-28: Printed-command quoting is checked only against the test suite's own shell parser; some rows build the expected value with the builder under test

**File:** `install/installer-paths.test-support.ts:392-420` (shellWords), `:528-574` (runPrintedCommand); `install/agents-record.test.ts:271-303`; `install/kit-route.test.ts:2283`, `:2337`; `install/opencode-permission.test.ts:373-374`

**Issue:** `runPrintedCommand` splits the span with `shellWords`, a local re-implementation, and runs it
with `spawnSync(process.execPath, …)`. No row passes a printed command through a real `/bin/sh -c`. The
space-and-quote rows (agents-record.test.ts:271, :299) therefore show only that `shellWord` and
`shellWords` agree with each other, not that a shell reads the command as one word.

Several rows assert containment of `agentCommand(...)`/`commandContextFor(...)` output with no
builder-independent word check (kit-route 2283 and 2337, opencode-permission 373-374). kit-route:2337
also calls `commandContextFor` without `home`, so its default kit home is the real `~/.grugops` while
the product run's is the scratch one. It passes only because both differ from `row.kitHome`.

**Fix:** Add one row that runs a printed command, with a space and a `'` in the target and the kit home,
through `spawnSync("/bin/sh", ["-c", span])` and asserts the effect. Pass `home` at kit-route:2337. Add a
literal word check where only the builder's output is compared.

### IN-29: Install's closing note says "Recorded as chosen" for an agent counted from a legacy marker

**File:** `install/install.ts:7265-7305` (agentClosingLines)

**Issue:** Plan 34.1-29 (IN-24) made the doctor word the note by source: "counted as installed by an
install made before this release" for a marker with no `agents` list. The closing note reads the same
`INSTALLED_IDS_BEFORE`, which for a legacy marker is the LEGACY_ADAPTER_KINDS rows. It always says
"Recorded as chosen, not chosen in this run, and nothing is installed for it here". Nobody chose that
agent: this run is the one that writes it into `agents`. Under DRY_RUN nothing records it at all. This is
a DOC-1 sibling of IN-24.

**Fix:** Branch on `INSTALLED_BEFORE.source === "legacy"` with the doctor's wording. A shared helper keeps
both from drifting.

### IN-30: The new rmdirIfEmpty failure line calls a directory that is gone or unreadable "empty"

**File:** `install/uninstall.ts:681-708`

**Issue:** When `rmdirSync` fails, the second read sets `after = null` for any `readdirSync` error. The
line then says "install created this directory and it is empty, but it could not be removed (…)". For
`ENOENT` (the directory vanished between the two calls) the directory is gone. The outcome should be
`gone`, and asking the user to "remove it by hand" is wrong. For `EACCES` on the read, nothing shows it
is empty.

**Fix:** When the error code is `ENOENT`, `markGone(d)` and return `"gone"`. When the re-read fails, word
the line as "could not be read or removed (code)" and drop "it is empty".

### IN-31: Two wordings of install's no-flag selection chain, and the uninstaller's is out of order

**File:** `install/install.ts:514-516` (DOCTOR_NO_FLAG_CLAUSE), `install/uninstall.ts:259-262` (NO_FLAG_INSTALL_CLAUSE)

**Issue:** Each binary words `SELECTION_WHY` itself. The uninstaller's text, "chooses the agents
detected here, shows the agent list at a terminal, or refuses", puts detection before the terminal
list. `SELECTION_WHY` checks the terminal first, then a usable marker's record, then detection. Over an
unusable marker the record step correctly drops out, but the order still misstates which wins at a
terminal. Two hand-written copies of one rule will drift (brief §2.2).

**Fix:** Export one clause builder from host-tools.ts, taking whether a usable marker can be present, and
use it in both binaries in `SELECTION_WHY`'s order.
