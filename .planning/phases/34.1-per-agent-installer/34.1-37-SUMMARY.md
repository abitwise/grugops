# Phase 34.1 Plan 37: printed commands carry the kit checkout the run used (WR-23) Summary

**Printed commands now carry `GRUGOPS_SRC=<dir>` when the run used a kit checkout other than the running script's own. CommandContext.src is set once in commandContextFromRecord, and scriptCommand adds the word for both binaries. The doctor's stale-adapter WARN names one checkout, the one it compared. Its remedy renders from that checkout, and the WR-23 case follows the remedy as printed to show it. The test harness accepts a printed GRUGOPS_SRC only on a call that opts in, so no earlier follow-as-printed row is loosened.**

## Accomplishments

- `CommandContext.src: string | null` and `RunInvocation.src`/`checkout`. commandContextFromRecord sets `src` to null when `run.src === run.checkout`, and to `run.src` otherwise, whatever the record says (the marker records no checkout).
- scriptCommand: `[GRUGOPS_HOME=…] [GRUGOPS_SRC=…] node <script> [--symlink]` for install.js, and `[GRUGOPS_SRC=…] node <script>` for uninstall.js. The uninstaller carries it because its report of unrecorded files reads the kit source.
- install.ts and uninstall.ts pass `src: canonicalPathSpelling(GRUGOPS_SRC)` and `checkout: canonicalPathSpelling(resolve(SCRIPT_DIR, ".."))`. The stale-adapter WARN spells both checkout mentions as `canonicalPathSpelling(GRUGOPS_SRC)`. The two DI-12 lines ("re-run --check from a complete kit checkout") are unchanged.
- runPrintedCommand takes `expectSrc?: boolean`. Without it, a printed GRUGOPS_SRC throws before anything runs. With it, the value is applied, and the child's value is reported in `premise.grugopsSrc`. The test process's own GRUGOPS_SRC is still removed.

## WR-23 staleness setup (acceptance criterion)

The case uses the plan's primary flow with a different S:
1. Install from this repository (`runInstall`).
2. Premise: `--check` against this checkout names no stale adapter.
3. `--check` with `src: S` gives exactly one stale-adapter WARN.

**What S is:** `copyCheckoutWithEditedRole()` copies `agent-factory`, `.claude`, `AGENTS.md`, `scripts/runnable-ref` and the four generator twins. It then prefixes the Orchestrator role's `## One job` sentence with `In checkout S: `, so S renders `grugops-orchestrator.md` differently from this checkout.

**Why not makeSyntheticSrc():** both setups the plan named were measured first and could not serve.
- With `makeSyntheticSrc()` as S, the check gave zero stale-adapter WARN lines, because its render inputs are copies of this repository's.
- With DI-08's fallback (`runInstallFrom(S)`, then the tiered config), the doctor FAILed `.../agent-factory/workflows` (the synthetic kit has none). The staleness block runs only when the kit checks are clean, so it was never reached.

**What the setup buys:** because S renders differently, the row can tell the two checkouts apart by effect, not only by the printed words:
- the kit the remedy copied must hold S's edited role text;
- the following `--check` against S must name no stale adapter;
- that `--check` must reach a verdict (no `NO VERDICT`, and `ALL CHECKS PASSED`).
