<objective>
Start D-38 with the kit home. WR-25 showed that a printed command with no GRUGOPS_HOME word means "inherit the shell",
not "default": in a shell exporting GRUGOPS_HOME, following a `--check` remedy wrote a second kit and moved the
install. D-38 makes every printed command explicit; this plan does the kit-home half: CommandContext's kit home is a
path, never null, scriptCommand states `GRUGOPS_HOME=<dir>` on every command of both binaries, and the follow-as-printed
harness keeps a conflicting GRUGOPS_HOME in the child's environment so a missing word fails a row (the harness-premise
trap WR-25 named: the old harness stripped exactly the variable that inverts the meaning). Plan 34.1-48 does the
install mode and the checkout.

Purpose: a printed command finishes the job in the user's real shell, whatever it exports.

Output: the context and builder change, the harness change, R49, and the re-pins of every row that asserted the absent
word.

Why sixteen files in one plan: the builder and the harness change every printed command and every follow-as-printed
row at once, so every row that pinned "no GRUGOPS_HOME word" must move with the builder (brief §3: never a red
commit). The test-file edits are expected-value re-pins, not new behaviour.

How it fits the executor budget (plan check, 2026-10-13): Task 1 lands in two green commits. Commit A (expand) is
test-only: one test-support statement of the printed-command rule and one reader of a printed command's leading
assignments, and every row that pinned the absent word or a word position routed through them, each still asserting
exactly what it asserted before, green on the plan-46 build. Commit B (flip) changes the builder and that one statement
together, so the ~42 literal re-pins become one rule change plus the unit rows that spell whole command strings. If the
budget runs short, the stop rule in the execution notes says what the executor leaves behind and how the run resumes.
