<assumption_delta_decision>
The assumption-delta detector fired on this phase's ROADMAP wording ("alternative", "chosen"). The model change in this
plan is real and is the D-36 "derived to chosen" case: a printed command's kit home and install mode were derived from
the run alone; they now have two possible sources. Primary noun: the install record (`.grugops/install.json`, read
`ok`). Decision: promote. The record is the primary source for a run that does not choose the kit home itself (the
doctor; plan 34.1-36 the uninstaller), and the run's own values are demoted to the fallback for "no usable record" and
for runs that write the record themselves. Not add-alongside: there is still one CommandContext per run and one function
that builds it.
</assumption_delta_decision>

<objective>
Fix WR-21 (34.1 review WR-21, the WR-19 class one step over) by making ONE owner, per D-36, decide where a printed
command's kit home and install mode come from. host-tools.ts gains `commandContextFromRecord(record, run)`: the record's
`grugopsHome` and `installMode` only when the record reads `ok`, this run's values otherwise. install.ts builds its
COMMAND_CONTEXT through it. Under `--check` the record is the marker the doctor reads, so a doctor run without the
custom GRUGOPS_HOME prints commands that carry the recorded kit home, and following them writes no second kit and does
not move the install. This plan does install.ts; plan 34.1-36 moves uninstall.ts to the same owner (WR-22), deletes the
old constructor and adds the construction census; plan 34.1-37 adds `src` (WR-23).

Planner's reading of D-36 for install.ts, stated so the checker and the human can see it: in the modes that choose the
kit home themselves (install, --migrate, --update, --prune-old-kit), install.ts passes no record, so their printed
commands repeat the invocation the user gave (D-36's "from this run otherwise"). When such a run writes the kit,
writeMarker records this run's kit home and mode (kitFromThisRun), and the printed commands match the marker it
leaves. In that case, taking the kit home from the marker as it was BEFORE the run would print the old kit home, and
following that command would move the install back: WR-21's harm in reverse. One case does not fit that picture.
When the run writes no kit file and Claude Code stays installed after it (for example `install --codex` with a new
GRUGOPS_HOME over an existing Claude Code install), writeMarker's kept() (install.ts ~5499) keeps the PREVIOUS
marker's grugopsHome, kitRoot and installMode. The marker then keeps the old kit home while the run's printed commands
carry the new one. The choice still follows D-36, because the commands repeat what the user ran, but whether
following such a command moves the install is not yet known. It is a DI candidate for the executor to confirm (see
the execution notes), not a scope change. Reversibility: reversible (one argument at one call site).

Purpose: the verifier reproduced WR-21 (a printed remedy created `HOME/.grugops` and rewrote the marker's kit home) and
the CHANGELOG claims it cannot happen.

Output: the owner, install.ts's context from it, the two WR-21 rows followed as printed, the owner's unit table, and the
README and comment corrections for the doctor's printed commands.
</objective>
