## Critical Issues

### CR-05: markerRemedy fails open: a marker it could not parse or open is treated as having no ledger, so a one-character typo gets "Fix or remove the marker" (CR-04 class, one step over)

**File:** `install/install-marker.ts:286-298` (the `blocked`, not-JSON and not-an-object arms set no `object`), `:450-454` (`ledgerWellFormed` requires `read.object !== undefined`); remedy sites `install/install.ts:1296-1298`, `:6762`, `:7009`; `install/uninstall.ts:1652-1655` (U3); `install/README.md:1023-1024`; `install/agents-record.test.ts:2092` (R36 control pins the behaviour)

**Issue:** The rule the brief sets (§5) is "never [offer removal] while the ledger is well-formed". `markerRemedy` puts it into practice as "offer removal unless I can show a well-formed ledger". The `unreadable` arms that fail before `JSON.parse` returns an object never set `object`. Those are: not valid JSON, JSON that is not an object, and a `blocked` read (EACCES, too large, a hard link). For every one of them `ledgerWellFormed` is false and `mayRemove` is true, whatever the bytes hold.

A trailing comma after the last `agents` member is the most likely hand-edit mistake. It is exactly the kind of edit CR-04 was about, and fixing it gives back the whole ledger. The README says the opposite: "A marker that is not JSON ... holds no record a fix could give back, so `--check` and the installer still say to fix or remove it."

Reproduced in scratch (HOME and GRUGOPS_HOME under `$S`):

1. `install.js --codex --claude --yes` recorded 57 ledger entries.
2. I changed `"codex"` to `"codex",` inside `agents` (a trailing comma).
3. `--check` printed: "... could not be read as a JSON object (it is not valid JSON) ... Fix or remove the marker, then re-run install.js `GRUGOPS_HOME=$S/kit node .../install.js --target ...`". The uninstall left line printed "fix or remove it by hand". Install's verify printed "Fix or remove the marker, then re-run the installer."
4. I followed the "remove" branch: deleted the marker, then ran the printed install command. The new ledger held 1 entry, with `agents: ["claude"]`.
5. A flag-less uninstall then exited 0 with 87 `left` lines. `.claude/` and `.agents/skills/grugops/` were still there.

This is CR-04's end-to-end harm (57 entries to 1, 87 left), reached through the owner that was built to prevent it. A marker made mode 000 gets the same "Fix or remove" FAIL (reproduced: "it could not be read (EACCES)").

**Fix:** Fail closed. "Could not see a ledger" must not mean "no ledger". Offer removal only when the bytes were read, parsed to an object, and that object has no `ledger` member, or its `ledger` reads `malformed` with no chance of recovery (see CR-06). For every other `unreadable` shape, print a never-remove wording that names the cause:

```ts
case "unreadable": {
  if (read.object === undefined) {
    // Not parsed or not opened: the ledger may be intact. Never offer removal.
    return { mayRemove: false, ledgerWellFormed: false, fix: [read.why.replace(/^it /, "the file ")] };
  }
  const ledgerWellFormed = readLedger(read.object).state === "ok" || read.duplicateKey === LEDGER_FIELD;
  const hasLedger = Object.prototype.hasOwnProperty.call(read.object, LEDGER_FIELD);
  return { mayRemove: !hasLedger, ledgerWellFormed, fix: read.problems ?? [] };
}
```

Then reword markerFixText so it does not claim "still the record" when that is not known (for example "may still hold the record of every agent installed here; fix it, never delete it"). Invert the R36 control. Add a row that adds a trailing comma, follows each printed alternative, then uninstalls and asserts that grugops' files are gone. Correct README:1023-1024.

### CR-06: A flag-less uninstall that removed nothing, over a malformed ledger, offers "fix or remove it by hand"; removing it makes the whole install irreversible

**File:** `install/install-marker.ts:446-447` (`ok`: `mayRemove: run === "uninstall-full"`, regardless of the ledger), `install/uninstall.ts:1666-1675` (the U4 arm); `install/agents-record.test.ts:1915` (R21 pins it), `:1682` (census row "markerRemedy yes (a FULL run): no agent stays installed")

**Issue:** For an `ok` read, markerRemedy decides `mayRemove` from the run kind alone. D-32's justification is that on a FULL run "no agent stays installed, so removing the marker drops no staying agent's record". That is true only for a FULL run that removed things. With a malformed ledger, the uninstaller fails closed before removing anything (the module-top verify at `uninstall.ts:2604-2610`: "No empty directory, no file install may have created ... is removed"). Every agent is still installed when the left line offers removing the only record of them.

A malformed ledger is typically one bad entry, and fixing that entry gives back the whole record. This is the brief §4 rule ("every remedy ... leaves every staying agent reversible") broken on the FULL arm.

Reproduced: `install --codex --claude`, then one ledger entry's `kind` set to `"banana"`. A flag-less uninstall exited 3 with 0 `removed` and 34 `left`. The marker line said "its install ledger is malformed ...; it was left in place — fix or remove it by hand". After the marker was removed, a second flag-less uninstall exited 0 with 0 `removed` and 32 `left`, and `.claude/skills/` still held 7 skills.

**Fix:** Pass the owner what the run actually did, or decide on the ledger state. An `ok` read with a `malformed` ledger is the same "recoverable record" case as CR-04, so it gets `mayRemove: false` whatever the run kind:

```ts
case "ok": {
  const wellFormed = readLedger(read.marker).state === "ok";
  return { mayRemove: run === "uninstall-full" && wellFormed, ledgerWellFormed: wellFormed, fix: [] };
}
```

The U4 arm then always prints the "fix the ledger field by hand" text. keepWithoutRecord's FULL branch is unchanged: it is reached only with a well-formed, owned ledger. Re-pin R21's flag-less half and census row `:1682`.

### WR-24: --check derives the kit home twice: printed commands use the record, the cross-check and header use the run; WR-21's own scenario still FAILs "stale/moved install" with no remedy

**File:** `install/install.ts:2080-2101` (`const a = KIT_ROOT`, the DISAGREE FAILs), the doctor header (`home:`/`kit:` from GRUGOPS_HOME/KIT_ROOT), `:2392` ("the installed kit at ${KIT_ROOT}"); `install/kit-route.test.ts` WR-21 row 1 (asserts the DISAGREE as a premise)

**Issue:** D-36 moved the printed commands to the record but left everything else on the run's kit home. In WR-21's reproduction (installed with `GRUGOPS_HOME=$S/opt/kit`, checked without it) the output contradicts itself:

- The header says `home: $S/home/.grugops` and `kit: $S/home/.grugops/agent-factory`, a kit that does not exist.
- It FAILs `kit-root sources DISAGREE (stale/moved install): rule=$S/home/.grugops/agent-factory marker=$S/opt/kit/... adapter=$S/opt/kit/...`, with no remedy on that line.
- The same output's printed install command carries `GRUGOPS_HOME=$S/opt/kit`.

The install is neither stale nor moved. I ran the printed command as printed, then the same plain `--check`, and it still exits 1 with the same FAIL. Only `GRUGOPS_HOME=$S/opt/kit ... --check` passes, and this output never prints that command. A user who reads "stale/moved install" and re-runs install the way they ran `--check` (without GRUGOPS_HOME) gets WR-21's harm back (MSG-1, DOC-1).

**Fix:** Under `--check` with an `ok` marker, take the rule source (a) and the header from the same owner as the commands (`contextKitHome(COMMAND_CONTEXT, DEFAULT_KIT_HOME)`). Alternatively, when the run's GRUGOPS_HOME differs from the record's, print a dedicated line: "this --check ran with kit home X; the install records Y; run `<doctorCheckCommand()>`". Drop "stale/moved" from that case, and add a row that runs the printed check command and asserts exit 0.

### WR-25: "No GRUGOPS_HOME word" and "no --symlink" mean "inherit the shell", not "default"; following a --check remedy in a shell that exports either variable moves the install (WR-19/WR-21 class)

**File:** `install/host-tools.ts:373` (`kitHome: kitHome === run.defaultKitHome ? null : kitHome`), `:413-420` (scriptCommand prints nothing for a null kit home or for copy mode); `install/install.ts:340-344` and `:323-333` (GRUGOPS_HOME and INSTALL_MODE are read from the environment); `install/installer-paths.test-support.ts:525-560` (runPrintedCommand removes GRUGOPS_HOME, GRUGOPS_SRC and INSTALL_MODE from the child's environment); `CHANGELOG.md:439`; `install/README.md:997-999` ("the install command is a copy install")

**Issue:** The context encodes "the default kit home" as the absence of a word, and copy mode as the absence of `--symlink`. A printed command is run in the user's shell, where an exported `GRUGOPS_HOME` or `INSTALL_MODE=symlink` then decides both.

Reproduced: a default-home copy install, AGENTS.md deleted, then `export GRUGOPS_HOME=$S/other/kit INSTALL_MODE=symlink` and `--check`. The doctor correctly took the record (default home, copy) and printed `node .../install.js --target $S/repo` with no prefix. Run as printed in that shell, it exited 0, copied a kit into `$S/other/kit`, and rewrote the marker to `grugopsHome: $S/other/kit`, `installMode: symlink`.

CHANGELOG:439 promises "following a `--check` remedy writes no second kit and leaves the install where it was". The README says the uninstaller's reinstall "is a copy install". Both are false in that shell.

No test can see this, because runPrintedCommand strips exactly these variables. That is the harness-premise trap of WR-19, inverted: the stripped environment is not the user's.

**Fix:** Make the printed text decide both values whatever the environment holds. Always print `GRUGOPS_HOME=<dir>`, or print it whenever the printing run's own environment has a non-empty GRUGOPS_HOME that differs from the context's. Print `INSTALL_MODE=copy` (or a `--copy` flag, if one is added) for a copy-mode install command whenever `INSTALL_MODE` is set in the printing run's environment. Add a follow-as-printed row that keeps a conflicting `GRUGOPS_HOME`/`INSTALL_MODE` in the child's environment and asserts the marker's `grugopsHome` and `installMode` are unchanged.

### WR-26: The duplicate-key arm decides on the FIRST duplicate only, and claims a well-formed ledger when both `ledger` values are garbage

**File:** `install/install-marker.ts:315-325` (one `duplicateKey`, from `firstDuplicateKey`), `:450-454`

**Issue:** I probed this by calling the compiled module directly:

- `{..., "agents":[...], "agents":[...], "ledger":[<good>], "ledger":7}` answers `mayRemove: true`, `ledgerWellFormed: false`, and `fix` names only the `agents` duplicate. JSON.parse kept `7`, and the duplicate `ledger` (one of whose values is a good record) is never looked at. The printed remedy offers removing the marker over a recoverable record (CR-05's harm).
- `{..., "ledger":5, "ledger":"x"}` answers `ledgerWellFormed: true`, so markerFixText prints "its install ledger is still the record of every agent installed here", although neither value is a ledger (DOC-1).

The fix text "keep the one install wrote" also gives the user no way to tell which value that is.

**Fix:** Have the strict reader report every duplicated key, not the first. Decide `ledgerWellFormed` for a duplicated `ledger` by reading each of its values with readLedger (true only if at least one reads `ok`). Never offer removal while any duplicate is `ledger`. Word the fix as "the key ledger appears N times; keep the value that lists the files install wrote (for example the longer list)" only when that can be shown.

### IN-32: The CHANGELOG says the uninstaller's install command "is the one `install.js --check` prints for the same marker and environment"; it is not for a per-agent run or under INSTALL_MODE=symlink

**File:** `CHANGELOG.md:476-478`; `install/uninstall.ts:252-254` (reinstallCommand carries the run's agent flags; COMMAND_CONTEXT has `symlink: false`), `install/install.ts:500-507` (the doctor's context takes `INSTALL_MODE` from the environment)

**Issue:** `uninstall.js --codex` over an unbound marker prints `install.js --target T --codex`, while `--check` prints the flag-less command. With `INSTALL_MODE=symlink` in the environment, `--check` prints `--symlink` and the uninstaller never does. R39 compares the two only for a flag-less run with INSTALL_MODE=copy. DOC-1.

**Fix:** Narrow the sentence to "for a run with no agent flag and no INSTALL_MODE", or drop the equality claim.

### IN-33: The never-remove lines word the cause wrongly or contradict themselves

**File:** `install/install.ts:5462-5469` (writeMarker skipped line), `:6759-6763` and `:7006-7010` (verify lines)

**Issue:** writeMarker's skipped line checks `ledgerWellFormed` before `jsonObject`. For a duplicate key or a strict-reader refusal (non-UTF-8 bytes, nesting) it therefore says "a field in it holds a value install never writes", which is not the cause. The verify line of writeAskRules and askRulesStep says "so the install ledger is unknown", then in the same sentence markerFixText says "its install ledger is still the record of every agent installed here".

**Fix:** Branch the skipped line on the read's cause (`duplicateKey`, `jsonObject`). In the never-remove arm, replace "so the install ledger is unknown" with "so this run uses none of its records", the uninstaller's wording.

### IN-34: The uninstaller's ask-rules verify is a remedy over the marker that does not ask markerRemedy, and contradicts the never-remove verify

**File:** `install/uninstall.ts:2319-2323`

**Issue:** Over CR-04's marker (a well-formed ledger with one bad field), the module-top verify says to fix the field and re-run. The ask-rules verify in the same run says "the ledger of rules grugops added is unknown and NO ask rule was removed. Remove the grugops ask rules by hand." That sends the user to hand-edit `.claude/settings.json` when the record would reverse the rules once the field is fixed. It also adds a second exit-3 verify for one cause. The line names `.grugops/install.json` and gives a remedy, but it is outside the D-35 census, which keys on `.mayRemove`.

**Fix:** When `markerRemedy(MARKER_READ, ...).ledgerWellFormed`, report `left` with "see the verify line above" (the shape the gemini arm uses at `:2305`). Keep the hand-removal text for a marker with no recoverable ledger.
