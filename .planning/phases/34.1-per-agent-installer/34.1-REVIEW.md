## Critical Issues

### CR-02: A per-agent uninstall that leaves a recorded entry in place drops the agent from `agents` anyway, so the reversal can never be finished per agent and the record contradicts itself

**File:** `install/uninstall.ts:192-194` (agentsAfter), `install/uninstall.ts:1582-1592` (the kept arm that calls updateKeptMarker), `install/uninstall.ts:1589` and `install/uninstall.ts:2549` (the remedy text)

**Issue:** On a partial run (not FULL), when one of the named agent's in-scope entries is still held (a
user-edited file the walk reports `left`, or a reversal that counted a verify), `removeMarker` takes the
`!markerDischarged()` arm and calls `updateKeptMarker`. That rewrite sets `agents` to `agentsAfter()`,
which is `STAYING` with no regard for which agents still have held entries. The removed agent leaves the
`agents` list while the install ledger still records its entries. Then:

- the printed remedy ("remove or restore what is named and re-run uninstall", lines 1589 and 2549) is
  false for a per-agent run: re-running `uninstall.js --claude` computes `NAMED = []` from the rewritten
  `agents` (line 477) and does nothing ("none of the named agents is installed here"), even after the
  user restores the file;
- the only run that can finish the reversal is a flag-less uninstall, which is FULL and also removes
  every other agent and the shared footprint;
- `install.js --check` (doctorHosts) and the unattended install selection (INSTALLED_BEFORE) both read
  the rewritten `agents`, so the agent whose recorded files are still in the target is no longer
  reported or re-chosen.

Reproduced (scratch target, scratch `GRUGOPS_HOME`): `install.js --yes --claude --codex`; append a line
to `.claude/skills/grugops-gate/SKILL.md`; `uninstall.js --claude` printed `left .claude/skills/grugops-gate/SKILL.md`
and `its agents list is now [codex]`, exit 0. The marker then held `agents: ["codex"]` and four ledger
entries under `.claude/`. After restoring the file's bytes, `uninstall.js --claude` printed
`== uninstall complete — no agent removed (none of the named agents is installed here); still installed: Codex CLI ==`,
exit 0, and left `.claude/skills/grugops-gate/` in place. The same arm on a FULL run writes `agents: []`
next to a ledger that still holds entries (agentsAfter returns `[]` when FULL), with the same mismatch
between the two fields.

This breaks the CLAUDE.md constraint that installers are reversible, and the phase brief's rule that the
install record must not contradict itself.

**Fix:** keep an agent in `agents` while any entry it owns is still held. Derive the kept list from the
same held set the marker rule already computes:

```ts
function agentsAfter(): string[] {
  // Agents owning an in-scope entry this run did not discharge stay recorded, so a re-run with the same
  // flag can finish the reversal, and --check and an unattended install still see them.
  const stillHeld = new Set(heldEntries().flatMap((e) => entryOwners(e)));
  const keep = (id: string): boolean => (!FULL && REMAINING.includes(id)) || stillHeld.has(id);
  return [
    ...HOST_TOOLS.filter((h) => INSTALLED.ids.includes(h.id) && keep(h.id)).map((h) => h.id),
    ...(!FULL && INSTALLED.source === "recorded" ? INSTALLED.unknown : []),
  ];
}
```

Also make the `kept` line and the closing banner on a partial run name the agent that stays recorded
and give the command that finishes it (`uninstall.js --<flag>` once the named file is restored or
removed). Add a test: partial uninstall with one edited owned file, restore the file, re-run the same
per-agent uninstall, and assert the file and the agent are gone.

## Warnings

### WR-17: Install's route note sends the user to a "line above" that the run never printed, for an agent installed earlier but not chosen in this run

**File:** `install/install.ts:3349` (hosts = hostsOf(AGENTS_AFTER)), `install/install.ts:3376-3381` (the absent/unread arm)

**Issue:** `noteStrandingCarriers` checks the carriers of every agent in `AGENTS_AFTER`, which includes
agents installed earlier and not chosen in this run. The writers for those agents never ran in this run
(the per-agent gates at lines 6311-6323), so no line about their carrier was printed. For such a carrier
that is absent or unreadable, the note still says `the line above about ${rel} says why and what to do`.
That line does not exist, so the note sends the user to output that was never printed, and it leaves out
the actual remedy (re-run install with that agent's flag). The function's own comment (lines 3344-3346)
says this should not happen ("naming it would point at a remedy line that does not exist"), but the code
uses AGENTS_AFTER, not SELECTION.

Reproduced: a target with a user's own `AGENTS.md` (no kit route); `install.js --yes --pi`; delete
`.pi/prompts/grugops.md`; `install.js --yes --opencode`. Output line 18:
`note .pi/prompts/grugops.md (is not present: it leaves Pi without a route to the kit after a scripted install; the line above about .pi/prompts/grugops.md says why and what to do)`.
No other line of that run mentions `.pi/prompts/grugops.md`.

**Fix:** in the absent/unread arm, when none of the stranded hosts is in SELECTION, name the remedy
directly instead of pointing upward:

```ts
const chosenHere = stranded.some((h) => SELECTION.includes(h));
const remedy = chosenHere
  ? `the line above about ${rel} says why and what to do`
  : `re-run install.js with ${stranded.map(agentFlag).join(" ")} to write it`;
```

### WR-18: The OpenCode "kit-read" rule is an `external_directory` allow, which by the project's own description covers every tool call on the shared kit, not only reads

**File:** `install/install.ts:6750-6758` (header), `install/install.ts:6803-6817` (kitReadPattern), `install/install.ts:6851-6978` (writeOpenCodePermission); `install/README.md:419-424`

**Issue:** The code, the ledger kind and the README all call this rule the "kit-read rule" and say it lets
OpenCode "read the kit ... without asking". The README's own description of the permission (line 420-421,
citing opencode.ai/docs/permissions/) is that OpenCode "asks before a tool call touches a path outside
the working directory unless a `permission.external_directory` rule allows it". That covers any tool call,
not only reads. The allow rule `~/.grugops/agent-factory/**` therefore also removes the prompt before an
OpenCode edit or write in the shared kit home. Every target repository on the machine reads its role
prompts from that kit. So one OpenCode session in one repository, for example one steered by injected
content, could change the role text every other repository loads, and the user is never asked. Whether
OpenCode's separate `edit` permission still asks in that case is not established anywhere in the reviewed
files. No line in the code or docs says which tools the rule opens. Calling it a read rule states a scope
nobody has verified.

**Fix:** either (a) state in the install note and in install/README.md that the rule allows every tool
call OpenCode gates by `external_directory` on the kit, including edits, and mark the interaction with the
`edit` permission `UNKNOWN - verify`; or (b) if OpenCode's permission grammar supports a per-tool
rule, write a read-only rule instead. Rename "kit-read rule" in user-facing text until (b) is shown to
hold.

## Info

### IN-18: The picker's `finally` can throw and leave the cursor hidden

**File:** `install/install.ts:401-423`

**Issue:** The cursor is hidden at line 401, before the `try`. If `stdin.setRawMode(true)` throws, the
`finally` calls `stdin.setRawMode(false)` (line 421), which can throw too. The original error is then
masked and the `\x1b[?25h` at line 422 (written in code as an escape sequence, not a raw byte) is never
written. A SIGTERM or SIGHUP during the picker also leaves the cursor hidden: Node resets the termios mode
on those signals, but not the cursor visibility.

**Fix:** wrap `setRawMode(false)` in its own try, and write the show-cursor sequence first in the `finally`:
`try { process.stdout.write("\x1b[?25h\n"); } finally { try { stdin.setRawMode(false); } catch {} }`.

### IN-20: removeOpenCodePermission drops the record and leaves install-created containers when only the rule is gone

**File:** `install/uninstall.ts:340-343`

**Issue:** When the recorded pattern is no longer in `external_directory`, the entry is `gone` and leaves

install's own scaffolding behind with no record and no `left` line naming it.

**Fix:** when the rule is gone and `createdExternalDirectory` / `createdPermission` / `createdFile` are
set, run the same stripped-text and oracle path for the empty containers (or at least report them `left`
with the by-hand remedy).

### IN-21: `agents` records every chosen agent even when every write for it was refused

**File:** `install/install.ts:5663-5666`, `install/install.ts:5351`

**Issue:** AGENTS_AFTER is "installed before, plus chosen", with no regard for whether anything was written
for the agent. One example: `--claude` with a refused kit plan (verify, exit 3). Another: `--opencode` where
the command file is the user's and the rule produced only a note. Each agent is still recorded as
installed while the ledger holds nothing of install's for it. The closing line does say "nothing of
install's is recorded for it", and a later `--yes` re-run retries, so this is consistent with D-04's
"chosen" meaning. But the field reads as "installed", and the doctor then reports reach lines for it.

**Fix:** document the field as "chosen" in install-marker.ts's header and the README, or record only
agents with at least one owned ledger entry or a recorded `note` outcome.
