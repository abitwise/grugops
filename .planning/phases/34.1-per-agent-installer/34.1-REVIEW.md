### WR-37: The doctor's kit-root cross-check no longer sees a moved kit home; its comment claims it does, and the only printed remedy copies a second kit to the old recorded home

**File:** `install/install.ts:514-517` (the comment "A real stale or moved install still FAILs: the marker's kitRoot or the adapter's KIT= line then disagrees with the recorded kit home"), `:2099-2130` (sources (a), (b) and (c) of the cross-check), `:2101-2105` (the comment saying the DISAGREE FAILs still fire); `CHANGELOG.md:443` ("following a `--check` remedy writes no second kit"); `install/README.md:591`

**Class:** DOC-1 (a sentence states behaviour the run disproves) and MSG-1 (no printed command reaches the state the user is in). This is a consequence of the WR-24 fix, not a regression of it.

**Issue:** D-38 moved source (a) of the D-03 three-source cross-check from the run's `KIT_ROOT` to `DOCTOR_KIT_ROOT`. Under an `ok` marker, that value is `<recorded grugopsHome>/agent-factory`. Source (b) is the marker's `kitRoot`, which install writes as `<GRUGOPS_HOME>/agent-factory` in the same `writeMarker` call (`kept()` keeps the two together). Source (c) is the adapter's `KIT=` line, rendered from the same kit root. So all three now come from the record, and the check can only disagree with itself after a hand edit or an adapter left behind. A kit home that was actually moved is the case the "stale/moved install" label exists for, and it no longer reaches that FAIL.

Reproduced in scratch:
1. `GRUGOPS_HOME=$S/kitA install.js --claude --codex --yes` exited 0.
2. `mv $S/kitA $S/kitB`.
3. `GRUGOPS_HOME=$S/kitB install.js --check` exited 1 and printed:

   - the kit route FAIL, whose only command is `GRUGOPS_HOME=$S/kitA INSTALL_MODE=copy GRUGOPS_SRC=... node .../install.js --target $S/repo`.

The output contradicts itself ("sources agree", then the kit root is absent). The comment at :516 and the one at :2102-2105 say the DISAGREE FAIL still catches a moved install, and that is false. CHANGELOG:443 says following a `--check` remedy "writes no second kit", and that is false here. No line names the command that keeps the kit where the user moved it (`GRUGOPS_HOME=$S/kitB ... install.js --target $S/repo`).

### WR-38: removeMarker's first arm says a linked, directory or FIFO marker is "not the marker install writes", right after the run's verify said never delete it because it is the one record (IN-33/CR-05 class, one arm over)

**File:** `install/uninstall.ts:1626-1632` (the arm before the D-37 arm: `report("left", \`${MARKER_REL} (${what}; not the marker install writes — left in place)\`)`), `:1638-1642` (the D-37 comment: "no line here offers removing it or says it is not install's"); `install/README.md:1034-1042` ("Each of them names the cause it saw ... and says never to delete the marker"); `install/agents-record.test.ts` R44 (the IN-33 wording row covers no `blocked` shape) and R48e (the link row asserts only the verify wording)

**Class:** IN-33 (a wording site beside the owner names a different cause or contradicts the owner), which brief §6 put in round-4 scope. It is also the claim CR-04/CR-05 removed ("so it is not install's") on the arm they did not reach.

**Issue:** D-37 says that for every marker read, a blocked read included, the message "states that the file is still the record of the installed agents". `readInstallMarker` puts a link, a directory, a FIFO and a mode-000 file in the `blocked` defect, so the module-top verify prints markerFixText for each: "never delete the marker: it is the one record install keeps ...". removeMarker then checks `wayTo`/`kindAt` before it reaches the D-37 arm, so a link, a directory or a FIFO never gets markerDefectText. It gets the older line, which says the file is not install's marker. The census does not catch this, because the line offers no removal. R44 and the matrix check no `left` wording for a `blocked` shape.

Reproduced:
- **Symbolic link at the marker path, then `uninstall.js --codex`.** The verify said "... symbolic link ...; never delete the marker: it is the one record install keeps of the agents installed here ...". The next marker line said `left .grugops/install.json (it is a symbolic link; not the marker install writes — left in place)`.
- **Directory at the marker path, then a flag-less uninstall.** The verify said "Fix .grugops/install.json by hand (the file is not a regular file (it is a directory): make .grugops/install.json the readable regular file install wrote ...); never delete the marker: it is the one record ...". The `left` line said "(it is a directory; not the marker install writes — left in place)".

A user who reads "not the marker install writes" has the same cue to delete it that CR-04 removed. For the link shape, R48e shows that the file it points to IS install's record. A directory is not a record of anything, so there the verify's "it is the one record" is the false half instead. That half belongs to DI-18's class (a file install never wrote, worded as the record), and it leaves no route forward: the only fix named is to restore a file the user may not have.

**Fix:** Route the arm through the owner. When `MARKER_READ.state === "unreadable"`, use the D-37 line for every blocked shape:

```ts
if ((way !== null && way !== "absent") || kind !== "regular file") {
  if (MARKER_READ.state === "unreadable") {
    report("left", `${MARKER_REL} (left in place — ${markerDefectText(MARKER_READ.defect)}; see the verify line above)`);
  } else {
    // present now, not when this run started: no verify was printed about it
    const what = way !== null && way !== "absent" ? `${way.at} ${way.reason}` : `it is a ${kind ?? "path that could not be read"}`;
    report("left", `${MARKER_REL} (${what}; this run read none of its records — left in place)`);
  }
  return { kind: "left" };
}
```

Give the `blocked` defect a cause clause that names the shape (`read.why` already does). Add the `left` line to R44's assertions for every `READER_STATES.blocked` shape, and record the directory and FIFO wording under DI-18 for the human.

## Info

### IN-35: jsonErrorPlace can take its position digits from the file's own text, which V8 quotes in its message

**File:** `install/install-marker.ts:448-469` (`/\bat position (\d+)\b/.exec(error.message)` searches the whole message)

**Issue:** The docblock says "Only the DIGITS of a reported position are read, never the rest of a message: V8's JSON.parse message quotes the file's text". The regex runs over the whole message, quoted text included. When V8 reports no position (an "Unexpected token" error), a short marker whose quoted head contains `at position N` supplies N. Probed with the compiled module: a marker holding exactly `x at position 9` reads "not valid JSON (line 1, column 10)", but the error is at column 1. The impact is a wrong place in a remedy (no bytes are echoed, and `pos > text.length` bounds it), and the docblock claim is false. On Node 26 an object trailing comma does carry a position ("Expected double-quoted property name in JSON at position 7"), which also contradicts the docblock's example.

**Fix:** Anchor the match to V8's own phrase, outside the quoted text: `/ in JSON at position (\d+)(?: \(line \d+ column \d+\))?$/`. Otherwise drop V8's message and always use the strict reader's `at character N`, whose message holds no file text. Correct the docblock.

### IN-36: The duplicate-key fix names no location and no way to tell which value install wrote (WR-26's third point, unaddressed)
