## Critical Issues

### CR-03: On a per-agent uninstall, the printed "delete the marker by hand" remedy throws away the install record of every agent that stays installed (MSG-1 class again; the CR-02 harm reached a second way)

**File:** `install/uninstall.ts:1631-1633` (the kept `left` line), `install/uninstall.ts:2705-2706` (the KEPT_FOR banner), `install/README.md:981-982`

**Issue:** This round rewrote the kept-marker `left` line and the KEPT_FOR banner (MSG-1). Both still offer, as
the alternative to finishing the reversal, "delete the marker by hand to keep them without a record" and "to keep
them, delete .grugops/install.json by hand (uninstall then has no record of them and changes nothing more)". The
README says the same: "To keep an edited file for good, delete `.grugops/install.json` by hand after the run".

On a partial run (not FULL), the marker is also the only record of the agents that stay installed. Deleting it does
not only drop the record of the edited file. It drops the ledger and the `agents` entry of every staying agent, and
after that no uninstall can reverse them. The remedy promises that uninstall "changes nothing more" about "them" (the
`left` items). In fact uninstall can never again remove anything for any agent in that repository. This is the harm
CR-02 described (a per-agent reversal that can never be finished), now reached by following the installer's own
advice. The rule that installers are reversible (CLAUDE.md) is broken the same way.

Reproduced (S1, scratch `HOME`/`GRUGOPS_HOME`): `install.js --yes --claude --codex --antigravity`; append a line to
`.agents/skills/grugops/SKILL.md`; `uninstall.js --codex --antigravity` printed the kept line with "or delete the
marker by hand to keep them without a record". After the marker was deleted, `uninstall.js --claude` printed
`note --claude: Claude Code is not installed here, so nothing is removed for it` and
`== uninstall complete — no agent removed (none of the named agents is installed here); still installed: none ==`,
exit 0. `.claude/agents`, `.claude/skills` and `.claude/settings.json` (with install's ask rules) stayed, with no
record left to reverse them.

**Fix:** offer the delete-the-marker alternative only on a FULL run. On a partial run, name the per-entry by-hand
remedy instead, and change the README to match:

```ts
const keepWithoutRecord = FULL
  ? "or delete the marker by hand to keep them without a record"
  : `or, to keep ${held.length === 1 ? "it" : "them"}, take ${held.length === 1 ? "its entry" : "their entries"} out of ` +
    `the install ledger in ${MARKER_REL} by hand (never delete the marker: it is still the record of ${nameList(STAYING)})`;
```

Apply the same split to the KEPT_FOR banner at line 2705. Add a row that runs the printed alternative on a partial
run and asserts that `uninstall --<staying agent>` still removes that agent.

## Warnings

### WR-19: The printed remedy commands only work from the checkout root with the default kit home, and the "run it as printed" tests cannot see this, because the harness supplies both (MSG-1 class again)

**File:** `install/host-tools.ts:293-296` (agentCommand), `install/installer-paths.test-support.ts:424-440` (runPrintedCommand); every agentCommand site, for example `install/install.ts:1905-1907` (the doctor's nothing-installed note), `install/install.ts:3439-3440` (WR-17's remedy), `install/install.ts:7241` (INCOMPLETE banner), `install/uninstall.ts:2514-2517` (finishCommand)

**Issue:** agentCommand always prints `node install/<binary> --target <t> <flags>`. That command:

1. resolves `install/<binary>` against the user's current directory, so it runs only from the grugops checkout
   root. The installer knows where it lives (`SCRIPT_DIR`) but does not print that path. The README itself shows
   `node install/install.js --target /path/to/repo --claude` under "run from anywhere"
   (`install/README.md:52-53`).
2. leaves out `GRUGOPS_HOME` (and `INSTALL_MODE`), which the README documents as the way to keep the shared kit
   somewhere other than `~/.grugops` (`install/README.md:68-69`). A printed `install.js` command run as printed then
   uses `~/.grugops`. That is exactly the failure this project has hit in practice: a run without `GRUGOPS_HOME`
   overwrites the real `~/.grugops` kit.

runPrintedCommand, the support every MSG-1 remedy row uses, runs the command with `cwd: REPO_ROOT` and injects
`GRUGOPS_HOME: opts.grugopsHome` (`installer-paths.test-support.ts:430-434`). So the "a remedy is tested by running
it" proof (brief §2.1) holds only in the harness's environment, never in the user's.

Reproduced (S2): `GRUGOPS_HOME=<scratch>/kitA install.js --yes --claude --pi` with `.pi` as a regular file (Pi
refused, exit 3); `--check` printed `` `node install/install.js --target <t> --pi` writes its entry ``. After the
cause was fixed, running that exact command (scratch `HOME`, no `GRUGOPS_HOME`) printed
`copied kit → <scratch HOME>/.grugops/agent-factory`. A second kit was written into the default kit home that the
user had chosen not to use. If that path already holds a kit recorded by another repository's install, the copy's
replace/backup arms act on that kit.

**Fix:** have agentCommand take the invocation context and print it, and make the test run the command from
another directory with no injected kit home:

```ts
export function agentCommand(binary: "install.js" | "uninstall.js", target: string, hosts: readonly HostTool[],
  ctx: { readonly scriptDir: string; readonly kitHome: string | null }): string {
  const env = ctx.kitHome === null ? [] : [`GRUGOPS_HOME=${shellWord(ctx.kitHome)}`];
  return [...env, "node", shellWord(join(ctx.scriptDir, binary)), "--target", shellWord(target), ...hosts.map(agentFlag)].join(" ");
}
```

Here kitHome is the run's `GRUGOPS_HOME` when it is not the default, or, in the doctor, the marker's recorded
`grugopsHome`. In runPrintedCommand, set `cwd` to a scratch directory, remove `GRUGOPS_HOME` from the environment,
and let the printed words supply it.

### WR-20: The unusable-marker remedy, rewritten this round, does not finish a per-agent uninstall: "install with any agent flag, then run this command" leaves the old agent's files unreported (MSG-1 class again)

**File:** `install/uninstall.ts:2442-2458`

**Issue:** For an unbound marker (copied from another directory) and for a no-target or no-ledger marker, the
verify now says: re-run install.js here, "with any agent flag (every install writes a marker for this directory,
whatever agents it names)". The second branch then says "then uninstall with `${rerunCommand()}`", and both claim
that "what an earlier install made here is then left and reported, for you to remove by hand". On a per-agent run,
rerunCommand keeps this run's flags (for example `--codex`). If the new install named another agent (which the text
explicitly allows), the new marker does not record Codex. The printed uninstall then finds "none of the named agents
installed", walks nothing and reports nothing. The old Codex files are neither reversed nor reported, which
contradicts what the message promises. The remedy also tells the user to install an agent (and the shared footprint)
only to get a fresh marker.

Reproduced (S3): `install.js --yes --claude --codex` in `a`; `mv a b`; `uninstall.js --target b --codex` printed the
unbound verify (exit 3). Following it with `install.js --yes --target b --claude` and then
`uninstall.js --target b --codex` printed `note --codex: Codex CLI is not installed here` and an empty "grugops-shaped
paths the install ledger does not record" section, exit 0. `b/.agents/skills/grugops/SKILL.md` stayed unreported.

**Fix:** name the install command with this run's own agents. Then the follow-up uninstall names agents the new
marker records:

```ts
const sameAgents = HOST_TOOLS.filter((h) => REMOVE.has(h.id));
`... re-run \`${agentCommand("install.js", TARGET, sameAgents)}\` (it writes a marker for this directory and carries ` +
`none of these records), then \`${rerunCommand()}\`: what an earlier install made here is then left and reported`
```

When the run is flag-less, the flag-less forms already agree. Add a row that follows the printed two-step remedy from
an unbound marker on a per-agent run and asserts that the old entry is reported.

### IN-24: The doctor's nothing-installed note claims a record the doctor did not read

**File:** `install/install.ts:1523-1539`, `install/install.ts:1901-1909`

**Issue:** The note says "<agent> is recorded in .grugops/install.json as chosen ... (the install ledger records
nothing of install's for it ...)". For a `legacy` source (a marker with no `agents` field), nothing is recorded as
chosen: the row comes from LEGACY_ADAPTER_KINDS. For a malformed ledger, `withEntry` is computed over `[]`, so
"records nothing of install's for it" is unknown, not established. In that case Claude Code can also fall into
`nothingInstalled`, and `claudeInstalled` (`:1914`) then skips the Claude Code checks. This is DOC-1: prose states
behaviour the read does not show.

**Fix:** word the note by `installed.source` ("counted as installed before this release" for legacy). On a malformed
ledger, put no row in `nothingInstalled`, because the doctor cannot tell, and it already FAILs on the ledger.

### IN-26: Install's call to agentsToRecord can never use the ledger (keep equals known), so the census proves only how the call is written

**File:** `install/install.ts:5411-5427`

**Issue:** writeMarker passes `known: knownAfter, keep: knownAfter`. agentsToRecord then returns exactly `knownAfter`
plus `unknown`, whatever `entries` holds. REC-1 asks for one derivation "from the ledger state the run leaves
behind", in both directions. Install does not do this: a ledger entry owned by an agent missing from `agents` (for
example a marker written by the round-0 uninstall in the CR-02 state, or a hand-edited one) stays contradicted after
any later install. Mutation M4 and the census row check that writeMarker calls agentsToRecord, not that the result
satisfies the invariant. Low reach today: the round-0 code is unreleased.

**Fix:** pass `known` as the registry ids that own an entry of `nextEntries` or are in AGENTS_AFTER. Shared-entry
co-owners stay excluded because they own no recorded agent's entry. Alternatively, state in the agentsToRecord
header that install's call is the identity by design, and drop "install" from REC-1's list of derivations.

### IN-27: On an unusable marker, the uninstall banner says "none of the named agents is installed here; still installed: none"

**File:** `install/uninstall.ts:2642-2647` (AGENTS_CLAUSE, unchanged this round)

**Issue:** When the marker is unbound or has no target or ledger, INSTALLED is `none`, and the banner asserts that
nothing is installed. In S3 the closing line read
`== uninstall INCOMPLETE — 1 item(s) need verification — no agent removed (none of the named agents is installed here); still installed: none ==`,
while Claude Code's and Codex CLI's files were in the directory. The record cannot be read, so it is unknown, not
none. This is the same "installed" wording class as IN-21. The site was not changed this round.

**Fix:** when `INSTALLED.source === "none"` and a marker is present, print "which agents are installed here is
unknown (the marker cannot be used; see the verify line above)".
