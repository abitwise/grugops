## The kit home a printed command carries (D-33, with the planner's reading for uninstall)

D-33: "prefixes GRUGOPS_HOME=<dir> only when the run used a non-default kit home".
- install.ts, every mode (install, --check, --migrate, --update, --prune-old-kit): the run resolves GRUGOPS_HOME and
  uses it. The context's kit home is that value, null when it equals the default
  (canonicalPathSpelling(resolve(homedir(), ".grugops"))). In a doctor run given a kit home other than the one the
  marker records, the doctor already reports the kit-root disagreement. Its printed commands carry the kit home the
  doctor itself used.
- uninstall.ts resolves no kit home of its own; uninstall never reads or removes the kit. The kit home its printed
  commands carry (the install command of plan 34.1-21 matters here) is: the GRUGOPS_HOME the run was given (non-empty,
  resolved and spelled as install does), else the `grugopsHome` the target's marker records (an `ok` marker, or the
  object of an `unbound` one, whose kit fields the doctor already reads), when it is a non-empty absolute string, else
  the default. Without the marker's value, an uninstall run given no GRUGOPS_HOME would print an install command that
  writes a second kit into `~/.grugops`, which is WR-19's harm. The prefix is applied to both binaries' commands: one
  rule in one builder. uninstall.js ignores GRUGOPS_HOME, so the prefix is harmless on its commands.
