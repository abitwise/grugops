It checks the four committed generator twins exist under `GRUGOPS_SRC`, `mkdtempSync`es a `grugops-install-render-` tree, copies the twins file-wise and `agent-factory/{roles,packaging}` recursively, writes a `package.json` and the resolution probe, drops the target's own `.grugops/factory.config.json` in **only if it already exists**, spawns the mirrored generator with `process.execPath` and no shell, reads the rendered listing back out of the mirror, reads the announced resolution back through the mirrored `model-tiers.js`, and removes the tree in a `finally` on every path out.

## Decisions Made

- **R-1 (b), as the planner ruled.** `install.ts` writes a fixed ES-module reader into the mirror, spawns it with the generator's stdout on stdin, and parses the one JSON line it prints. The reader imports the **mirrored** `./model-tiers.js` and calls that module's own exported `resolvedAssignmentsIn`. So `install.ts` spells neither announcement prefix (`grep -c` for both prints `0`) and `install/`'s module graph is untouched (`grep -cE 'from .[.][.]?/?scripts/'` prints `0`).
- **The relayed line is a mention, not a second announcement.** Both readers require their prefix at byte 0 of the trimmed line (finding WR-03), and the relay sits indented under the installer's padded report label — so `resolvedPresetsIn(installerStdout)` and `resolvedAssignmentsIn(installerStdout)` both return `[]`. The generator says what it resolved; the installer forwards it; the two authorities stay distinguishable (T-29.2-08). This is pinned as an assertion, not left as a property nobody checks.
- **`readRenderedAlias` is a reporting projection, not a decision predicate.** Nothing routes, refuses or writes differently because of the value it returns; the value is printed and the *set* of values is cross-checked. The one thing it decides is the exactly-one floor. Its comment states what bounds its input: bytes this run just rendered for an agent adapter, never a skill and never a file in the target.
- **`--dry-run` does not also print the doctor's staleness verdict** (RESEARCH Open Question 4). It reports the resolution and reads `would-materialize … (KIT=…, model=<alias>)`; the two modes stay separate surfaces.

### 2. [Rule 2 — Missing critical] The mirror declares `{"type":"module"}`

- **Found during:** Task 1 (surfaced at the checkpoint; user approved folding it in).
- **Issue:** The committed twins are ES modules with a **bare `.js`** extension, and Node resolves that from the nearest `package.json` `type` field. A `mkdtemp` directory under the system temp root has none above it, and implicit-ESM detection for a bare `.js` only became the default in **Node 22.12** — on 22.0 through 22.11 the mirrored generator dies with `Cannot use import statement outside a module`, and R-5 would turn that into an install that laid down **no adapter at all** on a supported Node.
- **Fix:** `MIRROR_PACKAGE_JSON = '{"type":"module"}\n'` written at the mirror root. One extra file; no directory added; no prohibition touched (the mirror-layout `mkdirSync` calls still create only `scripts`, `.claude/agents` and conditionally `.grugops`).
- **Verification:** pinned by `model delivery: the mirror declares its module type, so a bare `.js` twin cannot fail to parse on Node 22.0-22.11`, asserted over **both** `install.ts` and the committed `install.js`.
- **Committed in:** `3e87e69`.

### 3. [Rule 2 — Missing critical] Every spawn uses `process.execPath`

- **Found during:** Task 1 (surfaced at the checkpoint; user approved).
- **Issue:** The analog (`scripts/adapters-freshness.ts`) spawns a bare `"node"`, which is a `PATH`/`PATHEXT` lookup and wrong on Windows.
- **Fix:** both the generator spawn and the resolution probe use `process.execPath` with `shell` unset. Pinned by `model delivery: install.ts reaches the generator by SPAWNING it, never by importing anything under scripts/`, which also asserts `shell: true` appears nowhere.
- **Committed in:** `3e87e69` (generator) and `4157d8a` (probe).

### 4. [Rule 2 — Missing critical] The missing-generator-twin arm had no case

- **Found during:** post-Task-2 review of the fail-closed arms.
- **Issue:** `renderAdaptersInMirror()`'s partial-checkout pre-check is the branch R-5 exists for and had no coverage. A safety invariant with a green suite and no case over its own arm is the failure mode this repository's own memory names.
- **Fix:** a case removing each twin in turn (so it cannot pass by covering whichever is checked first) and then all four at once (so the count in the message is exercised).
- **Discrimination measured:** with the pre-check made unreachable in a scratch build, the case reds `status=1 named=false` against `status=3 named=true` — the absent twin makes `cpSync` throw **uncaught** and the installer dies at exit 1 with a stack trace instead of emitting a named finding. The pre-check is not decoration; it converts a crash into a report.
- **Committed in:** `b8c0d31`.

## Issues Encountered

Fixed by anchoring on the first `];` instead; the declared-versus-parsed refusal (the WR-04 idiom, applied here to a list of single strings rather than tuples) is what made the failure loud rather than a silent under-match.
- **The `verify` finding text is multi-line.** Findings now carry continuation lines indented to align under the padded report label. This is new for this file — every prior finding was a single (wrapped) string. It is deliberate: the relayed generator refusal is itself multi-line, and folding it onto one line would destroy the message the generator wrote.
