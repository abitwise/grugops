  <context>
    D-05 settled the five keys and six section names. Inside that, these were left to Claude's discretion and are proposed by 45-RESEARCH.md Pattern 2 (assumptions A1, A3):
    History forms, one per line, each `- YYYY-MM-DD: <event>` (UTC date):
      `open, by BA/PM` | `edited, by BA/PM: <what changed>` | `carried, by human:<name>` | `answered, by human:<name>, pin <commit>` with an optional `, not-descendant` | `withdrawn, by BA/PM: <reason>` (from open) or `withdrawn, by human:<name>: <reason>` (from carried).
    `<name>` uses the note schema's stamp grammar `human:[A-Za-z0-9._-]+` (for example `human:jane.example`), so a role name never satisfies it. It is a prose-tier record, not a security boundary.
    Other parts: the recommended option opens `- (recommended) `; `## Upstream IDs` may be the single line `none` (a request about something upstream has not decided has no ID); `<n>` is the highest number in the folder plus one, never reused (terminal files stay); the ticket bullet is `- <date>, raised by <role>: waiting on build request BR-<n> (owner: human carrier)`; `open → answered` is refused (withdraw instead).
    Undo cost: renaming any of these after 3.1.0 needs a migrate step over users' committed files.
  </context>
  <options>
    <option id="option-a">
      <name>Adopt the research forms as listed (recommended)</name>
      <pros>Every human move is a named stamp the grammar checks; "changed since carried" is derivable from `edited` lines; a carried request can still be dropped, but only by a named human; matches the existing `human:<name>` stamp</pros>
      <cons>Names cannot contain spaces (`human:jane.example`, not `human:Jane Example`)</cons>
    </option>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BA/PM (agent) → build-request file | the writer is an agent; the History lines record human moves it was told about |
| build-request file → every consumer | the parser is the only gate between a file and the validator, state-check and the reader |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-45-08 | Spoofing | History `carried` / `answered` entries | high | mitigate | the grammar admits these only with a `human:<name>` stamp (the note schema's HUMAN_STAMP_RE); BA/PM as actor is `bad-transition`; the contract (plan 45-09) states it is a prose-tier record, not authentication |
| T-45-09 | Tampering | `answered` entry | medium | mitigate | the answer pin must be a full object id of the raising pin's length and differ from it (BR-05), so an unchanged pin cannot close a request |
| T-45-10 | Tampering | parseBuildRequestDocument | medium | mitigate | closed grammar: the legal form is declared and the complement refused by code; reasons quote no file text, so a refusal cannot carry injected text into a report |
| T-45-SC | Tampering | npm/pip/cargo installs | low | accept | this plan installs no package |
</threat_model>
