§ 2 — EVERY ARM THAT CONSUMES THE TICKET POPULATION, PROBED ON THE MISMATCH FIXTURE
------------------------------------------------------------------------------------------------

The five arms are enumerated in a comment in `scripts/board-model.ts` immediately above the
population indexes. Each was driven with the id/stem mismatch and its output recorded — because the
lesson from five consecutive rounds is that a fix is correct in the arm it was written for and wrong
in the arm next to it.

Fixture P0: board `## Ready` carrying `- [ABC-300]` TWICE; `plans/tickets/ABC-300.md` declares
ABC-777 with `column: In Development`, `status: in-development`.

| Arm (as the module enumerates it)   | Reads                        | Produced for the mismatch fixture                                                                 | Verdict |
|-------------------------------------|------------------------------|---------------------------------------------------------------------------------------------------|---------|
| `board-vs-ticket`, arm one (column) | `ticketById.get(p.id)`       | nothing                                                                                            | correct |
| `board-vs-ticket`, arm two (status) | `ticketById.values()`        | nothing (this fixture's status IS the kebab of its column, so the arm is legitimately silent)      | correct |
| `ticket-unplaced`                   | `ticketById.values()`        | `[ticket-unplaced] ABC-777 :: no row names ABC-777`                                                | correct |
| `ticket-duplicated`                 | the BOARD alone              | `[ticket-duplicated] ABC-300 :: Ready, Ready`                                                      | correct |
| `row-without-file`                  | `presenceOf(p.id, …)`        | `[row-without-file] ABC-300 :: plans/tickets/ABC-300.md exists and declares the identifier ABC-777, so it is joined under that identifier and not this one` | correct |

WHY THE TWO `board-vs-ticket` ARMS ARE SILENT, AND WHY THAT IS THE HONEST ANSWER. Arm one looks the
ROW's identifier up and finds no record, because the file was admitted as ABC-777. Arm two iterates
the admitted records and asks whether ABC-777's status is the kebab of its column, which it is. The
board's ABC-300 and the file's ABC-777 are not two descriptions of one ticket — they are two
identifiers — so there is no column or status disagreement to report. The disagreement is the
IDENTITY, and it is reported twice, once from each side.

P0b PROVES THE TWO ARMS STILL FIRE IN THE MISMATCH CASE when there is something for them to say.
Same shape, with the file declaring `column: Done`, `status: ready`, and a second row naming the
DECLARED identifier:

  [board-vs-ticket] ABC-777 :: expected=done   :: actual=ready    (arm two, the status rule)
  [board-vs-ticket] ABC-777 :: expected=Done   :: actual=Ready    (arm one, the column rule)
  [row-without-file] ABC-300 :: … declares the identifier ABC-777, so it is joined under that
                                 identifier and not this one

So the presence fix did not silence the arms beside it; those arms were answering about ABC-777 all
along, and now the row for ABC-300 says so out loud.

CAN A HUMAN READING BOTH CONFLICTS TELL THEY ARE ONE DISAGREEMENT? Yes, and that is new. The pair
now reads:

  ABC-300  expected: plans/tickets/ABC-300.md   actual: … declares the identifier ABC-777 …
  ABC-777  expected: a row on the board          actual: no row names ABC-777

The first names the second. At the RED baseline the pair read "no file carries ABC-300" and "no row
names ABC-777", and nothing in either sentence pointed at the other — two unrelated-looking findings
about one document.

------------------------------------------------------------------------------------------------

Same machine, same copies, same method: one warm-up `readSnapshot`, then three timed calls, best of
three reported and all three shown.

| Entries | Admitted | BEFORE (`records.find`) | AFTER (`seenById` map) | Change  |
|---------|----------|-------------------------|------------------------|---------|
| 2,507   | 2,500    | **92.3 ms**             | **83.2 ms**            | -9.9%   |
| 5,007   | 5,000    | **212.5 ms**            | **164.7 ms**           | -22.5%  |
| 10,007  | 10,000   | **510.5 ms**            | **340.5 ms**           | **-33.3%** |

All three AFTER runs at 10,000: 340.5, 353.5, 353.0 ms.

THE SHAPE CHANGED, NOT ONLY THE NUMBER. Doubling the input used to cost 2.30x and then 2.40x; it now
costs 1.98x and then 2.07x. The superlinear term is gone and what remains is the per-file I/O and
parsing that is linear in the entry count by construction. The saving grows with the directory,
which is the point: the number that mattered was never the one at seven files.

D-14's rule is that a hung read is a stale badge and never a frozen screen, and the refresh runs on
every watch event and every poll tick — so this is a correctness-adjacent cost reachable by anyone
who can add files to `plans/tickets/`, not a micro-optimization.

A deterministic suite case guards the SHAPE rather than the timing: `scripts/board-read.test.ts`
walks `readTicketsSource`'s syntax tree and requires no `find`/`some`/`filter`/`includes`/`indexOf`
call over the accumulating `records` array, with the `seenById` lookup asserted present so the
emptiness cannot be vacuous. It reads the AST rather than the bytes because the docblock beside the
fix NAMES the call it replaced, and a text scan would find the sentence describing the fix and
report the defect as still present.


§ 5 — REACHABILITY
------------------------------------------------------------------------------------------------

THE `empty-stem` REFUSAL. Input: any entry under `plans/tickets/` whose name is exactly `.md` —
the only name that satisfies the walk's `endsWith(".md")` test and leaves nothing in front of it.
Call site: `readTicketsSource` in `scripts/board-read.ts`, immediately after the path authority
returns a contained child path and BEFORE any byte of the file is requested. Command: every command
that reads a snapshot — `node scripts/board-dashboard.js <root> --once`, `--once --json`, and every
refresh under `--watch`. Measured above as V6: the entry appears in `readErrors` with the code, is
absent from `tickets[]`, and is counted in the refused half so the walk's partition stays total. A
`pathRecorder` seam case asserts the file is never opened, so refusing it costs no read.

THE `admitted-under-another-id` ARM. Input: a board row naming an identifier `X` while
`plans/tickets/X.md` exists, parses, is admitted, and declares an identifier other than `X`. Call
site: `joinSnapshot`'s `row-without-file` arm in `scripts/board-model.ts`, which calls
`presenceOf(p.id, populations)` once per distinct placement identifier and takes both the decision to
raise a conflict and the text of its `actual` from the arm returned. Command: the same three. The arm
is gated behind `ticketsListingComplete`, so it is unreachable while the tickets source is anything
other than `ok` — measured above as V5. Reached in this proof from the plain frame, the `--json`
document and `readSnapshot` directly, on three independent trees.

THE `absent` ARM IS REACHABLE ONLY AS A COMPLEMENT. There is no input that selects it directly: it
is what `presenceOf` returns after three lookups all came back empty. That is the mechanism, not a
description of it — the one sentence in the module that asserts a negative is the one sentence no
measurement can produce.


§ 6 — MUTATION RUNS: EVERY ARM WATCHED TO FAIL
------------------------------------------------------------------------------------------------

Each mutation makes one arm answer as its neighbour, then `scripts/board-model.test.ts` and
`scripts/board-read.test.ts` are run against the REBUILT `.js`. A case that passes under a mutation
is a case that was not deciding anything.

| Mut | What was mutated                                              | Reddened | The case for that arm, named                                                              |
|-----|----------------------------------------------------------------|----------|--------------------------------------------------------------------------------------------|
| M1  | `admitted-under-its-stem` never fires (falls to the stem arm)   | 11       | `(1) an identifier a document DECLARES answers admitted-under-its-stem`, and `still raises NO row-without-file for a row whose file declares the row's identifier` |
| M2  | `admitted-under-another-id` never fires (falls to `absent`)     | 5        | `(2) an identifier that is a FILE STEM answers admitted-under-another-id, carrying it`, and `raises NO conflict asserting absence for an identifier whose file was admitted` |
| M3  | `refused` answers `absent` instead                              | 10       | `(3) an identifier the reader REFUSED answers refused, carrying the code`, and `leaves the refused and genuinely-absent rows BYTE-IDENTICAL to what they said before` |
| M4  | `absent` answers `refused` instead                              | 11       | `(4) an identifier in NONE of the three sets answers absent`, and `(b) a row whose identifier is GENUINELY ABSENT carries the UNCHANGED absence sentence` |
| M5  | the `empty-stem` refusal becomes a silent skip                  | 3        | `lands in the unadmitted half under empty-stem, leaving the source ok`, and `keeps the partition TOTAL, against a denominator derived from the listing` |
| M6  | `seenById` overwrites on every hit, so LAST by name wins         | 1        | `reports THREE files claiming one identifier against the FIRST, not against each other` |

Every mutation ALSO reddened `every arm produces its OWN sentence, and only absent asserts a
negative` (M1-M4) — the case that holds all four sentences at once — and three of the four reddened
`the count answered absent EQUALS the count derived independently of the arm`, which is the
arithmetic assertion that exists to catch an arm nobody wrote a case for.

M6 IS REDDENED BY EXACTLY ONE CASE, AND THAT CASE WAS WRITTEN BECAUSE OF IT. A two-file duplicate
corpus cannot see a first-wins rule turn into a last-wins rule: with two files, the surviving report
names the other one either way. The three-file row isolates it. That is the mutation-derived row
discovery this phase's earlier plans recorded, appearing again.

A MUTATION THAT DOES NOT COMPILE IS A MUTATION THAT NEVER RAN, AND IT REPORTED GREEN. M3's first
spelling narrowed its binding to `never` and then read a property off it, which `tsc` refuses;
`tsconfig.json` sets `"noEmitOnError": true`, so nothing was emitted, the suite ran against the
UNMUTATED build, and the transcript read `298 passed` — indistinguishable from a clause that decides
nothing. The re-spelled M3 above type-checks, emits, and reds ten cases. Recorded here because this
repository has logged a false verification-harness premise repeatedly, and this is one: the harness's
own premise — that the thing under test is the thing that was built — has to be asserted, not
assumed. `npm run build` was checked for a non-empty error tail on every subsequent mutation, and the
mutated line was read back out of the emitted `.js` before the suite was believed.
