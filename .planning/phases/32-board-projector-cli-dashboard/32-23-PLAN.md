<objective>
The round's adversarial self-review: re-measure everything this round claims, probe the arms next to
every fix, and record a ledger in which no gap-inventory item is missing.

This plan is the round-2 instance of the 32-14 shape, and it carries all eight requirement IDs
because it measures the phase rather than a slice of it.

**This plan does not decide phase completion. The verifier does.** Nothing here flips a requirement
checkbox or a phase status; the ledger records what was measured and leaves the verdict where it
belongs.

Round position: this is round 2 of the four-round gap-closure cap this project adopted after Phase 31.
Two rounds remain after this one. That budget is what makes recording an open finding safe rather than
a failure — and it is also why a finding recorded here must carry a reproduction somebody else can run,
not a description.

Purpose: every round of this phase, and of the four phases before it, the fix closed one spelling and
left the capability reachable one register over — five consecutive rounds in which a new finding was
created by the previous fix. The mechanism against that is not more care; it is a pass whose whole job
is to ask the sibling question.

There is no `SPEC.md` for this phase, so there is no `## Edge Coverage` and no `## Prohibitions`
section to satisfy.
</objective>

  <action>
BUILD THE REACHABILITY TABLE FIRST. One row per refusal branch added this round: the branch, the
predicate that decides it, the command that carries it, and the answer to how that command is reached
in a normal run of this repository's gates. A branch nothing reaches passes by never running, and this
repository added its foundation guards precisely because it once shipped a gate invoked by nothing.

THEN PROBE THE SIBLINGS, ONE QUESTION PER FIX. For each fix this round, write down every arm that
consumes the same input, and probe each with a legitimate input and with a hostile one. The questions
that have found the last five rounds' bypasses, asked here explicitly:
  - which SET does this predicate enumerate, and what is outside it;
  - at which POSITIONS is the predicate even asked, not only which values it accepts;
  - what is the predicate's INPUT assembled from, and who assembles it;
  - after splitting a predicate into arms, what does their UNION admit;
  - when a resolver DECLINES, what does the caller do with the decline;
  - which number does the specification anchor on, and which one did the code have in hand.
For this round specifically that means at least: the tickets partition asked at every walk, not only
the tickets walk; the honest conflict sentence asked when an identifier is BOTH admitted and
unadmitted; the stdout chokepoint asked for a document written by a path that is not the emit arm; the
allow-list asked for a specifier that is neither bare nor relative; the global member census asked for a
member reached through a binding rather than a literal root; and the classification of check scripts
asked for a script that runs two commands.

RECORD WHAT YOU FIND, AND DO NOT QUIETLY FIX IT. A finding gets a name, a severity, a reproduction and
a disposition. Close one here only when the closure is inside a file this plan already touches AND is
provably small; otherwise record it OPEN with its reproduction, because a fifth fix in a sixth file at
the end of a round is how the next round's first finding is made. Say which you did and why.

STATE THE RATIO. Count the findings this round created versus the findings it inherited, as the round-1
review did. The number is the project's own running measurement of whether the approach is converging,
and hiding it would remove the only signal that says a canonical-form cutover is overdue.
  </action>
