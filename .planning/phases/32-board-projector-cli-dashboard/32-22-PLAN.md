ONE SPAWN HELPER, THREE MEASUREMENTS. Write a helper that copies `scripts/fixtures/board-snapshot/`
into a scratch directory outside the repository root, spawns
`node scripts/board-dashboard.js <scratch> --watch --json --interval 1000`, collects stdout as complete
lines with their arrival timestamps, and always kills the child and removes the tree in a `finally`.
Give every wait an explicit deadline and fail with the measured elapsed time rather than hanging: a
test that can hang is a test CI cannot run.

THE PREMISE FIRST. Before measuring anything, assert that the first document arrives within the
deadline and parses, and print the platform, the Node version and the measured first-document latency.
A suite measuring a process that never started produces a false green as easily as the program under
it, and this repository has six recorded instances of a harness whose own premise was never checked.

CASE ONE — THE EVENT PATH, THROUGH THE WRITE THE KIT ACTUALLY USES. Modify the board by writing a temp
sibling in the same directory and renaming it over the target, which is what this kit's writer does and
what orphans a file-level watch. Assert a NEW document arrives carrying the change, and record the
latency. Set the deadline well below the configured poll period so that passing means the EVENT path
delivered it, not the poll — otherwise the case proves the poll twice and the watch never.

CASE TWO — THE POLL PATH ALONE. Spawn a second process with the forced-watch-error seam naming every
watched directory, so no watch survives its first event, then make the same atomic-rename edit. Assert
a new document arrives within a window that allows for the poll period plus one period of slack, and
assert the emitted document carries a watch-failure record. This is the safety net D-14 exists for,
measured with the low-latency path disabled.

CASE THREE — THE DEBOUNCE. Make five rapid edits inside the debounce window and assert the number of
documents that arrive in the following window is fewer than five and at least one. State the bound as
an inequality over measured counts rather than as an exact number: a wall-clock test asserting an exact
count is a flake generator, and a flaky safety test gets deleted.

NEVER SKIP SILENTLY. If a precondition cannot be met, fail with the measured numbers and the platform
in the message. Do not wrap a case in a platform conditional that turns a missing measurement into a
pass; if a platform genuinely cannot run one of these, name it in the failure and in this plan's
summary so the boundary is visible.

KEEP IT BOUNDED. The whole file must complete in under about fifteen seconds of wall clock. Say so in
the header with the arithmetic — three processes, a one-second poll period, and the deadlines chosen —
so a future edit that adds a case knows the budget it is spending.
