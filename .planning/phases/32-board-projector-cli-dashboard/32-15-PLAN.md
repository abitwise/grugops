<objective>
Close verification gap 1 (= `32-REVIEW.md` CR-01): a ticket file that exists and is readable, and is
merely refused by the ticket grammar, still makes the projector assert that no file on disk carries
that identifier.

Gap mapping for this plan (from `32-VERIFICATION.md` frontmatter `gaps:`, truth 3):

| Gap | Finding | Task |
|-----|---------|------|
| "never renders a torn read, a partial parse, or an ENOENT as an empty board" | `readTicketsSource` pushes a `readErrors` entry for a grammar refusal and deliberately does not set `firstReadFailure`, so `sources.tickets` stays `ok`; `joinSnapshot` then has no way to tell "no file exists" from "a file exists and was refused", and raises a positive, false claim about the filesystem under an `[ok]` header. Independently reproduced by the verifier against the current tree. | Task 1 (the reader's total partition), Task 2 (the join's per-identifier answer), Task 3 (the union of every arm) |

Purpose: `CLAUDE.md`'s no-fabrication rule — "never fake a passing gate, a test result, or a
citation … the trace is the proof" — applied to the surface DASH-03 introduced. The projector may
say it could not read something; it may not say something is not there when it is.

Output: the tickets walk becomes a TOTAL partition (every `.md` entry it lists becomes either an
admitted record or an unadmitted entry, never nothing), that partition is carried into the join, and
the presence-dependent derivation answers per identifier instead of per source.

WHY THIS IS NOT "GATE ON THE SOURCE STATE AGAIN". Plan 32-09 already gated the two presence-dependent
kinds on `sources.tickets.source === "ok"`, and that gate is correct for what it asks: was the
LISTING obtained. Degrading the whole source on one refused document would suppress every
`row-without-file` and every `ticket-unplaced` on the board because one ticket has a stray tab —
which is the "one refusal blanks the other five" failure plan 32-10 spent a whole plan closing, one
register up. The answer is per identifier, and the set it is answered from is derived from the
directory listing rather than from the parse successes.

This plan runs FIRST in round 2: every later plan in this round either analyses the compiled closure
that contains `scripts/board-read.js` and `scripts/board-model.js`, or changes which documents this
reader refuses.

There is no `SPEC.md` for this phase, so there is no `## Edge Coverage` and no `## Prohibitions`
section to satisfy.
</objective>
