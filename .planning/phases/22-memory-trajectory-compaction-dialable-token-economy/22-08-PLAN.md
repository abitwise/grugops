<objective>
Close the 6th distinct CMP-02 bypass — the splitNotes/parseNote DRIFT — and, more importantly, close
the CLASS it belongs to once and for all by making splitNotes FAIL CLOSED on every fence-ish region it
cannot cleanly recover.

THE BUG (verified, reproduced end-to-end by the round-6 verifier): the round-6 executor narrowed the
note-boundary predicate to a column-0 `---` line followed by a column-0 `id:` line
(`isNoteOpeningLine = /^id:/`, context-io.ts:273; `isBoundaryAt` requires `lines[i] === "---"` exact,
context-io.ts:324). That `/^id:/` set is a STRICT SUBSET of parseNote's recognized-frontmatter-line
grammar. So a note #2 whose opening frontmatter line is NOT a column-0 `id:` —
  • KIND-FIRST (`kind:` on the first frontmatter line, `id:` second),
  • INDENTED-ID (` id:` with a leading space/tab),
  • or preceded by a TRAILING-SPACE `--- ` / `---\t` boundary line —
is NOT recognized as a boundary. splitNotes returns `count=1, trailingMalformed=null,
malformedLines=[]` (NO fail-closed signal of any kind) and folds note #2 entirely into note #1's body.
Its §14-gate-verified finding (`verified_by: §14-gate#…`) never becomes a parsed fence, so it never
enters the id-keyed required-survival set, both round-5 gates, or the byte-equal loop. The CLI exits 0
"carve-out intact" while the verified finding is dropped from the promoted set.

This is WRITER-REACHABLE, not hand-authored: the sanctioned `writeThread` no-`note` free-scratch path
(compactor.ts:571-573) glues ARBITRARY agent body bytes onto the same threads/<agent>.md, and the
plan's own threat model declares that file an adversarial boundary ("a single file holds MANY
adversary-authored note fences; the oracle must recover EVERY note"). Two sanctioned writeThread calls
(note #1 structured; note #2 via free-scratch with kind-first bytes) reproduce the exact file.

WHY THE 409-TEST SUITE STAYED GREEN: every round-6 fixture authors id-first notes (the production
shape via composeThreadNote), never the kind-first / indented / trailing-space shapes. Green suite ≠
proof, for the 6th time. The round-6 closure rests on an UNDOCUMENTED, UNTESTED, UNGUARDED "every
writer emits id: first" coupling — a benign field-reorder of composeNote re-opens the hole with a
fully green suite.

THE FIX (Fork A — read-path-only, USER-RESOLVED; do NOT re-open the fork, do NOT propose Fork B):
  1. FAIL-CLOSURE (the safety mechanism — this is what SC2 depends on). Make splitNotes refuse, never
     silently absorb. Whenever a `---`-boundary-shaped line (column-0 `---` OR a trailing-whitespace
     variant `--- ` / `---\t`) is immediately followed by a frontmatter-LOOKING line (a `<key>:` line
     at ANY indent, including the `key : value` space-before-colon shape) and splitNotes does NOT
     resolve that region into a clean, fully-parsed note, route it to `trailingMalformed` →
     `NoteDirResult.unparseable`. A fence-ish region is EITHER a recovered parsed note OR a loud
     refusal — NEVER swallowed into a body. Recognition can be broadened to whatever degree is safe,
     but the silent-drop class is killed by fail-closure regardless of which exotic shape is chosen.
  2. BROADENED RECOGNITION (usability on top, IN-02 — the single source-of-truth grammar). Replace the
     `/^id:/`-only boundary key with reuse of parseNote's recognized-frontmatter-line set (extract a
     shared predicate so the splitter and parser provably agree). A genuine kind-first / indented-`id:`
     note #2 that is UNAMBIGUOUS is RECOVERED (count increments, the note parses) rather than merely
     refused — broadened recognition is the usability layer, fail-closure is the floor.
  3. WRITER-ORDER GUARD (kills the unguarded coupling). Add a structural guard/test asserting BOTH
     composeNote and composeThreadNote emit a note-opening line splitNotes recognizes as a boundary,
     so a future field-reorder fails RED, not silent.
