<objective>
End the CMP-02 carve-out bypass cycle (round 3). The carve-out oracle in `scripts/compactor.ts`
has NO stable per-note identity, so it guesses the raw→promoted correspondence from forgeable,
collidable CONTENT TUPLES. All three surviving bypasses are this one defect:

- **CR-01** (compactor.ts:225-241): `verifiedKey = (kind, verified_by, by, at)` keyed into a Set,
  tested with `.has()` — set MEMBERSHIP not COUNT. One §14-gate run stamps N findings identically,
  they collapse to one key, one promoted survivor satisfies all N, the rest drop at exit 0.
- **CR-02** (compactor.ts:194-219, 251-263): `if (!counterpart) continue` (line 197) is FAIL-OPEN.
  A non-verified note matched on `(kind, at)` returns null when both `by` AND `at` are mutated, or
  when two notes share `(kind, at)` → the field check is skipped → a `by` swapped engineer→attacker
  survives.
- **IN-01** (compactor.ts:198, 225-241): `supersedes` is in the alter-list but has no affirmative
  existence check → a wholly-dropped note loses its load-bearing supersedes link undetected.

The fix is the **STABLE-ID REWRITE** (not the minimal multiplicity patch). The id already exists:
`context-io.ts noteId()` (line 369) computes `<at-compact>-<by>-<kind>-<nonce>` and stores it as the
filename `notes/<id>.md`. This plan threads that existing identity through as an explicit frozen
`id:` frontmatter field, makes the carve-out an exact 1:1 id match (affirmative existence, fail
closed, byte-equal fields), folds `supersedes` into the same id comparison, and DELETES the
`findCounterpart` tuple fallback + the `verifiedKey` Set — they are the defect.

Purpose: make the CMP-02 carve-out genuinely un-cheatable — a safety invariant, not a green suite.
A green suite is necessary but NOT sufficient here (this is the round-3 lesson): the 4 held-out
adversarial cases must be RED-first against the committed pre-fix `.js`, then refuse against the
committed post-fix `.js`.

Output: a hardened `scripts/compactor.ts` (+ byte-fresh `compactor.js`), an `id:`-emitting
`scripts/context-io.ts` (+ byte-fresh `context-io.js`), the `id` field in the note-schema contract,
and a `scripts/compactor.test.ts` that pins the bypass CLASS with 4 held-out RED-first cases.

Design rationale (the strict-policy reversal — name it explicitly): this plan REVERSES the current
code comment at `compactor.ts:190-192` ("A durable note WITHOUT a verified_by stamp ... MAY be
dropped"). That comment CONTRADICTS locked decision D-03 (the tool does NO semantic folding except
the `supersedes` collapse). Under the strict policy, EVERY durable raw note survives into promoted
with intact provenance; the ONLY sanctioned removal is the `supersedes` fold (the D-03
`currentState()` collapse). Body compression (D-01) is the sole latitude. This also kills
drop-and-replace authorship laundering. The existing "a failed-attempt id always survives" rule
(carve-out rule 1) is a special case of this strict rule — keep it.
</objective>

## The thread-representation model (RESOLVED — implement exactly this, consistent with D-07/D-08)

D-08 keeps the thread tier a SINGLE file `.grugops/context/<task>/threads/<agent>.md`. The carve-out
`check` verb reads a DIRECTORY of per-note `.md` files. For id-based matching to be REAL (not test
fiction), the RAW side must carry per-note `id:` fields.

**Resolution (chosen): the `check` verb's "raw" input is an explicit per-note id-bearing
representation produced AT COMPACTION TIME.** The agent, following Workflow 18 step 3, hands the
carve-out check a per-note snapshot directory where each raw durable note is one `id:`-bearing `.md`
file. This is consistent with D-08: the ephemeral `threads/<agent>.md` blob stays a single file for
the agent's own scratch; the carve-out operates on the structured per-note set the agent proposes to
promote, and every such raw note carries the same frozen `id:` its promoted counterpart preserves.

`writeThread` is updated to APPEND an id-bearing structured note FENCE per recorded note (not
freeform body text), so the thread file itself is a sequence of id-bearing notes the compaction step
parses into the per-note raw set. The `id:` it stamps is the creation-time `noteId()` value — the
SAME id the promoted note must preserve byte-for-byte.

State this choice and its D-08 consistency in the SUMMARY.
</thread_representation_resolution>
