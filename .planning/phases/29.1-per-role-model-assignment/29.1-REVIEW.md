# Phase 29.1: Code Review Report

**Reviewed:** 2026-08-19
**Depth:** standard (with targeted adversarial reproduction against the committed `.js`)
**Files Reviewed:** 17 source files (plus 4 prose surfaces read for reach claims)
**Status:** issues_found — advisory, non-blocking

## Summary

The mechanism is well built. I verified the four review priorities directly and three of them hold:

- **`guard_model_assignment` independence (priority 1) — HOLDS.** Its inputs are the committed adapter bytes read through `admit()` and a resolution recomputed from `readModelsConfig` + `resolveModels`. It imports nothing from `generate-role-adapters`, never regenerates, and never byte-compares. Case `(j)` in `check-foundation-guards.test.ts` proves the direction that matters: seventeen byte-*fresh* adapters go red under a planted `preset: tiered`. This is not the CR-01 defect class.
- **Alias matching (priority 3) — HOLDS.** Verified empirically against the committed `model-tiers.js`: `Opus`, `OPUS`, `"inherit "`, `" inherit"`, `claude-opus-4`, `3`, `null`, `""` are all refused. No regex, no case fold, no trim, no coercion anywhere on the alias path.
- **Refusal ordering in the generator (priority 2) — HOLDS.** `readModelsConfig` and `resolveModels` both run at `generate-role-adapters.ts:291-300`, above the build loop and above `mkdirSync(OUT_DIR)` at line 527. A refused run creates no directory and writes no byte.
- **Build parity — HOLDS.** `npm run freshness` reports all 49 committed `.js` fresh against a rebuild.

What did not hold is the *completeness* of the D-04 zero-config pin, and a family of silent-acceptance gaps in the config reader. The single most important finding is CR-01: the pin this phase built specifically to stop "a configured regeneration certified as the zero-config output" observes only `preset` and is blind to `models.roles` — and a committed test case pins that blindness as correct behaviour.

## Critical Issues

### CR-01: The D-04 zero-config pin is half-blind — a `models.roles` override announces `none` and passes the freshness gate

**Files:**
- `scripts/generate-role-adapters.ts:543` (`console.log(...resolvedPresetLine(modelsConfig.preset))`)
- `scripts/adapters-freshness.ts:239-267` (the pin: `announced[0] !== ZERO_CONFIG_PRESET`)
- `scripts/generate-role-adapters.test.ts` — case *"a legal per-role OVERRIDE resolves, is announced as `none`"* (asserts `resolvedPresetsIn(...)` equals `["none"]` while `qe-e2e` emits `haiku`)

**Issue:** The announcement is derived from `modelsConfig.preset` alone. `resolveModels` produces its map from *two* inputs — the preset *and* the sparse `overrides` map — so the announced value describes only half of the resolution the run actually performed.

Reproduced against the committed `.js`. Mirror carrying `agent-factory/config/factory.config.json` = `{"models":{"roles":{"orchestrator":"opus","security-nfr":"opus"}}}`:

```
generate-role-adapters: wrote 17 adapters ...
generate-role-adapters: resolved model preset: none     <- the pin's expectation, satisfied
grugops-orchestrator.md   model: opus                   <- not the zero-config output
grugops-security-nfr.md   model: opus
```

**Failure scenario — the exact one `adapters-freshness.ts:70-78` predicts.** A future author adds `agent-factory/config` to the twin list (the header itself justifies mirroring a directory the generator does not open, so this is the plausible well-intentioned edit). The tree carries a `models.roles` block and the committed adapters were regenerated under it. Then:

| gate | verdict |
|---|---|
| `freshness:adapters` — pin | announced `none` → **passes** |
| `freshness:adapters` — bytes | both sides configured identically → **passes** |
| `guard_model_assignment` | reads the same config, expects `opus`, finds `opus` → **passes** |

The build is fully green while D-04 ("the committed adapters are the ZERO-CONFIG output") is false. The `preset` half of the same hole is caught (Case 10); the `roles` half has no case, and the generator case above cements the blindness as expected behaviour.

The only remaining catch today is `adapter-byte-baseline.test.ts`, whose whole purpose is to be re-pinned as the tree legitimately evolves — so it is a backstop with a scheduled expiry, not a pin.

**Fix:** announce the whole resolution, not one of its two inputs. Cheapest sound form — assert the *source*, which is `null` exactly under zero-config:

```ts
// model-tiers.ts — one grammar, both directions, as the preset line already is
export const RESOLVED_SOURCE_PREFIX = "resolved model config source: ";
export function resolvedSourceLine(source: string | null): string {
  return `${RESOLVED_SOURCE_PREFIX}${source ?? "none"}`;
}

// generate-role-adapters.ts, beside the existing announcement
console.log(`generate-role-adapters: ${resolvedSourceLine(modelsConfig.source)}`);

// adapters-freshness.ts, beside the existing preset assertion
// require exactly one source line, and require it to read "none"
```

Alternatively announce `overrides.size` (must be `0`) or a stable digest of the resolved map. Whichever is chosen, add the missing discrimination case: plant `{"models":{"roles":{...}}}` (no `preset` key) into `mirrorConfigDirectoryIntoTheTwinList`'s mirror and require the gate to go red.

## Warnings

### WR-01: A one-character typo inside the `models` block is silently swallowed — the exact outcome D-06 refuses for `roles` keys

**File:** `scripts/model-tiers.ts:812-888` (`readModelsBlock`)

**Issue:** `readModelsBlock` reads `models.preset` and `models.roles` and never enumerates the block's own keys. Any other key is silently ignored. D-06's stated principle — *"A silently ignored override is a tier the user believes they set and did not"* — is enforced for keys *inside* `models.roles` and not for keys inside `models` itself.

Reproduced against the committed `.js`:

```
{"models":{"presets":"tiered"}}                       => OK  preset=none  overrides=0
{"models":{"Preset":"tiered"}}                        => OK  preset=none  overrides=0
{"models":{"preset":"tiered","role":{...}}}           => OK  preset=tiered overrides=0
{"model":{"preset":"tiered"}}                         => OK  preset=none  overrides=0
```

**Failure scenario:** a user writes `"presets"`, regenerates, sees seventeen `model: inherit` adapters and no message of any kind, and has no way to tell a typo from "the dial did nothing". The `role` case is worse: the preset applies, the overrides silently do not, so the user gets a *partially* wrong tier map with a green run — which is precisely what the `unassigned` refusal calls "a partial preset is a tier the user believes they set and did not".

**Fix:** close the block by name, the same way the alias and preset vocabularies are closed:

```ts
const MODELS_KEYS = ["preset", "roles"] as const;
const unknown = Object.keys(models).filter((k) => !MODELS_KEYS.some((legal) => legal === k)).sort();
if (unknown.length > 0) {
  return { ok: false, reason:
    `model-tiers: ${path} sets ${unknown.map((k) => `\`models.${k}\``).join(", ")}, which is not a ` +
    `key of the \`models\` block. The legal set is exactly: ${MODELS_KEYS.map((k) => `"${k}"`).join(", ")}. ` +
    "A silently ignored key is a tier the user believes they set and did not (D-06)." };
}
```

### WR-02: `resolveModels` Floor 0 accepts `preset: null` (and any nullish) as `none` — the floor's own stated contract is false on the committed `.js`

**File:** `scripts/model-tiers.ts:629-639`

**Issue:** `const preset: PresetName = options?.preset ?? "none";` runs `??` *before* `isPresetName`. The docstring on `ResolveModelsOptions.preset` explicitly claims *"The resolver validates it by exact equality anyway — a JS caller can hand over anything"*. It does not: `null` and `undefined` are coerced past the floor.

Reproduced: `resolveModels(['a','b'], {preset: null})` → `{"ok":true,"value":{}}`. No refusal.

This matters because the tooling layer ships as committed `.js` with no type checking on hosts, and the module header names the installer doctor and "any future runtime reader" as consumers. `readModelsConfig` cannot produce a null preset today, so this is latent rather than live — but it is a floor that does not hold in exactly the direction its comment promises it does.

**Fix:**

```ts
const rawPreset = options?.preset;
const preset = rawPreset === undefined ? "none" : rawPreset;
if (!isPresetName(preset)) { /* the existing refusal */ }
```

### WR-03: `resolvedPresetsIn` matches the marker anywhere in a line, so an incidental mention satisfies the pin

**File:** `scripts/model-tiers.ts:265-273`

**Issue:** the reader uses `line.indexOf(RESOLVED_PRESET_PREFIX)` with no anchor and no owning-prefix requirement. Any line in the child's stdout that happens to contain the phrase is read as an announcement.

Reproduced:

```
resolvedPresetsIn('WARN could not read resolved model preset: none')  => ["none"]
resolvedPresetsIn('echo "resolved model preset: tiered" >> log')      => ["tiered\" >> log"]
```

**Failure scenario:** the announcement is dropped or moved in a refactor, but some diagnostic, help text or comment echo in the same run mentions the phrase. `announced.length === 0` never fires, and the gate reads an incidental sentence as consent — the failure mode the gate's own header calls *"the shape this repository has paid for repeatedly"*. Case 9 (`stripAnnouncement`) does not cover it, because it removes the only line that mentions the marker.

**Fix:** anchor the grammar and let the emitter own it end to end:

```ts
export const RESOLVED_PRESET_PREFIX = "generate-role-adapters: resolved model preset: ";
// ...
const trimmed = line.trimEnd();
if (!trimmed.startsWith(RESOLVED_PRESET_PREFIX)) continue;
found.push(trimmed.slice(RESOLVED_PRESET_PREFIX.length));
```

(Keep the `\r` trim; make it `trimEnd()` on the line rather than `trim()` on the captured value, so a value with internal spacing is still visible as wrong rather than normalised into shape.)

### WR-04: `adapters-freshness.ts` hand-spells the marker it just finished arguing must never be hand-spelled

**File:** `scripts/adapters-freshness.ts:354` (and its committed twin `adapters-freshness.js:303`)

**Issue:** the success verdict prints the literal string `Mirrored generator resolved model preset: ${announced[0]}`. `model-tiers.ts:213-222` states the rule for this grammar: *"the emitter and the reader are declared together, and **neither site spells the marker**"*, and the commit that introduced it is titled *"one authority for the resolved-preset line, both directions"*. This is a third site spelling it, and it is the repository's named second systemic failure class (a hand-maintained literal that rots while the suite stays green).

It is load-bearing, not cosmetic: `adapters-freshness.test.ts` Cases 7 and 8 assert `resolvedPresetsIn(r.stdout)` over the **gate's own stdout** — on the success path the child's stdout is not forwarded, so those cases are parsing this hand-written literal, not the generator's announcement.

**Fix:**

```ts
import { resolvedPresetLine } from "./model-tiers.js";
console.log(
  `Adapters fresh: ... set-equal.\nMirrored generator ${resolvedPresetLine(announced[0] as PresetName)}`,
);
```
(or a dedicated `mirroredResolvedPresetLine()` exported beside the other two halves).

### WR-05: The packaging authority names one config location; the resolver reads two, and the first existing file wins wholesale

**Files:** `agent-factory/packaging/subagent.frontmatter.md:202-207`; `scripts/model-tiers.ts:927-990`

**Issue:** the authority states the resolver *"reads the `models` block from the repository's `.grugops/factory.config.json`"*. It reads two candidates, and `factory.config.md`'s new `models` section names neither. Worse, the loop `return`s on the **first existing file** regardless of whether that file carries a `models` key — so a present-but-`models`-less `.grugops/factory.config.json` (which is exactly what the shipped seed is, per D-04) **shadows** a `models` block written into `agent-factory/config/factory.config.json`.

Reproduced: `.grugops/factory.config.json` = `{"quality":{"tdd":true}}` + in-kit config = `{"models":{"preset":"tiered"}}` → resolves `preset: none`, `source` = the `.grugops` file.

The precedence itself matches `readGovernanceConfig`'s established convention and is defensible; the defect is that **no shipped document says it**, and the one document that mentions a path names only one of the two. A user who follows the authority literally, in the standard installed shape, gets a silent no-op.

**Fix:** state both locations and the whole-file precedence in `factory.config.md`'s `### models sub-fields` section, and correct the sentence in `subagent.frontmatter.md` to name both. Add a case to `model-tiers.test.ts` for the shadowing shape (present-but-`models`-less first candidate over a `models`-carrying second) — the existing precedence cases only cover *both* files carrying a `models` block.

### WR-06: The host-CLI scope sentence is an unsourced factual claim about four third-party CLIs, shipped without `UNKNOWN - verify`

**File:** `agent-factory/packaging/subagent.frontmatter.md:243` (pinned verbatim by `model-dial-consistency.test.ts:80-84`)

**Issue:**

> Per-subagent model selection is a Claude Code capability: the other four host coding-agent CLIs grugops supports — Codex CLI, Gemini CLI, OpenCode and GitHub Copilot CLI — have no per-subagent model concept, so the model dial does not reach them...

This is a positive factual assertion about four external products. It cites no source, and nothing in `29.1-RESEARCH.md` addresses it — grep for `opencode|codex|gemini|copilot` across the whole phase directory returns exactly one hit, the sentence itself in `29.1-05-SUMMARY.md`. Meanwhile the far lower-stakes *alias vocabulary* got a full `UNKNOWN - verify` block with a named source and a human ratification.

The claim is at least disputable on this repository's own evidence: `CLAUDE.md:106` records that OpenCode supports "native-agent mapping (markdown agent files: `review.md` → `review` agent)", and OpenCode's agent definitions are widely documented as carrying a per-agent `model` field. If that is right, the sentence is simply false — and it is the surface an oracle pins as the *single authority*, so every other document defers to it.

The project's hard rule is explicit: *"Unknown commands are marked `UNKNOWN - verify`; never fake a passing gate, a test result, or a **citation**."* An unverified claim about four third-party tools, presented flat, is the same class.

**Fix:** either cite a source per CLI, or downgrade the sentence to what was actually established and mark the rest:

```
Per-subagent model selection is a Claude Code capability, and the model dial writes only into the
Claude Code sub-agent adapters this kit generates.

**`UNKNOWN - verify`** — whether Codex CLI, Gemini CLI, OpenCode or GitHub Copilot CLI expose an
equivalent per-agent model concept was not verified during phase 29.1. The dial does not reach
them today because grugops emits no per-agent artifact for them, which is a fact about this kit
rather than about those CLIs.
```
That version is true, is the same practical guidance, and needs no citation.

### WR-07: A malformed live `models` block has no fail-closed reader in CI

**Files:** `scripts/check-foundation-guards.ts:1952-1975`; `scripts/adapters-freshness.ts:184-209`; `.github/workflows/ci.yml:131-146`

**Issue:** three facts compose into a fail-open:

1. `guard_model_assignment` degrades an unreadable config to `inherit` and reports it through `warn()`, which `check-foundation-guards.ts:392-394` documents as *advisory only — it does NOT increment FAILS*. Test case `(i)` confirms the guard passes green.
2. `adapters-freshness`'s mirror copies only `agent-factory/roles` and `agent-factory/packaging` — no config — so the mirrored generator never sees the broken file and announces `none`.
3. CI runs `freshness:adapters` and `check-foundation-guards.js` but **never** `npm run generate:adapters`.

**Failure scenario:** a `models` block with an illegal alias, an unknown preset, a typo'd role key or invalid JSON sits committed in `agent-factory/config/factory.config.json` or `.grugops/factory.config.json`. Every CI gate is green. The only thing that refuses it is a developer manually running the generator. The six named refusals the phase built — its most-tested surface — are unreachable from the build.

**Fix (either):** make `guard_model_assignment`'s degradation a `fail()` rather than a `warn()` (a config that cannot be read is a different fact from a config that says `inherit`, and the guard already words it that way); or add `npm run generate:adapters && git diff --exit-code -- .claude/agents/` to the ubuntu gate block, which closes it fail-closed and additionally proves the committed adapters match the live config.

### WR-08: The guard's degraded-branch source label states the opposite of what happened

**File:** `scripts/check-foundation-guards.ts:1951, 1953-1959`

**Issue:** `sourceLabel` is initialised to `"neither standard location"` and is only reassigned inside the `config.ok` branch. On the degraded path — where a config file **does** exist at a standard location and was refused — the PASS/derivation line still reads `from neither standard location`.

**Failure scenario:** a reader of the green line is told there is no configuration anywhere, while the actual state is "a configuration exists and this gate could not read it". That is exactly the conflation the module's own header spends a paragraph forbidding (`"off" and "I typed something that cannot mean anything" are different statements`).

**Fix:** have `readModelsConfig`'s refusal carry the path it was reading (it already names it in the reason text), or set `sourceLabel = "a configuration that was refused — see the warning above"` in the `!config.ok` branch.

## Info

### IN-01: `roleCorpusCardinalityRefusal` and `tieredCorpusRefusals` have no production consumer

**File:** `scripts/model-tiers.ts:537-582, 1019-1028`

Both are exported, both are documented as *"the place a consumer that genuinely means 'is this the whole live corpus' asks that question out loud"* — and a grep across `scripts/` shows the only callers are `model-tiers.test.ts`. `guard_model_assignment` asserts `TIERED.length !== MODEL_TIERS_COUNT` and `adapterRels.length !== stems.length` instead, and never calls either function.

This is not a hole in practice: `model-tiers.test.ts:143` and `:374` assert both predicates against the live corpus on every CI run, and `guardKitCounts` (`check-foundation-guards.ts:1510`) pins `ROLE_FILES.length === ROLE_COUNT`. But the accepted rationale for moving the D5 floor out of `resolveModels` was that "cardinality lives in `roleCorpusCardinalityRefusal` / `tieredCorpusRefusals`", and today it lives in the *tests* for those functions. Worth either wiring `tieredCorpusRefusals(stems)` into `guard_model_assignment`'s tiered path (it is strictly stronger than the length check already there — a renamed table stem moves neither count) or amending the header comment to say the consumer is the oracle.

### IN-02: The guard's PASS line embeds an absolute filesystem path

**File:** `scripts/check-foundation-guards.ts:1961, 2078-2081`

`config.value.source` is an absolute path built from `ROOT`, so the green line reads `preset "none" from /Users/<name>/Projects/public/grugops/agent-factory/config/factory.config.json`. Every sibling finding in this gate uses repo-relative paths, and this guard's own header commits to output that is *"byte-identical"* across runs — which this breaks across machines and leaks a developer home directory into CI logs. Render it relative to `ROOT` before printing.

### IN-03: Four assertions of one fact in the surface-roster vacuity case

**File:** `scripts/model-dial-consistency.test.ts:159-162`

`toHaveLength(SURFACE_COUNT)` twice plus `toBeGreaterThanOrEqual`/`toBeLessThanOrEqual` on the same number. The last two are strictly implied by the second and add no discrimination. Keep the two `toHaveLength` calls (they read two different derivations) and drop the bounds pair.

### IN-04: The stray-pin "bound" enumerates two surface families by hand

**File:** `scripts/check-foundation-guards.ts:2063-2066`

`nonAgentSurfaces` is `SKILL_ADAPTERS ++ PLUGIN_SKILL_RELS` — correct and complete on today's tree (verified: `grep -rl '^model:'` over the shipped tree returns exactly the 17 agent adapters plus two fenced doc examples). But the *family list* is hand-written, and `CLAUDE.md:91` documents `model` as a legal frontmatter field on **slash commands** too. A `.claude/commands/` or plugin `commands/` directory arriving later would be silently outside this arm, with no count tying `nonAgentSurfaces` to a derived roster of "every shipped frontmatter surface the platform loads". Consider deriving the family list from the same authority that answers "what surfaces does this kit ship", or at minimum record the promote trigger beside the constant.

### IN-05: Dead initialiser

**File:** `scripts/check-foundation-guards.ts:1950`

`let presetLabel = "none";` is reassigned on every reachable path (lines 1958, 1960, 1971). Harmless, but the initial value is a plausible-looking default that no run ever prints, and a later edit that adds a fourth path would silently inherit it.

### IN-06: The byte baseline pins an abbreviated SHA

**File:** `scripts/adapter-byte-baseline.test.ts:63`

`PRE_PHASE_ADAPTER_BASELINE = "6f8411e"` is a 7-character prefix. As history grows this can become ambiguous; `git ls-tree` then errors and the case throws (loud, which is the right direction), but the throw would read as "the pinned baseline tree could not be read" rather than "the abbreviation is now ambiguous". Pin the full 40-character SHA — the residual note already accepts the reachability dependency, so nothing else changes.
