### CR-01: the Assertion-1 exemption counts LINES, not mentions — unbounded kit-internal references absorb into an already-exempt line while the two-sided cardinality assertion never moves

**File:** `scripts/check-kit-refs.ts:173-178`, `scripts/check-kit-refs.ts:217-228`,
`scripts/check-kit-refs.ts:402-420`

**Issue.** `grepSubstring` emits **one hit per LINE** (`hits.push(\`${file}:${i + 1}:${lines[i]}\`)`,
line 223). `CONFIG_SELF_REF_HITS = 2` is therefore a cap on *lines*, not on *mentions* — so a line
already inside the exempt set can grow an arbitrary number of additional
`agent-factory/config/…` references and neither cardinality assertion moves.

The constant's own comment states the weaker fact as though it were the stronger one:

> `// Exactly TWO exempt mentions. Measured 2026-08-20 on this tree: factory.config.md:3 … and factory.config.md:138 …`

Measured on this tree: **three** occurrences on **two** lines (line 3 carries one, line 138 carries
two). The test file's `linesContaining()` helper (`check-kit-refs.test.ts:169-177`) *knows* this —
its docstring says "a line naming the kit-internal path twice is ONE hit … the file carries THREE
substring occurrences and TWO hits" — but the case that pins the exemption
(`"a THIRD kit-internal mention … fails, naming both counts"`) plants its third mention on a **new
line**, which is the one shape the counting unit does catch. No case plants on an existing line.

**Reproduced** against the committed `scripts/check-kit-refs.js` on a hermetic mirror. One sentence
appended to the *existing* exempt line 3:

```
Also edit `agent-factory/config/` directly and see `agent-factory/config/../../install/README.md`
and `agent-factory/config/.gitkeep`.
```

```
$ grep -o 'agent-factory/config/' $M/agent-factory/config/factory.config.md | wc -l
       6
$ CHECK_ROOT=$M node scripts/check-kit-refs.js
  PASS  no agent-factory/config/ refs remain (2 counted self-reference(s) exempt, in agent-factory/config/factory.config.md)
  PASS  the config self-reference exemption is exactly 2 hit(s) in 1 file(s), as declared
$ echo $?
0
```

Six kit-internal mentions, including *"edit `agent-factory/config/` directly"* — verbatim the thing
D-08.1 exists to forbid ("no kit document points a reader at a path inside the kit to edit") — and
the gate publishes `exactly 2 hit(s) … as declared`. The gate's own header says a new mention
"must be argued and counted, never absorbed"; it is absorbed.

**Fix.** Count the unit the claim is about. Derive the exempt-mention cardinality from the same
`CONFIG_NAMED_PATH` extraction the predicate already runs, not from the hit list:

```ts
// in exemptConfigSelfRefs, alongside `exempt`:
let exemptMentions = 0;
…
if (inConfigDir && allResolve) {
  exempt.push(hit);
  exemptMentions += named.length;   // MENTIONS, not lines
  files.add(file);
}
…
return { exempt, exemptMentions, strays, files: [...files].sort() };
```

then assert `exemptMentions !== CONFIG_SELF_REF_MENTIONS` (3 on today's tree) **in addition to** the
existing line and file counts, and correct the comment at `:176-178` to say three mentions on two
lines. Add a red case that plants a second mention on an already-exempt line — that is the case the
suite is missing.

### CR-02: the "self-reference" predicate admits `.` and `..`, so a reference pointing *outside* the configuration directory is exempted as a reference to a sibling inside it

**File:** `scripts/check-kit-refs.ts:186` (`CONFIG_NAMED_PATH`), `scripts/check-kit-refs.ts:246-283`
(`exemptConfigSelfRefs`)

**Issue.** The predicate is documented (lines 246-256) as:

> (b) the line names at least one kit-internal path, and EVERY path it names **resolves to a file
> that exists in that directory** on the tree under judgement.

Neither half holds. `CONFIG_NAMED_PATH = /agent-factory\/config\/([A-Za-z0-9._-]+)/g` admits `.`
and `..` as basenames (both are pure `[._-]`), and the resolution test is
`existsSync(abs(join(CONFIG_SELF_REF_DIR, base)))` — which returns `true` for a **directory** as
well as a file. So `agent-factory/config/..` captures `..`, resolves to `agent-factory/` (exists),
and is exempted as a self-reference to a sibling of `factory.config.md`.

**Reproduced** against the committed `.js`. Line 3's legitimate mention replaced by:

```
See `agent-factory/config/../../install/README.md` for the traversal case.
```

```
$ CHECK_ROOT=$M node scripts/check-kit-refs.js
  PASS  no agent-factory/config/ refs remain (2 counted self-reference(s) exempt, in agent-factory/config/factory.config.md)
  PASS  the config self-reference exemption is exactly 2 hit(s) in 1 file(s), as declared
$ echo $?
0
```

A kit-internal path that leaves the configuration directory, climbs two levels and lands in
`install/` is reported as a counted self-reference. The suite's ghost case
(`"a kit-internal mention naming a path that does not exist is a stray"`) cannot see this, because
`..` *does* exist.

**Fix.** Refuse the two relative names by canonical form (not by pattern-widening), and require a
regular file rather than any entry:

```ts
const allResolve =
  named.length > 0 &&
  named.every((base) => {
    if (base === "." || base === "..") return false; // a self-reference names a sibling, not a parent
    const p = abs(join(CONFIG_SELF_REF_DIR, base));
    return existsSync(p) && statSync(p).isFile();
  });
```

Add a red case per shape: `agent-factory/config/..`, `agent-factory/config/.`, and (once a
subdirectory can exist there) a directory basename.

### WR-01: the R2-WR-02 right-bound fix has no case that can see it — `(r-bound)`'s central assertion is unconditionally true by construction, and bounded/unbounded slices are byte-identical on this workflow

**File:** `scripts/check-foundation-guards.test.ts:10869-10883` (`(r-bound)`),
`scripts/skill-twins-freshness.test.ts:286-291`; reader at
`scripts/check-foundation-guards.test.ts:10836-10847` (`ubuntuBlock`)

**Issue.** `ubuntuBlock` returns `next === -1 ? rest : rest.slice(0, next)` where
`next = rest.indexOf(STEP_MARKER)`. **Either branch returns a string that cannot contain
`STEP_MARKER`** — the `slice(0, next)` branch cuts immediately before the first occurrence, and the
`-1` branch is taken only when there is no occurrence. So

```ts
expect(
  block.includes(STEP_MARKER),
  "the sliced ubuntu gate block must contain no second step marker — if it does, the slice has swallowed a following step …",
).toBe(false);
```

is a tautology. Its failure message is unreachable. The case's own comment claims the opposite:

> "THE PROPERTY. Asserted rather than inherited from the coincidence that this block happens to be
> the last step today"

It is inherited from exactly that coincidence. Measured on the committed workflow:

```
$ node -e '…'
next marker index: -1
bounded === unbounded ?  true
bounded.includes(MARKER): false
unbounded.includes(MARKER): false
commands equal?          true
```

The ubuntu block is the last step in `ci.yml` (final `- name:` at line 131 of 451). Reverting
`ubuntuBlock` to the pre-fix `return rest` leaves `(r-bound)` and `(r-commands)` fully green today —
which is the same "green in both worlds" shape R2-WR-02 was raised about, one level up. The
`(r-class)` case only checks that the marker *literal* appears in each reader's source text; it does
not exercise either reader.

The second half of the R2-WR-02 fix — comment-stripped, exact-equality command lines — **does**
discriminate and is not in question. It is only the bound whose proof is vacuous.

**Same class, lower stakes, in a third file:** `scripts/model-dial-consistency.test.ts:900-901`
asserts `occurrences(region, "\n- ") === 0` and `occurrences(region, "\n## ") === 0` over
`modelBulletRegion()`'s output. Both are guaranteed by `rest.slice(0, Math.min(...ends))` and can
never fail. (Here the *throw* paths are genuinely proven — deviations F and G in `29.1-16-SUMMARY.md`
record real reds — so only the two containment lines are dead weight.)

**Fix.** Assert the bound over a **synthetic** workflow the reader has never seen, the way
`gateScanSet` is already tested in `check-kit-refs.test.ts:206-217`:

```ts
it("(r-bound) the reader stops at the next step, proven on a workflow that HAS one", () => {
  const ci = ciWorkflow();
  const withAppended = `${ci}\n      - name: A step appended after the gate block\n        run: npm run generate:adapters\n`;
  const block = ubuntuBlock(withAppended);
  expect(block).not.toContain("A step appended after the gate block");
  expect(ubuntuBlockCommands(withAppended).filter((c) => c === "npm run generate:adapters"))
    .toHaveLength(1);   // the appended occurrence is NOT adopted
});
```

That case reds on `return rest`. Delete the tautological `block.includes(STEP_MARKER)` assertion (in
both files) rather than leaving a message no input can print, and do the same for the two
`occurrences(region, …)` lines in `model-dial-consistency.test.ts`.

### WR-02: `resolveModels` throws a `TypeError` out of its own refusal path — the exact contract Floor 0 and Floor 0b were added to hold

**File:** `scripts/model-tiers.ts:1007` (Floor 0's `JSON.stringify(preset)`),
`scripts/model-tiers.ts:1178` (the override-alias refusal's `String(JSON.stringify(alias))`),
`scripts/model-tiers.ts:1250-1252` (`quoteValue`)

**Issue.** The module header is unambiguous:

> "Returning a result rather than throwing is what lets one reader serve all three … A throw would
> force every degrading consumer to write a catch, and a catch is where a refusal quietly becomes a
> default nobody chose."

R2-WR-01 was raised because `overrides: {a:'opus'}` produced `TypeError: object is not iterable`.
Floor 0b closed the *iteration* throw and left the *refusal-message* throw open: both floors build
their reason with `JSON.stringify`, which throws on a circular object and on a `BigInt`. So the
value that reaches the refusal is the value that prevents the refusal from being returned.

Reproduced against the committed `scripts/model-tiers.js`:

```
preset circular    THREW: TypeError Converting circular structure to JSON
preset bigint      THREW: TypeError Do not know how to serialize a BigInt
override circular  THREW: TypeError Converting circular structure to JSON
```

The plan's own recorded justification for fixing rather than deleting these docstrings applies
verbatim: *"the tooling layer ships as committed `.js` with no type checking on hosts … a floor that
holds only under `tsc` is not a floor."* The installer doctor and any future runtime reader named in
the header still have to write a catch for these three inputs.

**Fix.** Make `quoteValue` total, and route both sites through it (they are currently two spellings
of one operation — a second authority for one predicate, in a module that argues against exactly
that):

```ts
function quoteValue(value: unknown): string {
  try {
    return String(JSON.stringify(value));
  } catch {
    // A value JSON cannot serialise is still a value the user handed over, and a refusal is the
    // only channel telling them it was rejected. Describe it rather than dying inside the message.
    return `<${describeShape(value)} that cannot be serialised>`;
  }
}
```

then replace `JSON.stringify(preset)` at line 1007 and `String(JSON.stringify(alias))` at line 1178
with `quoteValue(…)`. Add the two cases beside the existing Floor 0b cases:
`resolveModels(stems, {preset: circular})` and
`resolveModels(stems, {preset:"none", overrides: new Map([[stem, 1n]])})` must each return
`ok:false`, not throw.

### IN-01: `(o-one-consumer)`'s inner predicate is a 300-byte window, so a second consumer that builds its pattern into a local first is not counted

**File:** `scripts/check-foundation-guards.test.ts:10437-10448`

The residual pin scans for `new RegExp(` and then tests `/\bROOT\b/` against `code.slice(at, at + 300)`.
A gate written as `const pat = ROOT.replace(/…/g, "\\$&") + BOUNDARY; … new RegExp(pat, "g")`
acquires the R2-CR-01 defect class and is invisible to this census, because the window after
`new RegExp(` contains `pat` and not `ROOT`. The `.toEqual(["check-foundation-guards.ts"])` assertion
would stay green.

**Fix:** widen the predicate to "the file contains `new RegExp(` **and** a `\bROOT\b`-bearing
`.replace(/[.*+?^${}()|[\]\\]/g` escape call", or test the assembled source between the two rather
than a fixed byte window. State the residual either way — a fixed window is a heuristic, and this
case's whole purpose is bounding a blast radius.

### IN-03: `(r-class)` derives its reader set by one exact step-name substring, and the two readers it certifies are not the same slice

**File:** `scripts/check-foundation-guards.test.ts:10974-11007`;
`scripts/skill-twins-freshness.test.ts:283-286`

Two gaps in the "close the class, not the instance" claim:

1. Membership is `textOf(f).includes(UBUNTU_BLOCK_STEP_NAME)` — the *full* name including
   `(ubuntu only)`. A future reader locating the block by `"Freshness gates + repo gates"` is not a
   member, is never required to carry the bound, and does not move `UBUNTU_BLOCK_READER_COUNT`.
2. The case certifies only that each member's source contains the marker *literal*. The two members
   slice differently — `ci.slice(at + UBUNTU_BLOCK_STEP_NAME.length)` in
   `check-foundation-guards.test.ts` vs `ci.slice(at)` in `skill-twins-freshness.test.ts`. They agree
   today by luck of where the marker sits; nothing asserts they return the same region.

**Fix:** derive membership from the step-name *prefix* the workflow actually uses (or from the set of
`- name:` values parsed out of `ci.yml`), and assert that every member's extracted command list is
equal — one comparison closes both gaps without sharing a helper.

### IN-04: `anchoredValuesIn` trims the captured value's trailing whitespace, contradicting its own docstring

**File:** `scripts/model-tiers.ts:390-398`; docstring at `scripts/model-tiers.ts:372-376`

The docstring says the trailing carriage return is trimmed "off THE LINE … and **never off the
captured value**", and that "a value carrying internal or leading spacing stays visible as wrong
rather than being normalised into shape". The implementation `trimEnd()`s the line *before* slicing,
so trailing whitespace inside the value is normalised away too. Measured:

```
resolvedPresetsIn(RESOLVED_PRESET_PREFIX + "none   ")  ->  ["none"]
resolvedPresetsIn("  " + RESOLVED_PRESET_PREFIX + "none") -> []      // the anchor holds, correctly
```

The anchoring behaviour is correct and the practical effect is benign (the values are members of a
closed set). The docstring is the thing that is wrong, and this module's stated posture is that a
published claim wider than its mechanism is the defect.

**Fix:** reword to "trailing whitespace — including a Windows child's carriage return — is trimmed
off the line and therefore off the tail of the captured value; leading and internal spacing is
preserved so it stays visible as wrong."
