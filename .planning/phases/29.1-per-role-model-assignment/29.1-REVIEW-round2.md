### R2-CR-01: `relativeToRoot` builds a regex from an unvalidated `ROOT` and silently corrupts every path it renders — reproduced, and it makes the guard publish a green verdict naming a file that does not exist

**File:** `scripts/check-foundation-guards.ts:1917-1926` (and its committed twin)
**Introduced by:** plan 29.1-09, the IN-02 closure.

**Issue.** `ROOT` is taken verbatim from `process.env.CHECK_ROOT` with no `resolve()`, no absolute
check and no refusal (`:374-376`). `relativeToRoot` then compiles it into a **global, unanchored**
regex and applies it to every refusal reason and to the verdict's `sourceLabel`:

```ts
const ROOT_PATH_RE = new RegExp(
  `${ROOT.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")}([^\\s'"\`]*)`,
  "g",
);
```

When `ROOT` is a relative value — `.` is the obvious one, and `check-kit-refs.ts:11-12` documents
`CHECK_ROOT` as a general "point the gate at a hermetic mirror" override with no absoluteness
contract — the escaped pattern becomes `\.([^\s'"`]*)`, which matches **any period followed by
non-whitespace anywhere in the message**. Reproduced on this tree:

```
$ CHECK_ROOT=. node scripts/check-foundation-guards.js
  PASS  model assignment: 17 committed adapter(s) under .claude/agents compared against a
        resolution recomputed for 17 derived role stem(s); preset "none" from
        agent-factory/config/factoryconfig.json; distinct aliases resolved: inherit; ...
```

`factory.config.json` → `factoryconfig.json`. The gate exits 0 while its verdict names a path that
does not exist.

**Why this is Critical rather than cosmetic.** This is the WR-08 defect class the same round just
closed, in a new shape: a verdict that misdescribes the run it performed. WR-08's fix was accepted
because *"a reader of the green line is told there is no configuration anywhere, while the actual
state is different."* Here a reader is told the configuration came from a filename that was never
opened. Worse, it is silent and it is on the **green** path — the failing path is affected too,
because the same helper is applied to `config.reason` and `resolution.reason`, so a refusal can
name a mangled path and send an operator to the wrong file. The guard's own header (`:1867`)
commits to output that is byte-identical for a given tree; that commitment is now a property of the
*shape of the override string*.

The unanchored match is also wrong for any `ROOT` that is a string-prefix of a sibling path
(`ROOT=/a/b` rewrites `/a/bc/d` to `c/d`); that variant is not reachable today because every
rendered path is built from `ROOT`, but nothing enforces that.

**Fix:** normalise and constrain the root before compiling anything from it, and require a
separator after the match so the regex is a *path prefix* rather than a substring:

```ts
// at :374 — a relative or empty override is refused, not silently accepted
const ROOT = process.env.CHECK_ROOT
  ? resolve(process.env.CHECK_ROOT)
  : join(import.meta.dirname, "..");

// at :1917 — require a separator (or end-of-token) after the root, so the match is a path prefix
const ROOT_PATH_RE = new RegExp(
  `${ROOT.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")}(?=[\\\\/]|[\\s'"\`]|$)([^\\s'"\`]*)`,
  "g",
);
```

Add a case that runs the guard with `CHECK_ROOT` set to a **relative** path and asserts the verdict
still names `agent-factory/config/factory.config.json` verbatim — today's cases `(o)` and
`(o-reason)` both pass absolute mirror roots, so neither can see this.

### R2-WR-01: WR-02 was closed on `preset` and left open on `overrides` — the same nullish coercion, in the same function, defended by the same docstring

**File:** `scripts/model-tiers.ts:1025` (`for (const [stem, alias] of options?.overrides ?? [])`), docstring at `:874-880`

**Issue.** Plan 29.1-08's own argument for fixing `preset` rather than deleting its docstring is
recorded at `:863-870`: *"the tooling layer ships as committed `.js` with no type checking on hosts
… the declared type above is advisory at run time … A floor that holds only under `tsc` is not a
floor."* That argument applies verbatim to `overrides`, whose docstring makes an equally strong
claim (*"the resolver keeps a last-line alias floor anyway, because this value is written straight
into emitted frontmatter"*). The floor is not reached at all for a nullish or non-iterable value.

Reproduced against the committed `scripts/model-tiers.js`:

```
resolveModels(['a','b'], {preset:'none', overrides: null})
  => {"ok":true,"value":[["a","inherit"],["b","inherit"]]}          <- silently discarded

resolveModels(['a','b'], {preset:'none', overrides: {a:'opus'}})
  => TypeError: object is not iterable (cannot read property Symbol(Symbol.iterator))
     at resolveModels (scripts/model-tiers.js:854)
```

Both outcomes contradict the module's stated posture. The first is *exactly* the fact the WR-02
comment says must be distinguished (`"absent"` vs `"I typed something that cannot mean anything"`).
The second is a **throw** out of a module whose header (`:27-30`) argues that returning a result
rather than throwing is what lets one reader serve the generator and every degrading consumer — the
installer doctor and "any future runtime reader" now inherit an uncaught crash on a plain object,
which is the natural shape for a caller that read `models.roles` out of JSON without building a Map.

**Fix:** give `overrides` the same pre-default validation `preset` received:

```ts
const rawOverrides: unknown = options?.overrides;
const overrides =
  rawOverrides === undefined
    ? new Map<string, ModelAlias>()
    : rawOverrides instanceof Map
      ? rawOverrides
      : null;
if (overrides === null) {
  return {
    ok: false,
    reason:
      `model-tiers: the overrides argument is ${describeShape(rawOverrides)} rather than a Map of ` +
      "role stem to alias. An ABSENT overrides map is the zero-config contract; a value that is " +
      "present but not a Map is a caller whose overrides would be silently discarded, which is a " +
      "tier the caller believes they set and did not.",
  };
}
// …then iterate `overrides` rather than `options?.overrides ?? []`
```

Add the two cases beside the existing `"resolveModels REFUSES a null preset by name instead of
coercing it"`.

### R2-WR-02: the CI-wiring pin slices `ci.yml` to end of file and matches inside comments — the case's own claim that "a hit anywhere else in the workflow does not put the command on the gated path" is false

**File:** `scripts/check-foundation-guards.test.ts:10170-10185`

**Issue.** The case locates the ubuntu block by step name and then takes **everything to EOF**:

```ts
const at = ci.indexOf("Freshness gates + repo gates (ubuntu only)");
const block = ci.slice(at);            // <- unbounded on the right
```

Two consequences, both in the direction that lets the pin go green while the gate is gone:

1. **No right bound.** Today the block happens to be the last step (`ci.yml:131` → EOF at 437), so
   the slice is accidentally correct. The moment a step is appended after it — a publish step, a
   coverage upload, a `windows-latest`-only leg — a `npm run generate:adapters` occurring *there*
   satisfies this case while the ubuntu gate no longer runs it. This is the **exact** defect plan
   29.1-10 identified and fixed in the sibling oracle four commits earlier:
   `scripts/model-dial-consistency.test.ts:365-370` — *"A section reader that searches to EOF is not
   reading a section; it adopts every later block that happens to be appended after it, and the day
   someone appends one, assertions written about THIS section start passing on someone else's
   text."* The lesson was recorded in the same round and not applied here.
2. **Comments satisfy it.** `.toContain()` runs over the raw slice, and this block is roughly 80 %
   comment. A future comment reading `# we used to run npm run generate:adapters here` keeps the
   case green with the command deleted. The 29.1-09 load-bearing proof (deleting each command → RED)
   cannot see this, because it deleted the command *and* left no comment carrying the literal.

The case's own header asserts the stronger property it does not hold: *"The BLOCK, not the file. A
hit anywhere else in the workflow — a comment, another job, a different OS leg — does not put the
command on the gated path."*

**Fix:** bound on the right at the next step, and probe code lines only — the same two disciplines
this round already applied elsewhere:

```ts
const at = ci.indexOf("- name: Freshness gates + repo gates (ubuntu only)");
expect(at).toBeGreaterThan(-1);
const rest = ci.slice(at + 1);
const next = rest.indexOf("\n      - name: ");
const block = next === -1 ? rest : rest.slice(0, next);

// commands, not prose: drop comment lines before probing
const commands = block
  .split("\n")
  .map((l) => l.trim())
  .filter((l) => l.length > 0 && !l.startsWith("#"));
expect(commands).toContain("npm run generate:adapters");
expect(commands).toContain("git diff --exit-code -- .claude/agents/");
```

Also assert the block really is the last-or-bounded one by checking `next === -1 ||
block` does not contain `- name:`, so the "accidentally correct today" state becomes an asserted
property rather than a coincidence.

### R2-WR-06: `MODELS_KEYS` closes *presence* and nothing closes *consumption* — a key added to the tuple is admitted and silently dropped, which is WR-01 restored

**File:** `scripts/model-tiers.ts:231`, `:1136-1160`; oracle at `scripts/model-tiers.test.ts:1299-1306`

**Issue.** `readModelsBlock` refuses any key not in `MODELS_KEYS`, then reads `models.preset` and
`models.roles` and nothing else. Nothing anywhere ties the tuple's membership to the set of keys the
reader actually consumes. Add `"tiers"` to `MODELS_KEYS` without adding a reader and
`{"models":{"tiers":{...}}}` is admitted, ignored, and reported as the zero-config answer with no
message — verbatim the WR-01 defect this constant exists to close, one level up.

The source comment overstates what the tuple buys:

> "a third legal key can only arrive by editing the tuple, which moves the mechanism and the message
> together."

Editing the tuple moves the **message** (the refusal quotes `MODELS_KEYS`). It does not move the
**mechanism** — no reader is added, no assertion fires.

The oracle's mitigation is a second hand-typed literal
(`expect([...MODELS_KEYS].sort()).toEqual(["preset","roles"])`), which does make the addition visible
in a diff — but that is a two-sided pin whose two sides are both hand-written lists edited together
by construction, this repository's named first failure class. Its own comment claims it is
"DERIVED-ADJACENT rather than a second hand-maintained list"; it is the second list.

**Fix:** assert consumption, not just membership. Cheapest sound form — drive each legal key through
the reader and require that setting it *changes the result*:

```ts
it("every member of MODELS_KEYS is CONSUMED by readModelsBlock, not merely permitted", () => {
  const stems = kitStems();
  const probes: Record<ModelsKey, unknown> = {
    preset: "tiered",
    roles: { [stems[0]]: "opus" },
  };
  // PREMISE: the probe table covers the tuple, both directions — a key added to MODELS_KEYS with
  // no probe is a key nobody proved is read.
  expect(Object.keys(probes).sort()).toEqual([...MODELS_KEYS].sort());

  const base = readModelsConfig(rootWithConfig({ models: {} }), stems);
  for (const key of MODELS_KEYS) {
    const r = readModelsConfig(rootWithConfig({ models: { [key]: probes[key] } }), stems);
    expect(r.ok && base.ok && JSON.stringify([r.value.preset, [...r.value.overrides]]))
      .not.toBe(JSON.stringify([base.value.preset, [...base.value.overrides]]));
  }
});
```

and correct the source comment to the weaker true claim.
