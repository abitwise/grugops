### Locked Decisions

Copied verbatim from `.planning/phases/29.1-per-role-model-assignment/29.1-CONTEXT.md` § Implementation Decisions.

**Delivery path — how a config change reaches an adapter**

- **D-01:** Install performs **install-time generation**: it resolves the target's config and mirror-spawns the generator (cpSync the generator twin, the `kit-model` twin and the kit sources into a temp tree, spawn, read results out) rather than copying pre-generated adapters. This is the pattern `scripts/adapters-freshness.ts` already proves in-tree, and it keeps the generator's `OUT_DIR` a fixed literal with no output flag — the T-27-28 path-traversal mitigation is untouched, not relaxed. — **Reversibility:** costly — reverting means install goes back to copying, and every repo installed under the new path holds adapters no longer reproducible by the old one; the `--check` assertion in D-02 and the `--symlink` arm in D-03 both hang off this.
- **D-02:** A post-install config edit is caught by **re-running install**, and the existing `--check` doctor gains an assertion that each installed adapter's `model:` frontmatter value equals the target config's resolved value, naming stale adapters. Rejected: a target-side freshness gate (more machinery), and install-time-only with no detection (silent staleness — the failure mode `adapters-freshness.ts`'s own header was written against).
- **D-03:** `--symlink` install **plus** a non-default `models` block: install proceeds, materializing the **adapters as copies** because they are now per-repo derived artifacts, while everything else still symlinks. The divergence from the requested install mode is **reported by name**, never silent. Rejected: refusing the install outright, and dropping the models block.
- **D-04:** `scripts/adapters-freshness.ts` regenerates under an **explicit zero-config resolution**, not under whatever config happens to sit on the tree. Otherwise adding a `models` block to grugops's own config either turns CI red for a reason nobody expects, or ships tier-pinned adapters as the committed artifact. grugops's own repo therefore keeps no `models` block and its 17 committed adapters stay `model: inherit`.

**Config shape and precedence**

- **D-05:** The block is `{"models": {"preset": "<name>", "roles": {"<stem>": "<alias>"}}}`. `preset` resolves first against `kit-model.listRoles()`; `roles` is a **sparse override**, never a full map. An absent `models` block means `inherit` for every role. Role identity is the **role file stem** from `listRoles()` (e.g. `software-engineer.md` → adapter `grugops-software-engineer`), and the resolved map's cardinality is asserted against `ROLE_COUNT` so role #18 cannot arrive unassigned. Rejected: a per-role map with no preset — a hand-keyed 17-entry map in user config **is** the set-literal-drift class this milestone exists to eliminate. — **Reversibility:** one-way — `models` is a published config-dial contract; once users write it, changing the key shape needs a migration in `install --migrate` and breaks every repo already carrying the block.
- **D-06:** An unknown key in `roles` — a typo, or a role renamed or removed — is **refused, naming the key and the valid set**. A silently-ignored override is a tier the user believes they set and did not.
- **D-07:** The preset name is a **closed set** and **exactly one preset ships**. Values: `none` (the default; every role `inherit`) and the one shipped preset. Any other value is refused by name. Adding a second preset later is a visible source change, not a config-side surprise.

**Preset assignment and rationale**

- **D-08:** The preset is named **`tiered`**, not `cost`. `"preset": "cost"` is itself a cost claim, and MODEL-07 forbids shipping an unmeasured one. `tiered` names the mechanism without asserting the saving.
- **D-09:** The `tiered` preset assigns **`opus` to 4 roles and `sonnet` to the other 13. No role is assigned `haiku`.** The four: `orchestrator`, `architect-design`, `security-nfr`, `compliance-officer`. Rationale for the shape: every role in this kit either writes into the shared verified context or produces an artifact a human signs off on. The §14 gate catches correctness, not judgment — a thin-model UAT pack, ticket, or test plan degrades *past* the one mechanism that would have caught it rather than into it. Per-role reasons for the four: decomposition quality determines every downstream task; architectural boundaries are expensive to reverse; a missed vulnerability and a misclassified regulated-data field are both real-world harm rather than rework. Rejected: the literal MODEL-03 reading (`opus`×3 / `haiku`×3 / `sonnet`×11), which exercises all three aliases but puts the thin tier exactly where quality degradation is least visible. **Noted as genuinely arguable:** `incident-responder` — an incident is where time pressure and blast radius coincide — was considered for `opus` and left on `sonnet` because the role is procedural and hands to a named human. A later reader disputing this assignment is the intended use of D-10.
- **D-10:** The per-role rationale is a **required field in the exported tier table**, not a comment and not a separate prose doc. A role entry with no rationale **fails generation**. One mechanism therefore serves both MODEL-03's asserted count and MODEL-07's disputability, and the rationale cannot drift away from the assignment it explains.

**Refusal, degradation, and the guard**

- **D-11:** Split by consumer. **Absent** value → `inherit` (the zero-config contract, not an error). **Present but illegal** — a full model id, a typo, a non-string — → the **generator refuses hard**: exit 1, naming the role, the offending value and the legal set, writing nothing. That is the generator's existing all-or-nothing posture (T-27-32), not a new behaviour. **Every other consumer** of a resolved model — the `--check` doctor, any runtime reader — **degrades to `inherit`**, never to a pinned tier. Legal aliases, closed set: `inherit` / `opus` / `sonnet` / `haiku`. Full model ids are refused because they rot into the hand-maintained stale literal this milestone exists to eliminate, and because an alias degrades gracefully for a user whose account lacks the stronger tier.
- **D-12:** A **new `guard_model_assignment`** in `scripts/check-foundation-guards.ts` reads each **committed** adapter's frontmatter through `scripts/frontmatter.ts` (the one authority) and compares it against a resolution computed **without re-running the generator**, with the member count asserted against `ROLE_COUNT`. **Why not extend `adapters-freshness`:** that gate regenerates and byte-compares, so both sides move together — it proves determinism, not that the resolution is correct. That is structurally the CR-01 defect Phase 29 spent rounds on (a check that "parses components out of the run and compares them to a tally over the same live document"). The guard must be an independent second opinion.
- **D-13:** MODEL-06's Claude-Code-only scope statement is **authored in `agent-factory/packaging/subagent.frontmatter.md`** — the single upstream source, which already documents the `model: inherit` choice and which MODEL-02 requires change in the same commit. `agent-factory/config/factory.config.md`'s `models` entry **points at it rather than restating it**. `CLAUDE.md`'s "What NOT to Use" entry against non-`inherit` wrappers is amended to name this mechanism as the documented reason. Rejected: two full statements held byte-identical by a claim-registry anchor (correct but adds a registry row for a claim with one authority).

**Honesty floor (MODEL-07)**

- **D-14:** **No measurement is taken this phase and no cost claim ships.** The tier split is described as a plausible, unmeasured spend shift; every cost or limit-savings statement carries `UNKNOWN - verify`. `scripts/measure-cost.ts` is **untouched** — its standing `UNKNOWN - verify` (the `claude --output-format json` usage schema was never confirmed against a real authed capture, D-10/D-11) remains the honest answer. This matches how v2.0's ~50% figure was handled: grugops has never shipped an unmeasured cost claim, and a tier assignment is not evidence of a saving. Rejected: doing the authed capture this phase (pulls a deferred Tier-2 live-capture concern into a config phase), and wiring a measurement hook now (machinery with no consumer).

## Summary

This is a small change in a large blast radius. The mechanical core is four lines of TypeScript: read a config block, resolve a per-role alias, replace `lines.push("model: inherit")` with the resolved value, and assert the emitted value equals the resolution. Everything hard about the phase is the **surrounding gate lattice** — five freshness gates, fourteen foundation guards, three audit gates, a build-parity gate and a 2,140-case vitest suite that all have opinions about the seventeen files this change rewrites.

Three findings materially affect planning, and each is one where a **locked decision meets a tree fact it did not have**:

1. **D-12 names `scripts/frontmatter.ts` as "the one authority". For adapters, the tree's current authority is `scripts/canonical-frontmatter.ts`.** Plan 27-65 cut the KIT-03 oracle over to `admit()`, and `canonical-frontmatter.ts`'s own header says of `frontmatter.ts` that "this module is the new safety authority and must not inherit the eleven-round parser's reach." Following D-12 literally would introduce the weaker reader onto a *new* safety surface. D-12's *intent* — one parsing authority, no second grammar — is better served by `admit()`, which already carries `model` in its 10-key schema.
2. **D-03's premise is already true, so its "divergence" does not exist.** Every one of the 17 adapters carries the materialization slot line, and `install/install.ts`'s adapter loop routes any slot-carrying source to `materializeAdapter()` — a `writeFileSync`. `INSTALL_MODE` never reaches an agent adapter on any path. Adapters are copies under `--symlink` **today**, so there is nothing new to report by name.
3. **D-01 reverses `install/install.ts`'s explicit D-18/D-28 decoupling from `scripts/`.** Both installer modules refuse to import `scripts/kit-model.ts` on purpose. Mirror-spawning three `scripts/*.js` twins from the installer is architecturally the opposite direction, and it also lands on an ordering problem: the adapter loop runs at line 1468 and `seedState()` — which creates the target's `.grugops/factory.config.json` — runs at line 1555.

**Primary recommendation:** Sequence the phase so the **generator + config reader + tier table + guard** land and go green first (they are self-contained and fully gate-covered), then take the install delivery path as a separately-planned wave with OPEN QUESTIONS 1–3 resolved by the user before its first task. Do not let the install work block MODEL-01..05, which are provable without it.

### Pattern 1: Derive the set, assert the count — with a required rationale field

The exact in-tree template for D-05 + D-10 already exists: `PLUGIN_COMPONENT_EXEMPT` is a readonly array of a readonly interface with a **required `reason` field**, paired with a two-sided count constant, asserted inside `guardKitCounts()`.

```typescript
// Source: scripts/kit-model.ts:487-525 (verbatim shape)
export interface PluginComponentExemption {
  readonly manifestKey: string;
  readonly reason: string;
  readonly bound: string;
}

export const PLUGIN_COMPONENT_EXEMPT: readonly PluginComponentExemption[] = [
  { manifestKey: "hooks", reason: "...", bound: "..." },
];

export const PLUGIN_COMPONENT_EXEMPT_COUNT = 1;
```

Applied to the tier table, the type makes D-10 a **compile error** rather than a runtime check:

```typescript
export type ModelAlias = "inherit" | "opus" | "sonnet" | "haiku";

export interface RoleTier {
  readonly stem: string;      // MUST match a listRoles() stem
  readonly alias: ModelAlias;
  readonly rationale: string; // D-10 — required by the type; a missing one does not compile
}
```

The count assertion then has three directions, not one:
- `TIERED.length === ROLE_COUNT` (17) — role #18 cannot arrive unassigned;
- `new Set(TIERED.map(t => t.stem))` equals `new Set(listRoles(root).map(stripExt))` — **set equality, both directions**, so a renamed role is named rather than merely counted;
- every `rationale` is non-empty after trim — a blank string satisfies the type but not D-10.

The third is the one a type cannot give you. `check-audit-register.ts` already "refuses a blank observation, a bare-word observation" [VERIFIED: .github/workflows/ci.yml, the AUDIT-01 step comment] — reuse that voice.

### Pattern 2: The generator's all-or-nothing refusal (T-27-29 / T-27-32)

```typescript
// Source: scripts/generate-role-adapters.ts:99-102 (verbatim)
const fail: (m: string) => never = (m: string): never => {
  console.error(`  ERROR    ${m}`);
  process.exit(1);
};
```

The `: (m: string) => never` annotation on the **variable** is load-bearing — TypeScript only narrows control flow after a never-returning call when the callee is a function declaration or an explicitly-annotated const. The header at lines 93-98 says so. A new refusal arm added in `render()`'s caller path gets this for free; one added *inside* `render()` does not, because `render()` runs inside `adapters.map()` at line 418, **after** the build-everything loop. **Validate model resolution before the `adapters.map()`, not inside `render()`** — that is what keeps T-27-32 ("a structural miss never leaves a partial artifact") true.

The exact emit site, verbatim:

```typescript
// Source: scripts/generate-role-adapters.ts:400-415
function render(a: Adapter): string {
  const lines: string[] = [];
  lines.push("---");
  lines.push(`name: ${a.name}`);
  lines.push(`description: ${yamlQuote(a.description)}`);
  if (a.isCoordinator) lines.push("coordinator: true");
  const toolLine = a.isCoordinator
    ? `Agent(${grant.join(", ")}), ${a.tools.join(", ")}`
    : a.tools.join(", ");
  lines.push(`tools: ${toolLine}`);
  lines.push("model: inherit");
  lines.push("---");
  lines.push(...(a.isCoordinator ? coordinatorBody(a) : specialistBody(a)));
  lines.push(""); // trailing element → exactly one final "\n"
  return lines.join("\n");
}
```

Key ordering fact: `model:` is emitted **after** `tools:` and **immediately before** the closing `---`. The `Adapter` interface (lines 196-203) has no model field; adding `readonly model: ModelAlias` to it and pushing `` `model: ${a.model}` `` is the minimal change. **Emitting `model: inherit` for the zero-config case produces byte-identical output** because the string is identical.

### Anti-Patterns to Avoid

- **A second config reader.** `context-io.ts` already carries two (`readGovernanceConfig` + `readGovernanceConfigResult`) and **Phase 30 collapses them into one discriminated-result reader** [CONTEXT.md canonical refs]. ## Common Pitfalls

### Pitfall 1: The generator's zero-config path must produce *identical bytes*, not *equivalent output*

**What goes wrong:** A refactor that changes `lines.push("model: inherit")` into `lines.push(\`model: ${resolved}\`)` is byte-identical only if `resolved === "inherit"` exactly — no trailing space, no normalization, no `String()` of an enum object.
**Why it happens:** Template-literal interpolation of a value that went through JSON parse/serialize.
**How to avoid:** SC1 is already mechanically decidable **today**: `npm run freshness:adapters` byte-compares all 17 committed adapters against a fresh regeneration. Run it before and after; it must exit 0 both times with no adapter file's bytes changing in git.
**Warning signs:** `git diff --stat -- .claude/agents/` non-empty after `npm run generate:adapters` on a repo with no `models` block.

### Pitfall 2: `readGovernanceConfig` fails OPEN by design — copying it wholesale breaks MODEL-04

**What goes wrong:** The precedent reader's contract is "This function NEVER throws — zero-config grugops always runs lean" and "A value that IS present is returned VERBATIM. The reader does NOT validate it against the allowed set" [VERIFIED: scripts/context-io.ts:1237-1246]. Copying that shape makes a full model id flow through to the generator as an emitted `model: claude-3-5-sonnet-20241022`, which MODEL-04 forbids.
**Why it happens:** D-11's "shape discipline" reference is about *location resolution and degenerate-shape handling*, not about the fail-open verdict.
**How to avoid:** Split exactly as D-11 says — the READER returns a discriminated result carrying either the resolved map or a named refusal; the **generator** turns `ok:false` into exit 1, and the **doctor** turns `ok:false` into `inherit`. One reader, two consumer policies. Note that `readGovernanceConfig` already demonstrates the degenerate-shape care worth copying: a present-but-non-object config, a present-but-non-object sub-object, and a genuinely absent key are three distinct branches (lines 1285-1300).

### Pitfall 3: `adapters-freshness.ts` gets its zero-config by accident today, not by decision

**What goes wrong:** The mirror copies only `agent-factory/roles` and `agent-factory/packaging` — **not** `agent-factory/config` and not `.grugops/`. So a config-reading generator running in the mirror resolves *nothing* and defaults to `inherit`. That satisfies D-04 today by pure absence.
**Why it happens:** Absence is not a pin. The day someone adds `cpSync(agent-factory/config)` to the twin list — a plausible, well-intentioned edit, since the comment at lines 143-147 already justifies mirroring `packaging` "although the generator does not currently OPEN it" — the gate silently becomes config-dependent and D-04 evaporates while everything stays green.
**How to avoid:** Make the zero-config resolution **explicit and asserted**. Options: (a) an env var the gate sets and the generator honors as "resolve nothing", stripped from the child env by name; (b) the gate writes a pinned empty/absent config into the mirror and the *test* asserts the mirror carries no `models` block; (c) the generator prints its resolved preset on stdout and the gate asserts that line reads `preset: none`. **(c) is strongest** — it makes the pin an observable property of the run rather than a property of what was *not* copied, and it survives someone adding a config dir to the mirror.
**Warning signs:** A D-04 implementation whose only evidence is "the mirror has no config directory."

### Pitfall 4: The orchestrator adapter is 102 bytes under the WARN ceiling

**What goes wrong:** `guard_adapter_size` WARNs at 3072 B and FAILs at 4096 B [VERIFIED: scripts/check-foundation-guards.ts:1414-1415, `const AD_WARN = 3072;` / `const AD_FAIL = 4096;`]. `.claude/agents/grugops-orchestrator.md` is **2970 B** today [VERIFIED: `ls -l .claude/agents/`, measured this session].
**Why it happens:** Someone puts the MODEL-06 scope statement into the adapter body instead of into the packaging file.
**How to avoid:** D-13 already puts the statement in `subagent.frontmatter.md`. Keep it there. The `model:` line itself is safe in both directions: every alias (`opus` 4, `haiku` 5, `sonnet` 6) is **shorter than** `inherit` (7), so an adapter can only shrink.
**Warning signs:** Any prose added to `specialistBody()` or `coordinatorBody()`.

### Pitfall 5: `install --check` must not fail-closed to a tier, and must survive a missing config

**What goes wrong:** The doctor is "Read-only by construction" and folds absent-install into a clean FAIL [VERIFIED: install/install.ts:374-376, 404-408]. A D-02 assertion that throws on an unparseable target config turns `--check` into a crasher on a repo whose config a user hand-edited — the opposite of a doctor.
**How to avoid:** D-11's third clause is explicit: every consumer other than the generator degrades to `inherit`. The doctor's existing pattern is `docFail` / `docWarn` / `docReport("ok", ...)` with the exit matrix at lines 486-503; a stale adapter is a `docFail`, an unreadable config is at most a `docWarn` naming the file.
**Warning signs:** `throw` or `process.exit` anywhere inside `doctor()`.

### Pitfall 6: The install ordering — adapters are laid down BEFORE the target config exists

**What goes wrong:** On a first install into a clean repo, the adapter loop runs at line 1468 and `seedState()` — which creates `<TARGET>/.grugops/factory.config.json` — runs at line 1555 [VERIFIED: install/install.ts, `for (const f of SRC_ADAPTERS)` at 1468, `seedState();` at 1555]. So a D-01 resolution against the target's config reads **nothing** on the first install, emits `inherit`, and only a *second* install would pick up a config the *first* one seeded.
**Why it happens:** The seed step is a state-plane concern that historically ran after the kit plane.
**How to avoid:** Either (a) resolve against the seed source when the target config is absent, or (b) move the resolution ahead of the adapter loop and read `agent-factory/seed/.grugops/factory.config.json` as the second candidate — which is *already* the shape of the two-location resolution, just with the seed path substituted for the in-kit path. Either way, the shipped seed carries **no `models` block** (D-04 + the byte-identity case), so the first-install answer is `inherit` regardless — but the code must arrive there by decision, not by an ordering accident that changes the day the seed gains a key.
**Warning signs:** An implementation whose correctness depends on the seed config never carrying a `models` block.

### Pitfall 7: The build/freshness ordering is pinned, and the freshness gate reads HEAD

**What goes wrong:** New `.ts` without its committed `.js`, or a `.js` built but not committed.
**Why it happens:** `tsconfig.json` sets `outDir`/`rootDir` to `"./"`, so `npm run build` rewrites tracked `.js` in place.
**How to avoid:** The exact CI ordering is: `npm ci` → `npm run freshness` (**before any build**) → `npm run check:build-parity` → `npm run typecheck` → `npx vitest run --exclude '**/scripts/e2e/**'` → the ubuntu gate block [VERIFIED: .github/workflows/ci.yml, read this session]. `freshness.ts` reads its committed side with `git show HEAD:<path>` and derives its set from `git ls-tree -r HEAD` [VERIFIED: scripts/freshness.ts:28-32], so it is ordering-independent — but that also means **an uncommitted `.js` is a case-4 "UNCOMMITTED BUILD OUTPUT" failure**, not a silent pass.
**Warning signs:** `git status` showing modified `*.js` after a commit.

### Pitfall 8: `npm test` runs the live authed e2e lane

**What goes wrong:** `npm test` is `vitest run` with no exclusion, and `scripts/e2e/uat-live.test.ts` exists [VERIFIED: package.json, `"test": "vitest run"`; `ls scripts/e2e/`]. On an authed box that spends tokens and can hang.
**How to avoid:** Use `npx vitest run --exclude '**/scripts/e2e/**'` — the command CI itself uses, and the one already set as `workflow.test_command` in `.planning/config.json`. **Measured this session: 52 test files, 2140 passed, 2 skipped, 169.55 s, exit 0.** [VERIFIED: run this session]

## Open Questions

These are the three places a **locked decision meets a tree fact it did not have**. Per the research contract, none is re-opened here — each is surfaced for the user with the fact that prompted it.

### 1. D-12 names `frontmatter.ts`; the tree's adapter authority is `canonical-frontmatter.ts`

**What we know.** D-12 says the guard "reads each **committed** adapter's frontmatter through `scripts/frontmatter.ts` (the one authority)." That sentence was true of the tree before plan 27-65. It is no longer. `guardReferentialIntegrity` — the guard that reads adapter frontmatter today — reads through `admit()` from `scripts/canonical-frontmatter.ts`, and its own comment records the cutover: "(27-65 / D-64 Part A) THE SAME PARSER GUARD_WR05 READS IS NOW THE CANONICAL ADMISSION READER" [VERIFIED: scripts/check-foundation-guards.ts:2977-2985]. `canonical-frontmatter.ts`'s header states the relationship directly: "In particular the GRANT PREDICATES of `frontmatter.ts` are NOT imported: this module is the new safety authority and must not inherit the eleven-round parser's reach" [VERIFIED: scripts/canonical-frontmatter.ts:37-40].

**What's unclear.** Whether D-12 intends the *named file* or the *property* ("the one authority, no second grammar"). The property is satisfied — better — by `admit()`, which already carries `model` in `CANONICAL_SCHEMA` and needs no change. Following the letter would put the weaker reader on a new safety surface, which is the shape twelve review rounds were spent removing.

**Recommendation.** Read the committed adapters through `admit()`, exactly as `guardReferentialIntegrity` does, and record the substitution explicitly in the guard's header with this session's citation. Surface the substitution to the user before planning, since D-12 is locked. Note that `frontmatter.ts` is **still** the right authority for reading the *role* files, which is what `generate-role-adapters.ts` does today — the two are not in conflict, they answer questions about different corpora.

### 2. MODEL-07 has no mechanical decider in this repo today

**What we know.** `BANNED_CLAIM_LITERALS` has 22 members in exactly three groups: `standard-name`, `token-economy`, `comprehension`. There is no cost group. The gate's own declaration states its direction: "FAIL-OPEN, and the consequence stated plainly. A conformance, token-economy or comprehension claim written in words this list does not contain PASSES THIS GATE" [VERIFIED: scripts/check-banned-claims.ts:349-353]. `measure-cost.ts` honestly returns `UNKNOWN - verify` but nothing consumes it. So a cost claim written into `factory.config.md` this phase would ship green.

**What's unclear.** Whether MODEL-07 is to be held as **content** (the D-59 precedent — "Totality claims are content, not mechanism", the claim registry is the authority, with a disclosed fail-open backstop underneath) or as a **fourth literal group**. The project's own most recent and most expensive lesson points at content.

**Recommendation.** Hold it as content: add the cost-claim prohibition to `docs/audit/28-claim-registry.md` and to the packaging file's honesty statement, and state the direction. If the phase *also* wants the backstop, a fourth `cost` group is available — but it must be admitted the way every existing member was: measure the candidate literals over the 117-document corpus and record the per-file hit count **before** adding them, refusing any literal that hits live correct text. Do not predict the number; read it off the gate's own refusal, which is that module's explicitly recorded rule.

### 3. D-01 and D-03 both rest on install-path premises the tree contradicts

**What we know.**
- D-03 describes materializing "the adapters as copies … while everything else still symlinks" as a *new* divergence to be reported by name. **All 17 adapters carry `MAT_SLOT`** (measured: `grep -c` returns 1 for each), `srcCarriesSlot()` therefore returns true for all of them, and `materializeAdapter()` — a `writeFileSync` — runs for all of them on every install mode. `INSTALL_MODE` never reaches an agent adapter.
- D-01 requires the installer to mirror-spawn `scripts/generate-role-adapters.js` + `scripts/kit-model.js` + `scripts/frontmatter.js`. Both installer modules refuse to import from `scripts/` **by decision**: `install/kit-source.ts:29-30` reads "D-18 IS AMENDED, NOT ABANDONED. This module deliberately does NOT import scripts/kit-model.ts. D-18's actual rationale is decoupling the installer from the `scripts/` layout."
- The adapter loop (line 1468) runs **before** `seedState()` (line 1555), so on a first install the target config does not yet exist when adapters are laid down.

**What's unclear.** Whether D-03 should become a no-op with a recorded note, or be re-scoped to the true statement ("agent adapters are materialized as per-repo copies on every install mode, including `--symlink`"). And whether D-01's mirror-spawn is still preferred now that (a) it reverses an explicit decoupling decision, and (b) `materializeAdapter()` already performs exactly the line-surgery a `model:` substitution needs.

**Recommendation.** Split the phase: land MODEL-01..05 (generator, resolver, tier table, guard, freshness pin) as a self-contained, fully-gated first wave; take the install delivery path (D-01/D-02/D-03) as a second wave after the user rules on this question. MODEL-01..05 are provable without any install change, and the install work carries all three of this phase's premise conflicts.
