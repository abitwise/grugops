### Gaps Summary

The mechanism this phase set out to build is genuinely good, and I want to be precise about what survives adversarial reproduction, because most of it does. The resolver's alias vocabulary is airtight — eighteen probes, exact equality, no fold, no trim, no regex, no coercion, and a YAML-injection shape refused. The tier table really is derived against `listRoles()` and really does go red when I plant an eighteenth role. `guard_model_assignment` really is an independent second opinion: I planted a config the adapters disagreed with and it turned red, planted six adapter mutations and every one was named, and it imports nothing from the generator. The generator really does refuse above the loop and leave the directory untouched — I checked the filesystem, not the exit code. Zero-config really is byte-identical, proven both by regeneration and by sha256 against the pre-phase tree. Build parity is green at 49/49.

Three things do not survive.

**First, the phase's own headline pin is defeated by the exact edit it names.** Plan 29.1-03 promised a D-04 zero-config pin that "survives a future edit that adds a config directory to the twin list". I made that edit — one line, the one `adapters-freshness.ts:70-78` itself calls plausible and well-intentioned — planted a `models.roles` block, regenerated, and watched the freshness gate print `resolved model preset: none` and exit 0 while two committed adapters carried `model: opus`, with `guard_model_assignment` passing green alongside it. The cause is structural, not a typo: `resolveModels` has two inputs and the announcement reports one. The repository has a name for this shape — a predicate whose published scope is wider than its mechanism — and it is the same lesson Phase 29 paid for across eight rounds. What makes it worse than an ordinary miss is that `generate-role-adapters.test.ts:1427` currently pins announcement-says-`none`-while-emitting-`haiku` as *correct behaviour*, so the blind spot is not merely unguarded, it is certified. The fix is small and structural: announce the resolution's **source** (which is `null` exactly under zero-config) or its `overrides.size`, through the same one-grammar-both-directions discipline the preset line already has, and add the missing `roles`-half discrimination case.

**Second, "refused fail-closed" is true of part of the config surface and not the whole of it.** `models.roles` refuses an unknown key; `models` itself does not. `{"models":{"presets":"tiered"}}`, `{"models":{"Preset":…}}` and `{"model":{…}}` are all swallowed in silence, and `{"models":{"preset":"tiered","role":{…}}}` is worse than any of them — the preset applies, the overrides vanish, and the user gets a partially wrong tier map with a green run and no message. That is verbatim what the `unassigned` refusal calls "a tier the user believes they set and did not". Compounding it, none of the six named refusals is reachable from continuous integration: I committed an illegal config to a mirror and both CI gates exited 0, because the guard reports a refused config through `warn()` (advisory by the module's own documentation) and CI never runs `generate:adapters` — the one thing that refuses. The phase's most-tested surface is currently unreachable from the build.

**Third, the single authority for MODEL-06 ships an unsourced absolute about four third-party products.** The structural work is done and done well — one authority, a one-way pointer, the `CLAUDE.md` row amended exactly as the requirement asked. But the sentence at the centre of it asserts that Codex CLI, Gemini CLI, OpenCode and GitHub Copilot CLI "have no per-subagent model concept", and the phase's own research file mentions none of those four products even once. The same phase gave a far cheaper claim — the alias vocabulary — a full `UNKNOWN - verify` block with a named source and a human ratification. This repository's hard rule is that you never fake a citation, and `CLAUDE.md:106` already records OpenCode's native markdown agent files, so the kit's own knowledge base leans against the sentence it pins as authoritative. I cannot settle the underlying fact without vendor documentation, which is why it is routed to a human — but I can settle that the phase established nothing, and an oracle that pins an unverified sentence propagates it rather than checking it.

None of the three is a defect in the design. All three are the same species: a guarantee published slightly wider than the mechanism behind it. That is the exact failure class this repository has spent two phases learning to name, which is the strongest argument for closing them here rather than carrying them forward.
