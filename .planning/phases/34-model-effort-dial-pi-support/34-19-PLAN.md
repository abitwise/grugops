## Diagnosis (brief §2.1), from source at planning HEAD 717eb29b

- A line can be lost in two places:
  - (A) Between the render and the write: the install-time transform drops a terminated sentinel
    block (install.ts:3414-3454).
  - (B) Inside the generator: render() writes the line wrongly or not at all (the verifier's
    reproduction).
- The installer compares bytes with the announcement only as a SET (install.ts:5039-5068), because
  the announcement carries only the set. Model payload `{roles, overrides, aliases}`: closed keys at
  scripts/model-tiers.ts:585, emitter :598-608, reader :623-700. Effort payload
  `{roles, overrides, levels}`: emitter :793-803, reader :815-870. So no per-member expectation exists
  that is independent of the bytes.
- The values the render writes come from the resolution: scripts/generate-role-adapters.ts:466-481
  takes `model` and `effort` from the resolution maps by stem and stores them on each adapter entry;
  render() (:553-575) writes them. The announcements (:628, :630) are built from the resolution maps,
  not from the bytes. The map is announced from that same adapter list, so a render() that writes
  anything else disagrees with it.
- Two readers, two shapes: the effort reader names a missing key and refuses a repeated level; the
  model reader does neither (RC-1 asymmetry, the grammar side of IN-07).

## Design (decided here)

- **Key `byAdapter`, keyed by adapter name.** The installer sees only rendered file names. The rule
  that turns a role stem into an adapter name (`AGENT_PREFIX` + stem, generate-role-adapters.ts:375)
  lives in the generator and is already spelled twice (generate-role-adapters.ts:153,
  check-foundation-guards.ts:3651). A third copy in the installer would be set-literal drift.
- **Built from the adapter list:** each entry's name, mapped to its resolved alias and level. The
  generator asserts each map has one entry per adapter it writes.
- **`roles` and the distinct list (`aliases`, `levels`) stay.** The installer's role-count check and
  the freshness gate's zero-config list assertion read them. The validator proves they agree with the
  map (size equals `roles`; the distinct values equal the list), so they carry no independent claim.
- **The model dial gets the map too** (RC-1, decided here): a value swap the alias set does not show
  is the same class for the model, and the model's exactly-one floor catches only a drop.
- **One validator for both payloads,** described per dial by its list key, membership predicate,
  legal set and refusal wording. Both exported readers keep their names and signatures.
- **Zero configuration.** Committed adapters do not change, because render() is untouched.
  adapter-byte-baseline and freshness:adapters stay green. The two announcement LINES change in every
  run, zero-config included: each now carries a 17-entry `byAdapter`. Lines that pinned the old text
  are listed below.
- DOC-1: the comment at scripts/model-tiers.ts:714-718 ("SEPARATE LINES, NOT A NEW KEY IN THE MODEL
  PAYLOAD ... Adding a key there would move both") becomes false and is rewritten. So are the
  ResolvedAssignment and ResolvedEffortAssignment docstrings and the generator's announcement comment
  block (:600-626).
