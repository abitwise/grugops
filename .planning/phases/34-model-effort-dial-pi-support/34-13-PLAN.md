## Root cause (established at planning from source and the printed CI log)

Log (`gh run view --job 112468804112 --log`): `<file> lost the user's mode: expected 438 to be 502`
(0o666 against 0o766) on 34 record-truth L1 rows; `expected '0666' to be '0600'` and `'0664'` on the
installer-prune IN-03 rows; `prune changed the backup` on the chmod-since row; in ledger.test.ts
`file mode is 0666, not the 0644` against an expected 0600, `mode=0666` against `mode=0644` and
`mode=0600`, a tree record that did not move after a chmod, and `owns` answering not-owned for a
fixture recorded at 0644.

- WRITE side (tests): record-truth.test.ts:335-336 computes `modeOf(p) ^ 0o100` (the owner-execute
  bit) and chmods to it; Windows keeps only the read-only attribute of a file, so nothing is stored
  and the mode stays 0o666. installer-prune.test.ts:204 chmods to 0o600 and 0o664, :390 to 0o600.
  ledger.test.ts:286 and :540 chmod to 0o644 and :312, :541 build the expected record with the
  literal 0o644; :338 chmods to 0o600 and expects "file mode is 0600"; :430 chmods to 0o600 and
  expects the tree record to move; :444 builds `fileRecord("x", 0o644)`; :620 builds
  `fileRecord("mine\n", 0o600)`.
- COMPARE side (product): install/install-marker.ts:407-419 `recordMatches` compares
  `modeText(mode)` of the fstat at uninstall with the `;mode=` recorded from the stat at install
  (install.ts:637 `fileRecord(bytes, lstatSync(path).mode)`); install/uninstall.ts:1172-1174 and
  :1414-1415 re-implement that comparison inline; install/user-file.ts:354 `modeOctal` duplicates
  install/install-marker.ts:393 `modeText`.
- So the product compares two modes the platform stored and correctly finds no change on Windows;
  the tests expected a change the platform never stored. The defect is in the tests; the product
  gets the one-helper consolidation the brief requires (§2.3).
