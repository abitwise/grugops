# 999.11: Test suite layers, speed and value (idea)

Captured 2026-10-18 during quick task 261018-hs8, by human decision. The full suite slows delivery:
each executor in 261018-hs8 spent most of its 1h20m-2h20m on repeated full runs. The human plans to
take this on as a `/gsd-quick` next time.

## Measured (full run on f48262c2's tree, 2026-10-18)

- **Size:** 114 test files and 8395 tests (8256 at base eba46ad5). The run took 31.4 min on one
  machine.
- **Durations by test:**

  | Duration per test | Tests | Total time |
  |---|---|---|
  | under 100 ms | 5144 | 1.7 min |
  | 100 ms to 1 s | 2932 | 16.8 min |
  | 1 to 10 s | 313 | 9.3 min |
  | over 10 s | 6 | 1.9 min |

- **Spawning:** 72 of the 114 files spawn a node subprocess (install.js, uninstall.js, `--check`, gate
  scripts) against a scratch repo. Most tests in the 100 ms to 1 s bucket are these spawns.
- **No parallel files:** `vitest.config.ts` sets `fileParallelism: false`, because some gate tests
  change the real working tree. These are the catalog and freshness tests, and the tests that plant
  drift in docs/ or agent-factory/roles. So no test file runs in parallel.
- **Top files:** the top 15 files take 81% of the time.

  | Time | File |
  |---|---|
  | 3.6 min | install/install.test.ts |
  | 3.4 min | scripts/runnable-ref/host-protection.test.ts |
  | 3.2 min | install/installer-write-set.test.ts |
  | 2.5 min | host-protection-floor.test.ts |
  | 2.3 min | install/kit-route.test.ts |
  | 1.9 min | uat-spec-integrity.test.ts |
  | 1.8 min | check-foundation-guards.test.ts |
  | 1.3 min | check-platform-shapes.test.ts |

- **Slowest tests:** the slowest single tests (20-25 s) are corpus sweeps:
  - the foundation-guards rounds-1-11 gate sweep;
  - the install all-or-nothing case over links, FIFOs and hard links;
  - the admission-guard proved-allow matrix;
  - the uat-gate disposition register.
- **Test files added by month:** Jun 25, Jul 8, Aug 18, Sep 40, Oct 21. The growth tracks the
  phase 31-34.1 gap rounds: each reproduced bypass became a permanent test.
- **Generated cases:** many cases are generated from data (every combination, every ordered pair,
  every corpus row, loops over the host registry), so one new host or path multiplies them. Quick
  task 261018-hs8 alone added about 140 tests.
- **Existing scripts:** `test` = `vitest run`, which also collects `scripts/e2e` and so runs the
  live claude-CLI e2e lane. `test:e2e` = `vitest run scripts/e2e`. There is no unit or integration
  split.

## Needs (from the human, 2026-10-18)

1. **Speed.** Make the suite fast enough that it does not gate progress. Candidate levers:
   - Move the tests that change the real tree into their own sequential project, so the other files
     can run in parallel.
   - Share one installed scratch repo per file where a test only reads it.
   - Move the 10 s+ corpus sweeps out of the default lane.
2. **Duplicate tests.** Find duplicate or overlapping tests that can be consolidated. Gap rounds
   often added a near-copy of an existing case for one more spelling, arm or register.
3. **Value audit.** Find out whether these guardrails and tests give grugops real value. For each
   guard or gate family, ask:
   - what grugops failure it prevents;
   - whether that failure is still possible since the retirements (the 33.1 D-17 command parser,
     the D-59 totality claims);
   - what it costs in run time and in planning drag.

   Retire or shrink what does not pay for itself. Record each retirement as a decision; never delete
   a safety test silently. Reference: memory notes on the P27-P34.1 gap rounds and the
   "green suite is not proof" lesson.
4. **Three layers, each runnable on its own:**
   - **unit:** pure logic, in-process, no subprocess, no real tree;
   - **integration:** spawns the committed .js against scratch repos and kit homes (with
     GRUGOPS_HOME and HOME set to scratch), and runs the gate scripts;
   - **e2e:** the live host-CLI lane (`scripts/e2e`), plus 999.1's adversarial installer lane
     when it lands.

   Each layer gets its own npm script. e2e runs only once, after the main development is done and
   the unit and integration layers pass. Plain `npm test` must not start the live e2e lane.
5. **Executor testing approach.** Write it into the GSD executor brief and, where it fits,
   CLAUDE.md or a project skill:
   - **While coding:** run only a subset, meaning the tests for the code that changed plus its
     direct dependents (for example `vitest related <changed files>`, or a mapped file list).
   - **When coding is done:** run unit, then integration, then e2e, stopping at the first failing
     layer.
   - The full-suite comparison against a base failure list stays the final integration check, not
     a step in the coding loop.
