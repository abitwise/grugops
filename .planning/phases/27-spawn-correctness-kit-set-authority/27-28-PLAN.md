<objective>
Close CR-04: `install/README.md` publishes an exit-code table that covers both binaries and documents
a code-1 self-checkout refusal — and `install/uninstall.ts` has no such refusal, no `--allow-self`
branch, and no exit-1 path at all; its only exits are 2 and 3. The review reproduced the consequence
on a throwaway copy of the source checkout: `uninstall.js --target <grugops checkout>` removed 17
adapters and 7 skills and exited 0. `isProtected()` covers `agent-factory/`, `plans/`, `.planning/`,
`docs/` and `src/` — but not `.claude/`, which is where the kit's own committed adapters and skills
live. Under this project's own no-fabrication rule, documenting a refusal that does not fire is worse
than documenting nothing.

**The disposition, chosen deliberately: implement the refusal, do not delete the row.** Both closures
would make the documents honest, but only one closes the data-loss path the reproduction demonstrated.
Deleting the row would leave a user able to destroy their own grugops checkout with a documented,
supported command and would merely stop promising otherwise. The safety constraint — installers stay
reversible and never delete content they did not add — is only satisfied by the guard existing. The
doc still moves, because the row must also be true about which binary offers which mode.

A second, related fabrication surfaced while reading the guard being ported, and it is in scope
because porting it verbatim would carry it across: the installer's own marker test requires
`install/install.sh`, and that file was deleted when the POSIX installer was retired. A source
checkout today does not contain it, so the marker half of the guard cannot fire and only the
path-equality half works. A guard whose condition cannot fire is the same defect as a documented
refusal that does not exist. The executor verifies this independently before acting on it.

Purpose: the exit code the table names is the exit code the binary returns, and the refusal it names
actually fires.
Output: a working self-checkout refusal on the uninstaller, a marker test built from files that exist,
a true exit-code table, and cases pinning both the refusal and its non-firing side.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a user-supplied `--target` -> the removal sequence | the target names a directory tree the uninstaller will delete from, and the user may have named their own grugops checkout |
| the published exit-code table -> a script chaining on the installer or uninstaller | a caller branches on a code the table promises, so a promised code that never occurs is a promise that silently fails |
| a guard's marker condition -> the guard's effect | a marker referring to a file that no longer exists is a guard that is present in source and absent in behaviour |
