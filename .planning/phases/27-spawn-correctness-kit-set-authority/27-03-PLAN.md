<objective>
Re-point the three remaining enumerating set literals inside `scripts/check-foundation-guards.ts`
through the KIT-01 authority stood up in plan `27-01`, completing that file's share of KIT-02 and D-16.

The distinction this plan must preserve is that derivation replaces the **literal**, never the
**scoping discipline**. Every one of these sets is deliberately bounded — the guards are explicit scan
sets and never repo-wide greps — and a derived set is still a bounded set. Widening a scan to a
directory that was deliberately omitted would be a different defect wearing this phase's clothes.

The highest-risk item here is not a set at all, it is a name. `WR05_SCAN` exists **twice** in the tree,
in two different files, meaning two unrelated things: the guards-side constant is this plan's target,
while the constant of the same name in `scripts/check-uat-oracles.ts` holds four `.planning/` tracking
documents and belongs to a currently-green Tier-1 oracle that the guard aggregator imports and folds
into its own fail count. Every edit in this plan is scoped **by file path**, never by identifier grep,
and the guards-side constant is renamed in the same commit so the collision cannot recur.

Per D-19, proof that no stale literal survived is a recorded inventory plus a per-consumer assertion,
never a grep-based literal-detector guard — such a detector would itself be a heuristic capable of
being a strict subset of the real predicate.

Purpose: `CTX_WORKFLOWS` currently enumerates 16 of 19 workflows, so three shipped workflow files have
never been scanned by `guard_context_writes` and nothing reports that.
Output: three derived sets, one rename, a vacuity floor for the adapter-side sets, and per-consumer
derivation assertions.

**Expected during this plan:** `node scripts/check-foundation-guards.js` exits non-zero with exactly
one FAIL — `guard_referential_integrity`, left deliberately red by plan `27-01` until plan `27-07`
commits the adapters. Any *second* FAIL is a regression introduced here.
</objective>
