<objective>
Close WR-01: a guard that is inconsistent with itself.

Plan 27-19 refused a `name` key carrying anything other than exactly one value, with an explicit
rationale — *which of the two the platform's YAML loader honours (first, last, or a duplicate-key
throw) is not this oracle's to guess*. Plan 27-20, thirty lines away in the same function, gave the
`tools` / `allowed-tools` answer an **absence** arm and an **emptiness** arm and no **cardinality**
arm. `keysHaveSpawnGrant()` is deliberately a disjunction over all occurrences: correct and fail-safe
for the rogue-spawner direction, fail-open for the coordinator-must-hold-the-grant direction. A
coordinator declaring `tools:` twice — a duplicate key a last-wins loader resolves by dropping the
first occurrence — passes both WR-05 and KIT-03 while the runtime grant is silently gone. Reproduced
on a hermetic mirror: `ALL CHECKS PASSED`, exit 0.

The remedy is the 27-19 rule applied to the same predicate in the same loop — not a second check, and
not a heuristic about which occurrence to prefer. The guard either has one answer or it refuses.

Purpose: one allow-list, one answer, or a named refusal.
Output: a cardinality arm beside its two siblings, the duplicate-key reproduction pinned red on both
key spellings, and the threshold pinned on both sides.
</objective>
