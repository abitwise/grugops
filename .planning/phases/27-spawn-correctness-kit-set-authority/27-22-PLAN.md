<objective>
Close WR-02 and WR-04, both in the installer's derivation surface.

WR-02 is a derivation asymmetry the review proved: `srcAdapterFiles()` filters on `ent.isFile()` from
`withFileTypes`, which is FALSE for a symlink, while `kit-model.walkFilesRelative()` deliberately uses
`statSync`, which follows symlinks — its own comment says so, matching how the platform would resolve
a symlinked adapter. `srcNestedAdapterFiles()` does not cover the gap either, so a symlinked source
adapter is not installed, not refused by name, not counted, and the run still prints
`== install complete ==`. That is exactly the failure `srcNestedAdapterFiles()` was written to
prevent: the installer must not be the one place a file disappears silently.

WR-04 is this project's second named systemic failure class caught mid-remedy. The case correctly
refuses to keep a third hand-copy of `RUNNABLES` and recovers it by regex over TypeScript source —
but the pair matcher is blind to any entry written in another shape, and the count it asserts is a
hardcoded literal. A third runnable added to both files in an unmatched shape leaves both derived
sets at two members, the count assertion still passes, and the new runnable is covered by none of the
five cases driven off it. Derive the set, assert the count — and derive the CARDINALITY too.

Purpose: one answer to "what files are in the kit source", and a derivation whose coverage cannot
shrink while its count stays green.
Output: statSync-based derivations in the installer, a symlinked conformance fixture, and a
self-checking `mappingDests`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kit source directory -> the installed target | a source entry the installer cannot see is an entry it cannot install and cannot refuse |
| TypeScript source text -> a test's derived set | a regex over source is a parser, and a parser that silently under-matches degrades a coverage claim |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-109 | Tampering | `srcAdapterFiles()` and `srcNestedAdapterFiles()` in `install/install.ts` | high | mitigate | File-ness is decided by `statSync`, matching the authority and the platform, so a symlinked adapter is either installed or refused by name and never disappears from the run. |
| T-27-110 | Repudiation | the `== install complete ==` banner over a vanished file | high | mitigate | With the entry visible, the nested refusal path reports it and the run's completion claim stays conditional on the verify findings. |

| T-27-113 | Information Disclosure | symlink following outside the source tree | low | accept | The source root is the kit the user chose to install from; the installer already reads every file under it, so following a link adds no read the run did not already have. |
