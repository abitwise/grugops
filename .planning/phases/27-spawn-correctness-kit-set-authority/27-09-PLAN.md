<objective>
Close SPAWN-03 by documenting the three entry paths honestly and by verifying, against a real Claude
Code session, that the generated coordinator adapter actually resolves.

There is no installer change here and there must not be one. Per D-01 the installer writes no
main-thread wiring into a target repository — no settings entry, not even sentinel-wrapped — because
such an entry would make *every* session in that repository run as the grugops coordinator, including a
session opened only to edit a readme, and settings files are user content the installer is bound never
to overwrite. What SPAWN-03 needs instead is that the full-capability path is **documented** and that the
adapter genuinely resolves on it.

The documentation must be careful about one verified ambiguity. The platform's subagent documentation
states the enumerated-allowlist rule for the command-line flag specifically; the settings documentation
says the corresponding key applies an agent's tool restrictions, which strongly implies parity but never
states it. Since D-01 removes that key from grugops's install path entirely, the ambiguity blocks
nothing — but anything grugops writes must describe the flag as the full-capability path rather than
claiming settings parity.

The verification half exists because a green suite is not evidence for a spawn fix. The recorded doctrine
here is that for a safety invariant or a guard, green tests are not proof — the milestone's founding
defect was a fully green suite over a structurally broken tree. Within this phase the substitutes are the
fixture-pinned oracle evidence from plan `27-01` and a real dogfood on this machine, where an above-floor
Claude Code is installed and can actually be run against the generated adapters before the phase closes.

Because `workflow.human_verify_mode` is set to end-of-phase, that dogfood is authored as a human check on
the final task's verify block rather than as a blocking mid-phase checkpoint. This plan is the last wave,
so the check lands at the phase end either way.

Purpose: SPAWN-03's system under test is the Claude Code runtime, and no in-repo command can observe agent
resolution.
Output: documented entry tiers, an automated assertion of the in-repo half, and a recorded human
verification of the runtime half.
</objective>

## Flagged Assumptions (probe-unresolved)

None unresolved for this plan's requirement. Its three probe edges are authored as backstop markers in
`must_haves.truths` above, because all three describe platform resolution behaviour that no in-repo
command can confirm. At verify time a backstop truth the verifier cannot confirm with explicit evidence
abstains and is escalated for human attention rather than silently passing — which is the correct
outcome for a claim about a runtime this repository does not own.

One documented platform ambiguity is carried rather than resolved: whether the enumerated allowlist is
enforced under the settings key as well as under the flag. The subagent documentation states the rule for
the flag only; the settings documentation says the key applies an agent's tool restrictions. D-01 removes
that key from grugops's install path entirely, so nothing in this phase depends on the answer — and the
prohibition above keeps any grugops-authored documentation from claiming parity.
